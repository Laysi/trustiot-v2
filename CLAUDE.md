# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository state

Bootstrapped on 2026-10-09; the Cargo workspace and toolchain pins landed on 2026-10-10. `tools/repo-check` enforces repository invariants as part of `cargo test`. Pin every new runtime or dev tool in `.prototools` and add its commands to this file.

Architecture decisions, rebuild scope (items A1–M8), service split, repository layout, and milestones (MS0–MS6) live in `docs/`; start at `docs/README.md`. `docs/` is the source of truth: when a decision changes, update `docs/` in the same change. In `docs/`, a bare `#N` refers to the legacy repo `Laysi/trustiot`; always write legacy references as `Laysi/trustiot#N` in issues and PRs here.

## Build, lint, and test

`.prototools` pins Rust, Bun, actionlint, cargo-deny, gitleaks, Helm, k3d, kubeconform, kubectl, and the release tools (zig, cargo-zigbuild, cargo-auditable, syft, cosign); tools without a built-in proto plugin get a schema plugin in `.proto/plugins/` that verifies the release checksum. proto installs Rust through rustup and does not shim cargo, so rustup picks the toolchain from `rust-toolchain.toml`: change `rust` in `.prototools` and `channel` in `rust-toolchain.toml` together (`cargo test -p repo-check` fails when they differ). Run every command from the repository root.

- Install the pinned tools: `proto install`
- Build: `cargo build --workspace`
- Format: `cargo fmt --all` (check only: `cargo fmt --all --check`)
- Lint: `cargo clippy --workspace --all-targets -- -D warnings`
- Test: `cargo test --workspace`
- Single test: `cargo test -p <crate> <test-name-filter>`, for example `cargo test -p repo-check toolchain_pins_agree`
- Local dev environment (podman, no Kubernetes; details in `scripts/README.md`): `bun scripts/dev.ts up` | `seed` | `status` | `env` | `down` | `purge`. Its Postgres serves TLS from a CA that `up` generates (kept under `$XDG_STATE_HOME/trustiot-v2/dev/<instance>/tls/`, never in the repo), so services connect with `verify-full`; `env` prints `TRUSTIOT_POSTGRES_{HOST,PORT,DATABASE,SSLMODE,CA_FILE}` and `PGSSLMODE`/`PGSSLROOTCERT`, so `set -a; eval "$(bun scripts/dev.ts env)"; set +a` is all a service or `psql` on the host needs. Script tests: `bun test scripts`, after `bun install --cwd scripts --frozen-lockfile` (add `TRUSTIOT_DEV_E2E=1` and the file `scripts/tests/e2e.test.ts` to run the podman end-to-end test).
- Helm chart (`deploy/chart`): `bun test deploy/chart` runs `helm lint`, kubeconform on both values files, the chart's own rules, and the README field check; a single check is `bun test deploy/chart -t "<test-name-filter>"`. The individual `helm lint`/`helm template` commands are in `deploy/chart/README.md`.
- SaaS host installer (`deploy/host`): `bun install --cwd deploy/host --frozen-lockfile`, then `bun run --cwd deploy/host typecheck`, `bun run --cwd deploy/host test` (simulated host; a single test is `-t "<test-name-filter>"`) and `bun run --cwd deploy/host build` (the x86_64 and aarch64 executables in `deploy/host/dist/`). Running it on a host is in `deploy/host/README.md`.
- Nightly workflow (`.github/workflows/nightly.yml`, `scripts/nightly/`): CI deploys the chart with both values files to a k3d cluster and smoke-tests it; it runs only in CI, because workstations do not run Kubernetes. On a pull request it deploys only while the PR carries the `smoke` label, which the coordinator adds before merging. Its unit tests need no cluster: `bun test scripts/nightly`. Renovate (`renovate.json5`) updates dependencies; a tool pinned in `.prototools` with a schema plugin needs a `# renovate:` comment above its pin (`bun test scripts/nightly` checks it). Details: `docs/architecture/ci-release.md`.
- Ingress e2e (needs a cluster with Istio ambient; never run Kubernetes locally): `E2E_NAMESPACE=<ns> E2E_IDENTITY_IMAGE=<image> bun test --timeout 600000 ./deploy/chart/tests/e2e/ingress.e2e.ts`; prerequisites and the other variables are in `deploy/chart/tests/e2e/README.md`. Its tunnel recovery (`raw-client.ts`, `tunnel-recovery.ts`) has cluster-free unit tests that `bun test deploy/chart` runs.
- Log pipeline e2e (OpenTelemetry collector to ClickHouse and a stand-in SIEM; needs a cluster, run on the lab k3s): `E2E_NAMESPACE=<ns> E2E_SERVICE_IMAGE=<example-service image> bun test --timeout 900000 ./deploy/chart/tests/e2e/otel.e2e.ts`; building the arm64 example-service image is in `deploy/chart/tests/e2e/README.md`.
- Container-backed tests: `crates/service-kit` starts throwaway Postgres and PID 1 containers with podman or docker (or uses `TEST_DATABASE_URL` for Postgres), and `crates/testkit` starts a TLS Postgres for the cross-tenant suite's self-test. Without them those tests skip locally; with `CI` set they fail instead.
- Cross-tenant negative tests (decision 29): every service declares its tables and endpoints with `crates/testkit` in `tests/`; how to hook a service in is in `crates/testkit/README.md`. `cargo test -p testkit -- --nocapture` prints every probe.
- Test time limits: workstations and CI runners are often loaded (load average 25–35 on 8 cores was seen), so no test may depend on a fixed short time. Wait for the condition with a generous bound that fails with a message naming what was awaited. Do not widen a number without asking what it waits for; assert ordering rather than elapsed time, and bound a duration only against what the test configured (a drain delay, a 60 s timeout it must not reach). Chart tests (`deploy/chart/tests`): call `useProcessTestTimeouts()` from `deploy/chart/tests/timing.ts` at the top of the file (bun applies `setDefaultTimeout` per file and ignores a bunfig test timeout), pass `SLOW_TEST_MS` to a test that runs many helm or kubeconform commands, and run commands through a helper with `timeout: COMMAND_TIMEOUT_MS` and `throwIfTimedOut`. Rust tests: use the named constants and helpers in the test file or `crates/service-kit/tests/support`, for example `wait_until_ready` and `refusal_through_pool` in `tenant_db.rs`.
- `crates/service-kit` without its default `contract` feature, which the `--workspace` commands never build: `cargo clippy -p service-kit --no-default-features --all-targets -- -D warnings` and `cargo test -p service-kit --no-default-features`
- API spec (`api/openapi.json`, generated from the code, never edited by hand): regenerate with `cargo run -p openapi` after changing any API type and commit the result; `cargo run -p openapi -- --check` only verifies it. `cargo test --workspace` and CI fail when the committed file differs from what the code generates. Each service exposes `pub fn openapi()` and registers it in `tools/openapi` (`tools/openapi/README.md`).
- Dependency licenses, advisories, and sources (rules in `deny.toml`): `cargo deny --locked check`
- Secret scan, as CI runs it: `gitleaks git --redact --log-opts="--full-history --diff-filter=tuxdb --diff-merges=first-parent HEAD" .`
- Workflow policy (job `permissions`, SHA-pinned actions): `bun scripts/ci/check-workflows.ts`
- Which ci.yml jobs a change runs: `scripts/ci/changes.ts` decides from the changed paths whether `rust`, `cargo-deny`, `helm`, and `host` run; `gitleaks` and `workflow-policy` always run. When a Rust test, a chart test, or the host installer starts reading a file outside its own directory, add the path to the rules there (`bun test scripts/ci/changes.test.ts` fails until you do). The `if` and concurrency conditions of ci.yml and nightly.yml are tested by `bun test scripts/ci/workflow-conditions.test.ts`. Details: `docs/architecture/ci-release.md`.
- Secret handling (every Dockerfile/Containerfile, container build commands, build args, where workflows read secrets, SOPS-encrypted Secret manifests; rules in `docs/architecture/secrets.md`): `bun scripts/ci/check-secret-handling.ts`
- Workflow syntax and expression check with the pinned actionlint, which rejects what GitHub cannot parse (for example `runner.temp` in job-level `env`): `bun scripts/ci/lint-workflows.ts` (run `proto install actionlint` first; the shellcheck integration is deliberately off, see `docs/architecture/ci-release.md`)
- Bun scripts in `scripts/` (the dev environment and the CI checks): `bun install --cwd scripts --frozen-lockfile` installs the type checker and the test dependencies (`bun test scripts` needs them too), then `bun run --cwd scripts typecheck` checks every `.ts` file there and under `deploy/chart/tests/` (the ingress e2e included, which needs a cluster to run but not to type-check); `bun run --cwd scripts test` runs the same test files as `bun test scripts`, and a single test is `bun run --cwd scripts test -t "<test-name-filter>"`
- Gateway crates (`crates/protocol` and every member under `edge/`) must build for aarch64: `rustup target add aarch64-unknown-linux-gnu` once, then `cargo build --locked --target aarch64-unknown-linux-gnu -p <crate>`
- Release scripts (`scripts/release`, run by `.github/workflows/release.yml`): `bun test scripts/release`; a single test is `bun test scripts/release -t "<test-name-filter>"`. Building the arm64 images locally and running the whole publish and verify flow against a throwaway registry are described in `scripts/README.md`.
- Images: each directory under `deploy/images/` is a published arm64 image (`image.toml` for a Rust binary, or its own `Containerfile`); see `deploy/images/README.md`. Base images must be pinned by digest.

`.github/workflows/ci.yml` runs these checks on every pull request and every push to main; its jobs and the required-checks list are in `docs/architecture/ci-release.md`. Every job must list its `permissions`, every action must be pinned to a full commit SHA with the tag in a trailing comment, and local actions belong under `.github/actions/`.

Every directory under `crates/`, `services/`, `edge/`, `factory/`, and `tools/` is a workspace member, so it needs a `Cargo.toml` that sets `edition.workspace = true` and `[lints] workspace = true`; list non-Rust directories in the root `exclude`. Declare third-party dependencies once in the root `[workspace.dependencies]`. Clippy fails on every lint in `[workspace.lints]`; suppress one only with `#[allow(lint, reason = "...")]`. Save test evidence under `docs/test-reports/` as its README describes.

## Work tracking: GitHub Issues + Project board

Work is tracked as real issues in `Laysi/trustiot-v2` on the org Project **TrustIoT v2** (`Laysi`, project #12). Follow the `github-loop-engineering` skill for every issue and board transition. Resolve field and option IDs at runtime; never hard-code them.

- **Status:** `Triage`, `Todo`, `In Progress`, `Blocked`, `Done`. Agents triage by best judgment, without waiting for a human: accepted work moves to `Todo`, and rejected work is closed as not planned. `Todo` includes accepted work that still waits on other issues in this repo. Those waits are native blocked-by dependencies, and the board's `Ready` view (filter `status:Todo -is:blocked`) lists the work that can start now.
- **Priority (board field):** `P0` incident or blocker, `P1` current focus (the milestone in progress), `P2` backlog. Set it when the issue is created, by best judgment; agents set it too and do not wait for human triage. The board field is the source of truth, and the issue carries exactly one matching `priority:P0|P1|P2` label.
- **Labels:** every issue carries at least one `area:*` label (or `documentation` for docs-only work). Add an `area:<component>` label, whose description names the component path, when a new top-level component is created. Other workflow labels: `blocked`, `tech-debt`, `security`.
- **Issue types:** `Feature` for new capabilities, `Bug` for incorrect behavior or vulnerabilities, `Task` for everything else.
- **Issue bodies** are written in Traditional Chinese and must be cold-start readable. Use the headings from `.github/ISSUE_TEMPLATE/`: 背景 (Why), 範圍 (What), 現狀 (State), 驗收條件 (Acceptance Criteria), 指標 (Pointers); bugs add 重現 (Reproduction). Use absolute dates only. Don't copy board fields such as Status or Priority into the body. The templates come from the `github-loop-engineering` skill (`zh-TW`); update them through the skill, not by hand.
- **Parallel work:** each milestone is a root issue whose sub-issues are epics and then leaves, and blocked-by dependencies connect leaves only. To work through a parent issue, follow the skill's fan-out: the board filter `parent-issue:Laysi/trustiot-v2#N status:Todo -is:blocked` lists its children that can start now.
- **Blocked work:** a blocker outside the work graph, such as missing hardware, a pending decision, or a customer, gets the `blocked` label, a `Blocked by` section in the body, and Status `Blocked`. A wait on another issue in this repo is a native blocked-by dependency instead.
- **CLI fallback:** use the GitHub MCP server for every GitHub read and write. The user has authorized the skill's `gh api` fallback for two things the server can't do yet, and nothing else: native blocked-by dependencies (list, add, remove) and creating milestones.
- **Assignment** is decided when work starts, not at creation.
- **Closing:** if the Project's auto-close workflow is enabled, setting Status to `Done` closes the issue, so close the issue through the completion ritual instead of moving the card first.

## Parallel agent work

To work through a parent issue with several agents at once, one coordinating session claims the ready leaves (the skill's fan-out), gives each leaf to its own agent, verifies the results and merges them. These rules come from MS0 (2026-10-10 to 2026-10-11).

- Each agent works on one leaf, in its own git worktree, on a branch from `origin/main`. Agents never merge. The coordinator verifies and merges `review:ai` PRs; `review:human` PRs wait for a person.
- Never rebase once a PR is open, and never rebase when the rebase has a conflict: a rebase does not run `.githooks/pre-commit`, so the conflict resolution is never reviewed. Merge `origin/main` instead.
- Never bypass `.githooks/pre-commit`. Keep work-in-progress checkpoints as patch files outside the repository, not as commits.
- Before the first push, scan the branch history (`gitleaks git --redact --log-opts="origin/main..HEAD" .`) and an exported copy of the head tree (`git archive HEAD`, then `gitleaks dir`). CI also scans the PR's test-merge commit, and main gets a squash commit, so a secret-looking value still in the tree comes back under a SHA that no `.gitleaksignore` entry can name. Build fake secrets at run time.
- Every push to a PR runs CI (about 11 minutes), which is the merge gate, not a debugger. Verify on the build host first, push a PR when it is ready to merge, and never push to find out what CI says. Add the `smoke` label only when deciding to merge a PR that changes what the nightly deploys. Since 2026-10-12 the repository is public, so CI no longer uses the organization's Actions minutes.
- Run heavy checks (the workspace build and tests, the container-backed tests with `CI=1`, the chart tests) on the build host, through one queue, one job at a time. The workstation that runs the coordinator only coordinates: on MS0 it was an old ultrabook, and several agents building there at once pushed the load average to 25–38, exhausted its memory and made time-sensitive tests fail. Each worktree keeps its own cargo target directory. Never share one between two checkouts of this workspace: cargo judges freshness by file times, with paths relative to the package, so one checkout can reuse the other's build of a crate and test the wrong code. Never build on the lab cluster's host.
- Outside CI, Kubernetes e2e runs only on the shared lab cluster, never on a workstation or build host. Hold the lab lock for the whole run, use a namespace `e2e-<issue>`, record every cluster-wide change and restore it byte-identical, and release the lock when the run ends.
- An agent can stop in the middle of a step (a usage limit, a build host outage). Before it continues, a resumed agent re-checks its git state (an unfinished merge or commit), what it has pushed, the locks it holds and anything it left running.
- The coordinator verifies a batch of PRs together:
  1. Build the tree of main plus each PR head with `git merge-tree --write-tree` and `git commit-tree`.
  2. Run every CI check on that tree with `CI=1`, so the container-backed tests run instead of skipping.
  3. Merge the PRs in the same order with `gh pr merge --squash --match-head-commit "$(git rev-parse <ref>)"`.
  4. Check that `git rev-parse origin/main^{tree}` equals the verified tree.

  A PR's own CI tests it against the main of that moment; the batch is what tests the PRs against each other. On MS0 it caught, for example, a chart test that read files the CI path filter did not cover.
- A security-relevant leaf also gets an independent verifier: a fresh agent that did not write the code and tries to break it. On MS0 these verifiers found real defects that the implementers' own tests had missed: Laysi/trustiot-v2#255, Laysi/trustiot-v2#260, Laysi/trustiot-v2#268, and Laysi/trustiot-v2#282 to Laysi/trustiot-v2#285. Before the merge, the verifier's branch can be merged into the implementer's branch, so both go out in one push.
- Keep the decisions that need a person (a release tag, a repository setting, hardware, a credential) in one list on the milestone's root issue, so they can be answered together instead of each one stalling its own PR.
- Most PRs edit the rows of `docs/architecture/decisions.md`, the command list in this file, and `deploy/chart/README.md`. Each merge can then force a main merge, and another CI run, on every other open PR. Merge the PR with the widest documentation footprint first.
