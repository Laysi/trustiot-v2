# 可行性測試結果（2026-10-09 雲端 PoC）

這一頁記錄的是第一批雲端 PoC 的範圍，共 8 項；主文清單後來加入的 Apache AGE、RAG 檢索題庫、Istio ambient 與 Cloudflare Tunnel 不在這裡，尚待驗證。8 項中，雲端側各項都已在 Mac mini M1 實驗機上實測，TPM 與 OTA 依指示不測。最大的發現是 Neo4j 租戶改寫：只在樣式上加過濾會洩漏，錯誤訊息會直接帶出別的租戶的資料。另一個改變設計的結果：4B 地端模型自由寫 SQL 只答對 2–5 成，改成呼叫參數化的分析工具後全對。

| 項目 | 結論 | 關鍵數字 | 對決策的影響 |
| --- | --- | --- | --- |

## MQTT broker（Mosquitto 2.1.2）

Mosquitto 可以當閘道器的唯一入口，但撤銷與權限的作法要依下列實測結果設計。客戶端為 rumqttc 0.25.1（MQTT v5）加 rustls，CA 用 rcgen 0.14 自建。

通過：

- mTLS 拒絕原因正確：無憑證、外部 CA（同 CN）、過期、EKU 錯誤各自回對應的 TLS alert。
- CSR 簽發：CA 只取 CSR 的公鑰，CN、EKU、SAN 由 CA 決定，簽出的憑證可連線。
- 隔離：閘道器發布到別人的 topic 會收到 PUBACK 0x87，也收不到別人的訊息；CN 為 `+`、`#` 的惡意憑證讀不到東西；別台閘道器冒用 client id 踢不掉原連線。
- 設定下發與 ack：retained 設定會送到後來才上線的閘道器；離線期間發的 ack 會在重連後送達；shared subscription 把 200 則訊息 100/100 分給兩個服務副本，無遺失、無重複。
- 443 與 WSS 都可用；2000 個 mTLS 連線 3.9 秒連完（p99 113 ms），broker 每連線約 46 KB。

要寫進設計的事：

1. 撤銷要三步：發新 CRL、SIGHUP，再用 dynsec 踢掉已連線的 session。只 SIGHUP 不會斷掉已連線的被撤銷憑證。
2. CRL 過期會讓所有閘道器都連不上，要有定期更新與到期告警。
3. `acl_file` 在 2.1 已棄用（3.0 移除），改用 dynsec 的 `%u` 樣式；未註冊的憑證可連線但什麼都不能做，所以佈建時要呼叫 dynsec 建立 client 並綁角色。
4. 內建持久化每 30 分鐘才寫一次，SIGKILL 會丟掉最新的 retained 設定；改用 persist_sqlite 且 flush_period 0，服務啟動時仍從 Postgres 重發 desired 設定。
5. rumqttc v5 預設每連線預配約 13 MB，要設 `set_outgoing_inflight_upper_limit`（32 時約 80 KB）；該套件最後發版是 2025-11，要注意維護狀態。

## ClickHouse（決策表的假設）

窄表加 row policy 的租戶隔離在 70 多個攻擊下成立，小主機配置閒置只用 199 MB。版本為 26.8.21.10 LTS，測試資料 25 萬筆。

通過：

- 以租戶 A 身分直接查、JOIN、子查詢、UNION、FINAL、merge()、view() 讀 B，全部 0 筆；throwIf 錯誤 oracle 從未觸發，因為 policy 永遠先於使用者運算式。
- 系統表、file()、url() SSRF、remote()、INTO OUTFILE、寫入與改權限都被拒絕；交叉 JOIN、記憶體炸彈、並發與每分鐘查詢數都被限制擋下。
- 單一 policy 可用 `getSetting('SQL_tenant_id')` 加每位使用者的 CONST 設定，新增租戶只要兩句；沒設定的使用者直接報錯。
- HTTP 200 之後資料立即可查；帶 `insert_deduplication_token` 的重送會被丟棄並仍回 200，可當端到端 ack 的冪等基礎。

要寫進設計的事：

1. 26.8 預設 async insert 且等待寫入，一次 INSERT 約 65 ms；不等待的模式在 SIGKILL 時會丟資料，端到端 ack 不可用。
2. 去重要在表上設 `non_replicated_deduplication_window`（預設 0 = 不去重），而且只能以批次數計算；長時間離線的重送仍要由服務記錄每台閘道器的已提交序號。
3. fsync 預設關閉，200 只代表進了 page cache；開啟後只多約 3 ms，建議遙測表開啟。
4. quota 必須 `KEYED BY user_name`，否則所有租戶共用一個計數，A 用完會擋到 B。
5. 設成「沒有 policy 就看不到」後，服務帳號也要另建 `USING 1` 的 policy。
6. 儲存的時間欄位是 UTC，AI 寫的 SQL 必須帶時區參數，例如 `toDate(ts, 'Asia/Taipei')`，否則日切點錯。

## 薄 OpenAI 相容 client（vLLM、Ollama）

約 330 行的 Rust client（reqwest）就能涵蓋工具呼叫、用量、推理欄位、串流取消與錯誤分類，不需要 SDK。測試對象為 Ollama 0.40.1（Mac 主機 Metal）與 vLLM 0.31.0（官方 CPU 映像，Qwen3-0.6B）。

| 檢查 | Ollama（qwen3 1.7B、4B、qwen3.5 4B） | vLLM 0.31 |
| --- | --- | --- |
| 推理欄位 | `reasoning`（不是 `reasoning_content`） | `reasoning`，用量另帶 reasoning_tokens |
| 工具呼叫 | 串流與非串流都正確，一輪可並行兩個 | 同左（hermes parser） |
| 取消串流 | 伺服器停止生成 | 伺服器停止生成 |
| 6 個並發 | 逐一排隊，第一個 token 延遲 0.1–44 秒，不回 503 | 連續批次，2.4–3.3 秒都開始回應 |

要寫進設計的事：

1. 排隊會表現成第一個 token 的延遲，不是錯誤；服務要有自己的每端點並發上限，首 token 逾時視為「過載，切備援」。
2. 推理模型連「回 pong」都會花 200–2300 個推理 token；計費與進度顯示要算進去，max_tokens 要留空間。`finish_reason=length` 且內容空白，代表推理用光了額度，要當成獨立結果處理。
3. vLLM 的 KV cache 不足時會搶佔執行中的請求，串流中間會靜默超過 60 秒；idle 逾時要容忍，地端規格要留 KV 空間。
4. qwen3.5:4b 的 nvfp4 版本在 Ollama 走 MLX，常駐 6.5 GB，不能與整套服務共用 8 GB 主機。

地端模型做資料分析：4B 模型不能自由寫 SQL，要給語意層工具。測法：10 題有標準答案的遙測問題（尖峰時段、斷訊、計數器歸零、停機區段），以租戶唯讀帳號查 ClickHouse，每個答案都人工複核。

| 模型 | 自由寫 SQL | 語意層工具 |
| --- | --- | --- |
| qwen3:1.7b | 1/10，會捏造數字 | 未測 |
| qwen3:4b | 5/10，另 2 題部分對 | 10/10 |
| qwen3.5:4b | 2/10，4 題在 8 輪內沒答出 | 10/10 |

要寫進設計的事：

1. 錯在領域語意，不在語法：把累計電表直接加總成約 42.9 億度、把 75 筆當成 75 次、看不出 2 小時的斷訊。錯的答案和對的一樣篤定，不能直接給使用者看。
2. 語意層是 5 個參數化工具（統計、區段、斷訊、用電量、最新值）：SQL 固定，參數用 ClickHouse query parameter 綁定，注入測試都被擋下。兩個模型都全對，工具錯誤 0 次，token 少 3–4 倍。
3. 這組工具是照這 10 題寫的，只證明 4B 模型會選對工具並正確轉述。正式版要從使用者實際會問的問題設計，範圍外的問題交給雲端模型，或回答無法回答。這和 Cypher 的結論一致：先給參數化工具，自由查詢語言放在後面。

## 警報腳本：Rhai 與 WASM

AI 寫的告警規則建議用 Rhai。兩條路 AI 寫對的比例打平，差別在維運成本。測法：6 條規則、共 25 個測試視窗，兩個 4B 模型各寫一次，失敗時把編譯錯誤或失敗案例回饋，最多修 2 次。WASM 路線是讓 AI 寫 Rust，再編成 wasm32 在 wasmtime 執行。

| 檢查 | Rhai 1.26 | Rust → WASM（wasmtime 49） |
| --- | --- | --- |
| AI 寫對（R1–R5，兩模型合計） | 7/10 | 7/10 |
| 雲端每次編譯 | 0.1–47 ms | rustc 0.5–3.6 秒，另加 Cranelift 0.1–0.3 秒 |
| 雲端需要 | 一個函式庫 | 約 1.6 GB 的 Rust toolchain |
| 每條規則常駐記憶體 | 0.5–1.8 KB | 354 KB |
| 每次評估（1440 筆視窗） | 約 1 ms | 約 1 ms |
| 惡意腳本 | 19 個全擋下，需補兩個洞 | 11 個全擋下，天生隔離 |
| 閘道器執行檔增加（未在 Pi 上實測） | +2.6 MB，直接傳原始碼 | +0.7 MB，雲端與閘道器的 wasmtime 版本必須一致 |

要寫進設計的事：

1. 多條 Rhai 規則共用同一份 ctx 時，前一條能竄改後一條看到的資料；每次執行要各給一份，或用唯讀型別包起來。
2. 只靠 `max_operations` 擋不住：逐筆 push 的迴圈跑了 3.6 秒。要再用 `on_progress` 設時間上限，50 ms 實測準時停止。
3. 空白答案也是合法的 Rhai 腳本，7 次空白腳本都「編譯成功」。部署前必須跑視窗測試，且至少要有一個「應該觸發」的案例。
4. 53 次嘗試中有 13 次被思考用光 8000 token，沒產出程式；生成規則要用非思考模式或更大的額度。
5. qwen3:4b 寫 Rhai 會混進 Rust 語法，qwen3.5:4b 不會。規則描述要明寫時間窗範圍：「連續 5 分鐘」曾被讀成「最新 5 筆」。
6. WASM 留給不受信任的第三方 plugin，而且要能接受 1.6 GB 的 toolchain 才考慮。生成時間（92–1193 秒）受 8 GB 主機 swap 與 Ollama 共用影響，不代表正式環境。

## RAG 自架（Qdrant 1.19.2）

Qdrant 的檢索品質、多租戶與備份還原都可行；Qwen3-VL embedding 與 reranker 已決定改用 API；向量處理已在 knowva 專案驗證，這次不重測。替代的 embedding 是 qwen3-embedding:0.6b（1024 維），語料為鍋爐、冰水主機、空壓機手冊與小字故障碼表，中英混排，共 30 個查詢。

| 模式 | MRR | 前 5 名召回 | 故障碼查詢排第一 |
| --- | --- | --- | --- |
| 只用 dense | 0.94 | 0.98 | 6/8 |
| 只用 sparse（BM25） | 0.96 | 0.97 | 8/8 |
| hybrid（RRF） | 0.97 | 0.98 | 8/8 |

- 多租戶：`tenant_id` 設為 `is_tenant` payload index，180 次過濾搜尋 0 跨租戶命中。
- 備份還原：collection snapshot（422 KB）在 4–6 秒內還原到另一個實例，索引與搜尋結果一致。
- 切換 alias 3 次，期間 4 個查詢迴圈共 12,604 次查詢、零錯誤；int8 量化加原始向量放磁碟，指標與全精度完全相同。

要寫進設計的事：

1. E-203、A-12 這類故障碼只靠 dense 會混淆相鄰的碼，必須有 sparse 這一路。
2. RRF 會產生許多同分，Qdrant 對同分的排序不固定；還原後的實例有 4/30 個查詢名次互換。要加確定性的 tie-break，或用 reranker。
3. snapshot 以 collection 為單位；整個儲存區的備份要在 k3s runbook 另外決定。
4. 4096 維向量的粗估（未實測）：100 萬個 chunk 原始約 16 GB，int8 後約 4 GB 在 RAM。

## Cypher 解析與租戶改寫器（Neo4j 2026.09 Community）

「由服務改寫查詢強制過濾租戶」可行，但只在每個節點樣式加過濾會洩漏。加強後的五層改寫器在 118 個攻擊下 0 洩漏。測法是 non-interference：同一個改寫後的查詢先在完整圖上跑，再在「刪掉租戶 B、事後 rollback」的交易裡跑，結果或錯誤不同就算洩漏。測試圖另埋了兩條跨租戶邊，模擬不變式被破壞。

| 改寫方式 | 攻擊洩漏 | 合法查詢結果正確 |
| --- | --- | --- |
| 不改寫（對照） | 106/116 | — |
| 完整五層 | 0/118 | 44/48，4 個被拒 |
| 少了 CASE 守衛 | 4 | 43/48 |
| 少了可變長度路徑轉 QPP | 3（要有跨租戶邊） | 43/48 |

五層改寫（每一層都是失敗即拒絕）：

1. 字元層：禁止註解、反引號識別字與特殊空白，避免解析器與 Neo4j 對「哪裡是程式碼」解讀不同。
2. 語法樹白名單：只允許 MATCH、OPTIONAL MATCH、WITH、UNWIND、RETURN、UNION；拒絕 CALL、USE、LOAD CSV、寫入、EXPLAIN、參數、外掛函式與 startNode()/endNode()。
3. 每個節點樣式（含子查詢、pattern predicate、comprehension、QPP）加 `{tenant_id: $__tenant}`。
4. 可變長度路徑改寫成 QPP，讓中間節點也被過濾；shortestPath() 改成 `SHORTEST 1`。
5. 每個使用者條件包成 `CASE WHEN <租戶守衛> THEN (條件) ELSE false END`。最後重新解析改寫結果並驗證每個節點與條件都有守衛。改寫耗時中位數約 90 µs。

要寫進設計的事：

1. Neo4j planner 會重排過濾條件：`properties(b).secret.foo` 會排在 `b.tenant_id = $t` 之前執行，對 B 的節點報錯。就算沒有任何跨租戶邊也會發生。
2. 錯誤訊息本身帶資料：實測回傳 `Expected the value 'CANARY-B' to be of type MAP`。Neo4j 的錯誤原文不可回給 LLM 或使用者，只回通用類別，原文只寫伺服器日誌。
3. 寫入端要保證「沒有跨租戶邊」，並定期用查詢檢查；可變長度路徑與展開關係時的洩漏都以此為前提。
4. 經 WITH 或 UNWIND 衍生的值（例如 `WITH properties(n) AS p`）無法加守衛，是殘餘風險；實測 5 種寫法都沒有洩漏。
5. Rust 的 Cypher 解析器全是 2026 年才出現，最好的 open-cypher 0.2.1 也只有單一維護者；應 vendor 並固定版本。它不支援 CALL 子查詢與不含 MATCH 的 `EXISTS {}`，約 8% 的 LLM 寫法會被拒、需重寫。
6. 唯讀由 `access-mode: READ` 強制，Community 有效；交易逾時只能寫在伺服器設定（10 秒已驗證會終止笛卡兒積）。
7. planner 行為可能隨版本改變：這組攻擊測試要放進 CI，每次升級 Neo4j 都要重跑。第一版可先只給 LLM 參數化的圖查詢工具，自由 Cypher 放在開關後。

## 單節點資源（k3s 整套）

實測 · Mac mini M1 上的 lab VM（Debian 12 aarch64），2026-10-09。8 GB 主機跑整套服務仍有過半餘裕：閒置合計 2.7 GB，剩 5.3 GB；不含 Rust 服務與地端 LLM。k3s 與五個資料服務在 4 GiB VM 內實測；Neo4j、Grafana、OTel 為單獨容器量測。

| 元件 | 閒置記憶體（MB） |
| --- | --- |
| k3s 本身（含系統 pod） | 953 |
| Neo4j Community | 860 |
| 作業系統（Debian 12） | 358 |
| ClickHouse | 189 |
| Grafana | 151 |
| Qdrant | 106 |
| OTel collector | 45 |
| Postgres | 40 |
| RustFS | 39 |
| Mosquitto | 2 |
| 合計 | 2,743 |

k3s v1.36.5 本身約吃 0.95 GB，比官方文件的 1.2–1.6 GB 少；ClickHouse 載入 25 萬筆並跑分析後也只到 273 MB。Traefik 以 SNI 把 MQTT 直通到 Mosquitto，與 HTTPS 共用 443，broker 測試 23/23 通過。

要寫進設計的事：

1. Mosquitto 讀不到經 ConfigMap 掛載的 acl_file（k8s 用 symlink），要用 subPath 掛成一般檔案。
2. SNI 直通後 Mosquitto 只看得到 Traefik 的 pod IP，依閘道器 IP 的稽核與限流會失效；要端到端的 PROXY protocol（未驗證 Mosquitto 2.1 是否支援）。
3. TLS port 用 tcpSocket readiness probe 會每次記一筆 unexpected eof，改用 exec probe。
4. Docker Hub 沒有 `eclipse-mosquitto:2.1.2` 這個 tag，要用 digest 固定版本。

## 8 GB 記憶體負載測試（Fedora Asahi 實機）

依目前決策的架構，每秒寫入 1 萬筆時整機尖峰 4.36 GB（可用 7.4 GB），沒有 OOM，記憶體壓力為 0。加上還沒實作的 10 個 Rust 服務，估計尖峰約 5 GB，8 GB 夠用。

環境：k3s v1.36.5 關閉 Traefik，改用 Istio ambient 1.30.5（istiod、ztunnel、istio-cni、Gateway API 入口）。HTTPS 與 MQTT 共用 443，MQTT 經 TLSRoute 以 SNI 直通 Mosquitto。服務為 Postgres 18、ClickHouse 26.8、Qdrant 1.19.2、Mosquitto 2.1、Grafana 13，OTel collector 寫入 ClickHouse。ClickHouse 預載 30 天、52 億筆（15.2 GiB，每筆約 3.1 bytes）。

| 階段 | 負載 | 整機尖峰 | 最低可用 | 錯誤 / OOM |
| --- | --- | --- | --- | --- |
| 閒置 | 無 | 3.74 GB | 3.81 GB | 0 / 0 |
| M | 1,000 台閘道器每秒 2,000 筆；AI 查詢 3 路、儀表板 2 路、每分鐘一次 30 天重查詢；Qdrant 4 萬筆 4096 維每秒查 5 次；pgbench 每秒 200 筆；OTel 每秒 300 筆 log | 4.14 GB | 3.41 GB | 0 / 0 |
| L | 2,000 台閘道器每秒 1 萬筆，其他負載加倍以上 | 4.36 GB | 3.19 GB | 0 / 0 |

L 級各服務的 anon 記憶體尖峰（不含 page cache）：ClickHouse 613 MB、Qdrant 249 MB、Grafana 120 MB、Istio 入口 110 MB（2,000 條直通連線）、Mosquitto 94 MB（2,000 條連線）、OTel 73 MB、Postgres 52 MB、istiod 47 MB、ztunnel 25 MB；k3s 本身約 800 MB。閘道器從送出到收到 ack 的 p95 約 1 秒，一般查詢 p95 約 0.3 秒，30 天分位數重查詢 21 秒、259 MiB。

要寫進設計的事：

1. Qdrant 記憶體上限至少 2 GiB：設 1 GiB 時，4096 維向量建索引到 2.4 萬筆就被 OOM kill（原始向量已放磁碟、int8 在 RAM）；2 GiB 寫完 4 萬筆。
2. 大量匯入要錯開：ClickHouse 預載與向量寫入同時跑時，約 600 MB 被擠進 swap。
3. 小主機設定下 ClickHouse 每個查詢只用 2 個 thread，30 天重查詢要 21 秒；瓶頸是 CPU，不是記憶體。
4. k3s 內建 Traefik 的 CRD chart 已裝好 Gateway API v1.6.1 標準版（含 TLSRoute v1）；實驗版 CRD 會被 safe-upgrades 政策擋下，用標準版即可。
5. 未測到：10 個 Rust 服務（估 0.3–0.6 GB）、調大的 Postgres shared_buffers（約 0.4 GB）、Istio ext_authz。正式容量仍以 MS3 用實際服務重測為準。

限制：負載產生器與服務跑在同一台，記憶體已扣除，但會搶 CPU；16K page 可能讓記憶體用量比 x86 略高。
