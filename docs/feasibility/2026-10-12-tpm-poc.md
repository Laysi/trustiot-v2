# 可行性測試結果（2026-10-12 閘道器 TPM：mTLS、換發挑戰與 LUKS 自動解鎖）

這一頁記錄 MS1 開始前的 TPM 可行性測試（Laysi/trustiot-v2#74），在 lab Pi（`trustiot-lab`，Raspberry Pi 4 加 Infineon SLB9670）上實測，三項都通過：Rust 閘道器程式以 TPM 內不可匯出的 ECC P-256 金鑰和 Mosquitto 完成 mTLS，採用 rustls 外部簽章，不需要 tpm2-pkcs11；換發挑戰以同一把金鑰簽章，驗證端以登錄的公鑰驗過，重放被拒；檔案型的 LUKS2 容器開機時由 TPM 自動解鎖，複製到別台電腦打不開（以複製容器檔模擬拔卡，沒有實際把 SD 卡移到別台電腦）。

最影響設計的數字是 SLB9670 做一次 ECDSA P-256 簽章約 70 ms：每次完整的 mTLS 握手多約 70 ms，每秒最多約 14 次簽章。另外三個發現：lab 的 TPM 模組接在 SPI0 的 CE0，官方 overlay 偵測不到，要用自編的 overlay；Pi 4 的韌體不做 measured boot，PCR 0–7 開機後一律是 0，而且軟體重開機不會重置這塊 TPM，PCR 只在斷電後歸零，所以 LUKS 不綁 PCR，只擋得住 SD 卡被拔走，擋不住整台被偷；Mosquitto 預設不設 TCP\_NODELAY，握手很快時 CONNACK 會多等約 43 ms。

| 項目 | 結論 | 關鍵數字 | 對決策的影響 |
| --- | --- | --- | --- |
| TPM 偵測 | 通過（要自編 overlay） | SLB9670，韌體 7.63.3353.0；模組接在 CE0 | 映像的 overlay 要對應模組的 CS 腳位 |
| TPM 金鑰 mTLS（rustls 外部簽章） | 通過 | TPM2\_Sign p50 69.6 ms、p99 71.0 ms；完整握手 p50 71.9 ms（軟體金鑰 2.2 ms） | 決策 12 照做；不需要 tpm2-pkcs11 |
| 換發挑戰簽章 | 通過 | 9 個案例全部符合預期（重放、竄改、過期、綁定不符都被拒） | 決策 12 照做；簽章內容由閘道器組、格式為 SHA-256 加 DER |
| LUKS 由 TPM 自動解鎖 | 通過（拔卡以複製容器模擬） | 開機解鎖 1.8 秒、不問密碼；別台電腦（無 TPM、不同 TPM）都解不開 | D5 照做；不綁 PCR，威脅模型交給 Laysi/trustiot-v2#95 |

## 環境整理：TPM 模組接在 CE0

2026-10-12 全新安裝的 Raspberry Pi OS 沒有 `/dev/tpm0`。照官方說明在 `/boot/firmware/config.txt` 加 `dtparam=spi=on` 與 `dtoverlay=tpm-slb9670` 後，`tpm_tis_spi spi0.1` 的 probe 回 -110（逾時），手動重新 bind 一次也一樣。官方 overlay 把 TPM 放在 SPI0 的 CE1（GPIO7）。以 spidev0.0 直接讀 TIS 的 `DID_VID` 暫存器（locality 0，位址 0xD40F00）得到 `0x001B15D1`（Infineon、SLB9670），所以這塊模組接在 **CE0（GPIO8）**。

改用自編的 `tpm-slb9670-ce0` overlay 後，核心印出 `tpm_tis_spi spi0.0: 2.0 TPM (device-id 0x1B, rev-id 16)`，`/dev/tpm0` 與 `/dev/tpmrm0` 出現。第一次開機的 `A TPM error (256) occurred attempting the self test` 是 TPM 還沒收到 `TPM2_Startup`（Pi 的韌體不會送），核心隨即自己送，屬正常。overlay 與官方的只差 `reg` 與停用的 spidev：

```dts
/dts-v1/;
/plugin/;
/ {
	compatible = "brcm,bcm2835";
	fragment@0 { target = <&spi0>; __overlay__ { status = "okay"; }; };
	fragment@1 { target = <&spidev0>; __overlay__ { status = "disabled"; }; };
	fragment@2 {
		target = <&spi0>;
		__overlay__ {
			#address-cells = <1>;
			#size-cells = <0>;
			slb9670: slb9670@0 {
				compatible = "infineon,slb9670";
				reg = <0>;
				#address-cells = <1>;
				#size-cells = <0>;
				spi-max-frequency = <32000000>;
				status = "okay";
			};
		};
	};
};
```

```sh
dtc -@ -I dts -O dtb -o tpm-slb9670-ce0.dtbo tpm-slb9670-ce0-overlay.dts
dtmerge /boot/firmware/bcm2711-rpi-4-b.dtb /tmp/merged.dtb tpm-slb9670-ce0.dtbo   # 重開機前先確認合併得進去
sudo install -m 0755 tpm-slb9670-ce0.dtbo /boot/firmware/overlays/
# config.txt 的 [all] 段落加上：dtparam=spi=on 與 dtoverlay=tpm-slb9670-ce0
```

`config.txt` 原有的 `dtoverlay=nospi10` 在 `[pi5]` 段落下，只對 Pi 5 生效（停用 Pi 5 的 spi10），與 Pi 4 的 SPI0 無關。

TPM 的狀態（`tpm2_getcap`）：製造商 IFX、SLB9670，韌體 7.63.3353.0（`FIRMWARE_VERSION_1=0x0007003F`、`_2=0x000D1900`），TPM 2.0 規格 1.16；支援的曲線只有 NIST P-256 與 BN P-256。模組留有舊狀態，符合[現場硬限制](../requirements/field-constraints.md)的「重刷 SD 卡後 TPM 內的狀態仍在」：持久 handle `0x81000001` 已有一把 ECC P-256 的儲存金鑰，名稱與 tpm2-tools 預設範本（`tpm2_createprimary -C o -G ecc256:aes128cfb`）重建的 primary 完全相同，就是標準的 SRK；owner、endorsement、lockout 的授權都沒設；`LOCKOUT_COUNTER` 為 1；EK 憑證的 NV index `0x1C00002`（RSA）與 `0x1C0000A`（ECC）存在。測試沒有清除或刪除任何舊狀態。

## TPM 金鑰 mTLS（rustls 外部簽章）

通過，採用 rustls 外部簽章：實作 rustls 的 `SigningKey` 與 `Signer` 兩個 trait，就能把 CertificateVerify 的簽章交給 TPM，不必經過 PKCS#11，所以 tpm2-pkcs11 沒有試。

做法：

1. **金鑰**：以 tss-esapi 7.7.0（經 libtss2 4.1.3 與核心的資源管理器 `/dev/tpmrm0`）在 SRK `0x81000001` 下 `TPM2_Create` 一把 ECC P-256 簽章金鑰，scheme 固定為 ECDSA-SHA256，再以 `TPM2_EvictControl` 持久化在 `0x81000100`。範本用 tss-esapi 的 `create_unrestricted_signing_ecc_public`，屬性是 `fixedtpm|fixedparent|sensitivedataorigin|userwithauth|sign`：私鑰在 TPM 內產生，fixedTPM 與 fixedParent 讓 `TPM2_Duplicate` 帶不出去，也就無法匯出。authValue 為空。
2. **CSR**：rcgen 0.14.10 的 `SigningKey` trait 讓 CSR 的自簽章在 TPM 內完成。工作站以 `openssl req -verify` 驗過，CSR 的公鑰與 `TPM2_ReadPublic` 讀出的相同，再由一次性的測試 CA 簽發（CN `gw-lab-01`、EKU clientAuth）。
3. **TLS**：rustls 0.23.45（ring 0.17.14 provider、只開 TLS 1.3）以 `with_client_cert_resolver` 掛上 `CertifiedKey`。其中的 `SigningKey` 只在對方提供 `ecdsa_secp256r1_sha256` 時回傳 `Signer`；`Signer::sign` 收到 CertificateVerify 要簽的完整內容，先在軟體算 SHA-256，再以 `TPM2_Sign`（null hashcheck ticket、空密碼的 password session，不另開 HMAC session）簽這個摘要，把 TPM 回的 r、s 轉成 DER。tss-esapi 的 `Context` 只在一條專用執行緒上使用，rustls 的 `Signer` 經 channel 交給它。啟動時以 `CertifiedKey::keys_match` 確認憑證的公鑰就是 TPM 的公鑰。
4. **broker**：工作站上 rootless podman 跑的 Mosquitto 2.1.2（`eclipse-mosquitto:2.1.2-alpine`），只開 mTLS 的 listener：`require_certificate true`、`use_identity_as_username true`、`allow_anonymous false`，ACL 為 `pattern readwrite gw/%u/#`。閘道器程式以 MQTT 3.1.1 連線（keepalive 60 秒），不帶使用者名稱。

結果：broker 記錄 `New client connected ... (p4, c1, k60, u'gw-lab-01')` 與 `negotiated TLSv1.3 cipher TLS_AES_256_GCM_SHA384`；閘道器訂閱 `gw/gw-lab-01/#` 成功，QoS 1 發布到 `gw/gw-lab-01/telemetry` 收到 PUBACK，也收回了自己的訊息。

TPM 簽章延遲（`TPM2_Sign`，從送出到收到結果，n=300，每個簽章都以公鑰在軟體驗過）：

| 指標 | min | p50 | p90 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| TPM2\_Sign（ECDSA P-256） | 68.8 ms | 69.6 ms | 70.1 ms | 71.0 ms | 73.1 ms |

握手時間（Pi 與工作站在同一個區網，TCP 連線 p50 0.2 ms；broker 設 `set_tcp_nodelay true`，原因見下）：

| 連線方式 | 次數 | TLS 握手 p50 | TLS 握手 p99 | CONNACK p50 | TPM 簽章次數 |
| --- | --- | --- | --- | --- | --- |
| TPM 金鑰，完整握手 | 30 | 71.9 ms | 75.2 ms | 1.7 ms | 每次 1 |
| 軟體金鑰（同一曲線），完整握手 | 30 | 2.2 ms | 3.7 ms | 1.2 ms | 0 |
| TPM 金鑰，TLS 1.3 session resumption | 19 | 1.4 ms | 1.6 ms | 0.6 ms | 0 |

完整握手比軟體金鑰多出的時間就是一次 TPM 簽章。TLS 1.3 的 session resumption（PSK）不做 CertificateVerify、不用 TPM，broker 也照樣認得身分（`u'gw-lab-01'`）。

Mosquitto 預設不對連線設 TCP\_NODELAY：沒有設的時候，握手很快的連線（軟體金鑰、resumption）CONNACK 要多等約 43 ms（p50 43.3 ms），是 broker 端的 Nagle 演算法在等前一段 TLS 資料（NewSessionTicket）的 ACK；TPM 的完整握手本身就要 70 ms，看不出這段等待。加上 `set_tcp_nodelay true` 後 CONNACK 降到約 1 ms。

## 換發挑戰簽章

通過。驗證端是一支小的 Rust 程式（axum 0.8.9、p256 0.13.2），代替決策 12 的憑證服務：`POST /challenge` 對登錄過的裝置發 32 位元組的隨機 nonce（base64url），綁定裝置 ID 與用途（`cert-renewal`、`rebind`），30 秒到期；`POST /redeem` 收到請求時**先把 nonce 移除**，再檢查裝置與用途、是否過期，最後只用伺服器自己存的欄位重建訊息，以登錄的公鑰（出廠時從 TPM 讀出的 SPKI）驗章。

閘道器簽的內容由閘道器自己組，不簽伺服器給的任意位元組：

```text
trustiot-v2 challenge v1\n
device=<裝置 ID>\n
purpose=<用途>\n
nonce=<伺服器給的 nonce，base64url>\n
expires=<到期的 Unix 秒>\n
```

閘道器的 mTLS 與換發用同一把 TPM 金鑰，所以簽的內容要和 TLS 的簽章內容分得開：TLS 1.3 的 CertificateVerify 以 64 個 0x20 開頭，TLS 1.2 簽的是以 ClientHello（0x01）開頭的握手紀錄，這個訊息以 `trustiot-v2` 開頭，與兩者都不可能相同。若伺服器能讓閘道器簽任意內容，冒充的伺服器就能拿到可用在 TLS 上的簽章。

簽章格式：ECDSA P-256，雜湊 SHA-256（TPM 簽的是訊息的 SHA-256 摘要），簽章是 DER 編碼的 `ECDSA-Sig-Value`（`SEQUENCE { r INTEGER, s INTEGER }`，最長 72 位元組），以 base64 放進 JSON，與 X.509 和 TLS 用的格式相同。TPM 回的是固定長度的 r、s，由閘道器轉成 DER；不採用 r‖s 的 64 位元組格式（IEEE P1363，WebCrypto 用的那種），是為了和 CSR、TLS 共用同一套程式庫。同一份簽章也以 `openssl dgst -sha256 -verify` 驗過。

| 案例 | 預期 | 結果 |
| --- | --- | --- |
| 正確簽章 | 200 | 200 |
| 同一個請求再送一次（重放） | 409 | 409：nonce 不存在或已用過 |
| 竄改簽章的 1 個位元 | 401 | 401：簽章不符 |
| 竄改失敗後，以正確簽章重送同一個 nonce | 409 | 409：失敗的嘗試也作廢 nonce |
| 用途不符（發給 `cert-renewal`，以 `rebind` 兌換） | 403 | 403 |
| 裝置不符（發給 `gw-lab-01`，以另一台登錄過的裝置兌換） | 403 | 403 |
| 簽章內容改了到期時間 | 401 | 401 |
| 沒發過的 nonce | 409 | 409 |
| 等 32 秒才兌換（超過 30 秒到期） | 410 | 410 |

## LUKS 由 TPM 自動解鎖

通過，「SD 卡移到別台電腦」以複製容器檔模擬。依 issue 的範圍不重新分割 SD 卡：資料分割區以根目錄上的 64 MiB 檔案 `/var/lib/trustiot-poc74/data.luks` 代替，systemd-cryptsetup 會自動掛上 loop 裝置。

建立與登錄（systemd 257.13、cryptsetup 2.7.5，Debian 13 的套件）：

1. `cryptsetup luksFormat --type luks2 --pbkdf argon2id --pbkdf-memory 262144`，以工作站產生的隨機密碼建立容器，格式化成 ext4 並寫入一個標記檔。這個密碼只為了測試（證明複製出去的容器本身完好），只存在工作站，沒有留在 Pi 上，也沒有進 repo。依 Laysi/trustiot-v2#95 的設計，正式映像不留密碼 keyslot。
2. `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs= <容器>`：新增 keyslot 1 與 `systemd-tpm2` token，金鑰封在 SRK `0x81000001` 下（token 的 `tpm2-srk: true`、`tpm2-primary-alg: ecc`），不綁任何 PCR（原因見下一節）。這個 keyslot 的金鑰本身是高熵的，cryptsetup 只用 PBKDF2 1000 次。容器加密是 `aes-xts-plain64`、512 位元金鑰、4096 位元組 sector。

不輸入密碼、只用 TPM 開啟（`cryptsetup open --test-passphrase --token-only`）三次分別花 1.50、1.38、1.39 秒，主要是 TPM 的解封。

開機自動解鎖的設定。每一項都是 nofail，解鎖不輸入密碼（headless），所以解不開時只會少掛這個分割區，不會卡住開機或 sshd：

```text
# /etc/crypttab
poc74data /var/lib/trustiot-poc74/data.luks none luks,tpm2-device=auto,tpm2-measure-pcr=yes,headless=true,nofail
# /etc/fstab
/dev/mapper/poc74data /mnt/poc74data ext4 defaults,nofail,x-systemd.device-timeout=60s 0 2
# /etc/systemd/system/systemd-cryptsetup@poc74data.service.d/poc74.conf
[Unit]
Wants=dev-tpmrm0.device
After=dev-tpmrm0.device
[Service]
TimeoutStartSec=120
```

drop-in 是因為 SPI 的 TPM 由核心模組在開機途中才偵測到，systemd 產生 unit 時還看不到它（`tpm2.target` 要等 `/dev/tpmrm0` 出現才被帶入），所以讓解鎖等 `dev-tpmrm0.device`，並以 120 秒為上限（產生出來的 unit 預設 `TimeoutSec=infinity`）。nofail 讓產生出來的 unit 只被 `cryptsetup.target` 與 `local-fs.target` 拉起、不排在它們之前。

重開機（2026-10-12T09:15:54Z）後：`systemd-cryptsetup@poc74data.service` 在開機 6.44 秒開始、8.25 秒完成（`systemd-analyze blame` 1.81 秒），fsck 82 ms，8.40 秒掛載完成；重開機前寫入的標記檔都在；journal 只有 `Automatically discovered security TPM2 token unlocks volume`，沒有任何密碼提示。multi-user.target 在 userspace 9.3 秒到達。

「SD 卡移到別台電腦」以複製模擬：把容器檔（sha256 與 Pi 上相同）複製到工作站，在 rootless podman 的 Debian 13 容器（與 Pi 相同的 cryptsetup 2.7.5、systemd 257.13）裡開啟。容器檔就是 SD 卡上的全部 LUKS 資料，拔卡與複製讓另一台電腦拿到的位元組相同；不在卡上的只有 TPM 內的儲存種子。實際把 SD 卡插到別台電腦需要有人到場，這次沒有做。

| 另一台電腦 | 結果 |
| --- | --- |
| 沒有 TPM | 拒絕：`Failed to create TPM2 context`，headless 不會改問密碼 |
| 有 TPM（swtpm），且在 `0x81000001` 放了同一個範本的 SRK | 拒絕：`TPM2_Load` 回 `TPM_RC_INTEGRITY`（0x1DF），systemd 報 `Failed to unseal secret using TPM2` |
| 同上，以 `tpm2_load` 直接載入 token 裡的封裝資料 | 拒絕：`integrity check failed`；同一份資料在 lab Pi 的 TPM 上 `tpm2_load` 成功 |
| 對照組：在同一個 swtpm 上新建並登錄的容器 | TPM 解封成功（`Failed to activate with TPM2 acquired key`，只因 rootless 容器沒有 device-mapper 而無法掛上） |
| 對照組：複製出去的容器以測試密碼開啟 | 成功，容器本身完好 |

同一個範本在不同 TPM 上產生的 SRK 名稱不同（swtpm 的是 `000b1280…`，lab Pi 的是 `000baf00…`），因為 SRK 由每顆 TPM 自己的儲存種子推導，封裝資料只有在原本那顆 TPM 上通得過完整性檢查。

## PCR 綁定與威脅模型（給 Laysi/trustiot-v2#95）

實測的事實：

- Pi 4 的開機鏈（EEPROM bootloader、VideoCore 韌體、核心）都不量測，PCR 0–16 與 23 在開機後都是 0（17–22 是 DRTM 用的 PCR，初始值全為 F），重開機後再讀 PCR 0–7、10、11、14 也還是 0。systemd 量測相關的 unit（`systemd-pcrextend`、`systemd-pcrmachine`、`systemd-tpm2-setup`）都因 `ConditionSecurity=measured-uki` 不成立而略過；crypttab 的 `tpm2-measure-pcr=yes` 也沒有作用，開機解鎖後 PCR 15 沒有改變。
- systemd-cryptenroll 綁 PCR 時，自己就警告 `none of the selected PCRs are valid! Firmware apparently did not initialize any of the selected PCRs ... PCR policy effectively unenforced!`。它的預設是 PCR 7（Secure Boot 狀態），在 Pi 上永遠是 0。
- TPM 確實會執行 PCR policy：綁 PCR 15 的測試容器在 PCR 15 為 0 時打得開，`tpm2_pcrextend` 之後被拒（`Failed to unseal secret using TPM2: Operation not permitted`）。
- **軟體重開機不會重置這塊 TPM**：測試把 PCR 15 extend 成 `0x2F60673D…` 後執行 `systemctl reboot`，開機後 PCR 15 仍是同一個值，核心也沒有像斷電後第一次開機那樣補送 `TPM2_Startup`。模組的 reset 腳位沒有跟著 SoC 重置，PCR 只在斷電後歸零。

結論：

- **不綁 PCR**（`--tpm2-pcrs=` 空字串，要明確指定，否則 systemd 預設綁 PCR 7）。綁 PCR 0–7 沒有保護效果：攻擊者在同一台 Pi 開自己的系統，看到的也是全 0；反而若日後的韌體或 bootloader 開始量測，解鎖就會失效，依 Laysi/trustiot-v2#95 的設計會清掉資料分割區。
- **不採用「解鎖後 extend PCR 15 鎖住」（lock after use）**：它本來能讓之後拿到 TPM 存取權的程式（例如被入侵的閘道器 agent，它為了 mTLS 本來就能用 `/dev/tpmrm0`）解不出磁碟金鑰；但這塊 TPM 不隨軟體重開機重置，extend 之後的每次軟體重開機都會解鎖失敗，直到斷電為止。而且 systemd 在 Pi 上不會自己 extend，要另寫一個 unit。
- **防得住：SD 卡被拔走或被複製**。金鑰封在 SRK 下，SRK 由這顆 TPM 的儲存種子推導，別台電腦（不論有沒有 TPM）都解不開，上表已實測。
- **防不住：整台被偷**。小偷拿到 Pi、SD 卡與 TPM，原本的系統開機就會自動解鎖（這正是設計目的）；換一張自己的 SD 卡開機也能叫同一顆 TPM 解封，PCR 分不出差別。lab 的 SLB9670 是插在 GPIO 排針上的模組，連同 SD 卡一起移到另一台 Pi 4 也一樣解得開，閘道器的 mTLS 金鑰同樣跟著模組走。
- 整台被偷的緩解不在 TPM：雲端除役並撤銷憑證（決策 12），資料分割區只放緩衝與設定；Pi 的 secure boot（簽章的 boot image）加上焊死的 TPM 才能讓「換卡開機」與「把模組移到別台」都失效，屬於 MS6 的 D6。開機輸入 TPM PIN 不適用於無人值守的閘道器。

## 要寫進設計的事

1. 閘道器映像的 device tree overlay 要對應 TPM 模組的 CS 腳位：lab 的模組在 CE0，要用上面的 `tpm-slb9670-ce0`；官方的 `tpm-slb9670` 只認 CE1。採購時要確認模組型號與腳位，映像只放一種 overlay（Laysi/trustiot-v2#95）。
2. TPM 金鑰：ECC P-256、ECDSA-SHA256，屬性 fixedTPM、fixedParent、sensitiveDataOrigin，放在標準 SRK `0x81000001` 下並持久化；程式經 `/dev/tpmrm0` 存取，正式環境以 `tss` 群組的專用帳號執行，不用 root。產線工作站工具（Laysi/trustiot-v2#80）同樣以 tss-esapi 經 `/dev/tpmrm0` 產生金鑰與 CSR，持久 handle 的編號在那裡定；模組可能留有舊狀態（舊的 SRK、lockout 計數），出廠時要決定沿用標準 SRK 還是先清除，以及要不要設定 owner 與 lockout 授權。
3. mTLS 用 rustls 外部簽章，不用 tpm2-pkcs11。每次完整握手多約 70 ms、簽章只能一個接一個做（每秒約 14 次）；rustls 的 `sign` 是同步呼叫，TPM 操作放在專用執行緒，握手不要跑在同時負責 Modbus 輪詢的單執行緒 runtime 上（Laysi/trustiot-v2#86）。
4. 閘道器先不開 TLS session resumption：它能省掉重連時的 70 ms，但被撤銷的閘道器能否憑舊的 session ticket 繞過新的 CRL，取決於 Mosquitto 重新載入 CRL 時是否換掉 ticket 金鑰，這次沒有測。70 ms 對重連不是負擔。
5. Mosquitto 要設 `set_tcp_nodelay true`，MQTT 轉接服務的 TCP 連線也要設 TCP\_NODELAY，否則小封包會被 Nagle 多延遲約 40 ms。
6. 換發挑戰（Laysi/trustiot-v2#83 與憑證服務）：簽章內容由閘道器以固定前綴自己組，含裝置 ID、用途、nonce 與到期時間；nonce 32 位元組、只能用一次（伺服器在檢查前就移除，失敗也作廢）、綁定裝置與用途、短效（PoC 30 秒）；伺服器只用自己存的欄位重建訊息；簽章為 SHA-256 加 DER。
7. 資料分割區（Laysi/trustiot-v2#95）：crypttab 用 `tpm2-device=auto,headless=true,nofail`，fstab 用 `nofail`，再加等待 `dev-tpmrm0.device` 且有上限的 drop-in；登錄時明確寫 `--tpm2-pcrs=`；正式映像不留密碼 keyslot（以隨機金鑰建立、登錄 TPM 後清掉那個 keyslot）；開機解鎖約 1.8 秒。
8. 資料分割區的加密演算法可考慮 Adiantum：Pi 4 的 CPU 沒有 AES 指令，`cryptsetup benchmark` 的 `aes-xts`（512 位元）約 83 MiB/s，`xchacha12,aes-adiantum` 約 240 MiB/s。選哪一個由 Laysi/trustiot-v2#95 決定。

## 範圍外與後續

- 沒有實際把 SD 卡插到別台電腦，以複製容器檔模擬（見上方的理由）。要實體驗證時，需要有人把卡插到別台電腦。
- tpm2-pkcs11 沒有試，因為 rustls 外部簽章就可行。
- RSA 沒有重測，沿用 Laysi/trustiot#81 的結論只用 ECC P-256。
- 決策 12 的「工作站從 TPM 取出 EK」沒有測：EK 憑證的 NV index 存在，讀取與驗證 Infineon 的 EK 憑證鏈留給產線工作站工具（Laysi/trustiot-v2#80）。
- 整台被偷的緩解（secure boot、焊死的 TPM）屬於 MS6 的 D6。

重現步驟：

1. 啟用 TPM：如上建 overlay、改 `config.txt` 後重開機，`tpm2_getcap properties-fixed` 確認。
2. 交叉編譯 `gw`：從 Debian 的 `libtss2-dev` 4.1.3-1.2（arm64）取標頭、`.so` 連結與 pkg-config 檔，連同 Pi 上的 libtss2 執行期函式庫放進一個 sysroot，然後：

   ```sh
   export PKG_CONFIG_ALLOW_CROSS=1 PKG_CONFIG_SYSROOT_DIR=<sysroot> \
     PKG_CONFIG_LIBDIR=<sysroot>/usr/lib/aarch64-linux-gnu/pkgconfig PKG_CONFIG_PATH=
   ```

3. 測試 PKI（全部 ECC P-256、30 天，只在工作站產生、不進 repo）：`openssl ecparam -name prime256v1 -genkey` 產生 CA 與 broker 的金鑰，broker 憑證的 SAN 是工作站的 IP、EKU serverAuth；閘道器憑證以 `openssl x509 -req` 簽 TPM 產生的 CSR，EKU clientAuth。
4. broker：

   ```text
   per_listener_settings false
   allow_anonymous false
   acl_file /mosquitto/config/acl          # pattern readwrite gw/%u/#
   persistence false
   connection_messages true
   listener 8883
   cafile /mosquitto/config/ca.pem
   certfile /mosquitto/config/server.pem
   keyfile /mosquitto/config/server.key
   require_certificate true
   use_identity_as_username true
   set_tcp_nodelay true
   ```

   ```sh
   podman run -d --name poc74-mosquitto --userns=keep-id --user "$(id -u):$(id -g)" -p 18740:8883 \
     -v <設定目錄>:/mosquitto/config:Z,ro docker.io/library/eclipse-mosquitto:2.1.2-alpine \
   ```

5. 在 Pi 上（`/dev/tpmrm0` 屬 `tss` 群組，PoC 以 sudo 執行）：

   ```sh
   sudo ./gw keygen --parent 0x81000001 --handle 0x81000100     # 印出 SPKI，作為出廠登錄的公鑰

     --server-name <工作站 IP> --cn gw-lab-01 --iterations 30 [--resume yes]
   ./gw mqtt --key-file gw-soft-01.key --cert gw-soft-01.pem ...   # 軟體金鑰對照
   ```
