# 可行性測試結果（2026-10-10 Istio ambient 與 Cloudflare Tunnel）

這一頁記錄 MS0 開始前的兩項可行性測試，都在 Mac mini M1 實驗機上以 SaaS 的實際路徑實測：Istio ambient 通過，Cloudflare Tunnel 的雲端側有條件通過。最影響設計的結果是 Cloudflare 對 125 秒沒有資料的 WebSocket 與 HTTP 串流一律切斷，所以閘道器的 MQTT keepalive 要設 60 秒。另一個是 dynsec 的 disableClient 在憑證身分下只踢不擋，停權不能只靠它。雙層 TLS 在 Pi 上的 CPU 與延遲，2026-10-10 決定不測。保活、來源 IP、停權與 SIGTERM、身分服務回應規則四組結論已寫進[架構決策總表](../architecture/decisions.md)的決策 6、27 與[部署與可搬移性](../architecture/deployment.md)。

| 項目 | 結論 | 關鍵數字 | 對決策的影響 |
| --- | --- | --- | --- |
| Istio ambient（k3s、ext\_authz） | 通過 | ext\_authz 讓每個請求多約 1 ms（p50）；身分服務停機時 9 ms 回 403；11 種路徑繞過全部擋下 | 決策 27 照做；身分服務允許請求時一定要回內部身分標頭 |
| Cloudflare Tunnel 與 MQTT 轉接（雲端側） | 有條件通過 | 無資料 125.0 秒被切；1,000 條 WSS+mTLS 連線 p99 372 ms、0 斷線；5 種中斷各 0.4–3.5 秒恢復，12,000 筆 0 遺失 | keepalive 60 秒；來源 IP 只信 CF-Connecting-IP；轉接服務要處理 SIGTERM 並調小 WebSocket 緩衝區 |
| 雙層 TLS 在 Pi 上的 CPU 與延遲 | 範圍外 | — | 2026-10-10 決定不測 |

## Istio ambient（k3s、ext\_authz）

清單列的四項都成立：入口以 ext\_authz 依 cookie 換發內部身分，偽造的身分標頭進不到後端，身分服務失效時一律拒絕，ServiceAccount 授權與 NetworkPolicy 兩層各自生效。身分服務、後端與服務間呼叫都用自寫的 Rust 替身（axum，內部身分以 Ed25519 簽章）。

| 檢查 | 結果 |
| --- | --- |
| global.platform=k3s 下的 CNI 與 ztunnel | 正常；入口到後端、服務之間都走 HBONE（15008），kubelet 健康檢查經 169.254.7.127 照常通過 |
| 有效 cookie | 200；後端收到 1 個身分標頭，驗簽通過，帶使用者、租戶、角色、受眾與 60 秒到期 |
| 沒有 cookie、cookie 錯誤 | 401，身分服務的回應原樣回給用戶端 |
| 有效 cookie 加偽造的身分標頭 | 被身分服務的值覆寫，後端只看到 1 個 |
| 例外路徑加偽造的身分標頭 | 被路由的 RequestHeaderModifier 剝除，後端看到 0 個 |
| 身分服務延遲 3 秒 | 0.517 秒回 403（逾時 0.5 秒、failOpen false） |
| 身分服務停機 | 需要 cookie 的路徑 9 ms 回 403；例外路徑照常 200 |
| 11 種路徑繞過（`..`、`%2e%2e`、`;`、`//`、大小寫、`?`、`%23` 等） | 全部擋下：10 種回 401；`/healthz/..%2fapi/whoami` 被當成 /healthz 底下的路徑，回 404 |
| ServiceAccount 授權（ztunnel L4） | probe-a→probe-b 放行；probe-c→probe-b、probe-a→身分服務、probe-c→轉接服務與 broker 都被重置 |
| NetworkPolicy 第二層 | 非 mesh 的 pod 連 pod IP 與入口都被拒。拿掉 NetworkPolicy 後，沒有授權政策的 probe-c 連得到，有授權政策的 probe-b 仍被 ztunnel 擋下，兩層各自生效 |

| 入口壓測（壓測程式與服務同機） | 每秒請求 | p50 | p99 |
| --- | --- | --- | --- |
| 例外路徑，不經 ext\_authz，32 併發 | 40,300 | 0.70 ms | 1.97 ms |
| 經 ext\_authz，32 併發 | 17,700 | 1.70 ms | 3.85 ms |
| 經 ext\_authz，128 併發 | 20,200 | 5.82 ms | 13.7 ms |

記憶體（metrics-server 的 working set）：istiod 95 MiB；ztunnel 閒置 29 MiB、壓測時 41 MiB；入口新起的 pod 閒置 46–54 MiB、壓測時 59 MiB；istio-cni 36–39 MiB；身分服務在每秒 2 萬次檢查下不到 15 MiB。另一個入口 pod 因為前一天的 2,000 條直通連線停在 121–130 MiB，記憶體沒有還回去。

要寫進設計的事：

1. 身分服務允許請求時一定要回內部身分標頭。Envoy 用回應的值覆寫用戶端帶來的同名標頭；若某次允許沒回這個標頭，偽造的值就會原樣進到後端。例外路徑另外用 RequestHeaderModifier 剝除。
2. 身分服務停機時 Envoy 回 403，和「沒有權限」同一個狀態碼。前端要區分「該重新登入」與「服務暫時不可用」時，可設 statusOnError（例如 503），這點未實測。
3. NetworkPolicy 預設拒絕時，要放行 TCP 15008 與 169.254.7.127/32（ambient 的 kubelet 探測來源），健康檢查才會通過。
4. 主機連入口 ClusterIP 時，來源是 cni0 的 10.42.0.1，不是節點 IP；入口的 NetworkPolicy 依此只放行本機。
5. Gateway 的副本數與 Service 類型用 infrastructure.parametersRef 指向 ConfigMap 設定（2 副本、ClusterIP）。改成 ClusterIP 後沿用原本的 ClusterIP，主機上的 443 也隨之關閉。
6. ztunnel 拒絕時，呼叫端看到的是連線重置，不是 HTTP 403。服務間呼叫失敗要記錄對方服務與錯誤種類，否則權限問題會被當成網路問題。

## Cloudflare Tunnel 與 MQTT WebSocket 轉接（雲端側）

依[部署與可搬移性](../architecture/deployment.md)的路徑實測：閘道器經 443 以 wss 連到 Cloudflare，再經主機上的 cloudflared、入口 gateway 的 ClusterIP 與 MQTT 轉接服務到 Mosquitto，mTLS 由閘道器直達 broker。閘道器端是自寫的 Rust 測試程式（tokio-tungstenite 加 rustls，MQTT 3.1.1），從辦公室網路經網際網路連到 Cloudflare 台北節點；轉接服務是約 150 行的 Rust（axum）。測試用的 tunnel 與網域測完已刪除。

通過：

- cloudflared 在 systemd 沙箱下正常運作：DynamicUser、ProtectSystem=strict、NoNewPrivileges、所有 capability 為 0，token 經 LoadCredential 傳入；`systemd-analyze security` 評分 1.4（沒加沙箱的維運 SSH tunnel 是 9.6）。唯一的影響是 ICMP proxy 停用，產品用不到。
- 主機不開產品埠：入口改成 ClusterIP 後，主機上沒有 80 或 443 在監聽；入口的 NetworkPolicy 只放行本機，叢集內其他 pod 連不到。
- mTLS 經 WebSocket 端到端：Mosquitto 看到的使用者是憑證 CN；訂閱別台閘道器的 topic 回 0x80，發布到別台的 topic 被丟棄；CRL 裡的憑證收到 `CertificateRevoked` 的 TLS alert，一路回到閘道器；dynsec 的 `%u` 樣式可用。
- dynsec 踢除：下 disableClient 後 1 秒內，連線中的 session 經轉接服務斷開。
- 來源 IP：轉接服務與後端都拿到正確的 CF-Connecting-IP；用戶端自帶 CF-Connecting-IP 時，Cloudflare 直接回 403（error 1000）。
- 1,000 條 WSS+mTLS 連線：41 秒全部連上，連線建立 p50 343 ms、p99 372 ms，150 秒內 0 斷線。

| 閒置與串流 | 結果 |
| --- | --- |
| WebSocket 完全沒有資料（MQTT keepalive 0） | 60、90、110 秒仍活著；其餘 6 條都在 125.0 秒被切，沒有關閉握手 |
| MQTT keepalive 240 秒 | 125 秒被切，第一次 PINGREQ 之前就斷了 |
| MQTT keepalive 60 秒 | 撐滿 25 分鐘，送了 24 次 PINGREQ |
| 轉接服務每 50 秒送 WebSocket ping，MQTT keepalive 0 | 撐滿 400 秒；300 秒時探測仍活著 |
| SSE 每 30 秒一次心跳 | 撐滿 600 秒，21 個事件全到 |
| SSE 事件間隔 95、115 秒 | 正常結束 |
| SSE 事件間隔 150 秒 | 125 秒被截斷，HTTP 狀態仍是 200 |
| 首位元組 90 秒 | 正常 |
| 首位元組 140 秒 | 125 秒回 524 |

斷線重連：閘道器以每秒 20 筆 QoS1 連續發送 600 秒，期間依序製造五種中斷。12,000 筆全部收到 ack，其中 128 筆是重連後補送；叢集內的消費者收到 12,000 筆，0 遺失、0 重複。

| 中斷 | 閘道器何時察覺 | 恢復時間 | 說明 |
| --- | --- | --- | --- |
| cloudflared 正常重啟（SIGTERM） | 30 秒後 | 3.5 秒 | cloudflared 先等 30 秒寬限期才斷線；新的 tunnel 連線註冊前，Cloudflare 回 530 |
| cloudflared 被 SIGKILL | 5 秒後 | 2.5 秒 | systemd 5 秒後重啟；期間送出的 100 筆沒有 ack，重連後補送 |
| 轉接服務滾動更新 | 30 秒後 | 0.4 秒 | 轉接服務是容器的 PID 1 且沒處理 SIGTERM，舊 pod 撐到寬限期結束才被 SIGKILL |
| 入口 gateway 滾動更新 | 約 3 秒後 | 0.4 秒 | 新 pod 就緒約 3 秒後，舊 pod 關閉連線 |
| broker 重啟（Recreate） | 立即 | 2.6 秒 | 重連時 broker 還沒起來，第一次失敗 |

| 1,000 條連線時的記憶體增量 | WebSocket 緩衝區 128 KiB（預設） | 8 KiB |
| --- | --- | --- |
| 轉接服務（2 副本合計） | +159 MiB | +32 MiB |
| 入口 gateway（2 副本合計） | +31 MiB | +94 MiB |
| cloudflared | +74 MiB | +72 MiB |
| Mosquitto | +40 MiB | +40 MiB |
| ztunnel | +19 MiB | +18 MiB |
| 整機 | +383 MB | +265 MB |

入口兩輪的差異來自起點不同：第一輪有一個 pod 沿用前一天配置的記憶體，第二輪兩個 pod 都是新起的，+94 MiB 較能代表實際。依第二輪估算，2,000 台閘道器約多 0.5 GB；這是保守值，沒有扣掉 2026-10-09 已計入的 broker 與入口連線。加上 2026-10-09 估的尖峰約 5 GB，仍在 7.4 GB 內。

要寫進設計的事：

1. 閘道器的 MQTT keepalive 設 60 秒。Cloudflare 對兩個方向都沒有資料的連線在 125 秒切斷，keepalive 要遠小於 125 秒，才容得下一次延遲。另一個做法是由轉接服務每 50 秒送 WebSocket ping，實測 MQTT keepalive 設 0 也能撐過 125 秒，不必依賴每台閘道器的設定；兩者可以並用。
2. 來源 IP 只信 CF-Connecting-IP。用戶端自帶的 X-Forwarded-For 與 True-Client-IP 會原樣傳進來，不能拿來稽核或限流。
3. 後端看到的 x-forwarded-proto 是 http，因為 cloudflared 到入口是明文 HTTP。判斷 https 的地方（Secure cookie、重導向網址）以「SaaS 一律 https」為前提，或由入口改寫這個標頭；cloudflared 到入口要不要改走 HTTPS 尚未決定。
4. SSE 被截斷時狀態碼仍是 200，前端不能只看狀態碼。串流要有不超過 60 秒的心跳，中斷時從斷點續傳（J2 已要求）。
5. dynsec 的 disableClient 只踢不擋：用憑證身分登入時，被停用的閘道器能立刻重連，權限照舊。停權照 2026-10-09 的結論走「發新 CRL、SIGHUP、踢除」三步，不能只呼叫 disableClient。
6. 每個 Rust 服務都要處理 SIGTERM。容器的 PID 1 不會套用 SIGTERM 的預設動作，沒處理就會撐到寬限期被 SIGKILL。轉接服務收到 SIGTERM 時應送 WebSocket close，讓閘道器立刻改連新的 pod。
7. 轉接服務的 WebSocket 讀寫緩衝區要調小，見上表；tungstenite 預設各 128 KiB，MQTT 封包遠小於此。
8. cloudflared 重啟會先等 30 秒寬限期，再中斷約 3.5 秒。OS 套件更新 cloudflared 時，閘道器靠緩衝補送不丟資料，但即時圖會斷一下。同一個 tunnel 跑兩個 cloudflared 可以輪流重啟，這點未實測。
9. MQTT 3.1.1 下發布到無權限的 topic 仍會收到 PUBACK，訊息被默默丟棄；閘道器用 MQTT 5 才拿得到 0x87（2026-10-09 已實測）。
10. Mosquitto 若用 tcpSocket 健康檢查，每 10 秒會記一筆 TLS 錯誤，要改用其他探測方式。

## 範圍外與後續

- 雙層 TLS 在 Pi 上的 CPU 用量與延遲：2026-10-10 決定不測。
- 實驗機的入口已改成目前的決策：ClusterIP、2 副本、只放行本機；2026-10-09 的 SNI 直通設定已移除，原檔留在實驗機的 `~/stack/platform/gateway-sni.yaml.superseded`。
