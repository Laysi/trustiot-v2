# 現場脈絡與知識圖（Apache AGE）

機台實體（C4）、生產紀錄（C5）與知識圖是同一件事：描述現場有哪些機台、彼此怎麼連、什麼時候在做什麼，讓 AI 依此判讀資料。三者由同一個「現場脈絡」服務負責，資料存在我們自己的 Postgres 裡的 Apache AGE，SaaS 與地端相同。每個租戶一個 graph，LLM 可以自由寫 Cypher，越界由資料庫擋下。

現場脈絡的內容與規則：

1. 機台是獨立實體，與設備（Modbus 端點）分開：一個端點可對多台機台，一台機台也可接多個端點；資料點可以歸屬到機台。機台之間的關係先收斂到最小集（供電、驅動、上下游製程）。assetNotes 可由 AI 抽成結構化草稿，使用者確認後才寫入，原欄位保留，只放不會變的實體背景（C4，[#154](https://github.com/Laysi/trustiot/issues/154)）。
2. 生產紀錄掛在機台上，不掛在設備：料號、開始與結束時間，工單號與目標數量選填；同一台同時只有一筆進行中。現場換料時在畫面上切換，系統記下時間；可以補登與修正，每次變更都留紀錄（C5）。料號與生產區間都是節點，讓異常、警報、AI 結論與人的處置能掛在「哪一次生產」上。從客戶 MES／ERP 帶入、由 AI 推測換料，先不做。
3. 每個租戶一個 graph（即一個 Postgres schema），名稱用不透明的 ID，從共用目錄看不出是哪個租戶；graph 與 label 由 migration 角色建立並擁有。每個租戶有一個專屬的登入角色，只能使用自己的 schema、不屬於其他任何角色；現場脈絡服務的寫入與 LLM 的查詢都以這個角色直接連線，不靠 SET ROLE 切換，連線池依租戶分開：每個池的上限很小、閒置時回收到 0，所有池合計控制在 Postgres 連線上限的預算內，並在數百個租戶的規模下做負載測試。角色在建立租戶時建立；停權時不動（入口已擋下）；合約終止刪資料時連同 graph 一起刪除。AGE 的 cypher() 查詢本文不能當參數綁定，只能拼進 SQL；就算 LLM 的文字跳脫到 SQL，也切不到別的租戶。
4. 跨服務：資產服務刪除設備時發事件，現場脈絡服務解除對應；每件耗電與週期時間由 AI 助理向現場脈絡服務取生產區間，再查 ClickHouse；警報服務依資料的事件時間，向現場脈絡服務取得當時那段生產區間的零件，補送的舊資料不套用當下的零件。
5. 備份與搬遷：現場脈絡隨 Postgres 備份與還原（M8），每租戶的角色與權限由 migration 依租戶表冪等重建；租戶在 SaaS 與地端之間搬遷時，由以租戶為單位的匯出與匯入工具一併帶走。
6. 降級：現場脈絡服務連不上時回報不可用；警報沿用最後已知的零件，AI 分析明說現場脈絡暫時不可用，不猜。
7. 公司概況是每個租戶知識圖的根節點：產業、主要產品、主要機台、最在意的事，來自首頁引導的訪談與接上的設備（L3），由租戶管理員確認、可修改；首頁的卡片與建議問題、AI 分析與警報 agent 都以它為背景。

AI 記憶：

1. AI 自產的記憶直接存在租戶的 graph，標記為 AI 產生並附證據與時間；不設核可流程。
2. AI 只把記憶當線索，引用數字前要回查資料；使用者可以刪改錯的記憶。
3. 記憶與現場脈絡一起隨 Postgres 備份，不再要求從事件層重建。
4. 事件層在 Postgres，append-only，當作操作紀錄（K2）：人的操作與狀態變化由各服務經 outbox 寫入，與業務資料同一筆交易，不會漏；由身分服務集中保存與查詢（決策 34，2026-10-21，Laysi/trustiot-v2#130），做法見 [services/identity](../../services/identity/README.md) 的「事件層與操作紀錄」。agent 軌跡（Laysi/trustiot-v2#205）寫入失敗不阻塞回答，但必須可觀測，並標記該段軌跡不完整。
5. 圖與 Qdrant 分工：語意相似走 Qdrant，關係遍歷走圖。

LLM 自由寫 Cypher 的護欄（隔離由資料庫強制，以下列為驗收條件）：

1. 以該租戶專屬的登入角色連線、在唯讀交易內執行；角色只能使用自己租戶的 schema、不屬於其他任何角色，越界由 Postgres 拒絕。
2. LLM 只寫 Cypher 本文，graph 名稱由服務決定；包裝用的 dollar-quote 標記每次查詢以亂數產生，LLM 猜不到就無法跳脫；本文含有該標記就拒絕。
3. 設定查詢逾時（statement\_timeout）與結果筆數上限。
4. 錯誤原文不回給 LLM 或使用者，只回通用類別，原文只寫伺服器日誌（Neo4j 實測時，錯誤訊息曾帶出別的租戶的資料）。
5. 跨租戶負向測試：以實際的執行角色測跨 graph 呼叫 cypher()、直接讀 label 表、共用目錄 ag\_catalog 的可見範圍、search\_path、建立 label、唯讀交易中的寫入、角色切換與連線池重用，並確認沒有過度授權的 SECURITY DEFINER 路徑；攻擊查詢由 Opus 5.5 在測試機產生，放進 CI；每次升級 AGE 或 Postgres 都重跑。
6. AGE 的已知缺口：沒有 APOC 與圖演算法、函數長尾有缺、不支援多標籤節點；LLM 用到不支援的函數會報錯，由 agent 重試。需要圖演算法時，用 Rust 的 petgraph 在程式內計算。
7. 改用 Neo4j 的條件（任一成立就重新評估）：圖演算法需求超出 petgraph 能處理的範圍、單一租戶的邊數超過 10 萬、常態查詢深度超過 5 層且 p95 超過 200 ms、租戶數超過數百（每租戶一個 schema 的上限）。

其他注意：要自建含 AGE 的 Postgres 映像，並跟著 Postgres 版本升級（2026-10-11 起是 [deploy/images/postgres](../../deploy/images/postgres/README.md)：CloudNativePG 的 PostgreSQL 18 加 AGE 1.8.0，升級步驟在該 README；AGE 要放進 `shared_preload_libraries`，每租戶的登入角色才不必 `LOAD` 就能執行 cypher()）；AGE 1.7.0（2026-01）起才支援 RLS，我們用 schema 權限隔離，不依賴它；這是決策 29「帶租戶資料的表一律啟用 RLS」的明確例外，以上面第 5 條的權限測試取代 RLS 驗收。選型推導見舊 repo 的 `docs/agentic-data-foundation.md` §7–8（[#152](https://github.com/Laysi/trustiot/issues/152)，2026-08-06）。
