# AI 警報規則

舊系統沒有任何遙測告警（[#20](https://github.com/Laysi/trustiot/issues/20)）。新系統由 cloud agent 定期檢查警報與資料後自動撰寫規則。規則只在雲端執行，AI 寫的腳本直接啟用，由人事後停用。

- **執行位置**：只在雲端，由警報服務執行不碰 I/O 的 Rust 規則引擎；單一設備、跨設備與歷史視窗的規則都在這裡。地端部署時，這套服務本來就跑在客戶現場。
- **閘道器離線時**：資料隨緩衝補送後，雲端依資料時間補算規則，零件也取資料時間當時的生產區間，不漏判、不套錯門檻；通知依規則、設備與時間窗去重，補算不重複通知；事後補登或修正生產紀錄不回頭重發通知。
- **腳本語言**：定案 Rhai。AI 寫對的比例兩者打平（7/10），WASM 路線要在雲端放 1.6 GB 的 Rust toolchain；Rhai 要補每次執行獨立的 ctx 與 on\_progress 時間上限，部署前必跑回測（空白腳本也能編譯）。
- **通知管道**：產品內通知中心、Email（地端用客戶自己的 SMTP）、Webhook。
- **日後放回邊緣的條件**：閘道器接上現場警示燈，或要在斷網時就地告警。規則引擎不碰 I/O，搬過去不用重寫。

自動啟用必須搭配的安全護欄（列為驗收條件）：

1. 用自動檢查取代人工核准：啟用前先拿過去 14 天的資料回測；語法錯誤、執行出錯、觸發次數異常多，任一項就擋下。每條規則至少要有一個「應該觸發」的案例，回測時這個案例沒觸發就擋下（空白腳本也能編譯成功，見[可行性測試結果](../feasibility/2026-10-09-cloud-poc.md)）；歷史資料裡沒有符合的片段時，用 M7 的人工異常片段合成。新設備歷史不足 14 天時，用現有的資料加上合成的應觸發案例回測、照常啟用，誤報靠第 4 條的冷卻時間與通知上限擋下。
2. 沙箱：只能讀資料點、時間視窗內的狀態，以及資料時間當時生產的零件（C5），只能輸出警報事件；不能讀寫檔案、連網路、寫入設備；運算次數與記憶體都有上限。
3. 規則之間互不影響：每條規則獨立執行，超過上限就停掉那條規則並回報。
4. 防止通知洪水：每條規則有冷卻時間與每小時通知上限。
5. 可追溯、可快速停用：標明是 AI 建立、保留版本歷史；通知裡就能一鍵停用該規則，租戶也能一鍵暫停全部 AI 規則。
6. cloud agent 有排程與預算：花費算進 AI 額度，結果與人的處置寫進事件層（[#153](https://github.com/Laysi/trustiot/issues/153)），作為下一輪的學習來源。
