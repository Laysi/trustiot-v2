# 功能重建清單

## A–E：身分、租戶、資產、佈建、設定下發

「現況」是舊系統的狀態：可用、部分可用、有缺陷、只有規劃。「重建必須」的內容會成為日後 issue 的驗收條件。A1–M8 共 55 項已於 2026-10-10 全部確認。

| 項目 | 現況 | 重建必須 |
| --- | --- | --- |
| A1 登入與 session | 可用：email 驗證碼、redirectTo 只粗略檢查同站、session 12 小時、背景續期 | 不能繞過驗證碼改用密碼（[#116](https://github.com/Laysi/trustiot/issues/116)、[#7](https://github.com/Laysi/trustiot/issues/7)）；不留繞過正式流程的公開註冊入口（[#46](https://github.com/Laysi/trustiot/issues/46)）；session 密鑰不寫死（[#100](https://github.com/Laysi/trustiot/issues/100)）；開發用假登入只存在本地版本，是否啟用只看伺服器設定、不看 cookie（[#100](https://github.com/Laysi/trustiot/issues/100)）；導回網址做真正的同源驗證；登出撤銷該 session，並提供登出所有裝置 |
| A2 角色與權限 | 可用：viewer、editor、admin，加上 platform admin | 權限只在後端判斷；第一位 platform admin 要有正式建立流程 |
| A3 成員管理 | 部分：加人時會默默建立帳號 | 改為邀請加同意（[#46](https://github.com/Laysi/trustiot/issues/46)）；「至少一位 admin」的檢查要原子化（[#107](https://github.com/Laysi/trustiot/issues/107)） |
| A4 服務間身分 | 有缺陷：一把內部密鑰就能冒充任何人，產線登錄與 AI 用量也共用這把 | 服務間呼叫帶著實際使用者的身分：沿用 API 閘道簽發的內部 token，服務自行驗證簽章、受眾與到期時間，代表使用者呼叫其他服務時向身分服務換一張受眾是對方的 token（只換一跳，多跳見 Laysi/trustiot-v2#509；2026-10-21，Laysi/trustiot-v2#106）；背景工作與事件消費用服務自己的身分，不冒用使用者；呼叫的服務本身由 Istio ambient 的 mTLS 驗證身分，AuthorizationPolicy 限定誰可以代表使用者呼叫哪些服務（決策 27）；驗收包含服務冒用與 token 重播測試 |
| A5 自助註冊、API key | 只有規劃 | 自助註冊（[#8](https://github.com/Laysi/trustiot/issues/8)），不做試用（B3）；MCP API key（[#141](https://github.com/Laysi/trustiot/issues/141)）；OIDC 已列入登入決策 |
| B1 租戶生命週期 | 部分：軟刪除沒有作用（[#117](https://github.com/Laysi/trustiot/issues/117)）、停權沒有實際阻擋（[#72](https://github.com/Laysi/trustiot/issues/72)） | 停權一律記錄原因（資安或濫用、欠費、合約終止），三種都完全切斷（[#72](https://github.com/Laysi/trustiot/issues/72)）：API 與 AI 由每次請求的 session 檢查即時擋下，只顯示停權說明頁；該租戶所有閘道器的憑證撤銷（更新 CRL 並 SIGHUP），閘道器因此沒有有效憑證而在 dynsec 失去角色並被踢線（決策 6），停止設定下發。停權與恢復依決策 4 走事件，但事件只當通知：租戶狀態帶遞增的版本號，消費端收到後讀租戶目前的狀態收斂、不照事件內容執行，晚到或重播的舊事件不會蓋掉新狀態。停權時後台先顯示「處理中」，確認已踢線、CRL 已生效才顯示「已停權」。停權期間的資料留在閘道器緩衝，超過緩衝上限的部分遺失。恢復由平台管理員操作，依序：租戶狀態改回正常、開放憑證換發、閘道器以 TPM 金鑰換發憑證（D2），broker 角色隨新憑證加回（決策 6，不必另外在 dynsec 重新啟用，2026-10-24），閘道器自動重連並補送、恢復設定下發。合約終止不恢復：資料依合約保留一段時間，由平台管理員匯出交付，期滿刪除，並清掉 broker 上保留的設定，閘道器回到設備池或除役。驗收包含併發停權、事件延遲與重播，以及停權與恢復交錯且亂序到達；後台要有停權與恢復按鈕 |
| B2 配額 | 部分 | 數量型配額：AI 月額度（只隨方案，不開放加購）、依方案可接入的閘道器數量、警報規則數與成員數（其餘方案限制見 B3）；設備與型號不設商業配額，每台閘道器設技術上限；綁定時的閘道器數量檢查原子化（[#107](https://github.com/Laysi/trustiot/issues/107)）；AI 額度檢查失敗時不能放行（[#53](https://github.com/Laysi/trustiot/issues/53)）；AI 額度可當月臨時調高，下個月自動恢復；後台可以調閘道器數量配額 |
| B3 方案與用量計費 | 只有規劃（[#38](https://github.com/Laysi/trustiot/issues/38)–[#42](https://github.com/Laysi/trustiot/issues/42)、[#9](https://github.com/Laysi/trustiot/issues/9)） | 方案分 Starter、Business、Enterprise、Enterprise On-Prem 四級（見[方案與權益](../product/plans.md)），以「權益」定義，設計成基本方案好用、但有看得到的升級牆：數量上限（B2）、可查期間（原始資料與彙總資料各自的天數）、最短採樣間隔、即時圖表、通知通道，以及進階功能（AI 寫警報規則、現場脈絡與每件耗電、文件 RAG、報表、API 與 MCP、SSO）。權益由身分與租戶服務統一管理，各服務在伺服器端自行檢查，AI 的查詢工具同樣受可查期間限制。實際保存期限全平台統一（原始資料 180 天，2026-10-21 訂，見[資料保存期限與磁碟水位](../architecture/data-retention.md)），最高方案（Enterprise）可查到全部保存期限，其他方案的可查期間較短，升級後立即看得到更早的資料；隱私說明寫明實際保存期限，客戶要求刪除時照辦。上傳檔案（附件、設備文件）以容量計。底線：方案限制永遠不擋資料寫入、不停用已啟用的警報、不無預警刪資料；超過數量上限時只擋新增，既有的照常運作。不做試用。各方案的可查天數、上限與價格在 MS6 訂；金流與訂閱狀態 |
| C1 設備型號 | 可用 | 保留命名規則（小寫英數加單一連字號，1–40 字）與資料點規則（功能碼 1–4、位址不重疊、字串需長度）；每個寫入入口都驗證（[#103](https://github.com/Laysi/trustiot/issues/103)） |
| C2 設備 | 可用 | 驗證連線設定與取樣間隔；統一取樣間隔的預設值 |
| C3 閘道器列表 | 部分：看不到是否在線（[#65](https://github.com/Laysi/trustiot/issues/65)、[#19](https://github.com/Laysi/trustiot/issues/19)） | 用 MQTT LWT 與心跳判定並顯示在線狀態、最後回報時間、已套用的設定版本 |
| C4 機台實體建模 | 只有規劃（[#154](https://github.com/Laysi/trustiot/issues/154)） | 機台是獨立實體，與設備分開；見[現場脈絡與知識圖](../architecture/field-context.md) |
| C5 生產紀錄 | 沒有（新功能） | 每台機台一份有時間區間的生產紀錄，現場換料時在畫面上切換；AI 依此算每件耗電與週期時間，警報規則可以依零件套用不同的正常範圍；見[現場脈絡與知識圖](../architecture/field-context.md) |
| D1 出廠登錄 | 可用 | 重複登錄不產生重複資料；只留產線工作站呼叫的 API（決策 12 之後 CSR 必須在工作站從 TPM 取出，不再有單筆畫面與 CSV），工作站以自己的憑證加平台管理員帳號呼叫，每筆登錄寫進操作紀錄；登錄後公鑰不能修改，TPM 或主機板更換視同新設備；除役不可逆 |
| D2 佈建 | 部分：雲端信任閘道器自報的 ID（[#118](https://github.com/Laysi/trustiot/issues/118)） | 改為出廠前預先註冊，由自建 CA 簽發 TPM 產生的 CSR；憑證換發走 443 上的 HTTPS 換發端點（決策 12）：閘道器用 TPM 金鑰簽伺服器給的一次性挑戰，比對出廠登錄的公鑰，登錄有效（未除役）、閘道器目前有綁定且所屬租戶未停權才簽發，到期、停權恢復與改綁都走這條路；憑證只帶硬體 ID、不帶租戶，簽不簽由簽發當下的綁定與租戶狀態決定，還沒綁定的閘道器不換發，出廠憑證到期後要等綁定才能換發；租戶狀態取自 certs 以事件收斂的本地狀態表（B1 的通知模式，Laysi/trustiot-v2#632），換發路徑不同步呼叫身分服務（決策 12，2026-10-24）；被拒絕時退避重試，端點限流；驗收包含重放的挑戰被拒，以及憑證已撤銷或已過期的閘道器都能經這條路換發 |
| D3 客戶綁定 | 部分：失敗後永遠卡在 409（[#84](https://github.com/Laysi/trustiot/issues/84)） | 失敗可以重試；以 API 閘道的通用限流防止猜測硬體 ID（SaaS 依 CF-Connecting-IP 計算；源站只接受 tunnel 進來的流量，這個標頭才可信）；保留閘道器數量配額檢查；閘道器的租戶一律是它目前的綁定：綁定寫 `assets.gateway_bound`，certs（換發與 broker 權限）、ingest 與 gateway-ops 各自消費它（之後加上解綁事件）維護「硬體 ID → 租戶」的對照表，不在資料路徑上同步呼叫資產服務；綁定之後閘道器才在 broker 有角色（決策 6、12，2026-10-24） |
| D4 解綁、除役、送修 | 可用 | 除役的憑證放進撤銷清單；清理舊設定（[#11](https://github.com/Laysi/trustiot/issues/11)）；解綁時撤銷這台閘道器目前的憑證並拿掉 broker 角色（以 Laysi/trustiot-v2#636 的撤銷函式）；閘道器的硬體可以給下一個租戶重用，SD 卡絕不重用：交給下一個租戶時一定換新卡，新卡在閘道器綁到新租戶之後經換發（D2）取得憑證，從空的緩衝開始並使用新的串流 ID；雲端不另外拒收舊綁定下採集的批次，前提是換新卡，把舊卡裝回同一台硬體不在支援的流程內（決策 12，2026-10-24） |
| D5 閘道器映像與強化 | 部分：防火牆擋住現場設備（[#140](https://github.com/Laysi/trustiot/issues/140)）、註冊 fail-open（[#119](https://github.com/Laysi/trustiot/issues/119)）、PIN 外洩（[#121](https://github.com/Laysi/trustiot/issues/121)） | 依設備清單動態開放 fieldbus 出口；註冊改為 fail-closed；PIN 不經命令列；存緩衝與設定的資料分割區以 LUKS 加密、由 TPM 自動解鎖（[#131](https://github.com/Laysi/trustiot/issues/131)），擋下拔卡到別台電腦直接讀取；整台被偷時會開機解鎖，但 SSH 只收金鑰、螢幕與 USB 關閉、serial 緊急密碼每台隨機，登不進去；剩下改開機分割區（cmdline.txt 加 init=/bin/sh）取得 root 這條路，閘道器的開機韌體不會量測進 TPM，要靠 MS6 的 secure boot 擋；TPM 解不開時視同新設備，清掉資料分割區、回產線重新登錄（決策 12），不需要復原金鑰 |
| D6 閘道器進階安全 | 只有規劃 | 閘道器的 secure boot（只開有簽章的開機映像）、唯讀根目錄（[#161](https://github.com/Laysi/trustiot/issues/161)）、復原金鑰託管（[#132](https://github.com/Laysi/trustiot/issues/132)）、雙人核准（[#133](https://github.com/Laysi/trustiot/issues/133)）、遠端維護通道（[#134](https://github.com/Laysi/trustiot/issues/134)，去 AWS 後不能再用 Secure Tunneling）、出廠映像（[#64](https://github.com/Laysi/trustiot/issues/64)）；資料分割區的磁碟加密（[#131](https://github.com/Laysi/trustiot/issues/131)）提前到 MS1，見 D5 |
| E1 設定下發 | 有缺陷：讀到舊版（[#139](https://github.com/Laysi/trustiot/issues/139)）、兩邊不一致（[#84](https://github.com/Laysi/trustiot/issues/84)、[#97](https://github.com/Laysi/trustiot/issues/97)） | 版本號加套用回報；連續變更合併節流；移除的設備真的清掉；即時送到閘道器（[#157](https://github.com/Laysi/trustiot/issues/157)）；開機不漏設定，取得失敗要重試（[#156](https://github.com/Laysi/trustiot/issues/156) 的教訓）；設定變更不得把設備最新值歸零或標成離線；引用不存在的資源要明確報錯 |

## F–I：邊緣採集、上傳、健康、時序資料

邊緣這一塊的 P0 都集中在上傳與離線（G1），時序資料則是改用固定窄表後最大的設計變動。

| 項目 | 現況 | 重建必須 |
| --- | --- | --- |
| F1 Modbus TCP 讀取 | 可用 | 只讀功能碼 1–4；相近位址合併讀取（間隔不超過 10、單次最多 125 個暫存器或 2000 個位元）；完整型別解碼，包含位元組順序與字組對調 |
| F2 RS485 轉換器（RTU-over-TCP） | 有缺陷（[#183](https://github.com/Laysi/trustiot/issues/183)） | 同一台轉換器下的設備共用一條連線、輪流讀取；丟棄站號不符的回應 |
| F3 被動模式 | 部分：從未實測 | 已定：新系統先不做，只支援主動輪詢；有客戶現場需要再加 |
| F4 取樣排程與自我恢復 | 部分：已有逾時（請求 5 秒、連線 10 秒）與讀到資料才重置退避；缺固定節拍、keepalive、watchdog | 固定節拍取樣；每次等待都有逾時；讀到資料才重置重連等待時間；TCP keepalive（[#164](https://github.com/Laysi/trustiot/issues/164)）；每台設備一個 watchdog（[#151](https://github.com/Laysi/trustiot/issues/151)） |
| F5 數值縮放與偏移 | 新缺口 | 型號可以定義 scale 與 offset，讓 MS300 這類設備上雲的不再是原始整數 |
| F6 模擬設備 | 可用 | 不保留：mock 設備類型與模擬器一併棄用（見 M7） |
| G1 上傳與離線韌性 | 有缺陷（[#177](https://github.com/Laysi/trustiot/issues/177)、[#178](https://github.com/Laysi/trustiot/issues/178)、[#179](https://github.com/Laysi/trustiot/issues/179)） | 依上限拆包，絕不能讓程式當掉；斷網持續採集、恢復後補送；所有設備合計有記憶體上限（以已編碼批次的位元組計，預設 16 MiB、可調上限 64 MiB，由程式強制，不依賴 systemd 的 MemoryMax；2026-10-14 使用者同意，實測見[可行性測試結果（2026-10-13）](../feasibility/2026-10-13-gateway-memory.md)）；每批資料帶串流 ID 與遞增序號，一次只送一批、收到確認才送下一批；序號在批次形成時編定、隨緩衝寫入磁碟，閘道器重裝後換新的串流 ID；時鐘未校正前的時間戳要能處理（[#180](https://github.com/Laysi/trustiot/issues/180)）；緩衝有最長保存時間（30 天，2026-10-21 訂，見[資料保存期限與磁碟水位](../architecture/data-retention.md)），超過就丟棄並記錄，且必須短於原始資料的保存期限（全平台統一，180 天；地端由客戶自訂時同樣要遵守，migration Job 拒絕不長於 30 天的設定），I1 的序號高水位才不會先被保留期限清掉 |
| H1 閘道器與設備健康 | 有缺陷：設備死了仍顯示在線（[#160](https://github.com/Laysi/trustiot/issues/160)、[#19](https://github.com/Laysi/trustiot/issues/19)） | 閘道器健康：在線以 MQTT LWT 與心跳判定（C3）；心跳附帶運作指標：CPU、記憶體、資料分割區用量、SoC 溫度、供電不足與降頻旗標、開機時間與重啟次數、程式與設定版本、離線緩衝積壓（未送筆數與最舊一筆的時間，G1）、時鐘是否已校正（[#180](https://github.com/Laysi/trustiot/issues/180)）、憑證到期日。設備健康：只依實際讀取結果判定，分正常、部分資料點讀取失敗、離線；閘道器離線時設備狀態顯示「未知」，不誤報離線；記錄最後成功讀取時間、讀取成功率、逾時次數與錯誤類型（連不上、逾時、Modbus 例外碼、站號不符），接線或轉換器問題（[#183](https://github.com/Laysi/trustiot/issues/183)）從這裡看得出來；數值本身的異常（例如卡住不動）交給警報規則。健康數據存進 ClickHouse 保留歷史，畫面看得到趨勢，警報規則也能使用；閘道器列表（C3）與設備頁（I3）顯示目前狀態與最新數值，平台後台有全部閘道器的健康總覽；設定錯誤回報照舊；離線先只在畫面顯示，不另外通知客戶 |

| I3 遙測畫面 | 新缺口 | 設備即時值、在線狀態與時序圖表；目前只能問 AI 才看得到數據，已定列入這次重建。即時圖表：有人打開設備圖表時，雲端經現有的 MQTT 連線通知閘道器對這些設備即時送值，頁面開著就續期，關掉或逾時就停；閘道器每次取樣立即送到另一個即時 topic（dynsec 限定只能發到自己的 topic），不進緩衝、不等確認、不寫資料庫；雲端以 SSE 推到瀏覽器，定時送心跳（Cloudflare 125 秒沒有回應會逾時）；圖表前段取 ClickHouse 的歷史、後段接即時點，該批正式資料寫進 ClickHouse 後，畫面自動把那段即時點換成存好的資料；即時頻率等於方案的最短採樣間隔；每租戶同時開啟的即時畫面數與每個畫面的設備數設上限；Starter 沒有即時圖表（B3） |

| L3 首頁與引導 | 缺：一打開不知道要做什麼 | 一打開就知道要做什麼。首頁是營運總覽：今天的用電、設備正常／異常／離線的數量（H1）、用電最多的設備、上次來之後的新異常，每張卡片可點進細節或一鍵問 AI；AI 對話收在側邊。新租戶在首頁上方看到設定清單：綁定閘道器 → 新增設備 → 看到第一筆資料 → 選第一個用途（依方案提供，例如問 AI 本週用電或設定每週報告）→ 邀請成員，每一步附「下一步」按鈕，可略過，全部完成就收起；沒有資料的頁面一律顯示下一步該做什麼，不留空白頁。AI 入口改成情境按鈕：圖表、設備頁、異常卡片上放「分析這段」「跟上週比」「為什麼離線」等按鈕，自動帶入設備與時間範圍；對話框空白時顯示依租戶設備產生的建議問題（與 J11 的問句範本同一套）。啟用漏斗：每個租戶每一步的完成時間寫進事件層（K2、[#153](https://github.com/Laysi/trustiot/issues/153)），看得出從註冊到看見第一筆資料要多久、卡在哪一步。AI 個人化：註冊後先問幾題（產業、主要產品、主要機台、最在意的事：電費、碳排、停機、品質，加一格自由描述），接上設備後再依型號與資料點補強；AI 依此從固定的卡片庫、用途庫與問題庫挑選、排序並寫一句說明，不自由生成介面，卡片數字仍只來自查詢（J5）；產生的公司概況由租戶管理員確認、可修改，存成現場脈絡知識圖的根節點，也是 AI 分析與警報 agent 的背景；不查公司官網；引導的 AI 呼叫不計 AI 額度（帳本照記）；AI 無法使用時（例如地端沒有 LLM）退回通用版面。設定清單與營運總覽在 MS2（先用通用版面），情境按鈕與建議問題在 MS3，AI 個人化在 MS4 |

| M5 CI/CD | 部分 | migration 自動化；閘道器程式的發佈與簽章流程；GitHub Actions 的 ci、release、nightly 三個 workflow 與 Flux 的 GitOps 部署，見[CI 與發佈](../architecture/ci-release.md) |
| M6 本地開發 | 部分（[#123](https://github.com/Laysi/trustiot/issues/123)） | 一鍵啟動；不用弱密碼、不對所有網路介面開放 |
| M7 模擬器 | 可用 | 棄用模擬器、行為模擬庫與測試資料產生器（[#106](https://github.com/Laysi/trustiot/issues/106)、[#115](https://github.com/Laysi/trustiot/issues/115) 隨之消失）；自動測試在測試程式內起最小的 Modbus 端點做故障注入（支援站號，才能重現 [#183](https://github.com/Laysi/trustiot/issues/183)）；AI 開發用 lab 實機錄下的資料集；警報回測、補送與分析回歸也用錄下的資料，在測試程式內插入人工異常片段（突波、停機、換料），事件時間可控、版本化，每段都標好預期的觸發結果 |
| M8 備份與還原 | 沒有（[#15](https://github.com/Laysi/trustiot/issues/15)） | 各資料庫用自己的增量備份送到 S3 相容儲存，不直接複製運作中的資料目錄：Postgres 以 CloudNativePG（k8s operator）部署，用它內建的備份送完整備份與持續的 WAL，可還原到任一時間點，日後要高可用時由同一個 operator 加副本，映像以 CloudNativePG 的映像加 AGE 自建；ClickHouse 用內建的 BACKUP 指令排程增量備份（base\_backup），還原需要整條增量鏈，定期做一次完整備份；自架的 Qdrant 用快照 API 排程備份；存放備份的 bucket 開啟版本保存或保留鎖；定期演練還原；演練從零重建整台主機並計時，訂出主機故障後的恢復時間目標，SaaS 上線前（MS4）完成；Qdrant Cloud 用快照 API 或由原始檔重建；現場脈絡與 AI 記憶在 Postgres（AGE）內，隨 Postgres 備份；每租戶的資料庫角色與權限是叢集層級物件、不在資料庫備份內，由 migration 依租戶表冪等重建；物件儲存（PDF、附件）開啟版本保存或保留鎖，防止誤刪與覆寫，選定 S3 或 R2 時確認支援；地端提供備份與還原指令 |
