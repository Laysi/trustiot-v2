# 閘道器 agent 的 Modbus TCP 讀取（2026-10-20）

Laysi/trustiot-v2#87：新增 `edge/agent` crate 與它的 `modbus` 模組：合併讀取的規劃、功能碼 1–4 的 PDU、Modbus TCP client（MBAP）、型別與位元組順序的解碼、scale 與 offset、把一台設備的讀取串起來的 `DeviceReader`。規則與失敗的對應見 `edge/agent/README.md`。

## 環境

- **程式碼**：分支 `feat/87-modbus-read`，基於 main `99d6120`（含 Laysi/trustiot-v2#452 的假 Modbus 端點）。
- **工具版本**：依 `rust-toolchain.toml`（Rust 1.99.0）、`.prototools`（bun 1.4.2，只用來產生 CPU 負載與重複執行；cargo-deny 0.20.2）與 `Cargo.lock`（tokio 1.53.2）。
- **機器**：開發者工作站（x86_64）。aarch64 只做交叉建置，沒有在閘道器上執行。
- **負載**：「負載下」是以 [cpu-hog.ts](data/2026-10-19-97-fake-modbus-endpoint/cpu-hog.ts)（Laysi/trustiot-v2#97 的腳本）開 32 個忙碌迴圈，等 45 秒讓負載平均升上去之後才開始。
- 不需要容器、叢集或 lab 的硬體：假端點與 client 都在測試行程內，只用 127.0.0.1。

## 指令

在 repo 根目錄：

```sh
cargo test -p agent                                     # 單元測試與兩個整合測試
cargo build --locked --target aarch64-unknown-linux-gnu -p protocol -p agent
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo fmt --all --check
cargo deny --locked check
cargo run --locked -p openapi -- --check
bun docs/test-reports/data/2026-10-20-87-modbus-read/repeat-under-load.ts 30   # 負載下重複執行
```

Mutation 檢查：把下表的一行程式改壞，執行 `cargo test -p agent --no-fail-fast`，記下失敗的測試，再還原（每次只改一處；改完以 md5 確認原始碼已還原）。

## 結果

### `cargo test -p agent`：54 通過、0 失敗

單元測試 37 個、`tests/modbus_fake_endpoint.rs` 9 個、`tests/modbus_tcp_framing.rs` 8 個。整合測試都用 `#[tokio::test(start_paused = true)]` 加 `testkit::clock::manual()`，逾時只在測試推進時鐘時觸發；所有等待都經過 `testkit::clock::bounded`（牆上時間 60 秒上限，失敗訊息寫出在等什麼）。

### 獨立審查

另一個 agent 以唯讀方式審查這份程式碼，試著讓設備的輸入造成 panic、無上限的記憶體、永遠的等待或錯置的值。沒有找到 panic、無上限的緩衝或沒有期限的等待。提出的問題與處理：

| 問題 | 處理 |
| --- | --- |
| 設備在回答後立刻關閉連線時，下一個請求遇上已關閉的連線，這次輪詢其餘的點全部失敗 | 修正：保持中的連線在請求時斷掉，在新連線重送一次（`a_device_that_closes_after_every_answer_is_read_every_time` 等 3 個測試） |
| 串流不是 Modbus TCP（例如 RTU 轉換器被設成 Modbus TCP）回報成 `connect`，看起來像連不上 | 修正：新的 `ReadError::Protocol`，回報 `invalid_value` |
| 呼叫端以自己的逾時丟掉寫到一半的讀取，設備端的框架錯位 | 修正：記下寫入中的狀態，下一次讀取換連線（`a_read_cut_off_while_sending_does_not_reuse_the_connection`） |
| 極大的逾時值讓 deadline 溢位 | 修正：`checked_add`，超過時等一年 |
| 測試裡沒有上限的等待 | 修正：全部經過 `bounded` |
| 另一個 client 經會廣播的閘道器讀同一站號、交易 ID 剛好相同時，它的回應會被當成自己的 | 交易 ID 改為隨機起始、請求之間到達的框架在送出前丟掉；剩下的風險寫在 `edge/agent/README.md`「限制」，RTU over TCP 的轉換器由 Laysi/trustiot-v2#88 處理 |
| 半開連線一直逾時、不會換連線；合併讀取跨到不存在的位址時整組失敗；字串裡的控制字元 | 不在本 issue：半開連線是 Laysi/trustiot-v2#89 的驗收條件；另兩項寫在 README「限制」，控制字元依 `protocol::Value` 的決定交給顯示的一方 |

## 結論

逐條對照 Laysi/trustiot-v2#87 的驗收條件：

- [x] 每種型別與位元組順序都有單元測試：`decode::tests` 9 個（u16、i16、u32、i32、u64、i64、f32、f64、字串、bool，`abcd`、`badc`、`cdab`、`dcba`），整合測試再對假端點讀一次。
- [x] 合併讀取的規劃有測試（間隔與上限邊界）：`plan::tests` 9 個，間隔 10／11、125／126 個暫存器、2000／2001 個位元；整合測試確認假端點收到的請求與規劃相同。
- [x] 程式不會送出功能碼 5 以上（測試）：型別上只能建立功能碼 1–4 的請求；`requests_carry_only_read_function_codes` 與每個假端點測試的 `assert_read_only`；送出 5–8 的 mutation 讓 13 個測試失敗。
- [x] 縮放與偏移後的值符合預期（測試）：`scale_and_offset_give_floats` 與整合測試的 voltage、frequency、temperature。
- [x] 對 testkit 假端點的整合測試通過：`tests/modbus_fake_endpoint.rs` 9 個，涵蓋假端點的每種故障。

不在本 issue、沒有測的：RTU over TCP 與共用連線（Laysi/trustiot-v2#88）；排程、keepalive、watchdog 與半開連線的恢復（Laysi/trustiot-v2#89）；系統時鐘是否已校正（Laysi/trustiot-v2#90，這裡的 `Clock` 由呼叫端提供）；在 lab 的閘道器與實際設備上讀取（要等 agent 的執行檔，Laysi/trustiot-v2#86）。
