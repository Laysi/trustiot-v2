# certs：撤銷後立刻重發該簽發 CA 的 CRL（2026-10-29）

Laysi/trustiot-v2#635：撤銷工作站憑證後，服務在回應之前為那張憑證的簽發 CA 重發 CRL；立即重發失敗時撤銷照樣成立，例行 CRL 工作在一輪之內補上；重發與例行工作同時執行時編號不倒退、不漏撤銷（規則與上限見 [services/certs/README.md](../../services/certs/README.md) 的「CRL 與告警」與「簽發、撤銷與換發」）。這份報告是驗收條件的證據：全部由下列自動化測試以 `CI=1` 實際執行（需要容器的測試不略過）。

## 環境

- **程式碼**：分支 `feat/635-crl-reissue-on-revoke`。功能 commit `0b868eb5`，安全審查後的修正 `cac85f1f`（都基於 main `781073bc`）。之後 rebase 到 main `b6a3a6d7`（Laysi/trustiot-v2#757、#758，改的是閘道器 agent、產線工作站與 `services/certs/README.md` 的另一段，沒有衝突），成為 `0f673dee` 與 `c55193d3`，內容相同；本報告的 commit 只加文件與測試輸出。
- **機器**：建置主機（arm64 Linux VM），經檢查佇列執行。容器測試由 podman 起 `testkit::product` 的拋棄式 TLS Postgres，以 migration Job 的程式套用整個產品的 schema；`tests/crl.rs` 直接呼叫 `crl::refresh` 與 `crl::reissue`，`tests/workstation.rs` 以 `certs_app` 與 `certs_platform` 啟動真的 `certs` 執行檔。同一個測試執行檔的測試共用一個資料庫，所以新測試只看自己的簽發 CA（以金鑰 id 篩選），不動全域的權限或工作鎖。
- **工具**：`.prototools` 與 `rust-toolchain.toml` 釘選的 Rust 與 Bun。
- **設定**：`CI=1`。`tests/crl.rs` 的新測試用 `crl.validity` 1 小時、`renew_before` 30 分鐘；`tests/workstation.rs` 的新測試先讓服務的 CRL 工作每小時一輪（啟動後不再插手，CRL 只會因撤銷而變），失敗後的補發改以每秒一輪重新啟動服務。

證據行（`--nocapture`，`cac85f1f`）：

- 撤銷後立刻重發（`tests/workstation.rs`，真的服務、CRL 工作每小時一輪）：`revoked 588cf1fab622deb45272b1e9cb4c0720: CRL 1 -> 2 before the response, listing it`。測試另外確認 `issued a new CRL` 的 `cause` 是 `revocation`，撤銷的 INFO 有平台管理員的使用者 id。
- 直接呼叫（`tests/crl.rs`）：`reissued after the revocation: CRL 2 lists 4e61ac76d0b3b0dab8d46031c9732452`，thisUpdate 是呼叫時間往前 300 秒、效期 300 + 3600 秒；撤銷後沒有重發時 `the round after a missed reissue: CRL 3 lists both revocations`，之後 thisUpdate 已超過撤銷時間，不再因它重發；不認得的金鑰 id 回 `UnknownCa`。
- 立即重發失敗（`tests/workstation.rs`：另一個 session 鎖住這個 CA 的 `certs.crls` 列，重發等鎖逾時）：撤銷仍回 200 與 `revoked_at`、原因，簽發紀錄是已撤銷，撤銷的 INFO 照記；`crl.pem` 不變、沒有列出它；ERROR 行：
  `{"fields":{"ca_key_id":"3b3cc37e…","check_interval":"3600s","error":"database: error returned from database: canceling statement due to lock timeout …","serial":"4ed311bf6f7cd06a5d9c17f5bbc01ac0"},"level":"ERROR","message":"could not issue a new CRL after a revocation; the revocation stands and the CRL job lists it within one check interval",…}`
- 例行工作補上（同一個測試，放開鎖、服務以每秒一輪重新啟動）：`{"fields":{"ca_key_id":"3b3cc37e…","cause":"unlisted_revocation","crl_number":3,"generation":1,"next_update":1793894562,"revoked":2,"revoked_serials":"[\"4ed311bf6f7cd06a5d9c17f5bbc01ac0\", \"588cf1fab622deb45272b1e9cb4c0720\"]"},"level":"INFO","message":"issued a new CRL",…}`，`crl.pem` 列出它；新 CRL 的剩餘時間大於 `renew_before`，表示這張不是因快到期才發。
- 並行（`tests/crl.rs`）：`24 reissues and 24 renewals by 4 concurrent round tasks: CRL numbers 2..=49 each used once; 206 observed CRLs, never going back, none missing a revocation whose reissue came before it`。24 次撤銷各自接一次重發，同時 4 個 task 各跑 6 輪「每次都該重發」的例行工作，另一個 task 持續讀這個 CA 的 CRL：編號各不相同、最後一號等於 1 加發出的張數、讀到的編號從不倒退、每張編號不小於第 i 次重發的 CRL 都列出第 i 個撤銷，最後一張列出全部。

## 結論

1. **撤銷後 `crl.pem` 立即列出該憑證、CRL 編號加一（測試）**：通過。`tests/workstation.rs` 的 `a_revocation_is_in_the_published_crl_at_once_or_after_a_failure_within_one_round` 在撤銷回應之後立刻讀 `crl.pem`：列出它、編號 1 → 2；`tests/crl.rs` 的 `a_revocation_gets_a_new_crl_at_once_and_the_job_catches_up_on_one_it_missed` 直接驗 `crl::reissue`。
2. **立即重發失敗時，撤銷回應與紀錄不變，下一輪例行 CRL 會列出它（測試）**：通過。同一個 `workstation` 測試以列鎖讓重發逾時：200 回應、簽發紀錄、INFO 不變並記 ERROR；重新啟動的副本第一輪就以 `unlisted_revocation` 發出列出它的 CRL 3。`crl` 測試另外驗證撤銷了卻沒有重發時，CRL 還沒到 `renew_before` 的下一輪也會重發並列出它。
3. **立即重發與例行重發同時執行時，編號不倒退、不漏撤銷（測試）**：通過。`tests/crl.rs` 的 `reissues_and_rounds_at_once_never_go_back_skip_a_number_or_miss_a_revocation`（見上面的並行證據行）。
4. **README 寫明最長時間；`cargo clippy --workspace --all-targets -- -D warnings` 通過**：通過。`services/certs/README.md` 的「CRL 與告警」新增「撤銷後的 CRL」「立即重發失敗時」「並行」「撤銷到 broker 拒絕的最長時間」：正常時撤銷回應時已在 `crl.pem`，broker 最多再過一個 `mqttBroker.trustInterval`（預設 30 秒）；立即重發失敗時再加最多一輪 `crl.check_interval`（預設 5 分鐘）；時鐘或提交延遲超出前提時，最長約 `crl.validity` 減 `crl.renew_before` 再加一輪（預設約 2 天）。「簽發、撤銷與換發」的撤銷段落同步改寫。clippy 在 `cac85f1f` 通過（上表）。
