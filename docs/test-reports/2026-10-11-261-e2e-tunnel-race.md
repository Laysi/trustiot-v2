# 入口 e2e 通道斷線復原的驗證

對應 issue：Laysi/trustiot-v2#261（ingress e2e：kubectl port-forward 斷線時 raw() 的重連判斷有競態）。

## 環境

- 本機（Fedora，x86_64），不跑 Kubernetes；沒有使用 lab 的 Mac mini M1，也沒有取得 lab 鎖。
- Bun 1.4.2、TypeScript 7.0.2、`@types/bun` 1.4.2（皆由 `.prototools` 與 `scripts/bun.lock` 固定）。
- 分支 `fix/261-e2e-tunnel-race`，基於 main 82e0480（含 Laysi/trustiot-v2#258）。
- 故障注入用真正的子行程：`deploy/chart/tests/e2e/fake-port-forward.ts` 是一個 TCP proxy，扮演 `kubectl port-forward`；真正的 HTTP 伺服器（`Bun.serve`）扮演 gateway。k3d 上的整合證據由 PR 的 CI `smoke` job 提供（見結論）。

## 指令

```sh
bun install --cwd scripts --frozen-lockfile
bun test deploy/chart/tests/e2e/tunnel-recovery.test.ts deploy/chart/tests/e2e/raw-client.test.ts
bun test docs/test-reports/data/2026-10-11-261-e2e-tunnel-race/legacy-vs-fixed.test.ts
bun run --cwd scripts typecheck
bun test deploy/chart
```

## 結果

### 1. 修正前後對照（同一個故障注入）

`fake-port-forward.ts` 在收到請求時切斷連線，300 毫秒後才結束行程：請求先失敗、行程稍後才結束，與 2026-10-10 的 kubectl 一致。[legacy-vs-fixed.test.ts](data/2026-10-11-261-e2e-tunnel-race/legacy-vs-fixed.test.ts) 對同一個 fixture 跑兩種邏輯，輸出在 [legacy-vs-fixed.out](data/2026-10-11-261-e2e-tunnel-race/legacy-vs-fixed.out)：

| 邏輯 | 結果 |
| --- | --- |
| 修正前（82e0480 的 `raw()`：失敗當下 `exitCode`／`signalCode` 為空就直接丟出） | 丟出 `no HTTP response for /api/whoami: ""`（與 run 38075563886 的訊息相同），沒有重開通道 |
| 修正後（`withTunnelRecovery`） | 等到行程結束，重開通道並重送，回 200，重開 1 次 |

### 2. 單元測試

[unit-tests.txt](data/2026-10-11-261-e2e-tunnel-race/unit-tests.txt)：`tunnel-recovery.test.ts` 與 `raw-client.test.ts` 共 22 項通過，連續 3 次執行都通過（排除時序不穩）。涵蓋：

- 故障注入：請求失敗時行程尚未結束（舊邏輯會在這裡丟出）。
- 請求進行中行程結束：重開通道、重送一次，回 200，gateway 只收到 1 個請求。
- 行程早已結束：直接重開，不等待寬限時間。
- 健康的通道：不重試、不重開。
- 最多重試一次：重開後再次連線失敗，丟出 `ConnectionError`，共 2 次嘗試、1 次重開。
- 連線失敗但行程在寬限時間內沒結束：丟出，不重試；沒有通道：丟出，不重試；重開本身失敗：丟出該錯誤。
- 非連線層失敗不被重試掩蓋：通道已結束時，gateway 回 503 仍原樣回傳、不重開、gateway 只收到 1 個請求，且測試端的 `expect(status).toBe(200)` 會失敗；狀態 500、502、503、504 同樣不重試；非 `ConnectionError` 的錯誤在通道已結束時也直接丟出。
- 已收到回應標頭之後才逾時或出錯，不算 `ConnectionError`，通道已結束時也不重送（Codex 閘門指出的情形）。
- 客戶端分類：連線被拒、在回應標頭前關閉、標頭被截斷、逾時都是 `ConnectionError`；有回應的請求（含 403）不是；請求目標原樣送出（`/a//b/../c?x=1`）；chunked 回應正確解碼。

### 3. 型別檢查

[typecheck.txt](data/2026-10-11-261-e2e-tunnel-race/typecheck.txt)：回報成立。在 82e0480 以 `scripts/` 的 tsconfig 選項檢查 `deploy/chart/tests/**/*.ts`，`ingress.e2e.ts(187,87)` 報 `Type 'Buffer<ArrayBufferLike>' is not assignable to type 'Buffer<ArrayBuffer>'`（`body` 由 `subarray()` 推論成 `Buffer<ArrayBuffer>`，`decodeChunked` 回傳 `Buffer`）。修正為 `let body: Buffer`。其餘檔案（`chart.test.ts`、`identity-double/server.ts`）沒有錯誤。

決定：把 `../deploy/chart/tests/**/*.ts` 加進 `scripts/tsconfig.json` 的 `include`，既有的 CI 步驟 `bun run --cwd scripts typecheck` 就涵蓋它們，不新增指令或步驟；`CLAUDE.md`、`scripts/README.md`、`docs/architecture/ci-release.md` 同步更新。修正後 `bun run --cwd scripts typecheck` 通過。

### 4. 既有測試

`bun test deploy/chart`：172 項通過、0 失敗（原有 150 項，加上本次 22 項）。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 確定性測試證明請求進行中通道行程結束時，`raw()` 重開通道並成功重送 | 通過：單元測試以真正的子行程故障注入（結果 1、2） |
| 回歸驗證：同樣的故障注入在修正前讓測試失敗 | 通過：舊邏輯對同一個 fixture 丟出 `no HTTP response`（結果 1） |
| 非連線層失敗（狀態碼不符）不被重試掩蓋，有測試證明 | 通過：結果 2 的「非連線層失敗」各項 |
| PR 的 CI `smoke` job 兩份 values 都通過 | 待測：PR 的 CI 執行後由協調者讀取，本機沒有 Kubernetes |
| 型別錯誤回報已確認並處理，型別檢查方式已決定並寫進文件 | 通過：結果 3 |
| 測試證據存到 `docs/test-reports/` | 本檔與 data 目錄 |
