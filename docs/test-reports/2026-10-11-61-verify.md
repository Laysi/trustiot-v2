## 攻擊類別

### 1. Cookie 解析（通過）

`cookie_parsing_accepts_only_one_exact_session_cookie`。

- 回 200：cookie 單獨、夾在其他 cookie 之間（含 `;` 前後空白、tab、空段落）、分成兩個 `Cookie` 標頭（HTTP/2 的形式）、其他 cookie 帶引號、`=`、非 ASCII 位元組、2000 字元、值恰好是 session cookie 的名稱、整個標頭 60 KiB。
- 回 401（回應沒有身分標頭）：沒有 cookie；同一個 cookie 出現兩次（同標頭或兩個標頭，值相同或不同，一個有效一個無效，兩個都有效）；值帶引號、前置空白、尾端 `=`、少一字元、多一字元、兩倍長、空值、沒有 `=`、只有值；名稱大小寫不同、少了 `__Host-`、名稱前後多字元；名稱出現在另一個 cookie 的值裡；值含 NUL 或非 ASCII 或 `%41`；SQL 元字元；值是 hash 而非 secret；標準 base64 字母（`+` 與 `/`）；全零 secret；8 KiB 的值；非標準寫法（最後一個字元只差尾端位元的 3 個寫法，以及其餘 60 個字元，皆被拒）。
- secret 放在別處無效：query string、路徑、`X-Cookie`、`Authorization: Bearer`、`Set-Cookie` 請求標頭，皆 401。
- 2 MiB 的標頭：不是 200（連線被 hyper 拒絕）；之後服務仍正常。
- 觀察（不是缺陷）：名稱與 `=` 之間有空白（`__Host-trustiot-session =值`）仍被接受，因為名稱會先去除前後空白；值本身嚴格。300 KiB 的 `Cookie` 標頭，含有效 cookie，服務仍回 200，服務本身沒有標頭大小上限，靠入口 Envoy 預設的 60 KiB 上限（F4）。

### 2. Session 到期邊界與時鐘偏差（通過，F2 為已知設計）

- 到期由資料庫的 `now()` 判斷，服務的時鐘不參與：3 秒的 session 在到期那刻轉 401，沒有快取。
- token 的 `iat` 用服務自己的時鐘：`token_claims::expiry_issued_at_and_skew_boundaries`：`iat` 比現在早 63 秒（`exp` 已過 3 秒）被接受，早 67 秒（`exp` 已過 7 秒）被拒（Expired），晚 3 秒被接受，晚 8 秒被拒（NotYetValid），極端時鐘（0、-1、`i64::MIN`、`i64::MAX`、`i64::MAX - 30`）沒有溢位也沒有被接受。身分服務的時鐘比驗證端快超過 5 秒時 token 一律被拒（fail closed）。
- F2：session 在資料庫被撤銷或到期後，已簽出的 token 仍可用到自己的 `exp`（最多 60 秒加驗證端 5 秒容差）。測試證實過期後的 token 仍驗得過；這與 README「效期 60 秒」一致，是已記錄的取捨。

### 3. Token claims 與演算法混淆（通過）

`tests/token_claims.rs`，全部對 service-kit 的 `IdentityVerifier`：

- 別把金鑰簽的、用已知 kid 冒名、kid 大小寫、空白、空字串、NUL：拒絕；沒有回退到其他金鑰。
- `alg` 為 `none`、`None`、`NONE`、`HS256`、`HS512`、`ES256`、`RS256`、`PS256`、`eddsa`、`Ed25519`、`EdDSA `（尾端空白）、空字串：UnsupportedAlgorithm；無簽章形式也拒絕；`alg` 缺少、null、陣列、數字：MalformedHeader；以公鑰位元組當 HMAC 的形式在檢查金鑰之前就拒絕。
- 標頭多出 `jwk`、`jku`、`x5u`、`crit`、`b64`、`cty`、`zip`：拒絕；`typ` 為 `JWT`、`at+jwt` 等：拒絕；`alg` 重複的標頭：拒絕。
- 簽章後改任何 claim（`aud`、`sub`、`exp`、`platform_admin`、`tenant.role`、`iss`）、改標頭 kid：BadSignature；簽章位元翻轉（4 個位置）、S + L（非標準簽章）、截短、延長、空、多一段、`=` 填充、前後空白、`Bearer ` 前綴：拒絕。
- `aud` 錯誤、大小寫不同、陣列、null；`iss` 錯誤：拒絕。真正的 `Issuer` 簽給 assets、certs、alerts 的 token 各自只有受眾驗得過。
- 壽命：`exp = iat`、`exp < iat`、超過 300 秒、`i64::MAX`、`i64::MIN..i64::MAX`：InvalidLifetime；300 秒剛好被接受（身分服務簽 60 秒）。

### 4. 租戶隔離（通過）

- 實作者的 `cross_tenant`（testkit 套件）通過；`identity.users` 與 `identity.sessions` 是明列豁免。
- `memberships_are_isolated_by_tenant_and_by_user`：服務角色沒有租戶設定時看到 0 列；設為租戶 A 看到 2 列、B 看到 1 列、不存在的租戶與空字串 0 列，`tenant_id <> 設定值` 的述詞也撈不到別人的列；設定值是 `not-a-uuid` 時查詢報錯而不是放寬；`SET ROLE`、`SET SESSION AUTHORIZATION`、`DISABLE ROW LEVEL SECURITY`、`DROP POLICY`、`CREATE POLICY`、`DELETE`、`UPDATE sessions`、`CREATE FUNCTION` 全部被拒；`GRANT ALL` 只有警告，事後 `INSERT INTO sessions` 仍被拒；`row_security = off` 沒有曝露列。
- 經服務：同一租戶另一個使用者的 admin 角色不會滲到 viewer 的 token；使用者在 A 是 viewer、在 B 是 admin，session 在哪個租戶就拿哪個角色；session 指向不存在的租戶，或使用者不是成員的租戶，token 沒有 tenant。

### 5. 資料庫停擺或太慢（通過，F1 為可用性發現）

- `slow_or_locked_database...`：以 owner 連線鎖住 `identity.sessions`（再換 `identity.memberships`）：單一請求 503，1.5 秒內回；連線池大小 2、12 個並行請求，全部 503、沒有身分標頭、各自 3 秒內回；沒有 cookie 的請求仍然 401。解鎖後下一輪就回 200，連續 20 次 200；結束後 `pg_stat_activity` 沒有 `identity_app` 的 idle in transaction 或仍在執行的查詢（被取消的查詢沒有留下東西）。
- `killed_connections...`：3 輪 `pg_terminate_backend` 全部服務連線：之後的回應只有 200 或 503，沒有 401（有效 session 不會被誤判成無效），最後恢復 200。把 `sessions` 的 SELECT 收回：503；把 `memberships` 的 CHECK 拿掉並寫入 `tenant_role = 'superuser'`：503 且不簽出未知角色。
- `wrong_credentials_or_database_fail_closed`：密碼錯、資料庫不存在、使用者不存在：check 503、`/readyz` 503。
- 沒有任何情境 fail open：每個失敗情境都斷言沒有 200、沒有 `x-internal-identity`。
- F1：冷連線會吃掉 0.4 秒的期限，見發現。

### 6. 健康埠（通過）

`the_health_port_serves_only_the_health_routes`：健康埠對 GET、POST、HEAD、PUT、DELETE、OPTIONS 各 14 種路徑（含 `/internal/ext-authz` 與其子路徑、`//internal/...`、`/%69nternal/...`、`/healthz/../internal/...`、`/metrics`、`/`）：只有 GET/HEAD 的 `/healthz` 與 `/readyz` 回 200，其餘 404 或 405，從不回身分標頭。API 埠的 `/`、`/metrics`、`/internal`、`/internal/keys`、`/internal/ext-authz-x` 也是 404 或 405。

### 7. 日誌（通過）

見驗收條件 4。補充：在這個建置裡 hyper、rustls 沒有發出 tracing 事件，所以 trace 等級的實質內容是 sqlx（陳述式文字，沒有綁定參數值）、service-kit 與身分服務自己的事件。每筆 deny 只記一行 `reason`；`BackgroundTenantDb::begin` 的 DEBUG 事件只有租戶 ID 與 purpose。

### 8. 金鑰載入（通過）

`the_service_refuses_to_start_without_a_usable_matching_signing_key`：以下都以 exit code 1 結束、沒有輸出 `listening`、輸出不含金鑰的任何寫法：檔案不存在、路徑是目錄、空檔、只有空白、只有 BEGIN 行、金鑰被截半、金鑰內容被改一個位元組、只有公鑰的 PEM、ECDSA P-256 的 PKCS#8、未部署公鑰的另一把 Ed25519、已部署的集合只有別把金鑰、`{"keys":[]}`、不是 JSON、空字串、權限 000 的檔案。權限 0644 的檔案可以啟動（服務不檢查權限，F3）。`TRUSTIOT__PLATFORM__IDENTITY_SIGNING_KEY_FILE`、`TRUSTIOT__IDENTITY__SIGNING_KEY`、`TRUSTIOT_IDENTITY_SIGNING_KEY` 這些繞道的設定名稱沒有效果也沒有被回聲。

### 9. 金鑰輪替（通過）

`rotation_across_restarts...`（真的重啟 binary）與 `token_claims::rotation_keeps_old_tokens_valid_until_they_expire`，照 docs/runbooks/secrets.md「內部身分簽章金鑰」：

1. 兩把公鑰（`2026-10-a`、`2027-04-a`）並存，舊私鑰簽：token 的 kid 是 `2026-10-a`，與啟動日誌記的 kid 相同。
2. 換成新私鑰重啟：新 pod 自己找出 `2027-04-a`；新舊 token 對兩把公鑰的驗證端都驗得過。步驟 1 沒做完就換（集合只有舊公鑰）：新 pod 拒絕啟動。尚未滾動的驗證端（只有舊公鑰）拒絕新 token（UnknownKey）。
3. 移除舊公鑰：舊 token 被拒（UnknownKey，runbook 因此要求等 305 秒）、新 token 仍通過；外洩的舊私鑰不能再簽出可用的 token；只有新公鑰時服務照常啟動並簽發。

## 設計檢視

- `BackgroundTenantDb`：`PgSessionStore` 的 `db` 與 `memberships` 欄位都是私有，型別只對外暴露 `SessionStore` 的 `lookup` 與 `ping`；`start` 只回傳 `Router`；租戶來自剛讀出的 session 列，不是請求。沒有看到請求可以影響租戶的路徑。使用 `BackgroundTenantDb` 而不是 `TenantDb` 的理由成立（查 session 時還沒有 `UserIdentity`）。
- 沒有租戶範圍就碰資料庫的唯一地方是 `ACTIVE_SESSION`（`self.db.pool()`）：讀 `sessions` 與 `users`，兩者沒有 `tenant_id`，也沒有 RLS；這是 README 與 migration 明載的設計，服務角色只有 SELECT。`sessions` 的資料以 `token_hash` 為鍵，hash 與 secret 都不進日誌。
- allow 只能由 `Decision::Allow(InternalToken)` 組成，編譯期就沒有「allow 但沒有 token」的路徑；任何資料庫、逾時、簽章錯誤都映到 503。
- 服務自己不驗證呼叫者；只有入口的 AuthorizationPolicy 限制誰能呼叫（chart 的 mesh 規則只讓 ingress gateway 呼叫 identity），這一層屬於 Laysi/trustiot-v2#77 的驗證範圍，本次未測。

## 發現

| # | 嚴重度 | 內容 |
| --- | --- | --- |
| F1 | 中（可用性，不是安全；fail closed） | 0.4 秒的檢查期限（`CHECK_DEADLINE`）同時是連線池取得連線的逾時，所以開新連線（TLS、SCRAM、RLS 的 session 檢查查詢）超過 0.4 秒時，請求回 503。一個請求最多需要兩條連線（session 查詢結束後，連線非同步歸還，緊接的 `memberships.begin` 常常開第二條）。readiness 只要求一條連線，所以「就緒」之後的第一批請求仍可能 503。pod 啟動、擴容、資料庫換主之後使用者會看到入口的 503。實作者在 20 核的機器上沒有遇到，本機高負載下 `ext_authz` 的 7 項中 4 項失敗，release 全過。重現與服務日誌時間軸見 [finding-cold-connection-deadline.txt](data/2026-10-11-61-verify/finding-cold-connection-deadline.txt)；指令：`CI=1 cargo test --locked -p identity --test ext_authz`（在 load average 超過 8 的 8 核機器上）。建議：連線逾時與檢查期限分開，或啟動時預熱兩條連線（`min_connections`）並讓 readiness 要求它們；測試也不要依賴冷連線在 0.4 秒內完成 |
| F2 | 資訊 | session 撤銷或到期之後，已簽出的 token 仍可用到自己的 `exp`，最多 60 秒加驗證端 5 秒容差。README 與決策已寫明；如要立即登出，需要另外的機制 |
| F3 | 資訊 | 服務不檢查私鑰檔的權限（0644 可啟動）。chart 的 Secret volume 沒有設 `defaultMode`（Kubernetes 預設 0644），只有身分服務的 pod 掛載，風險低；若要更嚴，在 chart 設 `defaultMode: 0400` |
| F4 | 資訊 | 服務本身沒有請求標頭大小上限：300 KiB 的 `Cookie`（含有效 cookie）回 200；2 MiB 被 hyper 拒絕。入口 Envoy 預設 60 KiB 先擋掉，所以目前不可達 |
| F5 | 資訊 | 每個 401 與 403 都記一行 INFO；沒有 cookie 的洪水會放大日誌量（只有 `reason`，沒有祕密） |
| F6 | 資訊 | cookie 名稱與 `=` 之間的空白被容忍（名稱先 trim），RFC 6265 不允許；不影響安全，因為值嚴格且名稱仍須完全相符 |

沒有發現可繞過驗證、洩漏金鑰或 fail open 的缺陷。
