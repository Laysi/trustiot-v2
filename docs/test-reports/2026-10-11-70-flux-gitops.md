# SaaS GitOps：Flux 拉取部署的 lab 驗證（2026-10-11）

對應 issue：Laysi/trustiot-v2#70。原始資料在 [data/2026-10-11-70-flux-gitops/](data/2026-10-11-70-flux-gitops/)。

在 lab 的 k3s 上以 [deploy/flux/README.md](../../deploy/flux/README.md) 的方式安裝 Flux，從 git 與一次性的 registry 部署一個小的測試 chart，證明 deploy commit 合併後在 GitRepository 的間隔內部署、revert 後回到前一版、別的金鑰簽的 chart 不會被安裝、SOPS 加密的拉取 Secret 被解密並用來拉 chart。測完移除 Flux 與測試 namespace，叢集層級的物件與其他 namespace 的 workload 與測試前相同。

## 環境

- **機器**：lab 的 Mac mini M1（`trustiot-mac-m1`），Fedora Linux Asahi Remix 44 Server，aarch64，k3s v1.36.5+k3s1。執行期間持有 `~/e2e.lock`（owner `Laysi/trustiot-v2#70`），測完立即釋放。沒有動到 `poc`、`trustiot` 兩個 namespace、`~/poc-edge` 與維運用的 cloudflared。
- **工作站**：proto 0.60.2；`.prototools` 的 Bun 1.4.2、Helm 4.3.0、cosign 3.1.3、SOPS 3.13.3、kubectl 1.36.5（kustomize）、Flux CLI 2.9.6；age v1.3.2 由 `scripts/flux/age.ts` 以 Go 1.27.2 從原始碼建置（經 Go checksum database 驗證）。
- **Flux**：`deploy/flux/clusters/saas/flux-system/` 的 manifest，即 Flux 2.9.6 的 source-controller v1.9.6、kustomize-controller v1.9.6、helm-controller v1.6.5，映像以 cosign 驗證過的 digest 固定。
- **程式碼**：分支 `feat/70-flux-gitops`，base 為 main 的 `9b13ad8`（尚未 commit 的工作樹，與後續 commit 的內容相同）。
- **測試用的伺服器**（都在 namespace `e2e-70`，以 digest 固定）：registry 3.1.2（TLS 用一次性 CA、htpasswd 帳密）、soft-serve v0.9.1（git，以 SSH 與唯讀金鑰讀取）、alpine/git v2.52.0（推送用的 git client）。

與正式環境不同的地方（都只在測試裡）：git 伺服器是 soft-serve 而不是 GitHub；registry 是一次性的 registry 而不是 GHCR；chart 是小的測試 chart（0.0.1、0.0.2 以信任的金鑰簽章，0.0.3 以另一把金鑰簽章）；簽章用一次性的 cosign 金鑰對，`chart.yaml` 以 `secretRef`（測試公鑰）取代 `matchOIDCIdentity`，並以 `certSecretRef` 信任測試 CA，因為 keyless 簽章只能由 release.yml 在 `v*` tag 上產生。其餘欄位與 `scripts/release/flux.ts` 的 `renderChartSource` 輸出相同。所有金鑰、密碼與憑證都在執行時產生，結束後刪除。

Flux 在 HelmRelease 的 chart 版本後加上 digest 的 build metadata（例如 `0.0.1+5062550e75fe`），所以腳本比對的是 `+` 之前的版本。

叢集層級物件的比對（[cluster-state.json](data/2026-10-11-70-flux-gitops/cluster-state.json)）：namespaces 8、CustomResourceDefinitions 29、ClusterRoles 82、ClusterRoleBindings 69、ValidatingWebhookConfigurations 2、MutatingWebhookConfigurations 1、APIServices 34、PriorityClasses 2、StorageClasses 1，測試前後的名稱與內容 sha256 都相同，`differences` 為空。

前 4 次執行的問題，都已在腳本修正，每次的清理也都比對通過：

1. SOPS 依檔案路徑比對 `.sops.yaml` 的規則，加密暫存檔要用 `--filename-override` 並在暫存目錄執行。
2. git client pod 內的 repo 擁有者不同，git 拒絕操作，加上 `safe.directory`。
3. Flux 已在 1 分鐘內裝好 0.0.1，但腳本比對版本時沒有去掉 `+<digest>`，等到逾時。
4. 連到 lab 的 SSH 在第一個指令就斷線（exit 255），什麼都還沒建立；腳本改為遇到 exit 255 時重試最多 4 次。

第 5 次執行之後，腳本的事前檢查與清理再收緊一次（commit 前的審查要求）：事前檢查也拒絕已經有 Flux CRD 的叢集，查 namespace 時 NotFound 以外的錯誤視為失敗；清理只刪除這次執行建立的 namespace 與 Flux。正常路徑上兩個 namespace 都由這次執行建立，清理的指令與第 5 次執行相同，所以沒有為此重跑（lab 的鎖同時有 Laysi/trustiot-v2#57 在等）。`kubectl get namespace e2e-70 -o name` 在 lab 上的輸出是 `Error from server (NotFound): ...`，與事前檢查比對的字串相符。

## 結論

| 驗收條件 | 結論 |
| --- | --- |
| 合併版本號 PR 後，SaaS 主機在設定的間隔內完成部署；revert 該 PR 可回到前一版 | lab 上的機制通過：deploy commit 27.6 秒、revert 49.6 秒，都在 60 秒的間隔內，簽章不符的 chart 不會被安裝。正式的 SaaS 主機待測：SaaS 主機還沒建立，GHCR 的機器帳號 token、`.sops.yaml` 的 age 公鑰與 deploy key 由人提供；release.yml 的 `deploy-pr` job 也要在合併後第一次推 `v*` tag 時才會實際開出 PR，keyless 簽章的驗證屆時以正式的 `chart.yaml` 驗證。 |
| GitHub 的 secrets 與 environments 中沒有任何叢集憑證 | 設計上成立：Flux 從叢集內拉取，沒有任何 workflow 連到叢集；workflow 讀的 secret 只有 `GITHUB_TOKEN` 與 release notes 用的 `AI_API_KEY`，`release` environment 只用來記錄發佈。叢集持有的是 GHCR 唯讀 token 與 git 唯讀 deploy key，GitHub 端只有 deploy key 的公鑰。 |
