# assistant：重新產生最後一個回答（2026-11-04）

Laysi/trustiot-v2#649。這份報告記錄重新產生回答的測試證據：`POST /api/assistant/v1/conversations/{conversation_id}/regenerate` 在提問的放行交易裡捨棄最後一輪、以同一個問題重新回答；前面的訊息逐位元組不動，被拒絕時什麼都不捨棄，複製來的最後一輪不能重新產生（使用者 2026-11-04 的決定）。請求以 `{"answer": <seq>}` 指名它取代的回答，指名的不是最後一個回答時 409、什麼都不捨棄（使用者 2026-11-05 的決定，安全審查之後加上，見「安全審查之後」）。

## 環境

- **程式碼**：分支 `feat/649-regenerate`，從 main 的 `c12a2d64` 開始，之後合併 main 的 `922dda9f`；沒有新的 migration（用既有的 `assistant.discarded_rounds`）。「結果」是第一輪實作的執行，「安全審查之後」是修正之後的執行。
- **建置主機**（Linux aarch64 VM，12 核，rootless podman）：經工作佇列執行，設 `CI=1`，容器測試沒有容器執行環境時失敗而不是略過。所有 cargo 的建置與測試都在這裡。
- **本機**：`cargo fmt`、frontend 與 `scripts/` 的 Bun 檢查、gitleaks。
- **工具**：`.prototools` 與 `rust-toolchain.toml` 鎖定的版本。
- **資料庫**：測試自己啟動的拋棄式 Postgres（TLS），schema 由遷移 Job（`tools/migrate`）套用。
- **替身**：`tests/regenerate.rs` 的替身 AI 閘道對每個問題先回一個工具步驟（thinking 與工具呼叫），工具結果之後回一個帶 thinking 的回答，回答的文字帶著呼叫的序號，所以測試分得出新舊回答；問題含 `[hold]` 時第一個模型呼叫等測試開閘，「提問進行中」是測試建立的狀態，不是競態。替身身分服務記下每個委派，可以指定 code 拒絕。

## 結論

重新產生回答只捨棄最後一輪：前面的訊息在資料庫與送給模型的請求裡都逐位元組不變，捨棄與新的提問在同一個交易，被拒絕時什麼都不捨棄，複製來的最後一輪被拒絕而歷史不變；請求指名它取代的回答，所以重試與同時送出不會多捨棄一輪，重新產生也算在每日開始的上限裡。commit 之後舊的回答不會回來，新的提問失敗或被停止時對話停在前一輪（`services/assistant/README.md` 的「背景執行」）。反覆重新產生與停止的壓力測試、重新產生與刪除兩種 commit 順序的測試沒有做（議題的進階驗證）。
