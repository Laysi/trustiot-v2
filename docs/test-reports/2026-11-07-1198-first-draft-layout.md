### 這次改的預覽

預覽的輸入框裡，問題含 `!draft` 時，回答在這段對話寫出一份草稿（`frontend/src/test/fake-questions.ts` 的 `writeDraftFor`、`frontend/src/test/fake-dashboards.ts` 的 `writeTemperatureDraft`、橋接模組 `frontend/src/test/preview-draft-writer.ts`；說明在 `frontend/README.md` 的測試替身一段與 `fake-questions.ts` 的檔頭）。草稿是劇本步驟 3 要求句的內容：兩個 KPI（現在的溫度與濕度）加一張長條圖（最近 7 天每天的平均與最高溫）。時序照下一節的程式推論：跑到四分之一時草稿已存在（對話的草稿列表此時就有它），一半與四分之三時串流出回答的第一、第二段，約 2.5 秒回答存下來，這時回答才有 `draft_versions` 指向草稿，第三段隨存下的回答出現。測試在 `frontend/src/ui-preview/preview.test.tsx`（四個，含停止的問題不會把延遲的草稿寫進下一個問題）。

### 與正式版不同、會影響怎麼讀這份報告的地方

- 預覽的假服務**立刻回答**（沒有網路與資料庫的時間）。所以草稿列表、卡片的版本與資料集查詢都在一兩個畫面格內回來，量到的「轉換」是最快的情況。為了看時間怎麼隨往返延長，每個視窗另跑一次工具列的「慢」設定 2000 ms（每個 API 請求等 2 秒才到假服務，代表一次往返；只有 0、2000、10000 三個選項）。2000 ms 的結果是**結構**的證據（哪些請求接在哪些後面），不是正式環境的秒數。
- 真模型的答覆與真的資料查詢時間沒有量：圖出現在轉換之後多久，取決於資料集查詢要多久（一個租戶同時最多 2 個在跑）。
- 預覽的回答固定三段，與正式環境的回答長度無關。

## 程式怎麼說：客戶端什麼時候知道回答寫了草稿

結論：**草稿在服務端早就存在，但客戶端只在回答存下來之後才知道**，所以一欄變兩欄一定發生在「回答結束」的那一刻，不會在回答串流中途。順序如下（檔案與行號為 `e976c301`／`67eb1895` 的內容）。

| 順序 | 誰 | 發生什麼 | 出處 |
| --- | --- | --- | --- |
| 1 | 首頁 | 建立對話、送出問題，導向對話頁（路由狀態帶著這個 run） | `HomeComposer.tsx:44-56` |
| 2 | 對話頁 | 讀對話（`GET /conversations/{id}`）；問題進行中時每 1.5 秒再讀一次 | `ConversationPage.tsx:83-87`、`QUESTION_POLL_MS` |

還有兩個會提早重讀草稿列表的路徑，都不在劇本的正常動作裡：

- React Query 的 `refetchOnWindowFocus` 在這個應用是關的（`app/query-client.ts:50`），視窗取得焦點不會重讀；草稿列表沒有輪詢，其他地方只有儲存草稿之後才失效（`drafts.ts` 的 `usePublishDraft`）。
- **在回答進行中重新整理頁面**（或離開再回來）：頁面重新掛上時才讀草稿列表；若模型已經寫出草稿，這次讀就有，兩欄會在回答還在串流時就出現。依程式推論，沒有實測。彩排與展示時不要在回答進行中重新整理。

## 指令

```sh

bun install --cwd frontend --frozen-lockfile

TREE=B LATENCY_MS=2000 REPEATS=1 SHOTS=1 bash docs/test-reports/data/2026-11-07-1198-first-draft-layout/run.sh
# 把 JSON 行整理成表：
bun docs/test-reports/data/2026-11-07-1198-first-draft-layout/summarize.mjs \
  docs/test-reports/data/2026-11-07-1198-first-draft-layout/browser-check-A.jsonl \
  docs/test-reports/data/2026-11-07-1198-first-draft-layout/browser-check-B.jsonl
```

[`run.sh`](data/2026-11-07-1198-first-draft-layout/run.sh) 啟動預覽、等它回應、在 Playwright 容器裡執行 [`browser-check.mjs`](data/2026-11-07-1198-first-draft-layout/browser-check.mjs)，最後停掉預覽；可用環境變數 `TREE`（樹的名稱）、`VIEWPORTS`、`REPEATS`（預設 2）、`LATENCY_MS`（0、2000、10000）、`SHOTS=1`（用 CDP screencast 在最後一次重複時印出轉換前後的畫面格，只給審查的人看，不進 repo）、`FRAMES=1`（印出每個取樣畫面格）。原始輸出：[A](data/2026-11-07-1198-first-draft-layout/browser-check-A.jsonl)、[B](data/2026-11-07-1198-first-draft-layout/browser-check-B.jsonl)（各 155 行，`summary` 行的 `failures` 是空陣列）。

腳本做的事（劇本步驟 3）：

1. 首頁輸入「做一個儀表板：最近 7 天每天的平均溫度與最高溫度，用長條圖比較，另外用一個數字顯示現在的溫度和濕度。以台北時間分天。 !draft」，按「送出」。
2. 在新的對話頁等條件：回答存下來（第三段出現）、卡片與圖出現、草稿面板出現、版面連續 30 個畫面格（約半秒）不變。不手動捲動，只記錄捲動位置。
3. 送出前裝好探針：`requestAnimationFrame` 每個畫面格取樣（欄寬與位置、面板、問題與各段回答與卡片標題與圖的位置、捲動、輸入框焦點、圖的 canvas 身分與寬度）、`MutationObserver`（卡片、面板、骨架屏、警示、canvas 的加入與移除，外框 class 變化）、`PerformanceObserver` 的 `layout-shift`、應用建立的 API 請求（預覽在頁面裡回答，沒有網路紀錄，建立 `Request` 的時間代表送出時間）。
4. 時間都以「回答存下來」為零點：第一個畫出第三段（存下的回答最後一段）的畫面格。
5. 每個視窗重複 2 次（2000 ms 的變體 1 次），每次都是新頁面、新的假服務。

另外在對照視窗（1279×720）做一個**模擬**：卡片與圖已畫出後，把視窗從 1279 加寬到 1280 px，記錄同一張卡片在版面變成兩欄時是被替換還是只改尺寸、有沒有重查。這模擬的是「卡片先畫、面板後到」的**重排**，不是兩個請求的先後。

## 結果

### 實際的轉換：一個畫面格，單欄變兩欄（樹 A、B 相同）

1280×720、延遲 0（預覽的假服務立刻回答），逐段（A 的第一次重複；B 與其他視窗的順序相同，時間差在一個畫面格以內，16.7 ms）：

| 相對於回答存下來 | 畫面 |
| --- | --- |
| −2.4 s | 對話頁第一次畫出，問題在頂端（伺服器的 run 剛開始） |
| −1.25 s | 第 1 段回答出現，「正在寫回答…」 |
| −0.63 s | 第 2 段出現 |
| 0 | 回答存下來：串流的回答換成存下的回答（多了第 3 段），標題從「…開始的對話」變成問題的前 40 字，回答下是卡片的骨架屏；仍是單欄 768 px。所有東西下移 28 px（標題區多一行） |
| +16.7 ms（1 個畫面格） | **草稿列表回來：單欄變兩欄**。對話欄 768 → 520 px，x 從 248.5 變 72.5，面板出現在 x 616.5、寬 576、頂端 y 89；卡片在 520 px 欄裡「載入中」 |
| +33 ms … +50 ms | 卡片載入中 → 卡片有了文字但還沒有圖 |
| +117 … +133 ms | 圖畫出（兩處各 3 次資料集查詢共 6 次，全部在轉換之後） |

整個轉換只有一次重排（`reflows` 1 個畫面格），之後只是內容填入。單欄時卡片的骨架屏只存在 1 個畫面格（假服務立刻回答）；2000 ms 的變體裡，這個單欄、骨架屏的狀態延長成整個往返，即約 2.03 s，然後面板與卡片在同一個畫面格一起出現（卡片「載入中」），約 4.1 s 圖才出現（草稿列表一個往返，加資料集查詢一個往返）。**所以正式環境裡「單欄＋骨架屏」會持續一次草稿列表的往返時間，然後頁面跳成兩欄；圖再晚一些出現，取決於資料集查詢。**

**捲動與可見性**（A、B 相同）

| 視窗 | 頁面自己捲動 | 轉換前後 `scrollY` | 回答第 2、3 段是否在頂端列與輸入框之間 | 面板第一屏露出 |
| --- | --- | --- | --- | --- |
| 1280×720、1536×768、1920×1080、1279×720 | 沒有（見下） | 0 → 0 | 是（前、後都在） | 兩欄視窗 501／549／861 px，對照 0 |

- 「起點的捲動位置」：首頁打開時 `scrollY` 是 0；在 1280×720 與 1279×720 按「送出」時，頁面為了按到按鈕自己捲了 225 … 382 px（首頁在這個高度放不下），導向對話頁後第一個畫面格是這個值，下一個畫面格就回到 0（路由換頁）；1536×768 與 1920×1080 沒有這個捲動。之後整個轉換期間 `scrollY` 一直是 0。

換成

> **第一份草稿出現的那一刻，版面會跳一次**（2026-11-07 的實測，Laysi/trustiot-v2#1198）：新對話送出問題時是置中的單欄；回答寫完、存下來之後才讀到草稿，頁面一次變成兩欄。整欄對話向左移（1280 px 視窗約 176 px）、變窄，文字多換行，問題與回答往下移 50～130 px，右邊同時出現草稿面板，面板裡的數字與長條圖在第一屏。對話內容仍在畫面內，頁面不會自己捲動，焦點不動。這一刻是**一次**跳動，不是閃爍，不用處理。

> - 第一份草稿出現時，頁面從單欄（對話欄 768 px 置中）一次變成兩欄（對話欄 520 px 靠左、面板 576 px 在右）；之後追問寫出的新版本只換面板與卡片的內容，不再改版面。
