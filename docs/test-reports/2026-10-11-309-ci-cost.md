# 降低 Actions 用量：arm64 runner、依路徑決定 job、PR 的 smoke label

對應 issue：Laysi/trustiot-v2#309。設計與規則見 [CI 與發佈](../architecture/ci-release.md) 的「依變更路徑決定 job」、「省 Actions 分鐘數」與「PR 的部署要加 `smoke` label」。

## 環境

- 本機：Fedora 45 x86_64，Bun 1.4.2、git 2.56.0、skopeo 1.24.1、actionlint 1.7.12（`.prototools` 釘選）。
- build host（`ruisi-wsl`）在 2026-10-11 16:42 前後重新啟動、連線失敗，所以全部檢查改在本機執行；這些檢查都不需要容器。
- lab Mac mini M1（Fedora Asahi，aarch64，16K page）：只用來下載並執行 arm64 的工具執行檔；沒有 git，所以無法在上面跑 proto 本身（proto 解析版本時會呼叫 git）。GitHub 的 arm64 runner 是 4K page，與 lab 不同；本報告在 lab 執行的都是靜態連結的 Go 與 musl 執行檔，與 page 大小無關。
- 分支 `ci/309-path-filter`，以 `origin/main` `a0fcadf` 為基礎。
- 價格：GitHub 文件 [Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)，2026-10-11 讀取：Linux 2-core x64（`actions_linux`）每分鐘 USD 0.006，Linux 2-core arm64（`actions_linux_arm`）每分鐘 USD 0.005，arm64 便宜約 17%。該頁沒有寫 Free 方案的 2,000 分鐘是否同樣適用於 arm64；依 issue 背景的計費紀錄，組織的用量分成 Linux 與 Linux ARM 兩項計算。

## 指令

```sh
# 路徑規則、比較方式與輸出（暫存 git repo，不需要網路）；ci.yml 與 nightly.yml 的條件式
bun install --cwd scripts --frozen-lockfile
bun test scripts/ci
# workflow 規則與語法
bun scripts/ci/check-workflows.ts
bun scripts/ci/lint-workflows.ts
bun scripts/ci/check-secret-handling.ts
bun run --cwd scripts typecheck
# 全部腳本測試與 chart 測試
bun run --cwd scripts test
bun test deploy/chart
# arm64：Rust 測試啟動的容器映像，各自 digest 背後的平台
bun images.ts   # 對每個映像跑 skopeo inspect --raw docker://<image>@<digest>，列出 index 的平台
# arm64：lab 上下載 schema plugin 解析到的 linux arm64 資產、以 release 的 checksum 驗證並執行
bash lab-assets.sh
```

`images.ts` 與 `lab-assets.sh` 是一次性的驗證腳本，輸出存在 data 目錄。

## 結果

### 路徑規則與條件式

- `bun test scripts/ci`：5 個檔案、242 個測試全數通過（本機，2026-10-11）。其中 `changes.test.ts` 逐類列出路徑（Rust 原始碼、各 Cargo.toml、Cargo.lock、工具鏈、`.prototools`、`.proto/`、`api/`、`crates/`、`services/`、`edge/`、`factory/`、`tools/`、clippy 與 rustfmt 設定、`.cargo/`、任何位置的 `.rs`、`.sql` 與 AGENTS.md、`deploy/chart/values.yaml`、ci.yml、本地 action、未分類的新目錄等）與 `cargo-deny`、`helm` 的規則；兩項守門測試掃描全部 `.rs` 的字串常值與 include，以及 chart 測試讀的檔案（試著從規則拿掉 `deploy/chart/values.yaml` 與 `scripts/lib/stack.ts`，守門測試即失敗）；比較方式以暫存 git repo 驗證 PR 的 merge commit、搬移檔案、推到 main 時跳過還在跑、失敗、被取消或沒有執行的 commit、讀不到執行紀錄時全部執行。
- `workflow-conditions.test.ts` 以 `@actions/expressions` 0.3.61（GitHub actions/languageservices 的 expression 引擎）計算：ci.yml 的 `rust`、`cargo-deny`、`helm` 在 `changes` 回答 `false` 時略過，回答 `true`、空值或 `changes` 失敗時執行，被取消時不執行；`gitleaks`、`workflow-policy` 不等 `changes`；每個 job 都在 `ubuntu-24.04-arm`。nightly.yml：排程與手動執行一律部署；PR 沒有 `smoke` label 時不部署；加上 `smoke`（大小寫不拘）時部署，之後每次推送都部署；加上其他 label 時不部署，concurrency group 是 `nightly-no-smoke-<run_id>`，不會取消進行中的部署；同一個 PR 的部署共用 `nightly-42` 這類 group；`notify` 不因 PR 執行。
- `check-workflows.ts`：4 個檔案沒有違規；`lint-workflows.ts`：3 個 workflow 沒有錯誤；`check-secret-handling.ts`：沒有違規；型別檢查通過。
- `bun run --cwd scripts test`：491 通過、1 略過（沒有設 `TRUSTIOT_DEV_E2E` 的本地環境 e2e）、0 失敗；`bun test deploy/chart`：221 通過。輸出見 [local-checks.txt](data/2026-10-11-309-ci-cost/local-checks.txt)。

### 計費分鐘估算

改動前的數字來自 issue 背景（gh 讀 billing 與執行紀錄）：ci.yml 每次約 11 個 x64 計費分鐘，`rust` 約 7 分鐘、其他四個 job 各約 1 分鐘；nightly 的 PR 部署每次約 7 個 arm64 分鐘。每個 job 的分鐘數各自無條件進位。改動後假設各 job 在 arm64 上的時間與 x64 相同（2-core 對 2-core；實際以本 PR 的 CI 為準），`changes` 約 1 分鐘。

| 每次執行 | 改動前 | 改動後 | 金額（前 → 後，USD） |
| --- | --- | --- | --- |
| 只改 `docs/` 的 PR | 11 x64 | 3 arm64（changes、gitleaks、workflow-policy） | 0.066 → 0.015（−77%） |
| 只改 chart 的 PR（不含 nightly 部署） | 11 x64 | 4 arm64（再加 helm） | 0.066 → 0.020（−70%） |
| 　同上，nightly 部署 | 每次推送 7 arm64 | 沒有 `smoke` label 時 0；加上 label 時與之後每次推送 7 arm64 | 每次推送 0.035 → 0（合併前一次 0.035） |
| 只改 `scripts/` 的 PR | 11 x64（動到 `scripts/nightly/` 另加 nightly 部署） | 3 arm64（nightly 同上，要 label） | 0.066 → 0.015（−77%） |
| 改 Rust 原始碼的 PR | 11 x64 | 10 arm64（changes、rust、gitleaks、workflow-policy） | 0.066 → 0.050（−24%） |
| 改 Rust 與 Cargo.lock 的 PR | 11 x64 | 11 arm64（再加 cargo-deny） | 0.066 → 0.055（−17%） |
| 推到 main | 同上各類，各 11 x64 | 與同類 PR 相同；找不到通過的 commit 或讀不到執行紀錄時 12 arm64 | 依類別；最差 0.066 → 0.060 |

以 issue 背景的 102 次 ci 執行（2026-10-01～11）為例，若一半是不動 Rust 的 PR 與合併（3～4 分鐘），一半動到 Rust（10～11 分鐘），約 102 × 0.5 × 3.5 + 102 × 0.5 × 10.5 ≈ 714 分鐘，相較 102 × 11 = 1,122 分鐘少約 36%，且全部改以較便宜的 arm64 計價；nightly 的 PR 部署由每次推送一次，改為每個 PR 約一次。
