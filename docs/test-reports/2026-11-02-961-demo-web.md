對應 Laysi/trustiot-v2#961（父 issue Laysi/trustiot-v2#456；安全關卡來自 Laysi/trustiot-v2#498）。這份報告記錄打開 `services.web` 之前的唯讀檢查（istiod、記憶體、渲染的差異），以及合併後經展示環境真實入口的檢查。真實入口的檢查由能通過 Cloudflare Access 的人執行，結果在第 4 節。

## 結果

### 1. istiod 與 repo 一致（2026-11-01 16:32）

`web-check.ts istiod` 的完整輸出（結束碼 0）：

```text
pathNormalization.normalization: DECODE_AND_MERGE_SLASHES (repo: DECODE_AND_MERGE_SLASHES)
trustiot-identity.service: trustiot-identity.trustiot.svc.cluster.local
trustiot-identity.port: 8080
trustiot-identity.pathPrefix: /internal/ext-authz
trustiot-identity.failOpen: false
trustiot-identity.timeout: 0.5s
trustiot-identity.statusOnError: 503
trustiot-identity.includeRequestHeadersInCheck: cookie, origin, sec-fetch-site
trustiot-identity.headersToUpstreamOnAllow: x-internal-identity
PASS istiod's mesh config matches deploy/istio/istiod-values.yaml
```

- `includeRequestHeadersInCheck` 是 `cookie`、`origin`、`sec-fetch-site`，與 main 的 `deploy/istio/istiod-values.yaml` 相同：cookie 檢查收得到跨站檢查要的兩個標頭。provider 只有 `trustiot-identity` 一個，`failOpen` 是 `false`。
- 叢集裡沒有 `HelmChartConfig`（`No resources found`），HelmChart `kube-system/istiod` 的 values 只有 `values-k3s.yaml` 與 `istiod-values.yaml` 的內容（`profile`、`global.platform`、`meshConfig` 與 `pilot.resources`）。mesh ConfigMap 的 managedFields 最後一筆寫入是 2026-10-27 17:42。
- 入口的 AuthorizationPolicy `trustiot-ingress-cookie-check` 是 `CUSTOM`，provider `trustiot-identity`：cookie 檢查用的就是上面比對的 provider。
- 不需要對齊，所以沒有寫對齊與回復的步驟。若 PR Laysi/trustiot-v2#962（`includeRequestHeadersInCheck` 再加兩個標頭）先合併，這個比對會在 `includeRequestHeadersInCheck` 失敗，要先照 runbook「換 chart 版本」第 2 步以 `platform.ts` 對齊 istiod，再打開 `web`。

### 4. 經真實入口的檢查

由能通過 Access 的人（持有工作站的操作員）照 runbook「打開 SPA（services.web）」第 5 步執行，`web-check.ts` 的輸出原樣貼在下面（輸出不含網址、主機名稱、cookie、token 與本文）。合併前的基準（可選）沒有做。

第一次執行時的部署狀態（2026-11-02 06:06 的 `flux.ts status`）：GitRepository 在 main `2e882e56`（含打開 `web` 的 `e669182f`）；HelmRelease 第 10 版 `deployed`，chart `0.0.0-rc.13+1028ecbb8632`；`trustiot-web` 1/1 就緒，沒有重啟。

#### 第一次（2026-11-02 05:52）：11 項通過，2 項不通過

```text
PASS routing: GET / without a cookie: 200 from web (text/html)
FAIL routing: GET /devices/00000000-0000-4000-8000-000000000961/settings (a deep link) without a cookie: 200 from web (text/html); expected 200 from web, the same index.html as /
FAIL routing: GET / with the session cookie: 200 from web (text/html); expected 200 from web, the same index.html
PASS routing: GET /static/* (an asset index.html loads) without a cookie: 200 from web (text/javascript)
PASS routing: GET /api/assets/v1/platform/gateways?limit=1 without a cookie: 401 unauthenticated error.unauthenticated
PASS routing: GET /auth/login without a cookie (only POST is cookie-free): 401 unauthenticated error.unauthenticated
PASS routing: POST /auth/login without a cookie or a body: 400 invalid_request error.invalid_request
PASS cross-site: GET /api/assets/v1/platform/gateways?limit=1, the cookie, Sec-Fetch-Site: same-origin: 200 from Cloudflare (application/json)
PASS cross-site: GET /api/assets/v1/platform/gateways?limit=1, the cookie, Sec-Fetch-Site: cross-site: 403 permission_denied security.cross_site_request
PASS cross-site: POST /api/assets/v1/platform/gateways?limit=1, the cookie, Sec-Fetch-Site: cross-site: 403 permission_denied security.cross_site_request
PASS cross-site: POST /api/assets/v1/platform/gateways?limit=1, the cookie, a foreign Origin, no Sec-Fetch-Site: 403 permission_denied security.cross_site_request
PASS cross-site: POST /api/assets/v1/platform/gateways?limit=1, the cookie, the app's Origin, Sec-Fetch-Site: same-origin: 405 from Cloudflare (no content-type)
PASS cross-site: POST /api/assets/v1/platform/gateways?limit=1, the cookie, the app's Origin, no Sec-Fetch-Site: 405 from Cloudflare (no content-type)
FAIL 2 of 13 checks
```

不通過的 2 項（深連結與帶 cookie 的 `GET /`）不是路由的問題，所以沒有 revert：

- 兩者都是 `web` 回的 200 `index.html`。但 Cloudflare 的 JavaScript detections 在每個 HTML 回應的 `</body>` 前插入一段 inline `<script>`，裡面有每個請求都不同的值；當時的 `web-check.ts` 要求兩份 `index.html` 的位元組完全相同。
- 以同一個 service token、session 與 user agent 另送四個 GET 比對：`/` 兩次、深連結、帶 cookie 的 `/`。四個都是 200、`text/html`、1686 字元，都帶 `web` 的 CSP 與 `X-Frame-Options`，各有一段 Cloudflare 的 script（1114 字元，在 `</body>` 前）。原樣比對兩兩不同；拿掉這段 script 之後，四個本文完全相同（572 字元）。

輸出裡標成 `from Cloudflare` 的 3 行其實是資產服務的回應：200 的本文有 `gateways`，兩個 405 是只接受 GET 的路由回的。當時的版本把不是 `web` 送的、本文也沒有錯誤代碼的回應都標成 `from Cloudflare`，與 runbook 說的「Cloudflare 在 Access 之前擋下」不符。

處理（2026-11-02 維護者決定）：

- `web-check.ts` 比對 `index.html` 時，先拿掉 Cloudflare 插入的 script（內容含 `__CF$cv$params` 或 `/cdn-cgi/challenge-platform/` 的 inline `<script>`），其餘位元組仍要完全相同，並在輸出註明拿掉了幾段；其他 inline script 照樣算不同。
- `from Cloudflare` 只用在 Cloudflare 自己回的 HTML（`Server: cloudflare` 且是 `text/html`），其他回應印狀態碼與 content type。
- 讓來源的回應不被插入（`Cache-Control: no-transform`）是 Laysi/trustiot-v2#988。

## 結論

| 驗收條件 | 狀態 |

| 展示叢集的 istiod 設定與 `deploy/istio/istiod-values.yaml` 一致，或已先對齊 | 通過：2026-11-01 16:32 唯讀比對，路徑正規化與 provider `trustiot-identity` 的每個設定相同，`includeRequestHeadersInCheck` 含 `origin` 與 `sec-fetch-site`；沒有 `HelmChartConfig` 疊加（結果第 1 項） |
