對應 Laysi/trustiot-v2#961（父 issue Laysi/trustiot-v2#456；安全關卡來自 Laysi/trustiot-v2#498）。這份報告記錄打開 `services.web` 之前的唯讀檢查（istiod、記憶體、渲染的差異），以及合併後經展示環境真實入口的檢查。真實入口的檢查要能通過 Cloudflare Access 的人執行，執行後填入第 4 節；在那之前標為待測。

## 指令

```sh
# 1. istiod（只讀）：istiod 正在用的 mesh 設定，與 checkout 的 deploy/istio/istiod-values.yaml 比對
ssh "$DEMO_SSH_HOST" 'sudo k3s kubectl -n istio-system get configmap istio -o jsonpath="{.data.mesh}"' \
  | bun scripts/demo/web-check.ts istiod
ssh "$DEMO_SSH_HOST" 'sudo k3s kubectl get helmchartconfig -A'
ssh "$DEMO_SSH_HOST" 'sudo k3s kubectl -n trustiot get authorizationpolicy trustiot-ingress-cookie-check -o jsonpath="{.spec.action} {.spec.provider.name}"'

# 2. 記憶體（只讀）

# 3. 渲染的差異：values-saas.yaml + values-demo.yaml（打開與不打開 web），私有 values 以 .test 的名稱代替
helm template trustiot deploy/chart -n trustiot \
  -f deploy/flux/clusters/demo/trustiot/values-saas.yaml -f deploy/flux/clusters/demo/trustiot/values-demo.yaml \
  --set-literal hosts.app=app.example.test --set-literal hosts.gateway=gw.example.test \
  --set-literal hosts.ota=ota.example.test --set-literal smtp.from=x

# 4. 經真實入口（合併前的基準與合併後；持有工作站的操作員，runbook「打開 SPA（services.web）」第 3、5 步）
O="$XDG_RUNTIME_DIR/demo-app-origin"; printf 'https://%s\n' "$DEMO_APP_HOST" > "$O"
bun scripts/demo/web-check.ts --expected-origin-file "$O"; rm -f "$O"
```

## 結果

### 1. istiod 與 repo 一致（2026-11-01 16:32）

`web-check.ts istiod` 的完整輸出（結束碼 0）：

```text
pathNormalization.normalization: DECODE_AND_MERGE_SLASHES (repo: DECODE_AND_MERGE_SLASHES)
trustiot-identity.service: trustiot-identity.trustiot.svc.cluster.local
trustiot-identity.port: 8080
trustiot-identity.pathPrefix: /internal/ext-authz
trustiot-identity.failOpen: false
trustiot-identity.timeout: 0.5s
trustiot-identity.statusOnError: 503
trustiot-identity.includeRequestHeadersInCheck: cookie, origin, sec-fetch-site
trustiot-identity.headersToUpstreamOnAllow: x-internal-identity
PASS istiod's mesh config matches deploy/istio/istiod-values.yaml
```

- `includeRequestHeadersInCheck` 是 `cookie`、`origin`、`sec-fetch-site`，與 main 的 `deploy/istio/istiod-values.yaml` 相同：cookie 檢查收得到跨站檢查要的兩個標頭。provider 只有 `trustiot-identity` 一個，`failOpen` 是 `false`。
- 叢集裡沒有 `HelmChartConfig`（`No resources found`），HelmChart `kube-system/istiod` 的 values 只有 `values-k3s.yaml` 與 `istiod-values.yaml` 的內容（`profile`、`global.platform`、`meshConfig` 與 `pilot.resources`）。mesh ConfigMap 的 managedFields 最後一筆寫入是 2026-10-27 17:42。
- 入口的 AuthorizationPolicy `trustiot-ingress-cookie-check` 是 `CUSTOM`，provider `trustiot-identity`：cookie 檢查用的就是上面比對的 provider。
- 不需要對齊，所以沒有寫對齊與回復的步驟。若 PR Laysi/trustiot-v2#962（`includeRequestHeadersInCheck` 再加兩個標頭）先合併，這個比對會在 `includeRequestHeadersInCheck` 失敗，要先照 runbook「換 chart 版本」第 2 步以 `platform.ts` 對齊 istiod，再打開 `web`。

### 3. 打開 web 改變的物件

以 HEAD 的 chart（與 `v0.0.0-rc.13` 相同）渲染展示叢集的 values，比對打開與不打開 `web`：

| 物件 | 變更 |
| --- | --- |
| Deployment、Service、ServiceAccount、NetworkPolicy、AuthorizationPolicy `trustiot-web` | 新增；Deployment 1 個副本，requests 32Mi、limits 256Mi，`imagePullSecrets` 是 `ghcr-pull`，只有入口 gateway 的身分連得到它 |
| HTTPRoute `trustiot-ingress-app` | 多一條 `PathPrefix /` 到 `trustiot-web`，移除 `cookie` 與 `x-internal-identity`（含底線寫法） |
| AuthorizationPolicy `trustiot-ingress-cookie-check` | 改成 SPA 的形式：app 主機名稱上只檢查 `/api`、`/auth`、它們底下與 `/internal*`（[chart 的 README](../../deploy/chart/README.md)「入口 gateway」） |
| NetworkPolicy、AuthorizationPolicy `trustiot-otel-collector`，RoleBinding `trustiot-migrate-status` | 放行 `web` 送遙測、讓 `web` 的 init container 讀 migration Job 的狀態 |

migration Job 與其他每個 Deployment 都沒有變（Job 不重跑，其他服務不重啟）。`bun test deploy/flux` 也以展示叢集的 values 確認 `trustiot-web` 的 Deployment 與 app 主機名稱上唯一一條到 `web` 的路由。
