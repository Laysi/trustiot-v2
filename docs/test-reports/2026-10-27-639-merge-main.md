# ingest：合併 main 的彙總表與可查期間之後的 ClickHouse ID 遷移

對應 Laysi/trustiot-v2#639。

這份報告記錄 2026-10-27 在合併 main 之後的分支上重跑的結果。main 在這段期間加了彙總表（`0010_telemetry_rollups.sql`）與可查期間（`0011_queryable_period.sql`），所以本分支的 migration 改名為 `0012_gateway_stream_ids.sql`。合併前的結果見 `2026-10-24-639-clickhouse-ids.md`（當時檔名是 `0010`）。

## 環境

- 程式碼：分支 `feat/639-ingest-clickhouse-ids` 的 `63fc5ad4`，依序合併了 main 的 `304de010`（`fd8ebdb2`）與 `509c3f1f`。
- 建置主機（x86_64 Linux）：Rust 的 fmt、clippy 與測試。容器測試起暫時的 ClickHouse（映像以 digest 釘選，伺服器版本 26.8）與 Postgres；設定 `CI=1`，所以沒有容器執行環境時會失敗而不是略過。每次在工作樹的快照上執行。

## 指令

```sh
cargo fmt --all --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo run --locked -q -p openapi -- --check
CI=1 cargo test --locked --no-fail-fast -p ingest -p migrate -p telemetry-query -p sql-check -p assistant -p lab-dataset -p repo-check

# 輸出存成下方的資料檔
CI=1 cargo test --locked -q -p ingest --test migrations -- --nocapture
CI=1 cargo test --locked -q -p telemetry-query --test queryable_period -- --nocapture
```

## 結果

| 指令 | 結果 |
| --- | --- |
| `cargo fmt --all --check` | exit 0 |
| `cargo clippy ... --workspace --all-targets -- -D warnings` | exit 0 |
| `cargo run -p openapi -- --check` | `api/openapi.json is up to date`，exit 0 |
| `cargo test ... -p ingest -p migrate -p telemetry-query -p sql-check -p assistant -p lab-dataset -p repo-check` | 65 個測試執行檔，498 passed、0 failed、1 ignored（既有的 doc-test），exit 0 at 22:18:04 (build host) |
| `cargo test -p ingest --test migrations` | 7 passed，exit 0 |
| `cargo test -p telemetry-query --test queryable_period` | 1 passed，exit 0 at 22:20:24 (build host) |

資料檔在 `data/2026-10-27-639-merge-main/`：

- [`migrations.txt`](data/2026-10-27-639-merge-main/migrations.txt)：`0001`–`0012` 套用後的結構快照，全新與升級（先套 `0001`–`0011`、寫入舊形狀的資料，再套 `0012`）兩台伺服器相同。重點：
  - `telemetry.gateway_id`、`stream_id` 與 `stream_commits` 的兩欄是 `String`；`batch_commits` 維持原狀，`trustiot_ingest` 對它已沒有權限，只對 `stream_commits`、`telemetry`、兩張彙總表有 `SELECT`、`INSERT`。
  - row policy 清單含 `stream_commits` 的 `deny_by_default`、`service_all_rows`，以及 `0011` 在 `tenant_telemetry` 上的 `tenant_isolation`（含 `SQL_queryable_raw_days` 的期間條件），表示重建 view 之後 policy 仍掛在上面。
  - `legacy reading after the upgrade` 與 `through the tenant view`：升級前寫入的 UUID 讀值以文字讀回，經租戶 view 的型別是 `String`。測試同時斷言：帶 7 天可查期間的租戶帳號在套用 `0012` 前後經 view 都只讀到現在的那一筆，30 天前的那一筆（ingest 帳號讀得到）不會出現。
- [`queryable-period.txt`](data/2026-10-27-639-merge-main/queryable-period.txt)：`queryable_period` 的全部探測。測試先確認 `tenant_telemetry` 是 `0012` 重建的 view（`gateway_id` 是 `String`），之後原本的探測照樣通過：只問期間外的原始資料得到 0 行，想繞過期間的寫法（`since 1970`、`OR true` 等）被拒，或只讀到期間內的 12 行；沒有期間設定時 `UNKNOWN_SETTING`、方案變更後窗口跟著變（`windows 365 12 12`、`7 3 1`、`7 3 3`）。

## 結論

- 新 migration 在全新與「已套用 `0001`–`0011`」兩種資料庫上套用兩次都成功、結果相同：通過（`id_migration_gives_one_schema_on_fresh_and_upgraded_servers`）。
- 重建後的 `tenant_telemetry` 仍依可查期間過濾：通過（上述升級測試與 `queryable_period`）。
- `trustiot_ingest` 的權限、row policy、保存期限管理的四張表（完成表是 `stream_commits`）：通過（`ingest` 的 `clickhouse`、`migrate` 的 `clickhouse`）。
- 其他驗收條件的證據沿用 `2026-10-24-639-clickhouse-ids.md`，本次在合併後的樹上重跑相關 crate 全部通過。
- 沒有跑：`bun test deploy/chart`（chart 沒有變更）、`bun test scripts`（`scripts/` 只改了 README 與一行註解）。
