## 指令

全新 clone 的完整流程（`fresh.sh` 與 `leak.sh` 的內容，只用 README 記載的指令）：

```sh
git clone --branch feat/71-local-dev-up <repo> fresh-clone && cd fresh-clone
proto install
CARGO_BUILD_JOBS=2 bun scripts/dev.ts up       # 一個指令；第一次含 Rust 編譯
bun scripts/dev.ts status
ss -tlnp
bun scripts/dev.ts seed                        # 執行兩次，確認可重複
bun scripts/dev.ts down                        # 資料磁碟區保留
bun scripts/dev.ts up                          # 在既有資料上換新密碼
bun scripts/dev.ts seed
bun scripts/dev.ts purge
```

單元測試與端對端測試：

```sh
bun test scripts
TRUSTIOT_DEV_E2E=1 bun test scripts/tests/e2e.test.ts
```

觀察與限制：

- 預設 Postgres 映像的 `pg_hba.conf` 信任 127.0.0.1；實測 rootless 轉送進來的連線不是來自容器內的 loopback（本機埠要求 SCRAM），但這是轉送程式的行為而非設定，所以腳本改用自己的 `pg_hba.conf`：只信任容器內的 unix socket，其餘位址一律 SCRAM。
- 資料磁碟區在 `down` 後保留，舊密碼仍存在資料裡；`up` 以 `ALTER ROLE` 在容器內的 socket 上換成新密碼（本地 socket 的 trust 只有容器內的行程能用）。
- 檢查 Postgres 密碼時不能用容器內的 `127.0.0.1`（trust），改連容器自己的網路位址 `postgres`；第一版這樣寫時，「錯誤密碼被拒」檢查就失敗了，是實測才發現的。
- 與正式環境的差異（沒有 Istio、NetworkPolicy、TLS、dynsec 等）列在 `scripts/README.md`。
- 沒有測 k3d 與 Helm 路徑：本 issue 刻意不在工作站跑 Kubernetes，決定與取捨見 `scripts/README.md`「機制的決定」。
