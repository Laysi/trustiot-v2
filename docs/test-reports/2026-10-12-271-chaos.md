# outbox 混沌 harness 在新連線方式下的重跑（Laysi/trustiot-v2#271）

Laysi/trustiot-v2#271 讓 `outbox::Consumer` 依決策 29 連線：以消費端服務的平台角色在唯讀交易讀產生端的 `outbox_event`，再以服務角色在事件的租戶交易處理每個事件（[實作與測試報告](2026-10-11-271-outbox-consumer-tenancy.md)）。該報告的驗收條件 3「既有的有序、冪等遞送測試全部仍通過，包含 Laysi/trustiot-v2#54 獨立驗證新增的測試」，當時只以 `cargo test` 與交易邊界的推論代替 #54 的混沌 harness（[2026-10-11-54-verify](2026-10-11-54-verify.md)，harness 附在其 data 目錄），並記為待測。本報告補上這項證據：把 harness 改寫到新的連線方式，在 main `b4aae40` 上跑與 #54 相同長度的混沌，檢查項目一個不少，再加上「每個事件在自己的租戶處理」的檢查。

本次只驗證、不修改產品程式碼：分支相對 main 只多了 `docs/` 下的報告與 data。

## 2. 指令

從 repo 根目錄（腳本與原始碼都在 [data 目錄](data/2026-10-12-271-chaos/)，副檔名 `.txt` 是為了不讓 cargo 與 bun 撿到；[`run.sh.txt`](data/2026-10-12-271-chaos/run.sh.txt) 把它們複製成 `chaos.rs`／`*.ts` 並執行）：

```
S=<共用檢查佇列的入口腳本 rcheck.sh>
R=docs/test-reports/data/2026-10-12-271-chaos/run.sh.txt

bash $S 271c "bash $R chaos smoke 3 1 8"          # 煙霧測試：3 分鐘，seed 1，排空上限 8 分鐘
bash $S 271c "bash $R grants grants3"             # 權限矩陣
bash $S 271c "bash $R stall stall1 1"             # 長交易使讀取上限停滯的探針
bash $S 271c "bash $R chaos runA 20 271001 15"    # 混沌 run A：20 分鐘，seed 271001，排空上限 15 分鐘
bash $S 271c "bash $R chaos runB 20 271002 15"    # 混沌 run B：20 分鐘，seed 271002
```

`run.sh.txt` 內：`cargo build -p outbox --locked --example chaos`，再 `bun …/chaos.ts <binary> <outdir> <分鐘> <seed> <排空分鐘>`。每個腳本自己起、自己刪 Postgres 容器。（程式碼審查後，`run.sh.txt` 加了模式與執行名稱的檢查、建置失敗即停止、不覆蓋已存在的 `chaos.rs` 並在結束時移除複製出來的檔案；跑過的行為不變，之後再以 `grants` 模式重跑一次確認仍可執行，也確認 `../x` 這種名稱被拒絕。）主機上的執行目錄以 [`collect.sh.txt`](data/2026-10-12-271-chaos/collect.sh.txt) 精簡後放進 data（原始目錄有數百個行程日誌與約 1 MB 的 Postgres 日誌，並含該次執行的隨機密碼與 TLS 私鑰，不複製）。

seed 的作用：協調器的故障排程（殺哪個行程、間隔、重啟延遲、連線終止、長交易的長度）由 seed 決定，每個行程的亂數（產生端的交易形狀、handler 的失敗注入）也由 seed 衍生。行程的實際排程與 Postgres 的時序不是決定性的，所以同一個 seed 不會重現同一串事件，seed 是為了記錄與大致重現故障的組成。

## 3. harness 的改寫

除了連線方式，原 harness 的所有行為與檢查保留。改動：

| 原 harness（#54） | 新連線方式 |
| --- | --- |
| 一個非 TLS 的 `producer_role`、一個 `consumer_role`，`search_path` 設在連線 | 四個角色，TLS `verify-full`，service-kit pool；角色的 `search_path` 用 `ALTER ROLE`，如 outbox README |
| 產生端在一個 pool 裡寫事件 | 租戶事件：`BackgroundTenantDb::begin(<租戶>)` 的交易，`publish(tx.transaction(), …, Some(租戶))`；全平台事件（約 6% 的交易）：`PlatformDb::begin` 的交易，`publish(…, None)`。一筆交易只屬一個租戶（可有 1–3 個該租戶的聚合）。`ledger` 另記租戶，與事件同交易寫入 |
| `Consumer::new(pool, config, handler)` | `Consumer::new(&PlatformDb, BackgroundTenantDb, config, handler)`；`c1` 用 `run`，`c2`、`c3` 用 `poll_once` 迴圈，同原本 |
| handler 寫 `handled_log`、`aggregate_state`、`violations` | 同原本；另記 `setting_tenant`（handler 執行時資料庫連線的 `trustiot.tenant_id`）與 `delivery_tenant`；寫 `tenant_rows`（RLS 表，每個租戶事件一列）；約 5% 的事件探測：在 savepoint 裡寫另一個租戶的列（必須被 42501 擋下）、讀 `tenant_rows` 不得看到別的租戶的列（全平台事件不得看到任何租戶的列）。毒事件、寫入前後的暫時性失敗不變，handler 的所有寫入（含 `tenant_rows`）在失敗時必須一併回滾 |
| `replay_from` 用消費端 pool | 用 `BackgroundTenantDb::begin_without_tenant`（消費端服務角色、沒有租戶；訂閱與 `aggregate_state` 不是租戶資料） |
| 失敗注入的亂數以事件 ID 為種子（原本還混入時間，每次不同） | 種子加上嘗試次數，同一事件每次重試的注入結果不同，不會因確定性而永遠失敗 |
| 故障：SIGKILL 行程、`pg_terminate_backend`、Postgres 優雅重啟與 SIGKILL 崩潰、長寫入交易、跨崩潰的 prepared transaction、兩種重播 | 同原本，排程比例相同；`podman` 改 `docker`；終止連線的對象改為四個角色 |
| `verify` 的檢查 | 全部保留（見第 4 節），新增租戶檢查 |

### 4.4 權限矩陣與停滯探針

- [`grants-output.txt`](data/2026-10-12-271-chaos/grants-output.txt)：40／40 符合預期，錯誤都是 SQLSTATE 42501。消費端平台角色只讀得到產生端的 `outbox_event`（跨租戶，`consumer_read`）：讀不到其他資料表、`outbox_aggregate`、別的 schema，不能 INSERT／UPDATE／DELETE／TRUNCATE／`FOR UPDATE`、不能建表；消費端服務角色碰不到產生端 schema，只能寫自己 schema 的表，寫另一個租戶的 `tenant_rows` 被 RLS 擋下；產生端服務角色只能 INSERT 目前租戶的事件（別的租戶與全平台事件被擋）、不能 SELECT、UPDATE、DELETE；產生端平台角色只能 INSERT 全平台事件，不能 SELECT。
  - 觀察（不是缺陷，已記在腳本註解）：產生端平台角色若自己先 `set_config('trustiot.tenant_id', …, true)`，也能寫該租戶的事件，因為範本的 `tenant_isolation` policy 對所有角色生效；平台角色本來就是跨租戶的角色，`PlatformDb` 不會設租戶，在程式碼裡設租戶的 SQL 由 `tools/sql-check` 擋。
- [`stall-timeline.txt`](data/2026-10-12-271-chaos/stall-timeline.txt)、[`stall.csv`](data/2026-10-12-271-chaos/stall.csv)：一個產生端、兩個副本追上後開 30 秒的長寫入交易（`other` schema，持有交易 ID）：處理數固定在 173，事件 197 → 531、lag 20 → 354；交易結束後恢復（約 15 秒內 570）。接著 30 秒的長唯讀交易（無交易 ID）：處理持續增加（663 → 1 084），lag 120 → 0，沒有停滯。最後 `verify` 為 `failures: []`（1 188 個事件、43 個死信、1 145 個處理，租戶檢查與探測 58／58 全過；[`stall-verify.json`](data/2026-10-12-271-chaos/stall-verify.json)）。這與 README 的說法一致：長寫入交易會暫停所有訂閱，唯讀交易不會；也就是改用平台角色讀取與租戶交易處理後，讀取上限的行為沒有變。#54 的 `stall.ts` 取樣的 `phase` 標記在交易結束後仍沿用，這次的版本只在交易開著時取樣。

另有一次煙霧測試（3 分鐘、seed 1，6 337 個事件，`failures: []`；[`smoke-verify.json`](data/2026-10-12-271-chaos/smoke-verify.json)），用來確認 harness 本身；第一次嘗試因 bun 在執行目錄下找不到 proto 釘住的版本而失敗（改成從 repo 根目錄執行），harness 的檢查沒有因此改動。

## 5. 結論

| 驗收條件（Laysi/trustiot-v2#271 第 3 條） | 結果 | 證據 |
| --- | --- | --- |
| 既有的有序、冪等遞送測試全部仍通過，包含 #54 獨立驗證新增的測試 | 通過 | `cargo test -p outbox`（含 crash、delivery、tenancy 重複 3 次）見 [2026-10-11-271-outbox-consumer-tenancy](2026-10-11-271-outbox-consumer-tenancy.md)；#54 的混沌 harness 改寫到新連線方式（TLS `verify-full`、四個角色、RLS 範本、`Consumer::new(&PlatformDb, BackgroundTenantDb, …)`、多個租戶加全平台事件）後，在 main `b4aae40` 上跑兩次 20 分鐘的混沌（seed 271001、271002，共 89 299 個事件、229 加 249 次 SIGKILL、各 3 次 Postgres 崩潰與 2 次重啟、各 20 個長交易與 1 個跨崩潰的 prepared transaction、各 1 次兩種重播）：順序違反 0、遺失 0、重複處理 0、租戶不符 0，`verify` 全過 |

沒有發現產品程式碼的缺陷。原 harness 的每一項檢查都帶到新連線方式，沒有放寬任何一項，也沒有無法帶過來的項目。

## 6. 未涵蓋
