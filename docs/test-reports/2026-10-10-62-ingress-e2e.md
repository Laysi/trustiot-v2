### 過程中修正的事

- 身分服務停機時 503 的時間一開始量到約 1,040 ms：那是量到連線關閉為止，Envoy 對自己產生的回應延後最多 1 秒才關連線。改量第一個位元組後是一般的來回時間，表中數字都是這個。
- 例外路徑放在沒有路由的主機時，入口回 404 而不是 401，測試的預期依此修正（不呼叫身分服務、不到後端，同樣安全）。
- 透過 Cloudflare 的維運 SSH 偶爾斷線，會中斷 `ssh -L`；測試程式改為在通道程序結束時重開通道，並只重送那一個請求。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 沒有 cookie 回 401；身分服務停機時需要 cookie 的路徑在逾時內回 503、例外路徑照常（k3d 測試） | 通過。測試在 lab 的 k3s 執行（協調者指示，見「環境」）；沒有 cookie 401；停機時 503 立即回來，延遲時 0.5 秒逾時後回 503，`/certs/renew`、`/mqtt` 照常 200 |
| 後端收到的 x-forwarded-proto 為 https（測試） | 通過。需要 cookie 的路徑與例外路徑都是 `https`，用戶端帶 `http` 也被改寫 |
| 例外路徑帶偽造身分標頭時後端看到 0 個（測試） | 通過。四個例外路徑都是 0 個 |
| 以 edge PoC 的繞過寫法為底補齊至少 11 種寫成自動測試，清單放在測試檔，全部到不了需要 cookie 的後端 | 通過。28 種，清單在 `ingress.e2e.ts` 的 `BYPASS_CASES`，兩種型態全部擋下 |
| 兩份 values 的 helm template 都通過 kubeconform | 通過。Kubernetes 1.30.0 與 1.36.0，服務關閉與開啟時都有效 |

待測：

- 地端入口以預設的 LoadBalancer 在客戶網路開 443：只做了 render 與 kubeconform。lab 主機不對外開產品埠，所以 lab 上改用 ClusterIP 驗證 443 的 HTTPS listener 與 TLS 終止；客戶網路的實測等地端環境。
- OpenShift（`global.platform=openshift`、OpenShift Service Mesh 3、restricted-v2 SCC 指派的 UID）：目前沒有 OpenShift 環境。
- 接上真身分服務（Laysi/trustiot-v2#61）的端到端驗證：Laysi/trustiot-v2#77。
- 經 Cloudflare Tunnel 的完整路徑：主機安裝與 cloudflared 屬於 Laysi/trustiot-v2#64；本次從 lab 主機直連 ClusterIP，來源位址與 cloudflared 相同。
