# 平台管理者設定租戶成員的角色

Laysi/trustiot-v2#583：`PUT /api/identity/v1/platform/tenants/{tenant_id}/members`，成員資格與 `identity.member_role_changed` 事件在路徑租戶的 RLS 交易裡一起寫入。

## 環境

- 開發者工作站（x86_64 Linux）與另一台 x86_64 Linux 建置主機，容器用 podman。
- 工具版本依 `.prototools`：Rust 1.99.0、Bun 1.4.2。
- 分支 `feat/583-platform-member-roles`：先在 commit `1867c486` 上測，再合併 main `7371f15b` 後重測。
- Postgres 用 `crates/testkit` 的 TLS Postgres，schema 由 migration Job 的程式套用（`testkit::product`）。這次的 migration 是 `0005_member_roles.sql`。
- 沒有用到 Kubernetes、lab 或展示環境。

`identity` 測試的逐項結果見 [identity-tests.txt](data/2026-10-23-583-member-roles/identity-tests.txt)。

`tests/members.rs` 用真的服務 binary 跑過以下步驟：

1. **新成員**：成員原本沒有授權，下一個經 ext_authz 的 token 的 `tenant` 是 null。平台管理者送出 PUT（email 有大寫和前後空白），回 201，`previous_role` 是 null；成員的下一個 token 帶 `viewer`。
2. **改角色**：改成 `editor`，回 200，`previous_role` 是 `viewer`；下一個 token 帶 `editor`。
3. **角色沒變**：再送一次同樣的角色，回 200；成員資格、使用者與 outbox 的筆數都沒有變。
4. **事件**：outbox 有兩筆 `identity.member_role_changed`：
   - aggregate 是 `membership`，aggregate ID 是 `<租戶>:<使用者>`，序號 1、2；
   - 信封的租戶是成員資格所屬的租戶，`actor` 是平台管理者；
   - payload 是 `{user_id, previous_role, role}`，沒有 email。
5. **操作紀錄**：租戶 A 的 `admin` 以 `GET /api/identity/v1/event-log` 讀到這兩筆，新的在前，回應裡沒有 email；租戶 B 的操作紀錄沒有這兩筆。
6. **403**：以下 token 一律回 403，成員資格、使用者與 outbox 都不變，成員的角色仍是 `editor`：
   - token：租戶 A 的 `admin`、租戶 B 的 `admin`、沒有租戶的使用者、平台管理者經 assistant 換發的 token、平台管理者經 assets 換發的 token；
   - 請求：租戶 A、租戶 B、不存在的租戶、不是 UUID 的租戶 ID 配 `text/plain`、超過 4096 位元組的 body。
7. **401**：沒有 token，或平台管理者的 token 是給 assets 的，都回 401。
8. **404 與 422**：
   - 不存在的租戶回 404；
   - 沒有人用的 email 回 422 `/email` `member.email_unknown`，也沒有建立使用者；
   - 壞的 email 和壞的角色（`unrecognized`、`Admin`、`platform_admin`、空字串）回 422，兩個欄位都列出。
9. **400**：壞的租戶 ID；`Content-Type` 是空的、`text/plain`、表單或 multipart；不是 JSON 物件或缺欄位的 body；超過 4096 位元組的 body。這些都不寫入。
10. **並發**：兩個請求同時替同一個使用者在租戶 B 建立成員資格。狀態碼一個 201、一個 200，兩筆事件的序號接續，後一筆的 `previous_role` 是前一筆的 `role`，最後的授權等於最後一筆事件的角色。
11. **資料庫授權**：服務角色在租戶 A 的交易裡，下列操作都以 42501 被拒：
    - 新增租戶 B 的成員資格；
    - 新增時帶 `created_at`；
    - 修改 `tenant_id`、`user_id` 或 `created_at`；
    - `DELETE`、`TRUNCATE`。

    修改租戶 B 那一列的 `tenant_role` 影響 0 列。
12. **日誌**：有 `set a member's role` 和 `refused to set a member's role`，也有成員的使用者 ID，沒有任何 email（不分大小寫比對）。

另外，`delegation::tests::role_changes_show_in_the_next_token_and_a_removed_member_is_refused` 和 `tests/ext_authz.rs` 的 `role_changes_apply_to_the_next_request` 都通過。這兩個測試證明 ext_authz 與 run 委派每次都從資料庫重讀角色，沒有快取。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 平台管理者設定角色之後，該使用者下一個經 ext_authz 的請求帶新角色 | 通過（步驟 1、2）。已經簽出的 token 最多還帶舊角色 60 秒，`services/identity/README.md`「成員」有寫明 |
| 租戶 admin、沒有租戶的使用者、`act` token 都回 403，成員資格與事件紀錄都不變 | 通過（步驟 6） |
| 不存在的租戶或 email 回 404 或 422，不寫入，也不建立使用者 | 通過（步驟 8）：租戶回 404，email 回 422 |
| 租戶的操作紀錄有 `identity.member_role_changed`，含原本的角色、新角色與 actor | 通過（步驟 4、5） |
| 跨租戶測試涵蓋新端點，`openapi --check` 與 `api:check` 通過 | 通過。`tests/cross_tenant.rs` 以 `exempt_endpoint` 宣告這個端點並寫明理由：testkit 的正向對照是租戶 admin，而這個端點只給平台管理者。隔離由 `tests/members.rs` 測（步驟 6、11），cross_tenant 的資料庫探測也照常攻擊新的授權 |

待測（進階驗證，延後到 P2 issue）：經真實入口（Istio 與 ext_authz 的 cookie 路由）送 PUT 的 nightly smoke，以及在展示環境照 runbook 實際跑一次。
