## 指令

祕密的交付方式：在主機上產生 RSA-4096 金鑰，在 Cloudflare MCP 的沙箱內以 RSA-OAEP（SHA-256）加密 tunnel token，主機解密後直接以管線交給安裝程式；token 不出現在指令列、輸出或檔案。

```sh
# 工作站：建置並核對
bun install --cwd deploy/host --frozen-lockfile
bun run --cwd deploy/host typecheck
bun run --cwd deploy/host test
bun run --cwd deploy/host build
sha256sum --check --ignore-missing SHA256SUMS            # 在主機上

# 主機：交付 token 並安裝（VM 用預設 unit，lab 另加 --unit cloudflared-e2e-64 --skip-k3s）
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out handoff.key
base64 -d token.enc.b64 | openssl pkeyutl -decrypt -inkey handoff.key \
  -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256 \
  | sudo ./trustiot-host-install-x86_64 --token-stdin

# 重跑（不帶 token）與驗收
sudo ./trustiot-host-install-x86_64
sudo ss -tlnp; sudo ss -ulnp
sudo systemd-analyze security cloudflared

# lab：經 tunnel 的健康檢查，每 0.5 秒一次
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' https://trustiot-e2e-64-8ae851.laysi.io/healthz
# lab：token 輪替（Cloudflare API，在 MCP 沙箱內執行）
#   PATCH /accounts/{account}/cfd_tunnel/{tunnel}  {"tunnel_secret": "<32 bytes 隨機值的 base64>"}
#   GET   /accounts/{account}/cfd_tunnel/{tunnel}/token  → RSA-OAEP 加密後交給主機，同上管線
# 維運 SSH 主機名稱，沒有通過 Access（唯讀）
curl -sI https://trustiot-mac-m1-ssh.laysi.io/
```

### 3. 乾淨主機測到的問題與修正

第一次在 VM 上跑（[vm-run0-install.log](data/2026-10-11-64-saas-host/vm-run0-install.log)）在 k3s 之後失敗：`the k3s cluster does not use the networks the firewall trusts … its networks could not be read`。新 node 在建立後 1 秒就 Ready，controller manager 還沒指派 `spec.podCIDRs`，安裝程式把空值當成錯誤。修正：等待 node Ready 時一併等 Pod 網段出現才檢查（測試 `a new node that is Ready before its pod network is assigned is waited for`）。修正後在全新的 VM（重建 overlay 磁碟）上重跑，即第 1 節的結果。

同一次也量到 firewalld 檢查很慢：每個 zone 原本要呼叫 5 次 `firewall-cmd`（`--info-zone`、`--list-services`、`--list-ports`、`--list-forward-ports`、`--list-rich-rules`），`firewall-offline-cmd` 在 VM 上每次約 3.8 秒。改為每個 zone 與 policy 只呼叫一次 `--info-zone`/`--info-policy` 並解析所有欄位；輸出缺少任何預期欄位時停下，不當成「沒開」（測試 `parseFirewallInfo` 三項、`each zone and policy is read with one --info call`、`a zone description in an unknown layout stops the run`）。解析的格式取自這台 VM 上 firewalld 2.4.4 的實際輸出（`forward-ports` 與 `rich rules` 的項目在下一行，以 tab 縮排）。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 在乾淨主機執行腳本後，`ss -tlnp` 不顯示任何 80/443 監聽 | **通過**（VM：全新的 Fedora Cloud 44 x86_64，完整安裝後 TCP 與 UDP 都沒有 80、443，重開機後亦同）。範圍：VM 用 user-mode 網路、沒有公網 IP，與正式 SaaS 主機相同的是「只連出」；aarch64 的乾淨主機沒有測（aarch64 只測了既有主機 lab） |
| `systemd-analyze security cloudflared` 分數 ≤ 2.0 | **通過**：VM 與 lab 都是 1.1 |
| 經 tunnel 的健康檢查回 200，維運 SSH 只能經 Access 認證帳號使用 | **通過**：lab 經 tunnel `/healthz` 200；維運 SSH 主機名稱未通過 Access 時 302 到登入頁，政策只放行 laysi.io 帳號與指定 service token。正式 SaaS 主機的 SSH 主機名稱與 Access 應用程式要在主機上線時依 runbook 第 2 步建立，本次沒有建立新的 Access 應用程式 |
| runbook 在 `deploy/host/README.md`，含安裝、更新 cloudflared、輪替 token | **通過**：三項都有，輪替步驟在 lab 實測；更新 cloudflared 的指令（`dnf upgrade --repo=cloudflared-stable`）沒有實際執行升級，`dnf reinstall` 換套件與重啟中斷已實測 |

待測：正式 SaaS 主機（還沒有）上的完整流程，包括入口 chart、產品主機名稱與新的 SSH Access 應用程式；aarch64 的乾淨主機。
