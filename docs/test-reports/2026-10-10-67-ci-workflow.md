- 合併 main 之後：PR Laysi/trustiot-v2#240 開出後，main 加入 Laysi/trustiot-v2#71 的本地開發環境腳本（`4f9db40`）。PR 已開，rebase 要 force push，所以把 main 合併進分支（merge commit `3bc4e48`），所有檢查在 commit `9b9022a` 重跑，見「合併 main 之後（commit `9b9022a`）」。

- 讀取 GitHub 結果的方式：agent 可用的 token 沒有讀取 check run 與 Actions 紀錄的權限（check-runs API 回 HTTP 403），所以讀 PR 的 `mergeable_state`。repo 沒有必要檢查，`clean` 表示所有檢查都已通過（或根本沒有檢查），`unstable` 表示有檢查還在跑或已失敗；超過 job 的 `timeout-minutes` 仍是 `unstable` 就是失敗。校正：Laysi/trustiot-v2#228 沒有 workflow，立即 `clean`；Laysi/trustiot-v2#230 有一個會通過的 job，一分鐘內由 `unstable` 變 `clean`。
- 本 issue 不需要 lab 端到端測試。

### service-kit 收到 SIGTERM 正常收尾卻以 1 結束

把 service-kit（Laysi/trustiot-v2#51）納入 CI 時發現：設 `CI=true` 跑 service-kit 的測試，檢查 SIGTERM 後 exit code 為 0 的整合測試（lifecycle、errors、otlp）在忙碌的本機 10 輪有 5 輪失敗。原因是 `serve()` 等待停止訊號與 server task 的 `tokio::select!` 沒有偏向：停止後 axum 的 server 在沒有連線時可能先結束，兩個分支同時就緒時隨機挑一個，挑到 server 就記一筆 `server stopped unexpectedly`（outcome `Ok(Ok(()))`）並以 1 結束。修正（commit `e8acc6e`）讓 select 先看停止訊號；server 的結果仍留在 join handle，後面的 drain 照樣把非正常結束轉成 exit code 1。

| 重現（兩個範例服務同時收 SIGTERM，綁在同一顆 CPU） | 非 0 結束 |
| --- | --- |
| 修正前 | 120 次中 42 次，全部是 `server stopped unexpectedly` |
| 修正後 | 120 次中 0 次，再跑 300 次也是 0 次 |
| 修正後重跑上述三個測試檔 10 輪（預設 feature 與關閉預設 feature 各一次） | 0 輪失敗 |

細節與重現方式：[service-kit-shutdown-race.txt](data/2026-10-10-67-ci-workflow/service-kit-shutdown-race.txt)。這是 Laysi/trustiot-v2#51 的程式，為了讓 CI 穩定只做最小修正（select 加 `biased;` 與說明註解），沒有另加測試；能穩定重現這個競態的測試留給 service-kit 後續處理。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| PR 與推到 main 都會觸發；fmt、clippy、test、cargo-deny、gitleaks，以及 workflow 權限與 SHA 檢查全綠；其餘步驟寫明由哪張 issue 加入 | 通過。觸發條件為 `pull_request` 與推到 `main`；PR 觸發已在暫時 PR 上實際看到（Laysi/trustiot-v2#230、Laysi/trustiot-v2#232），推到 main 的觸發要合併後才看得到，合併後確認 main 上的那次執行。各項檢查在本機全部通過，在 GitHub 上逐 job 驗證過（gitleaks、workflow-policy、Rust 安裝），整份 CI 的結果見本 issue 的 PR。之後加入的步驟寫在 ci.yml 開頭與 `docs/architecture/ci-release.md`：整合測試與 `cargo sqlx prepare --check` 由 Laysi/trustiot-v2#60 加入（負向測試框架為 Laysi/trustiot-v2#56）、SQL 字串拼接檢查 Laysi/trustiot-v2#53、OpenAPI 比對 Laysi/trustiot-v2#55、前端 Laysi/trustiot-v2#123 |
| 每個 job 明列 permissions；所有第三方 action 都以 SHA 引用（以腳本檢查 workflow 檔） | 通過。`scripts/ci/check-workflows.ts` 檢查每個 workflow 與 `.github/actions/` 下的 action：23 個單元測試通過，fixture 的 9 項違規全數報出，repo 本身沒有違規；這個檢查就是 CI 的 `workflow-policy` job，在 GitHub 上通過（Laysi/trustiot-v2#236） |
| 放一個含假金鑰的測試分支時 gitleaks 失敗（驗證過一次並記錄在 PR） | 通過。Laysi/trustiot-v2#227（含假金鑰）失敗、Laysi/trustiot-v2#235（相同 job、沒有假金鑰）通過；本機以相同指令重現命中。記錄在本報告、[ci-runs.txt](data/2026-10-10-67-ci-workflow/ci-runs.txt) 與本 issue 的 PR |

範圍內其他項目：

- sqlx 離線檢查：rust job 全程 `SQLX_OFFLINE=true`。`.sqlx/` 與 schema 的一致性比對需要資料庫，由 Laysi/trustiot-v2#60 加入。
- service-kit：`cargo test --workspace` 包含它的 `cargo tree` 相依隔離檢查與容器測試；關閉預設 feature 另跑 clippy 與測試。GitHub 設 `CI=true`，沒有可用的容器執行環境時容器測試失敗而不是略過，所以 rust job 通過就表示它們真的跑過。
- 本地開發環境腳本（Laysi/trustiot-v2#71）：`workflow-policy` 對整個 `scripts/` 做型別檢查與測試；它的端對端測試要以 podman 起整套環境並編譯服務，只在設定 `TRUSTIOT_DEV_E2E=1` 時執行，不在 CI 執行。
- cargo-deny 擋下 BUSL-1.1 授權與漏洞公告（負向案例）；aarch64 交叉編譯步驟已驗證；helm lint 與兩份 values 的 kubeconform 由 `helm` job 執行。
- fork 來的 PR 拿不到 secret：ci.yml 不用 secret、token 只有 `contents: read`、checkout 設 `persist-credentials: false`，`pull_request_target` 與 `workflow_run` 由政策檢查擋下。待確認：私有庫 Actions 設定中「Send write tokens to workflows from fork pull requests」與「Send secrets to workflows from fork pull requests」是否維持關閉（GitHub 預設值）。token 沒有讀取這項設定的權限，需由管理者在 GitHub 設定頁確認。
- 必要檢查清單（`rust`、`cargo-deny`、`helm`、`gitleaks`、`workflow-policy`）寫在 `docs/architecture/ci-release.md`；Free 方案不能設分支保護，合併前由流程確認。
