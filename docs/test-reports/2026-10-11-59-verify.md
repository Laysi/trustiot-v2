# Laysi/trustiot-v2#59 獨立驗證：ClickHouse 窄表、row policy 租戶隔離、profile 與 quota

對應 issue：`Laysi/trustiot-v2#59`（PR #253 合併）。驗證者不是實作者，以租戶 A 的帳號對真的 ClickHouse 26.8 攻擊，範圍超出實作者的 49 項攻擊。

## 目的

1. 逐條驗收條件取得獨立證據。
2. 找實作者測試沒涵蓋的繞過：以租戶 A 讀取或推測租戶 B 的資料、提權、繞過 quota、寫入或改 schema。
3. 確認服務帳號改不了 schema，全新帳號預設拒絕。

### 2. 設定、角色與 session 的繞過（`p1-settings`、`p2-subquery-settings`、`p3-profile`，80 項）

全部失敗（A 仍只讀到自己的 3 列）：

- 查詢層 `SETTINGS SQL_tenant_id = B`、`readonly = 0`、`readonly = 2`、兩者併用：`READONLY`。
- `SET SQL_tenant_id`（有無 session）、`SET readonly = 0`：`READONLY`。
- `SET ROLE trustiot_ingest`：`SET_NON_GRANTED_ROLE`；`SET ROLE ALL`：仍只讀到 A；`SET ROLE NONE`：`ACCESS_DENIED`，之後 `SET SQL_tenant_id` 與 `SETTINGS readonly = 0` 仍是 `READONLY`，`getSetting('readonly')` 仍是 1，`max_threads` 仍是 2。
- URL 參數：`SQL_tenant_id`、`readonly=0`、`role=trustiot_ingest`（`SET_NON_GRANTED_ROLE`）、`user=tenant_b`（與 header 認證併用被拒）、`param_t={B}`（0 列）、`quota_key`（無效，見第 5 節）。
- `ALTER USER`（自己的設定、profile、密碼）、`GRANT trustiot_ingest TO` 自己、`CREATE TEMPORARY TABLE`、`EXECUTE AS ingest|tenant_b|trustiot_admin`：`ACCESS_DENIED`。
- 另建一個含 `readonly = 0`、`max_threads = 64`、`SQL_tenant_id = B` 的 profile，以 `?profile=`、`SET profile`、`SETTINGS profile =` 套用：`READONLY`（`CONST` 擋下），沒有改到任何設定。
- 缺少 profile 或 `CONST` 的範本誤用：只掛角色沒掛帳號 profile 的帳號，切換租戶仍被角色上的 `readonly = 1` 擋下。

巢狀 `SETTINGS`（發現 4）：子查詢、CTE、JOIN 子查詢、`view()`、純量子查詢裡寫 `SETTINGS SQL_tenant_id = B, readonly = 0` 不報錯（HTTP 200），但不生效，結果仍是 A 的 3 列，`getSetting('SQL_tenant_id')` 仍是 A，`readonly` 仍是 1，`max_rows_to_read = 0` 也沒有解除限制（`TOO_MANY_ROWS`）。

### 3. 讀取路徑（`p4`、`p5`、`p6`、`p8`、`p13`，約 330 項）

- **系統表**：掃 `system` 資料庫的全部 153 張表，租戶 A 只讀得到 24 張（`aggregate_function_combinators`、`collations`、`columns`、`completions`、`contributors`、`current_roles`、`data_type_families`、`database_engines`、`databases`、`dictionary_layouts`、`disk_types`、`enabled_roles`、`formats`、`functions`、`licenses`、`one`、`privileges`、`quota_usage`、`settings`、`table_engines`、`table_functions`、`tables`、`time_zones`、`user_query_log`），全部是靜態資料或只含自己的資料；沒有任何一張出現 B 的租戶 ID、值或帳號名稱。`query_log`、`query_thread_log`、`query_views_log`、`processes`、`parts`、`parts_columns`、`projection_parts`、`detached_parts`、`data_skipping_indices`、`asynchronous_metrics`、`metrics`、`events`、`dictionaries`、`users`、`grants`、`role_grants`、`row_policies`、`quotas`、`quotas_usage`、`user_processes`、`settings_profile_elements`、`clusters`、`disks`、`server_settings`、`information_schema.*`：`ACCESS_DENIED`。`system.user_query_log` 只有自己的 341 筆，沒有 B 的查詢；`system.quota_usage` 只有自己。
- **表函式**：94 個全掃，並對有網路或檔案功能的用合法參數重試。`remote`、`remoteSecure`、`cluster`、`clusterAllReplicas`（`remote('localhost')`、`remote('127.0.0.2')`、帶 `default` 帳號都試過）、`url`、`urlCluster`、`s3`、`s3Cluster`、`hdfs`、`mysql`、`postgresql`、`jdbc`、`odbc`、`sqlite`、`file`（`READ ON FILE` 或不在 `user_files`）、`executable`、`dictionary`、`loop`、`format`、`zeros`：全部被拒。可用的只有 `numbers`、`generateSeries`、`generateRandom`、`primes`、`values`、`view`、`null`、`merge`（只回 A 的列）。`mergeTreeIndex`、`mergeTreeCodecBlockCounts` 明確以 row policy 為由拒絕；另一個同類的內省函式沒有被拒絕（發現 1，`probes/p6-mergetree-fns.sql.txt`）。
- **查詢形式**（`p8`，55 項）：`WITH TOTALS`、`ROLLUP`、`GROUPING SETS`、`LIMIT BY`、視窗函式、`ARRAY JOIN`、`ASOF`/`RIGHT`/`FULL`/`USING` JOIN、`INTERSECT`/`EXCEPT`、`COLUMNS()`、`DISTINCT`、`argMax`、虛擬欄位（`_part`、`_part_offset`、`_row_exists`、`_block_number`）、`merge()` 搭 `_table`：結果都只含 A 的列。**錯誤訊息洩漏**：`toUInt64`、`CAST`、`toUUID`、`parseDateTime` 加在 `WHERE`、`PREWHERE` 與 `SELECT` 上，錯誤訊息只回聲 A 的值（`a-row-0`），從未出現 B 的值，因為 policy 先於使用者運算式；`throwIf`、`intDiv(…, 0)` 針對 B 的列的條件從未觸發。**時序**：`WHERE tenant_id = B AND sleepEachRow(0.5) = 0` 用 6 毫秒回 0，B 的列根本不會被讀取，沒有時序差。
- **內省**：`SHOW CREATE USER`（含自己與 B）、`SHOW GRANTS FOR` 其他使用者或角色、`SHOW USERS`/`ROLES`/`ROW POLICIES`/`QUOTAS`/`ACCESS`/`CREATE QUOTA`/`PROFILES`、`SHOW CREATE TABLE batch_commits`、`DESCRIBE batch_commits`、`EXISTS TABLE batch_commits`：`ACCESS_DENIED`。可用的：`SHOW GRANTS`（自己）、`SHOW CURRENT QUOTA`（自己）、`SHOW CREATE TABLE telemetry`、`DESCRIBE telemetry`。`EXPLAIN` 各種形式：只顯示 A 的 policy 過濾條件（`tenant_id = 'A'`）；`EXPLAIN indexes` 以 B 的 UUID 查詢得 `Parts: 0`，與不存在的租戶相同，沒有存在性偵測；`EXPLAIN ESTIMATE` 與 `system.tables.total_rows` 回整張表的列數（README 已記載，見發現 2）。
- **管理與寫入**（`p4`，約 50 項）：`KILL QUERY`（含 `WHERE user = 'tenant_b'`）、`KILL MUTATION`、`SYSTEM FLUSH LOGS`/`DROP MARK CACHE`/`STOP MERGES`/`RELOAD CONFIG`/`SHUTDOWN`/`SYNC REPLICA`、`OPTIMIZE`、`CHECK TABLE`、`INSERT`（含寫入 B 的 `tenant_id`、`batch_commits`、`INSERT SELECT`、`INSERT INTO FUNCTION file`）、`INTO OUTFILE`、`ALTER UPDATE`/`DELETE`/`DROP PARTITION`/`MODIFY TTL`/`ADD COLUMN`、`DELETE FROM`、`CREATE`/`ALTER`/`DROP ROW POLICY`、`CREATE`/`ALTER`/`DROP QUOTA`、`DROP`/`TRUNCATE`/`RENAME`/`CREATE TABLE`/`DATABASE`/`VIEW`/`MATERIALIZED VIEW`/`USER`/`FUNCTION`、`ATTACH`/`DETACH`/`UNDROP`、`USE`：全部被拒（`ACCESS_DENIED`、`READONLY`、`INTO_OUTFILE_NOT_ALLOWED`），其中最後 11 項因 quota 錯誤額度用完先是 `QUOTA_EXCEEDED`，改用同租戶的第二個帳號重跑後全是 403（`p4b-tail`）。
- **預設拒絕**（`p11`，54 項）：沒有角色的新帳號讀 `telemetry`、`batch_commits`：`ACCESS_DENIED`；被直接 `GRANT SELECT ON trustiot.*`（沒有任何 policy 點名）的新帳號讀兩張表：0 列；`GRANT SELECT ON *.*` 的新帳號讀 `telemetry`、`batch_commits`、`trustiot_logs`：0 列；bootstrap admin 讀兩張表：0 列（README 已記載）。
- **未認證**：`GET /?query=`（無帳密、`user=default` 有無密碼）：401；`/ping`、`/play`、`/dashboard`、`/replicas_status` 回靜態頁，不含資料。

### 4. 服務帳號（`p12`，75 項）

`trustiot_ingest` 可讀寫兩張表並刪列，這是設計；其餘：

- `CREATE`（表、資料庫、view、materialized view、temporary table）、`ALTER ADD/DROP/MODIFY/RENAME/CLEAR COLUMN`、`MODIFY TTL`、`REMOVE TTL`、`MODIFY/RESET SETTING`、`DROP CONSTRAINT`、`ADD INDEX`、`ADD PROJECTION`、`MODIFY ORDER BY`、`MODIFY COMMENT`、`ALTER UPDATE`、輕量 `UPDATE`、`FREEZE`、`MATERIALIZE TTL`、`RENAME`、`EXCHANGE`、`DROP TABLE`/`DATABASE`、`TRUNCATE`、`DETACH TABLE`、`OPTIMIZE`、`SYSTEM`、`CREATE USER`/`ROLE`/`FUNCTION`/`SETTINGS PROFILE`、`CREATE`/`ALTER`/`DROP ROW POLICY`、`ALTER QUOTA`、`GRANT`：全部 `ACCESS_DENIED`。
- 例外：`ALTER TABLE ... DELETE`、`DETACH PARTITION`、`DROP PARTITION`、`DROP DETACHED PARTITION`、`ATTACH PARTITION FROM`、`REPLACE PARTITION FROM` 都被允許（發現 6）。
- 約束：全零租戶、`point` 為空或超過 128 字元、兩個值欄同時有值：`VIOLATED_CONSTRAINT`。
- 讀系統表（`users`、`query_log`、`parts`、`processes`）、`remote`、`url`、`file`：被拒；`system.tables` 可讀。

### 5. Quota 與資源（`p9-quota`、`p10-memory-*`）

| 檢查 | 結果 |
| --- | --- |
| 讀表查詢的上限 | 第 121 個查詢 `QUOTA_EXCEEDED`（上限 120／分鐘）；錯誤上限 60／分鐘，第 61 個錯誤被擋 |
| `quota_key` 參數、`X-ClickHouse-Quota` header、新 `session_id`、`profile=default` | 全部仍 `QUOTA_EXCEEDED`，不能重置計數 |
| 另一個帳號同時 | 照常查詢（`KEYED BY user_name` 有效） |
| 同租戶多帳號 | 5 個帳號各自 4 個並行查詢，全部同時執行（上限是每帳號，設計如此） |
| 並行 | 單帳號 10 個並行 2 秒查詢：4 個執行、6 個 `TOO_MANY_SIMULTANEOUS_QUERIES` |
| 不讀表的查詢 | 400 次 `SELECT 1`：全部成功，`system.quota_usage` 不計；`SELECT count() FROM numbers(1000)` 會計，第 121 次被擋（發現 3） |
| `SET ROLE NONE` 之後 | 同一 session 300 次 `numbers()` 查詢全部成功，包含 `numbers(900000000)` 掃描 6.7 秒（發現 3）；`max_execution_time` 30 秒仍有效 |
| 記憶體 | 單一租戶 4 個並行約 500 MB 的查詢：3 次全部成功，同時的 `INSERT` 33 次全成功；3 個租戶各 4 個並行：3 次中 2 次有 `INSERT` 因 `MEMORY_LIMIT_EXCEEDED` 失敗（發現 5） |

### 6. 退路：用 view 隔離（`p19`，探索性，不是實作變更）

建一個 `DEFINER = ingest SQL SECURITY DEFINER` 的 view，在 view 上建租戶 row policy，只給租戶角色 view 的 `SELECT`、不給底表：租戶讀 view 只拿到自己的列；對底表的內省與直接 `SELECT` 都是 `ACCESS_DENIED`；`system.tables.total_rows` 為 `NULL`；`EXPLAIN ESTIMATE` 與 `read_rows` 仍回整張表的列數。只驗了讀取，沒有驗證效能、`DEFINER` 帳號輪替或 quota，是給 #260 決策用的線索，不是已驗證的方案。輸出：`p19-view-mitigation.out.txt`。

## 發現

| ID | 嚴重度 | 標題 | 追蹤 |
| --- | --- | --- | --- |
| F1 | Medium | 一個索引內省表函式不受 row policy 約束 | Laysi/trustiot-v2#260 |
| F2 | Low | 整張表的總筆數對租戶可見（README 已記載） | 不需處理 |
| F3 | Low | quota 不計常數查詢，卸除角色後也不計 | Laysi/trustiot-v2#119 |
| F4 | Low | 巢狀查詢的 `SETTINGS` 被接受但不生效 | 不需處理（已有回歸測試） |
| F5 | Low | 多租戶並行的大查詢造成伺服器記憶體競爭 | Laysi/trustiot-v2#119 |
| F6 | 資訊 | `ALTER DELETE` 授權也涵蓋分區管理語句 | Laysi/trustiot-v2#260（補 README） |
| F7 | 資訊 | `tools/repo-check` 的靜態掃描是文字比對，有盲點 | Laysi/trustiot-v2#260（補說明） |

- F1：只洩漏另一租戶的中繼資訊，不洩漏列資料；單一查詢探測見 `probes/p6-mergetree-fns.sql.txt`，修法與回歸測試在 #260。
- F2：`system.tables.total_rows` 與 `EXPLAIN ESTIMATE` 回整表筆數，README 已記載，沒有新增風險。
- F3：不讀表的查詢與卸除角色後的查詢不計入 quota，仍受 `max_execution_time` 與記憶體上限約束；實際數值在 #119 訂定時一併考慮（`p9-quota.out.txt`）。
- F4：巢狀 `SETTINGS` 不報錯但沒有效果，隔離不受影響；測試要檢查回應內容而不只是狀態碼，已併入 `extra_attacks()`。
- F5：單一租戶 4 個並行約 500 MB 的查詢，3 次測試都沒有影響同時的 ingest 寫入；3 個租戶各 4 個並行時，3 次中 2 次有 ingest 寫入因 `MEMORY_LIMIT_EXCEEDED` 失敗（`p10-memory-*.out.txt`）。這是伺服器總記憶體的容量規劃問題，在 #119 處理。
- F6：`trustiot_ingest` 的 `ALTER DELETE` 同時允許分區的 detach、drop、attach、replace，不能改欄位、TTL 或表設定；README 補一句即可（`p12-ingest.out.txt`）。
- F7：`tools/repo-check` 的掃描是輔助檢查，真正的強制是資料庫權限（第 4 節已驗證全部被拒）；在說明中寫明即可（`p15-static-check-evasion.out.txt`）。

## 新增的回歸測試

已併入 `services/ingest/tests/clickhouse.rs`（`CI=1 cargo test -p ingest --test clickhouse` 通過，輸出 `p17-new-regression-run.out.txt`）：

- `extra_attacks()`（以租戶 A 的第二個帳號執行，共 28 項）：巢狀 `SETTINGS` 9 項、URL 參數選角色或設定 3 項、其他表函式與遠端存取 7 項、內省與管理語句 16 項。
- `deny_by_default_covers_new_accounts()`：無角色的新帳號被拒；被直接授與 `SELECT` 的帳號、bootstrap admin 讀兩張表都是 0 列；租戶帳號對 `batch_commits` 是 `ACCESS_DENIED`。
- `quota_is_per_user()` 補強：quota 用盡後，`quota_key` 參數與新的 `session_id` 都不能重置計數。
- `ingest_account_cannot_change_schema()` 補強：18 個改 schema 或權限的語句併入拒絕清單。

F1 目前的行為是「函式可用」，所以不寫成通過的斷言；修好之後的回歸測試由 #260 補。其餘探測（全掃、quota、記憶體、view）留在 `probes/`。
