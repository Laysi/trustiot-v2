# AI 儀表板：`dashboard` 工具、跨服務的驗收與回答過濾

對應 issue：Laysi/trustiot-v2#150（AI 儀表板）。測試日期 2026-10-27（Asia/Taipei）。

這份報告是 Laysi/trustiot-v2#150 驗收條件的總表：本報告測的是主 agent 的 `dashboard` 工具、檢查服務的 client、回答過濾，以及跨服務的驗收測試（`services/assistant/tests/dashboard_acceptance.rs`）；其他條件的證據在同一張 issue 較早的兩份報告，「結論」逐條指出出處：

- [2026-10-26-150-dashboard-api.md](2026-10-26-150-dashboard-api.md)：assistant 的儲存、公開 API、以檢視者身分執行資料集、跨租戶負向測試。
- [2026-10-26-150-dashboard-check-image.md](2026-10-26-150-dashboard-check-image.md)：檢查服務的映像以真的 headless Chromium 檢查沙箱的每一個固定樣本，以及 nightly 隔離證明在叢集以外能驗的部分。

原始輸出在 [data/2026-10-27-150-dashboards/](data/2026-10-27-150-dashboards/)。

## 環境

- **受測程式碼**：本報告所在的 commit（分支 `feat/150-s5-tool`），含 assistant 後端（`feat/150-s1-backend`）、沙箱 runtime（`feat/150-s2-runtime`）與檢查服務（`feat/150-s3-checker`）的合併。
- **執行的地方**：開發工作站。容器引擎是 Docker，平台 `linux/arm64`；起容器的測試一次只跑一個。沒有設 `CI`。
- **工具版本**：`.prototools` 與 `rust-toolchain.toml` 釘選的 Rust 1.99.0、Bun 1.4.2。
- **檢查服務**：`deploy/images/dashboard-check` 以 `bun test deploy/images/dashboard-check` 在本機建出的 `localhost/trustiot-e2e/dashboard-check:image-test`（與 2026-10-26 的映像報告是同一個映像，manifest list digest `sha256:6ef0a921b483af748c6beb98012047727a972f5bbee0fd213764a19dfa77a056`）。驗收測試照 chart 的設定執行它：唯讀根目錄、`/tmp` 是 chart 的 `tmpSizeLimit`（128 MiB）的記憶體檔案系統、拿掉所有 capability、`no-new-privileges`、引擎預設的 seccomp、chart 的記憶體上限（512 MiB），使用者 `65532:65532`；兩個上限由測試從 `deploy/chart/values.yaml` 讀出。測試與服務之間是一個 loopback 代理，原樣轉送並記下服務送出的每個判定。
- **Postgres**：`crates/testkit` 的 TLS Postgres（`docker.io/library/postgres:18.6-alpine@sha256:77f585114c32fbca283dc835b0596f4e52b51b4c6662d7810b2f4084f60a1873`），migration Job 套用整個產品的 schema。
- **ClickHouse**（驗收 1）：`services/ingest/tests/common` 的拋棄式容器（`docker.io/clickhouse/clickhouse-server:26.8@sha256:110d3d1f8e1ed7e451a6b5d85a16761e948ad43bc2d9ddf10b155964a8b2b40c`），以 migration Job 的 ClickHouse 部分（`migrate::registry::PRODUCT.clickhouse`）套用產品的 schema；租戶帳號由 telemetry-query 的 `Accounts::ensure` 建立。
- **telemetry-query**：驗收 1 在測試程序裡以產品的 schema 起它真正的路由（SQL、統計與用量），以 `telemetry_query_app` 角色與服務的 ClickHouse 帳號執行；驗收 2 用 `tests/dashboard_world` 的替身，照沙箱固定樣本的資料回答。
- **AI 閘道**：loopback 上照腳本回答的替身（`tests/support`），不呼叫供應商、沒有 API key。主 agent 經 `Agent::ask` 執行，工具組只有 `dashboard`。
- **資料**：驗收 1 是 Laysi/trustiot-v2#679 的合成 lab 資料集（`datasets/lab/synthetic`，版本 1）：兩部電表（電能 `energy_kwh` 中途清零一次；32 位元的脈衝計數 `pulses` 回捲一次）與一台沖床，4 小時、每 5 分鐘一筆，含漏讀與斷線。以 `lab_dataset` 的載入方式寫進 ClickHouse，整段時間平移成在測試前一天之內結束（整日平移，每筆讀數在 UTC 小時裡的位置不變）。驗收 2 是沙箱 runtime 的固定樣本（`frontend/sandbox/fixtures`：`request.json`、`cases.json`、`pages/`）。

### 驗收 2：頁面與資料不符時拒絕，使用者仍看到上一版

`a_page_that_does_not_match_its_data_is_refused_and_the_user_keeps_the_previous_version`。一個問題裡，照腳本的模型呼叫三次 `dashboard` 的 `write`：

| 寫入 | 頁面 | 檢查服務的判定 | 工具給模型的結果 |
| --- | --- | --- | --- |
| 1：新草稿，三個資料集（兩個 SQL、一個用量）、三個計算、兩個常數 | `correct.html` | `passed`，62 個標記，與 `cases.json` 的 `correct` 逐項相同（含 `m|daily_energy|queried_at`） | `saved: true`、第 1 版、`kind: draft`、`check.marks` 62 |
| 2：同一份草稿，`base_version` 1 | `wrong-bar-height.html`（第三根長條只畫一半高） | `failed`：`mark_geometry`、`c|daily_energy|kwh|2`、`channel: height`，符合 `cases.json` | 錯誤結果 `saved: false`，問題只有 `mark_geometry`（帶參照、`channel` 與固定的 hint） |
| 3：同一份草稿，`base_version` 1 | `unmapped-mark.html`（第八列、不存在的資料集、沒有對應的 `rect`） | `failed`：三個 `unmapped`，符合 `cases.json` | `saved: false`，問題只有 `unmapped` |

之後經公開 API（`GET /api/assistant/v1/dashboards/{id}` 與 `/versions`，以擁有者的 token）讀到的仍是第 1 版、頁面是 `correct.html`，版本列表只有第 1 版。三次寫入只呼叫 telemetry-query 3 次（每個資料集一次，後兩次寫入重用同一個問題的結果），沒有其他呼叫。

### 驗收 1：儀表板上的數字等於 ClickHouse 的

`the_numbers_on_a_dashboard_equal_clickhouses`。模型寫一份草稿：四個資料集與六個計算，頁面以文字標記顯示每一格與每個計算（固定文字裡沒有數字）。檢查通過，報告的 48 個標記恰好是下表的 48 個量，每一個都等於以讀全部列的測試帳號直接查 `trustiot.telemetry` 算出的值（數字相差不超過 1e-9 倍，次數完全相同；文字與時間完全相同）。範圍是整點的 UTC 時間，涵蓋整份資料。

| 資料集或計算 | 來源 | 標記的量 | 直接查詢 |
| --- | --- | --- | --- |
| `power_raw` | SQL，原始讀數 view `tenant_telemetry` | 每部電表的 `device_id`、功率讀數筆數、最低、最高、總和 | `trustiot.telemetry` 依 `device_id` 分組的 `count`、`min`、`max`、`sum` |
| `power_hourly` | SQL，1 小時格 view `tenant_telemetry_1h`（第一部電表） | 每個小時、該小時的最高功率、平均（格的總和除以數值讀數數） | 讀數依 `toStartOfHour(ts, 'UTC')` 分組的 `max` 與 `avg` |
| `power_stats` | 統計 API，`interval: total`（兩部電表） | `device_id`、筆數、最小、最大、平均、最後讀數 | 依 `device_id` 的 `count`、`min`、`max`、`avg`、`argMax(value, ts)` |
| `energy` | 用量 API，`interval: total`（第一部電表的電能、第二部的脈衝） | `device_id`、`point`、總量、讀數數 | 相鄰讀數的增量加總，下降時（清零、回捲）算下降後的讀數（`lagInFrame`），與讀數數 |
| `peak_kw` | `max(power_raw.high)` | 全部功率讀數的最高 | `max` |
| `mean_kw` | `sum(power_raw.total) / sum(power_raw.readings)` | 全部功率讀數的平均 | `avg` |
| `spread_kw` | `max(power_stats.max) - min(power_stats.min)` | 最高與最低的差 | `max - min` |
| `hourly_peak_kw` | `max(power_hourly.peak_kw)` | 第一部電表的最高每小時峰值 | 第一部電表的 `max` |
| `kwh_per_interval` | `energy.total[0] / (energy.readings[0] - 1)` | 第一部電表每個讀數間隔的平均用電 | 用量總和除以讀數數減一 |
| `pulses_total` | `last(energy.total)` | 脈衝總數 | 第二部電表的用量 |

幾個值（完整的 48 個在 [acceptance.txt](data/2026-10-27-150-dashboards/acceptance.txt)）：第一部電表 48 筆功率、最高 49.732 kW；第二部 47 筆、最高 20.5 kW；電能總量 164.046 kWh；脈衝 3048（與 services/telemetry-query/README.md「用量」寫的 fixture 結果相同）；全部功率平均 30.468263157894743 kW。

## 結論

1. **以合成 fixture 測試，儀表板顯示的數字與直接查 ClickHouse 算出的值一致**：通過。見上方「驗收 1」：SQL（原始讀數與 1 小時格）、統計與用量 API 的每一格與六個計算，檢查服務報告的 48 個值都等於直接查詢的結果。用 lab 資料集再測一次：**待測**，2026-10-25 延後到 Laysi/trustiot-v2#681（測試經 `lab_dataset` 的載入方式讀資料集，補驗時換成 lab 錄製的 index）。
2. **標記的值與資料不一致、或對不到任何一列時，檢查不通過、不發布，使用者仍看到上一版（用真的檢查服務容器）**：通過。見上方「驗收 2」。檢查服務對全部 33 個固定樣本的判定（含 `wrong-row`、`format-injection`、`tick-outside-axis` 等其他不一致的種類）見 2026-10-26 的映像報告；拿不到可用判定的每種情況（503、400、500、不是判定、判定引用了沒送出的資料、連不上、逾時）都什麼都不存、草稿的最新版本不變，見 `tests/dashboard_tool.rs` 的 `a_failed_or_missing_verdict_saves_nothing_and_the_draft_keeps_its_version`。
3. **以權限較少的成員或另一個租戶的身分打開儀表板時，資料集以該身分重新執行**：通過，見 2026-10-26 的 API 報告（`datasets_run_as_the_viewer_who_opened_the_dashboard`、跨租戶負向測試 91 個探測）。`dashboard` 工具同樣以提問者的身分執行（`a_write_runs_every_dataset_as_the_user_and_saves_a_draft_only_after_the_check`：token 的使用者、租戶、角色、受眾與 `act`）。
4. **回答文字不出現 SQL 或 HTML**：通過。`tests/answer_guard.rs` 經 `ask` 與替身 AI 閘道：回答裡的 SQL 程式碼區塊、句子裡的 SQL 敘述、HTML 與含程式碼的行內程式碼在呼叫端與歷史裡都已移除，回報移除的類別、日誌只記類別；改變 schema 的敘述也移除；呼叫端拿到的文字與歷史存的逐位元組相同。`src/answer_guard.rs` 的單元測試涵蓋其餘種類、必須保留的文字（中文、數字、單位、比較符號），以及串流用的 `pending` 在每個前綴上的正確性。
5. **修改後產生新版本，舊版仍可讀回**：通過，見 2026-10-26 的 API 報告。
6. **打開與重新整理儀表板不呼叫模型、不扣 AI 額度**：通過，見 2026-10-26 的 API 報告。
7. **viewer 發布、回到舊版、封存都回 403；同租戶的其他使用者讀不到別人的草稿，回 404**：通過，見 2026-10-26 的 API 報告；工具一側，別的對話、別的使用者與別的租戶的草稿都是「不存在」（`the_tool_refuses_what_this_question_may_not_write`）。
8. **公開 API 不接受 SQL 與頁面內容**：通過，見 2026-10-26 的 API 報告。
9. **超過 2,000 列的資料集被拒並說明怎麼縮小；同一租戶一分鐘內超過 60 次資料集執行時回 429**：通過，見 2026-10-26 的 API 報告；`dashboard` 工具的執行算進同一個上限。
10. **對話軟刪除時它的草稿讀不到，還原後回來；清除對話時草稿與版本一起刪除；已發布的不受影響**：部分通過。清除的部分通過（2026-10-26 的 API 報告）。軟刪除與還原**待測**：需要 Laysi/trustiot-v2#644 的欄位，測試已寫好、以 `#[ignore]` 標記原因。
11. **檢查服務的隔離（nightly 叢集）**：**待測**。要在 nightly 的 k3d 叢集上證明（工作站不跑 Kubernetes），證據是合併前帶 `smoke` label 的 PR 觸發的 nightly run；assistant 的設定現在接受 chart 設的 `TRUSTIOT__DASHBOARD_CHECK__URL`，`bun test scripts/nightly/api.test.ts` 對 `src/api/dashboards.rs` 的檢查通過。探測 script 的本機部分見 2026-10-26 的映像報告。
12. **`cargo test --workspace`、`bun run --cwd frontend test`、`bun test deploy/chart`、`bun test scripts`、`cargo run -p openapi -- --check`、`bun run --cwd frontend api:check` 通過**：`cargo run -p openapi -- --check`、`bun run --cwd frontend test` 與 `api:check` 在本報告的程式上通過；`cargo test --workspace`、`bun test deploy/chart` 與 `bun test scripts` 這台工作站沒有整套跑（有已知只在本機失敗的測試），**待測**，由 PR 的 CI 執行。

CI 目前不跑 `dashboard_acceptance.rs` 的兩個測試（它們要檢查服務的映像，而建映像的 `dashboard-check-image` job 沒有 Rust 的測試環境）；要不要在 CI 跑、跑在哪個 job，留給整合時決定。
