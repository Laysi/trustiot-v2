### 驗收條件 1：無憑證、外部 CA、過期、EKU 錯誤、CRL 內的憑證都被拒

`gateways_need_a_current_certificate_of_our_ca`。閘道器埠 8883 是 TLS 1.3，只信任 certs 服務的 CA，並檢查 CRL。每一項都以 `mosquitto_pub` 連線，TLS 握手失敗的訊息如下：

| 情況 | broker 的回應 |
| --- | --- |
| 沒有用戶端憑證 | `tlsv13 alert certificate required` |
| 另一個 CA 簽的憑證（CN 同樣是 `gw-a`） | `tlsv1 alert unknown ca` |
| 過期的憑證 | `ssl/tls alert certificate expired` |
| 沒有 clientAuth EKU 的憑證 | `ssl/tls alert unsupported certificate` |
| CRL 列出的憑證 | `ssl/tls alert certificate revoked` |
| `gw-c` 在新的 CRL 撤銷它之後重連（sidecar 送 SIGHUP 重新載入） | `ssl/tls alert certificate revoked` |
| 有效的憑證，但 broker 裝的是佔位 CA（還沒拿到 certs 的 CA 時） | `tlsv1 alert unknown ca` |

同一個測試也確認了下列行為：

- 我們 CA 簽的有效憑證可以連線（`gw-a ... CONNACK (0)`），新的 CRL 載入後仍可連線。
- 閘道器的名稱不帶憑證，或改用密碼登入，都被拒（`CONNACK (135)`）。
- `gw-c` 在撤銷前建立的連線，在重新載入後仍收得到訊息：重新載入不會中斷連線。所以已連線的撤銷閘道器要主動踢掉，這交給 Laysi/trustiot-v2#82。
- 換新的伺服器 CA 後，信任新 CA 的用戶端可以連線，只信任舊 CA 的用戶端被拒（`certificate verify failed`）。

工作站憑證被 broker 拒絕，由 Laysi/trustiot-v2#534 的驗收條件證明（見 issue 的現狀）。

### 驗收條件 2：SIGKILL 後 retained 訊息仍在

`retained_messages_and_sessions_survive_sigkill`。設定以 `mosquitto_persist_sqlite.so` plugin 持久化到 `/mosquitto/data/mosquitto.sqlite3`，並設 `plugin_opt_flush_period 0`。測試的步驟：

1. `gw-a` 發布一則 retained 訊息。
2. `gw-b` 以會留下的 session 訂閱後離線。
3. 對它的 config 頻道送一則 QoS 1 訊息。
4. 以 SIGKILL 殺掉 broker，再啟動。

結果：

- 重新啟動時，SQLite 還原的筆數是 `Restored 2 base messages`、`1 retained messages`、`1 clients`、`1 subscriptions`、`1 client messages`。第一次啟動時都是 0。
- 重新啟動後讀到的內容：`after SIGKILL: retained ["trustiot/v1/gw/gw-a/up/status 1 1 online"], queued ["trustiot/v1/gw/gw-b/down/config 0 1 queued"]`。retained 訊息還在，`gw-b` 重連後也收到離線時排入的訊息。

### 驗收條件 3：broker 的 Service 在兩份 values 都不對叢集外開放

`bun test deploy/chart` 的「MQTT broker」測試群組：

- **預設不渲染**：`off by default and in both deployment shapes`。`values-saas.yaml`、`values-onprem.yaml` 與它們的 instance 檔都沒有設定 `mqttBroker`，渲染結果裡沒有任何 broker 的物件。`deploy/flux/tests/flux.test.ts` 另外確認 SaaS 與展示叢集都沒有設定它。
- **打開 broker 時也只在叢集內**：`saas` 與 `onprem` 各跑一次 `reachable inside the cluster only`，渲染時加上 nightly 的 `tests/values/smoke.yaml`（打開 broker）。
  - Service 是 `ClusterIP`，只有 8883 與 1883 兩個埠，沒有 nodePort、externalIPs 或 loadBalancerIP。
  - pod 沒有 hostNetwork、hostPID 或 hostPort。
  - 沒有任何 Route 指向 broker 的 Service；試圖在 `ingress.routes` 加一條指向 broker 的路由，渲染會失敗。
- **kubeconform**：`rendered manifests pass kubeconform -strict` 對每個部署形態渲染四組，結果都是 `Invalid: 0, Errors: 0`，每個列出的 Kubernetes 版本都通過。四組分別是：
  1. 只有部署形態的 values
  2. 加上 `smoke.yaml`（broker 打開）
  3. 加上 `smoke.yaml` 並打開所有服務
  4. ingress 的 e2e values

k3d 的部分：nightly（`scripts/nightly/smoke.ts`）以兩份 values 加上 `smoke.yaml` 部署到 k3d，部署前先以這次執行產生的 CA 簽出 broker 的伺服器憑證 Secret。部署後執行檢查「no Service of the release is reachable from outside the cluster, and no route sends traffic to the MQTT broker」，比對的是叢集裡實際的 Service。這個檢查本身的邏輯（`exposureProblems`）由 `bun test scripts`（`scripts/nightly/manifests.test.ts`）驗證。在叢集上的執行要等這次 PR 帶 `smoke` 標籤的 nightly。

### 驗收條件 4：健康檢查不產生 TLS 錯誤日誌

readiness 與 liveness 探針都是 exec，執行 `mosquitto_pub --unix /run/mosquitto/probe.sock -V 5 -I probe: -t trustiot/probe -n -q 0`。它經 Unix socket 建立一條 MQTT 連線，不經 TLS，也不經網路。

- `gateways_need_a_current_certificate_of_our_ca` 先執行這個指令 4 次，再讀 broker 的日誌：`probe: 4 runs, no error, warning or OpenSSL line`，每次連線都有記錄（例：`New client connected from /run/mosquitto/probe.sock:0 as probe:6`）。
- chart 測試 `the probes run the broker tests' command on the probe socket` 確認 chart 執行的正是這個指令，沒有 tcpSocket 探針、沒有 TLS 握手，也沒有給節點的埠。

### 其他行為（同一輪測試）

- **服務帳號**：`services_log_in_with_their_accounts_and_reach_only_their_channels`。
  - ingest 用別的密碼或 gateway-ops 的密碼登入，被拒；沒有 username 的連線也被拒（`CONNACK (135)`）。
  - 每個服務經 shared subscription 收到自己的頻道。
  - 只有 certs 能用 dynamic security 的控制主題（列出 broker 的 client）。
  - 1 MiB 的訊息可以通過。
  - certs 以 dynamic security 指令建立角色、client 與群組，並停用 client，broker 存下的檔案通過 init container 的檢查：`the file the broker saved after certs' changes passes the init container's checks`。
  - 1883 上可以同時開 11 條服務連線，探針仍然連得上：`max_connections 8` 只限制探針的 socket。
- **信任檔與重新載入**：`tests/mqtt_trust.rs` 的 4 個測試涵蓋三件事。
  - init container 安裝 certs 服務的檔案，沒有 certs 時改裝佔位 CA。
  - init container 拒絕與憑證不成對的伺服器私鑰。
  - sidecar 只在每個檔案都能載入時送 SIGHUP，並等 broker 已經處理 SIGHUP 才送。
- **帳號與密碼**：`tests/mqtt_accounts.rs` 的 3 個測試。
  - 密碼只寫進 Secret，dynamic security 檔裡只有雜湊。
  - 讀不到檔案或缺少 Secret 時，pod 不啟動。

### 這次修正的問題

pre-commit 的 Codex 審查逐次擋下並要求修正下列問題，修正後都在上面這一輪測試中通過：

- **`memory_limit` 的算式**：Sprig 的 `mul` 改成兩兩相乘。渲染結果不變，256Mi 得到 201326592。
- **dynamic security 檔的內容檢查**：init container 保留 broker 存的閘道器 client、群組與其他角色。這些項目若有下列情況，Mosquitto 2.1.2 讀檔時不會停止，而是默默略過或讀錯，可能丟掉 deny 規則、`disabled` 或 client id 綁定：
  - 缺名稱或名稱重複
  - 欄位型別不對
  - 不認得的 ACL 類型、重複的 ACL
  - 欄位名稱只差大小寫
  - 重複的 JSON key

  現在 init container 遇到這些情況就停止並指出是哪一筆，不改檔案。群組裡的服務帳號成員會被移除。單元測試是 `entries_the_broker_would_skip_or_misread_are_refused`（21 種情況）、`entries_the_broker_reads_as_written_are_kept` 與 `files_the_broker_cannot_use_are_left_alone`。
- **損壞的信任目錄**：同名目錄的內容與要安裝的不同時，不再連回它，改寫進新目錄，舊目錄由清理移除（`installing_swaps_the_link_and_leaves_one_directory`）。
- **CRL 必須有 nextUpdate**：沒有 nextUpdate 的 CRL 永遠不會過期，所以拒絕（`a_crl_without_next_update_is_refused`）。這次也一併加上兩項檢查：CRL 必須由同名 CA 的公鑰簽章，從 certs 取得的 CRL 必須在效期內。
- **`max_connections` 的範圍**：審查認為它限制整個 broker。Mosquitto 2.1 的原始碼（`src/conf.c`）是把它設在當前的 listener 上，所以只限制探針的 socket。設定檔加上說明，並以 11 條同時連線的測試證明。
