## 指令

在 repo 根目錄：

```sh
: "${DEMO_SSH_HOST:?set DEMO_SSH_HOST to the ssh host of the demo machine}"
: "${DEMO_GATEWAY_HOST:?set DEMO_GATEWAY_HOST to the gateway host name}"
# 切換前的關卡：以 0 結束才切換，origin 取自最後一行
bun scripts/demo/tunnel.ts route-origin --ssh-host "$DEMO_SSH_HOST"
# 切換之後，讀回設定確認之後馬上執行
bun scripts/demo/tunnel.ts check --ssh-host "$DEMO_SSH_HOST" --stage 2
# 略過路徑下面的子路徑（check 只探測 /mqtt/x），沒有 User-Agent
for spec in "POST /certs/renew/x" "GET /certs/renew/x" "GET /mqtt/x"; do
  set -- $spec
  curl -sS -X "$1" -A '' -o /dev/null --max-time 15 \
    -w "$1 $2 status=%{http_code} body-bytes=%{size_download} content-type=[%{content_type}]\n" \
    "https://$DEMO_GATEWAY_HOST$2"
done
```

Cloudflare 端由協調者在 Cloudflare 的 API 執行環境裡執行，每一步都在同一個環境內比對，只回傳比對結果：

- `GET /accounts/<帳號>/cfd_tunnel/<tunnel>/configurations`：切換前的設定（版本與每條規則）。
- `PUT /accounts/<帳號>/cfd_tunnel/<tunnel>/configurations`：只把五條 `http_status:418` 的 `service` 換成 `route-origin` 印出的 origin，其他內容原樣送回。
- `GET /accounts/<帳號>/cfd_tunnel/<tunnel>/configurations`：切換後立刻讀回，逐條和切換前比對。

展示機上（`DEMO_GATEWAY_HOST`、`DEMO_APP_HOST` 在那裡設定），直接對入口的 ClusterIP 送同樣的請求，用來比對經過 Cloudflare 的回應：

```sh
for spec in "GET /mqtt" "POST /certs/renew" "GET /healthz"; do
  set -- $spec
  curl -sS -X "$1" -D - -o /dev/null --max-time 10 -H "Host: $DEMO_GATEWAY_HOST" "http://10.43.0.80$2"
done
curl -sS -D - --max-time 10 -H "Host: $DEMO_APP_HOST" http://10.43.0.80/healthz
curl -sS -D - -o /dev/null --max-time 10 -H "Host: $DEMO_APP_HOST" http://10.43.0.80/
```

### 切換與讀回（驗收 2）

- 切換前：設定版本 1，六條規則，與 Laysi/trustiot-v2#466 變更清單的第一段相同（五條 `http_status:418`，最後是 catch-all `http_status:404`）。
- 07:43:39 以 API 只換掉那五條的 `service`。立刻讀回：
  - 版本 2，仍是六條規則，順序不變。
  - 指向入口的五條路由，`service` 都與 `route-origin` 最後一行的 origin `http://10.43.0.80:80` 逐字相同。
  - 每條規則除了 `service` 以外的內容（主機名稱、路徑、`originRequest.access`）都與切換前相同。
  - catch-all 仍是 `http_status:404`，`warp-routing` 仍是關閉。
- 切換前的設定另存在私有的紀錄，需要退回第 1 段時原樣送回。

### `check --stage 2`（驗收 2、3）

07:44:28 執行，以 0 結束。它先跑同一個關卡（三個位址相同、在靜態區段內），再從工作站與展示機（lab 網路）各探測一次。20 項都 PASS，兩處的結果相同：

| 請求 | 預期 | 結果（兩處） | 回應 |
| --- | --- | --- | --- |
| app 主機名稱 `/`，瀏覽器的 User-Agent，沒有 Access session | `access` | PASS，`access` | 302 到 Access 的登入頁 |
| gateway 主機名稱 `/mqtt`，WebSocket 升級，沒有 User-Agent | 到達 tunnel 後面 | PASS，`unexpected` | 404，body 0 bytes |
| gateway 主機名稱 `POST /certs/renew`，沒有 User-Agent | 到達 tunnel 後面 | PASS，`unexpected` | 404，body 0 bytes |
| gateway 與 ota 主機名稱的 `/auth/login`、`/healthz`（只有 app 才有的路徑），沒有 User-Agent | `access` | PASS，`access` | 302 到 Access 的登入頁 |
| gateway 與 ota 主機名稱的 `/`，沒有 User-Agent | `access` | PASS，`access` | 302 到 Access 的登入頁 |
| gateway 主機名稱 `/mqtt/x`（略過路徑下面的子路徑），沒有 User-Agent | `refused` | PASS，`refused` | 403，沒有 `content-type`，body 0 bytes |

`check` 把不是 Access、Cloudflare 的 challenge 或封鎖、tunnel 斷線，也不是 connector 拒絕的回應歸為 `unexpected`；第 2 段的略過路徑要的就是這一類（`scripts/demo/tunnel.ts` 的 `probePasses`）。維運 tunnel 的 `cloudflared.service` 在檢查前後是同一個行程。

### 略過路徑到達入口的佐證（驗收 3）

`check` 只看 client 收到的回應，而 Cloudflare 會把 `server` 標頭換成 `cloudflare`，所以另外佐證兩條略過 Access 的路徑到了入口：

- 第 1 段時，同樣的請求得到 connector 的 418（Laysi/trustiot-v2#466 的 `check` 與上面驗收 1 的瀏覽器實測），符合的是這兩條帶路徑的規則。切換只改了 `service`，主機名稱與路徑不變，所以第 2 段符合的仍是它們，而它們現在指向入口。
- 07:46 在展示機上直接對入口的 ClusterIP 送同樣的請求（`Host` 是 gateway 主機名稱）：`GET /mqtt` 與 `POST /certs/renew` 都回 404，`server: istio-envoy`，`content-length: 0`，與經過 Cloudflare 看到的 404、0 bytes 相同。
- 入口回 404 的原因：chart `0.0.0-rc.10` 在 gateway 主機名稱上沒有任何路由。橋接（`mqtt-bridge`）與憑證服務（`certs`）還沒部署，這兩條公開路徑只在後端打開時才掛上。
- 同樣直接對入口送請求：app 主機名稱的 `/healthz` 回 200（`application/json`，`{"status":"ok"}`，身分服務的回應），`/` 回 404（rc.10 還沒有網頁）。

### 略過路徑下面的子路徑（驗收 3）

`check` 只探測 `/mqtt/x`。07:46 從工作站補測 `/certs/renew/x`：

| 請求 | 回應 |
| --- | --- |
| `POST /certs/renew/x`，沒有 User-Agent | 403，body 0 bytes，沒有 `content-type` |
| `GET /certs/renew/x`，沒有 User-Agent | 403，body 0 bytes，沒有 `content-type` |
| `GET /mqtt/x`，沒有 User-Agent | 403 |

形狀與 `check` 判定為 connector 拒絕的 `/mqtt/x` 相同：tunnel 只以錨定的規則（`^/mqtt$`、`^/certs/renew$`）讓這兩個完整路徑不帶 JWT 通過，子路徑落到要求 Access JWT 的規則而被 connector 拒絕。

### 切換路由之後的瀏覽器實測（驗收 3）

2026-10-23 由維運人員以桌面瀏覽器的無痕視窗、Access 受邀名單裡的帳號手動操作，回報如下：

| 網址（app 主機名稱） | 看到的結果 | 判讀 |
| --- | --- | --- |
| `/` | 瀏覽器自己的「找不到網頁、HTTP ERROR 404」頁 | 本文為空的 404，與上面直接對入口送 `/` 的 404 相同；Cloudflare 擋下時會顯示 Cloudflare 的錯誤頁 |
| `/healthz` | `{"status":"ok"}` | 與直接對入口送 `/healthz` 的 200 本文相同，是展示環境裡 identity 的回應 |

沒有 Access session 的請求在 app 主機名稱一律得到 302 到 Access 的登入頁（上面 `check --stage 2` 的第一列），所以拿到 identity 的回應表示這次請求帶著受邀帳號的 Access session 到達展示環境。帳號依公開 repo 的規則不寫出。

### 限制

- curl 的 TLS 特徵（OpenSSL）和閘道器的 rustls 不同。展示用閘道器（Laysi/trustiot-v2#458）第一次連線後，再以 Cloudflare 的 Security Events 確認沒有被 challenge 或擋下的紀錄（runbook「檢查對外的請求」）。
- 第 2 段的 `check` 把 Cloudflare 對 WebSocket 升級回的 502 也當成「沒有被擋下」而通過；這次 `/mqtt` 得到的是入口的 404，不是 502。讓 `check` 自己讀 connector 的計數佐證是 Laysi/trustiot-v2#473（P2）。
