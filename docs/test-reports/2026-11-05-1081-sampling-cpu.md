# 自訂頁面沙箱：隨機時間比對的 CPU 上限（2026-11-05）

對應 issue：Laysi/trustiot-v2#1081。規則在 `frontend/sandbox/README.md`「顯示時比對的強制」的「取樣的 CPU 上限約 5%」與 `beat` 一項。

## 環境

- 程式碼：分支 `feat/1081-sampling-cpu-cap`，main `8b90f33c` 之後。「改之前」是同一棵樹把這次對 `frontend/sandbox/src/runtime.ts` 的改動反向套用後建置的（沙箱的其他檔案與 main 相同）；「改之後」是安全審查之後的程式（比對成本的估計 `sampleCostMs`、藏起後再顯示時重新抽取樣時間），在提交前的工作樹上量。
- 「被否決的估計」是審查後試過的兩種比對成本估計，其餘與「改之後」相同：只取移動平均與最近一次比對中較小的，以及取移動平均與最近兩次中較貴那次兩者中較小的。
- 建置主機（arm64 Linux）。Bun 是 `.prototools` 的版本；`bun run --cwd frontend build` 與 `bun frontend/e2e/custom-page/build.ts` 在主機上建置。
- 瀏覽器：`frontend/e2e/image.ts` 釘選的 Playwright 映像（Chromium 156.0.8078.4，linux/arm64），在容器裡執行，`--site-per-process`。
- 探測：[probe.mjs](data/2026-11-05-1081-sampling-cpu/probe.mjs)，以 [run.sh](data/2026-11-05-1081-sampling-cpu/run.sh) 在容器裡執行。外層頁面是瀏覽器端測試的 harness（`frontend/e2e/custom-page/harness.tsx`：真的元件、guard 與 host adapter），沙箱檔案由 Playwright 的 route 從 `frontend/dist` 提供，標頭同 `contract::api::dashboard::sandbox`；不需要伺服器。
- 頁面：`marks` 個文字標記（fixture 的第一個功率值）加 `boxes` 個沒有文字的方框，第一次畫完後不再改變。

## 指令

```sh
# repo 根目錄
bun install --cwd frontend --frozen-lockfile
bun run --cwd frontend build
bun frontend/e2e/custom-page/build.ts

# 靜止頁面的 CPU 占比（改之前每頁 30 到 60 秒，改之後 30 到 180 秒）
sh docs/test-reports/data/2026-11-05-1081-sampling-cpu/run.sh \
  '[{"name":"s10","marks":10,"boxes":0,"seconds":30},{"name":"m1000","marks":1000,"boxes":4000,"seconds":120},{"name":"m3000","marks":3000,"boxes":12000,"seconds":180},{"name":"m4500","marks":4500,"boxes":15000,"seconds":180}]'
# 較長的時間窗（改之後）
sh docs/test-reports/data/2026-11-05-1081-sampling-cpu/run.sh \
  '[{"name":"m1000-long","marks":1000,"boxes":4000,"seconds":480},{"name":"m3000-long","marks":3000,"boxes":12000,"seconds":480}]'

# 沒被通知的改動：只為探測拿掉 seal.ts 對 SVG <style> 的 disabled 包裝，重新建置，再跑攻擊
sed -i '/\["SVGStyleElement", \["disabled"\]\],/d; s/if (!name.endsWith("Element")) continue;/if (!name.endsWith("Element") || name === "SVGStyleElement") continue;/' \
  frontend/sandbox/src/seal.ts
bun run --cwd frontend build
sh docs/test-reports/data/2026-11-05-1081-sampling-cpu/run.sh \
  '[{"attack":true,"seconds":240,"name":"a4500-1","marks":4500,"boxes":15000}]'   # 每種頁面 3 次
git checkout -- frontend/sandbox/src/seal.ts

# 單元測試
bun run --cwd frontend test
```

量法：外層顯示 frame 後再等 5 秒，以 CDP 的 `Performance.getMetrics`（`threadTicks`，CPU 時間）在時間窗的頭尾讀沙箱 frame 主執行緒的 `TaskDuration`，除以經過的時間。外層可能顯示 frame 時，每次乾淨的比對都送一則 `compared`，所以時間窗裡的 `compared` 數就是比對次數；「一次比對」是 CPU 時間除以比對次數（含心跳，心跳幾乎不花時間）。攻擊是 2026-11-03 探測的 f-nocover：每個 animation frame callback 打開一個顯示錯的值的 SVG `<style>`，繪製後的第一個 task 關掉，不掩護；量的是攻擊開始到 `failed`（`unnotified`）之間外層顯示 frame 的時間。

## 結果

### 靜止頁面的取樣 CPU 占比

| 頁面（元素數） | 改之前：占比、比對次數／秒數、一次比對 | 改之後：占比、比對次數／秒數、一次比對 |
| --- | --- | --- |
| 10 個標記（22） | 3.7%，598／30，1.8 ms | 3.0%，579／30，1.5 ms |
| 1000 個標記加 4000 個方框（5012） | 12.0%，126／60，57 ms | 5.8%，118／120，59 ms；5.4%，468／480，55 ms |
| 3000 個標記加 12000 個方框（15012） | 29.2%，127／60，138 ms | 4.5%，54／180，149 ms；5.1%，166／480，148 ms |
| 4500 個標記加 15000 個方框（19512） | 96.7%，325／60，179 ms | 4.9%，42／180，211 ms |

原始資料：[cpu-before.jsonl](data/2026-11-05-1081-sampling-cpu/cpu-before.jsonl)、[cpu-after.jsonl](data/2026-11-05-1081-sampling-cpu/cpu-after.jsonl)。每一次都沒有發現、沒有 `failed`，frame 一直顯示。

取樣的間隔是指數分布，一個時間窗裡的取樣次數隨機起伏，占比跟著起伏約 1 ÷ √取樣次數：120 秒的 1000 個標記約 60 次取樣，約 ±13%（5.0% 的頁面量到 4.4% 到 5.7% 都正常）；180 秒的 3000 個標記約 ±19%。所以 1000 與 3000 個標記另外量了 480 秒（約 ±7% 與 ±11%）。「一次比對」是 CPU 時間除以比對次數，含心跳與其他工作，比 runtime 自己量的比對時間略多，所以占比略高於 5% 也符合預期。

#### 被否決的估計（安全審查之後試過）

| 頁面 | 移動平均與最近一次中較小的 | 移動平均與最近兩次中較貴那次兩者中較小的 |
| --- | --- | --- |
| 10 個標記 | 3.0% | 2.0% |
| 1000 個標記加 4000 個方框（120 秒） | 7.0%，143 次比對 | 5.4%，128 次比對 |
| 3000 個標記加 12000 個方框（180 秒） | 6.8%，80 次比對 | 6.0%，74 次比對 |
| 4500 個標記加 15000 個方框（180 秒） | 4.6%，40 次比對 | 5.8%，47 次比對 |

原始資料：[cpu-rejected-variants.jsonl](data/2026-11-05-1081-sampling-cpu/cpu-rejected-variants.jsonl)。取較小的總是挑到較便宜的比對：一次取樣在繪製後的那次比對比繪製前便宜，雜訊也偏一邊，所以估計偏低、取樣偏密。只取最近一次的 1000 與 3000 個標記比預期的取樣次數多出約 2.8 與 1.8 個標準差，超出上面說的隨機起伏；第二種偏高的幅度較小，單次量測不能和起伏分開。採用的做法（移動平均，但最多是最近兩次中較貴那次的 2 倍）在同一個頁面上不改變估計，所以與審查前的程式一樣約 5%，又讓一次昂貴的比對在之後兩次比對內失效（單元測試）。

- 改之前，一次比對超過 25 ms 的頁面被 1 秒的上限夾住：12% 與 29% 符合 2 × 成本 ÷ 1 秒（11.4%、27.6%）。
- 改之前的 4500 個標記占 97%：比對平均每 185 ms 一次，60 秒只有 118 個心跳（應有約 300 個）。一次取樣連著的兩次比對（約 360 ms）讓下一個心跳遲到超過 250 ms，遲到的心跳立刻比對（`sampleNow`，再加一次對齊繪製的取樣），又讓再下一個心跳遲到，runtime 就不停地比對。改之後 runtime 自己在心跳該到之後的比對不算遲到（`beatIsLate`），同一頁 180 秒有 843 個心跳，占 4.9%。
- 改之後，1000 個標記以上的頁面都是約 5%（平均間隔是一次比對成本的 40 倍：約 2.4、6、8.4 秒）；10 個標記的頁面被 100 ms 的下限夾住，占得更少，平均間隔與改之前相同（單元測試也確認一次比對 25 ms 以下的頁面平均間隔不變）。

### 沒被通知的改動被關閉的時間（改之後）

| 頁面 | 平均間隔 | 3 次，攻擊開始到關閉（期間外層一直顯示 frame） |
| --- | --- | --- |
| 10 個標記 | 100 ms（下限） | 92、28、354 ms |
| 1000 個標記加 4000 個方框 | 約 2.4 秒 | 553、1227、2816 ms |
| 4500 個標記加 15000 個方框 | 約 8.4 秒 | 8600、1370、1186 ms |

原始資料：[attack-after.jsonl](data/2026-11-05-1081-sampling-cpu/attack-after.jsonl)。每一次都以 `failed`（`unnotified`）關閉；只有 4500 個標記的第 3 次在關閉前送出一則 `compared`，外層一直顯示，所以是沒有發現的那種：這種安排每次取樣都碰得到，所以關閉的時間是平均約一個平均間隔的指數分布。2026-11-03 在開發者工作站，同一種攻擊在 15000 個方框的頁面（平均間隔約 1 秒）是 0.9 到 2.0 秒。

一次比對 800 ms 以上的頁面，平均間隔是上限 32 秒，沒有實測：依上表推算，關閉前的時間平均約 32 秒，1 分鐘後還沒關閉的機率約 15%，2 分鐘約 2%（README「頁面作者能把取樣拉到多稀」）。

### 單元測試

`frontend/sandbox/test/sampling.test.ts` 的 16 個測試通過（[sampling-test.txt](data/2026-11-05-1081-sampling-cpu/sampling-test.txt)）：一次比對 25 ms 以下的平均間隔與改之前相同；25、50、100、250、500、800 ms 的頁面占 5%，0 到 800 ms 每 0.25 ms 都不超過 5%；外層藏起時的間隔是 4 倍、不超過 32 秒、占不超過 2.5%；800 ms（上限的邊界）以上停在 32 秒；比對成本的估計（`sampleCostMs`）在同一個頁面上就是移動平均，一次取樣的兩次比對成本不同時仍約 5%，一次昂貴的比對（含第一次）之後兩次比對內就回到頁面成本的 2 倍以內；心跳的遲到不算 runtime 自己在該到之後的比對，頁面卡住的時間照樣算。整套前端檢查的結果在 PR。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 一次比對 25 ms 以上的頁面取樣不超過約 5%；25 ms 以下的平均間隔不變（單元測試） | 通過：單元測試；Chromium 實測 1000、3000、4500 個標記的頁面 4.5% 到 5.8%，480 秒的時間窗 5.4% 與 5.1%（隨機起伏見上） |
| 外層藏著 frame 時，間隔同樣守住上限（單元測試） | 通過：單元測試（間隔不超過 32 秒，占不超過 2.5%） |
| 在 Chromium 實測一次大頁面的取樣 CPU 比例 | 通過：1000 個標記加 4000 個方框從 12% 降到 5.4%（480 秒）；4500 個標記加 15000 個方框從 97% 降到 4.9% |
| README 的平均間隔、CPU 比例與大頁面的防禦數字已更新 | 通過：「取樣的 CPU 上限約 5%」、`beat` 一項與「還擋不住的」的表 |

待測：

- 其他裝置與瀏覽器：較慢的裝置比對更貴，平均間隔跟著變長（最多 32 秒）；Chrome 以外的瀏覽器在 Laysi/trustiot-v2#946。
- 比對成本撐到上限（32 秒）時被關閉的時間只是推算，沒有實測。
- 每種頁面的攻擊只跑 3 次。
