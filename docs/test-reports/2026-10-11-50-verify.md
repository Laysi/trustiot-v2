# Laysi/trustiot-v2#50 獨立驗證：protocol crate 的惡意輸入與 ACL

issue：Laysi/trustiot-v2#50（閘道器與雲端的 MQTT 訊息格式）。實作 PR：Laysi/trustiot-v2#250。

## 目的

閘道器在客戶現場，可能被入侵，所以每條解碼路徑都要當成處理惡意輸入。本驗證不信任實作者自己的測試，另外檢查：

- 每個解碼入口（11 種訊息、`peek_header`、`parse_topic`）在惡意輸入下不 panic、不配置無界記憶體、不花超線性時間、不接受超出限制的訊息。
- 版本欄位 `v`、`rev`、巢狀、不定長度、重複鍵、整數與浮點邊界、字串與 ID 邊界。
- topic 解析與 dynsec ACL：為某個 CN 產生的 ACL 不可能變成萬用字元。這一項除了單元測試，還用真的 Mosquitto 2.1.2 驗證。
- 拆包的序號規則與大小上限；固定樣本（golden）穩定性。

## 受測 commit

- 受測程式：`main` 的 `8931a63`（含 PR #250 的 `5feeb08`）。產品程式碼沒有任何修改。
- 本驗證只新增測試與資料，分支 `test/50-verify`。

## 環境

- 本機 Linux 7.2（Fedora），8 核共用；`CARGO_BUILD_JOBS=2`，cargo target 在 worktree 內。

## 發現

嚴重度標準：中 = 建議在上線前處理；低 = 有界或需另外條件才有影響，記錄即可；資訊 = 程式碼閱讀所得，未實測或僅提醒下游。

### F3（中，縱深防禦）：ACL 的 `up/#` 讓被入侵的閘道器能在 broker 上留下無界數量的 retained 訊息

角色規則 `publishClientSend trustiot/v1/gw/%u/up/#` 允許發布到自己 `up/` 之下任意深度的 topic，不限於協定的 6 個 `up` channel，ACL 也無法限制 retain。被入侵的閘道器可發布 `trustiot/v1/gw/<自己>/up/spam/<任意>` 並設 retain，每則最大到 broker 的 maximum packet size（1 MiB 加 8 KiB），數量不限，吃光 broker 記憶體，影響所有租戶。

- 重現：資料 `data/2026-10-11-50-verify/mosquitto/`，`setup.sh` 註冊角色與 client，`retained.sh` 以 `gw-1` 發布 3 則各 200,000 位元組的 retained 到 `up/spam/1..3`，`retained.out` 顯示雲端 client 訂閱 `trustiot/v1/gw/gw-1/up/#` 收到它們。
- 建議：`gateway_role_acls()` 改為每個 `up` channel 一條 `publishClientSend`（精確 topic，6 條，沒有萬用字元），這樣每台閘道器最多 6 個 retained slot；`up/` 本身也不需要發布權限。同時在 broker 層設定每個 client 的訊息與配額（屬 Laysi/trustiot-v2#84）。
- 這需要協調者決定，所以 PR 標 `review:human`。

### F2（低）：極小的惡意 payload 讓解碼暫時配置大量記憶體，README 的「不會配置記憶體」不精確

陣列宣告 N 個項目、後面接 N 個一位元組的 `true`，序列化前 serde 先預留空間，每個集合上限 1 MiB。結構檢查只保證「宣告數量不超過剩餘位元組」，擋不住這種預留。實測（release，`data/.../alloc-amplification-output.txt`）：

| payload | 大小 | 解碼配置高峰 |
| --- | --- | --- |
| 心跳，`devices` 宣告 1,000 項 | 1,017 位元組 | 184,000（181 倍） |
| 心跳，`devices` 宣告 4,200 項 | 4,217 位元組 | 772,800（183 倍） |
| 遙測，`series` 宣告 4,200 項 | 4,244 位元組 | 302,401（71 倍） |
| 心跳、遙測、日誌、設定，宣告 20,000 項 | 約 20 KB | 約 1 MiB（上限，之後倍數隨 payload 變大而下降） |

fuzz 的 954 萬輸入中，絕對高峰 13.3 MB，倍數最高約 180 倍。有界、暫時；但雲端對很多閘道器並行解碼時是放大因子（例如 100 個並行解碼各 1 MiB 就是 100 MiB）。精確重現輸入：`F2a-heartbeat-devices-x4200.cbor.hex`、`F2b-telemetry-series-x4200.cbor.hex`。新增的測試 `a_hostile_array_count_reserves_at_most_a_bounded_amount` 把上限固定在 1.2 MB，上限變大會失敗。建議：更正 README 的說法，或對 `Vec` 欄位用有上限預留的 visitor；雲端以並行上限約束解碼。

### F1（低）：map 型別的資料欄位重複鍵「後者勝出」，其餘欄位都拒絕重複

`LogEntry.fields`（`BTreeMap<String,String>`）與 `DeviceStats.exception_codes`（`BTreeMap<u8,u64>`）遇到重複鍵不報錯，後出現的值覆蓋前面的。結構欄位則一律以 `duplicate field` 拒絕。影響小：日誌欄位與例外碼計數沒有安全語意，但與 `codec.rs` 與 README「重複欄位拒絕」的精神不一致，且 `exception_codes` 的重複計數會被悄悄丟掉。重現：`F1a-log-fields-repeated-key.cbor.hex`（`LogBatch`，`timeout_ms` 出現兩次，解出 `OVERRIDDEN`）、`F1b-heartbeat-exception-codes-repeated-key.cbor.hex`（`Heartbeat`，例外碼 2 出現兩次，解出 999）。fuzz 中這兩個欄位名列為已知例外（`KNOWN_LAST_WINS_MAPS`），修正後應從清單移除。

### F4（低）：IPv4-mapped IPv6 位址繞過未指定、多播與廣播位址的檢查

`Host::new("::ffff:0.0.0.0")`、`::ffff:224.0.0.1`、`::ffff:255.255.255.255` 都被接受，而 `0.0.0.0`、`224.0.0.1`、`255.255.255.255` 被拒絕。設定來自雲端，不是閘道器可控的輸入，故為低。另（由程式碼閱讀推測，未實測）：`Host::canonical` 不正規化 mapped 位址，`::ffff:1.2.3.4` 與 `1.2.3.4` 被視為不同主機，同一個端點可混用兩種傳輸而繞過 `mixed_transport` 檢查。重現：`findings-summary.txt` 與 `probe-findings-writer.rs.txt`。

### 資訊

- 心跳沒有跨欄位檢查（程式碼閱讀，未實測）：`memory_available_bytes` 可大於 total、`failures` 總和可大於 `requests`、`requests` 可為 0；README 的成功率公式 `1 - (connect+timeout+exception)/requests` 在這些輸入下可能為負或除以 0，下游要處理。
- 遙測的文字值、日誌的 message、target、fields 接受 NUL 與控制字元（實測 NUL 接受）。寫入 Postgres 的 text 欄位會失敗，寫日誌需跳脫；下游要處理。
- `peek_header` 不檢查大小上限（程式碼閱讀）：呼叫端要先以 MQTT 的 maximum packet size 限制。

## 結論

四條驗收條件都有獨立證據；954 萬個解碼輸入加 600 萬個 topic 輸入沒有 panic、逾時或不變條件被違反；ACL 在真 Mosquitto 2.1.2 上的行為與 README 一致。發現 1 項建議在上線前處理（F3，`up/#` 過寬）與 3 項低風險（F1、F2、F4）、3 項資訊。因為 F3 需要決定，PR 標 `review:human`。
