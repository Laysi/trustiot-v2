# 換頁捲動位置重設的實測

對應 issue：`Laysi/trustiot-v2#1185`。依據：`docs/test-reports/2026-11-07-1179-projector-walkthrough.md` 的問題 4（`Laysi/trustiot-v2#1179`）。

- 一台 arm64 Linux 虛擬機（建置主機），rootless podman。
- 瀏覽器：`frontend/e2e/image.ts` 釘住的 Playwright 映像（Chromium），zh-TW、Asia/Taipei、淺色、縮放 100 %。
- 頁面：UI 預覽（`vite --mode ui-preview`），分支 `fix/1185-scroll-reset`（從 main `bcadc8e2`）。
- 預覽裡「回答加儀表板卡片」的對話（`3e7b1c94-…`）在 `Laysi/trustiot-v2#1175`（分支 `feat/1175-source-panel`，PR #1178）才有，main 還沒有。所以瀏覽器檢查在那個分支的樹上，套用本分支改動的所有 `frontend` 檔案後跑；腳本與分支無關。

## 上一頁沒有還原的原因

第一版修正只加了 `ScrollRestoration`：新頁面在頂端，但上一頁回對話時 1920×1080 的位置不對。用 `back-trace.mjs` 在 `goBack()` 前後記錄每次 `scroll` 事件、`scrollTo`／`scrollIntoView`／`focus` 呼叫與頁面高度（`back-trace-before-fix.jsonl`）：

- 沒有任何程式在回來後把頁面捲到頂端或聚焦某元素：整段只有一次 `scrollTo`，是 `ScrollRestoration` 自己的還原。先前報告的「789 → 0」是檢查腳本的問題：捲到最底時「開啟儀表板」連結被黏在下方的輸入框蓋住，Playwright 為了點它先把頁面捲動，路由器存下的位置因此是 0。現在的腳本像使用者一樣在連結中心按，連結被蓋住時改成往上找到可以點的最深位置（1920×1080 為 469 px）。
- 真正的原因有兩個，都是頁面回來時的高度和離開時不同：
  1. 還原發生在頁面還沒長完時：`scrollTo(0, 400)` 發生在頁面高度 1570，其後儀表板卡片與圖表載入，高度長到 1758。Chrome 的捲動錨定在這段時間把位置從 400 推到 470（469 的情況推到 539），都是 +70 px，所以看到的內容偏了 70 px。路由器只還原一次，不再修正。
  2. 離開前的版面比回來後的高 111 px（1869 對 1758）：卡片的「已儲存」提示與「開啟儀表板」連結是 `SavedDraftsProvider` 的頁面內狀態，離開頁面就沒了，回來時卡片又變回「草稿」與「儲存」按鈕。這 111 px 在圖表上方，所以就算位置精確還原，圖表也在不同的地方。
- 資料集（`gcTime: 0`，決策 33）在回來後重新執行，但卡片的標題、圖表與其占位的高度相同，不是高度差的來源；高度差來自上面兩點。

## 修正

- `frontend/src/lib/hold-scroll.ts` 與 `frontend/src/app/HoldBackScroll.tsx`（放在 `Layout`，與 `ScrollRestoration` 並排）：只在瀏覽器上一頁、下一頁（POP）時，以自己記錄的該歷史項目離開時的位置，在頁面高度每次改變時把位置放回去。使用者第一次輸入（滾輪、觸控、按鍵、指標按下）、頁面高度停止變動 1 秒、或 10 秒上限，三者最先到的就放手。位置按歷史項目記錄（頁面的 `scroll` 事件，隱藏頁面時寫進這個分頁的 session storage，所以重新整理後仍在）；保持期間的 `scroll` 事件是保持自己造成的（短頁面把位置夾住），不記錄，所以保持中又離開時，該項目仍是讀者離開時的位置。點連結換頁不受影響，仍從頂端開始。
- `frontend/src/pages/conversations/savedDrafts.tsx`：「這次存了哪些草稿版本」改存在 query cache（以租戶為鍵），不再是頁面內狀態。離開再回來，卡片仍是「已儲存」與連結，版面高度與離開前相同；登出、換使用者或換租戶時與其他快取一起清掉。不碰決策 33（沒有快取資料集結果）、資料集執行，也沒有動 `ConversationTurn.tsx`、`follow.ts`、`useFollowNewest.ts`、`lib/sticky-bars.ts`（#1182）。

## 結果

錨點：離開前，頂欄下緣以下第一個有文字的葉元素與它距頂欄下緣的位置；回來後找同一個元素（內容相同的第一個）量同一個位置。1280×600 與 1920×1080 的頂欄下緣分別在 154 與 110 px。

| 情境 | 離開前捲動 | 新頁面 scrollY | 儀表板頁首上緣 / 頂欄下緣 | 回來後 scrollY | 錨點位置（前 → 後） | 結果 |
| --- | --- | --- | --- | --- | --- | --- |
| 1280×600，對話 225 px | 225 | 0 | 186 / 154 | 225 | 59 → 59 | 通過 |
| 1920×1080，連結可點的最深處 | 469 | 0 | 142 / 110 | 469 | 1 → 1 | 通過 |
| 1920×1080，對話 400 px | 400 | 0 | 142 / 110 | 400 | 21 → 21 | 通過 |
| 1280×400，設備列表捲到底，開一台設備 | 408 | 0 | 不適用 | 408 | 不適用 | 通過 |

回來後頁面高度（1913 與 1869）與離開前相同。

對照（`browser-check-without-hold.jsonl`，有「已儲存」狀態的保存、拿掉 `HoldBackScroll`）：469 → 539、錨點 1 → −69；400 → 470、錨點 21 → −49；225 的情況通過。所以兩個改動都需要：只保存狀態不夠，只保持位置也不夠（見上一節的 111 px）。

## 結論

- 重現步驟（1280×600、225 px）：通過，儀表板頁從頂端開始，頁首完整可見。
- 1920×1080：通過。「捲到最底」時開啟儀表板的連結被輸入框蓋住，使用者點不到，所以最深是連結可以點的 469 px；400 px 也通過。
- 另一個換頁（設備列表到設備頁）：通過。
- 上一頁還原位置：三個對話情境的 scrollY 與錨點都回到離開時的位置，通過。
- 限制：保持位置在放手前（高度停止變動 1 秒，或 10 秒）若頁面還在長（例如回來時對話正在串流回答），它與頁面自己的捲動（#1182）可能互相拉扯，到放手為止；使用者一輸入就放手。這次沒有量這個情況。
- PR 第一次 CI 失敗的兩個前端測試：原因找到並修正，見下一節。

## PR 第一次 CI 的兩個前端測試失敗

PR 第一次的 CI（head `3a270046`）在 `frontend` job 失敗兩個測試。`bun run --cwd frontend test` 把測試檔分成 8 片，依序執行，兩個失敗各在一片：

- 第 2 片，`TenantDetailPage.test.tsx`「a suspended tenant can have its reason changed or be resumed; resuming makes it active again」：狀態卡裡找不到 `ops@example.test`，顯示的是使用者 ID 的縮寫。
- 第 4 片，`DevicePage.test.tsx`「consecutive buckets of the same text are one row」：找不到名稱符合 `/^History of /` 的區塊，歷史卡的名稱還是「History」。

兩者都是還沒載入完，不是資料錯誤。測試等到 h1 出現，就同步檢查第二個查詢才帶來的內容：

- 租戶頁的 email 由 `useUserNames` 查，這個查詢在租戶顯示之後才開始。
- 設備頁要等設備的 model 回來才選得出資料點，歷史卡的名稱跟著資料點。

稽核頁與佈建頁的測試本來就以 `findBy` 等 email。

### 重現

`contention.sh` 跑第 2 與第 4 片。測試程序與兩個忙碌迴圈共用兩個核心，讓計時器與 React 排程的先後接近負載高的 runner。每片約 7–8.5 秒，CI 上約 9.5 秒。

不加負載時，兩片各跑 3 次，本分支與 `Layout.tsx` 還原成 main 的樹都通過。加負載後的結果如下。各列的改動都做在建置主機的副本上，測試檔的組成不變，所以分片相同：

| 樹 | 兩片各跑 | 失敗 |
| --- | --- | --- |
| 本分支（`3a270046`） | 6 次 | 3 次：租戶頁 1 次、設備頁 2 次 |
| `Layout.tsx` 還原成 main | 6 次 | 0 |
| `Layout` 只有 `ScrollRestoration` | 6 次 | 4 次：設備頁 3 次、租戶頁 1 次；另有一次 `AnswerDashboards.test.tsx` 逾時，見「修正」 |
| `Layout` 只有 `HoldBackScroll` | 6 次 | 0 |
| 本分支，但 react-router 的 `enableScrollRestoration` 不做 `restoreScrollPosition` 的更新（改 `node_modules`） | 8 次 | 0 |

### 原因

React Router 的 `ScrollRestoration` 把已存的位置放在模組層級的物件，同一個 `bun test` 程序裡的測試檔共用。

1. 路由器每次換頁前，會存下目前的位置。記憶體路由器的第一個位置，key 都是 `default`。
2. 所以前面的測試只要換過頁，後面每個測試的路由器在掛載時，都會找到 `default` 的位置，多做一次 `restoreScrollPosition` 的狀態更新。這次更新在 `startTransition` 裡，整棵路由樹多 render 一次。
3. 負載高時，這次 render 改變了排程的先後，測試的同步檢查就跑在第二個查詢的結果畫上去之前。

上表最後一列只拿掉這次更新，失敗就消失，所以原因是它。

同一個機制也讓位置跟著順序走：本 PR 的捲動測試在 `default` 捲到 225 後換頁，同一片之後掛載的路由器都會 `scrollTo(0, 225)`。happy-dom 沒有版面，`scrollY` 會真的變成 225。

瀏覽器裡，只有 session storage 存有目前歷史項目的位置時（例如重新整理後），才會有這次更新。這正是 `ScrollRestoration` 原本的還原，不影響使用者。

### 修正

- `frontend/src/test/setup.ts`：每個測試前，把 `ScrollRestoration` 掛載時讀的 session storage 項目設成空物件，路由器就不帶任何已存位置。這個項目的 key 是 `react-router-scroll-positions`，React Router 文件寫明的預設值。
  - `routes.test.tsx` 在捲動測試之後加一個測試：新的路由器不還原前一個測試存下的 225。
  - 拿掉這個重設，這個測試就失敗（`Expected: not 225`）。
  - 只有這個重設、沒有下面兩處等待時，兩個 CI 失敗的測試在負載下各片 6 次都沒有失敗。
- 兩個測試改成等待：
  - 租戶頁的兩個 email 用 `findBy`。
  - 設備頁先等名稱為「History of …」的區塊。
- `AnswerDashboards.test.tsx`「a failing component or a dataset that fails affects only itself」：草稿改成另一個對話的，與同檔「datasets run only when the dashboard is near the viewport…」的做法相同。
  - 這個測試在建置主機逾時過 2 次，等到 bun 的 5 秒上限，都在有 `ScrollRestoration` 的樹：一次是先前不加負載的全套，一次是上表「只有 `ScrollRestoration`」那列。
  - 負載下，它的耗時與 `Layout.tsx` 還原成 main 的樹相近（各 8 次，中位數 50 ms 與 48 ms），所以是偶爾卡住，不是變慢。
  - 原因：草稿面板不等 viewport，就執行這個對話草稿的資料集，並與 answer 共用執行。
    - 面板那次 readings 失敗前，answer 的表格已經訂閱：兩邊都顯示「Run again」，測試通過。
    - 面板先失敗、answer 的表格才訂閱：React Query 對失敗的查詢在新訂閱時重查，這次成功，測試就一直等不到「Run again」。
    - 證實：修正途中曾改成先等儀表板區塊出現，再進入 viewport。面板因此每次都先跑完，這個測試 15 次全部逾時：負載下 14 次，不加負載 1 次。
    - 多出來的那次 render 可能讓 answer 較晚訂閱，所以兩次逾時都在有 `ScrollRestoration` 的樹；次數太少，無法確定。
  - 現在也先等 answer 的儀表板區塊出現，再只讓它進入 viewport。假的 viewport 只回報當下已在觀察的元素。

### 修正後

- 建置主機不加負載：`api:check`、`typecheck`、`lint`、`test`、`build`、`check:dist` 都以 0 結束，test 的結果是 1946 pass、0 fail。
- 加負載：第 2、4 片各跑 6 次，全部通過；全套跑 2 次，都是 1946 pass、0 fail。第 4 片平均 6.9 秒；修正前，本分支 7.6 秒，`Layout.tsx` 還原成 main 的樹 7.0 秒。
