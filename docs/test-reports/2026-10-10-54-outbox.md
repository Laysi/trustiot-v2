# outbox crate 驗收（2026-10-10）

對應 issue：Laysi/trustiot-v2#54 outbox crate：事件框架（同交易寫入、冪等消費、可重播）。原始資料在 [data/2026-10-10-54-outbox/](data/2026-10-10-54-outbox/)。

## 環境

- 機器：本機開發機，Fedora Linux 45（kernel 7.2.8），x86_64。驗收條件都在本機以真的 Postgres 與真的行程驗證，不需要 Kubernetes，本 issue 沒有 lab 端到端測試。
- 受測版本：分支 `feat/54-outbox`，從 `origin/main` 的 `4f9db40` 開始，之後合併到 `a25efe9`（含 CI workflow、service-kit 的內部身分驗證與測試時序修正）；下列結果是合併後的版本。
- 工具：Rust 1.99.0（`.prototools`）、podman 6.1.3（rootless）。所有 cargo 指令都設 `CARGO_BUILD_JOBS=2`。
- Postgres：`docker.io/library/postgres:18.6-alpine@sha256:77f585114c32fbca283dc835b0596f4e52b51b4c6662d7810b2f4084f60a1873`（與 service-kit 的測試相同）。兩種跑法都跑過：
  - 不設 `TEST_DATABASE_URL`、設 `CI=1`：每個測試起一個用完即刪的容器，缺容器執行環境時會失敗而不是略過。

- 當機與指標測試以 `outbox-example`（本 crate 的範例服務，建在 service-kit 上）為真的子行程，用 `kill -s KILL` 結束。

## 結果

- `CI=1 cargo test -p outbox`（容器模式）：單元 8、crash 2、delivery 13、metrics 1、notify 2、producer 3，全部通過，結束後沒有留下測試容器。輸出：[outbox-tests-containers.txt](data/2026-10-10-54-outbox/outbox-tests-containers.txt)。
- `cargo test --workspace`（共用資料庫）：contract、outbox、repo-check、service-kit 全部通過。輸出：[workspace-tests.txt](data/2026-10-10-54-outbox/workspace-tests.txt)。
- fmt、clippy（含 service-kit `--no-default-features`）沒有警告。

各測試做了什麼：

1. **回滾**（`a_rolled_back_transaction_leaves_no_event`）：三種失敗——明確 rollback、交易未 commit 就丟棄、交易中途出錯——之後 `outbox_event`、`outbox_aggregate`、業務表都是 0 列，消費端讀不到任何事件；接著一筆成功的交易送達，序號從 1 開始。
2. **當機**：
   - `an_event_committed_before_the_producer_is_killed_is_delivered_after_restart`：範例服務設定一小時後才開始處理，`PUT /v1/widgets/w-1` 回 200（已 commit）後以 SIGKILL 結束（確認是被訊號 9 結束）。事件在產生端的表裡、消費端尚無資料；重新啟動服務後事件送達，`applied = 1`，inbox 只有這個事件 ID。
   - `a_consumer_killed_mid_delivery_processes_the_event_once_after_restart`：handler 寫入後把交易開著，看到日誌「holding the delivery transaction open」（帶同一個 event_id）時 SIGKILL。Postgres 回滾該交易：沒有副本、inbox 0 列；重啟後送達一次，`applied = 1`，之後的輪詢不再套用。
3. **晚 commit 不漏讀**（`an_event_committed_late_is_delivered_not_skipped`）：C 先寫但不 commit、D 後寫並 commit；此時消費端一筆都不送（位置仍是 `0:0`，lag 顯示 D 在等），C commit 後兩筆依序送達。共用資料庫跑法下，其他測試的交易也會拖住讀取上限，`drain` 輔助函式因此以「lag 為 0」為完成條件，所有測試仍通過。
4. **重複投遞只處理一次**（`a_duplicate_delivery_is_processed_once`）：處理 10 筆後以 `Replay::SkipProcessed` 從頭再讀：`delivered = 0`、`duplicates = 10`，狀態與位置不變；從第 5 筆（含）再讀：`duplicates = 6`。測試用的 handler 若處理同一事件兩次會撞 `seen` 的主鍵而一直重試，測試會失敗。
5. **並行與副本**（`concurrent_writers_and_two_replicas_process_each_event_once_in_order`）：6 個寫入者 × 30 筆、4 個聚合，有的交易先取得交易 ID 並在交易內隨機停 0–4 ms，兩個消費端副本（各自的連線池）同時處理同一訂閱：180 筆全部處理、每筆一次（`seen` 180 列、inbox 180 列）、每個聚合的序號連續且依序（違規 0）。
6. **重播後狀態相同**（`replaying_from_a_position_rebuilds_the_same_state`）：30 筆、4 個聚合，狀態含每個聚合的總和與順序相關的雜湊；在同一筆交易清空狀態並 `Replay::Reprocess` 從頭重播後，狀態與第一次完全相同。
7. **lag 經 OTLP 可讀**（`the_lag_is_exported_over_otlp`）：範例服務設定 `telemetry.otlp_endpoint` 指向假的 OTLP/HTTP 接收端，延後處理並寫 3 筆；測試以 `opentelemetry-proto` 解碼 `/v1/metrics` 的內容，讀到 `outbox.consumer.lag = 3`（單位 `{event}`，屬性 `outbox.subscription = outbox-example.widget-names`、`outbox.source = <產生端 schema>`）與 `outbox.consumer.lag.age > 0`（單位 `s`）。另外 `lag_counts_committed_events_not_yet_processed` 驗證計數只含已 commit 的事件、處理完歸零；service-kit 的 `tests/otlp.rs` 驗證 kit 本身會送出指標。
8. **聚合內依序**（`an_aggregate_keeps_its_order_when_transaction_ids_are_inverted`）：B 先取得交易 ID（ID 較小），A 寫聚合 x 的第 1 筆並 commit，B 再寫第 2 筆。只用交易 ID 排序會先送第 2 筆；紀錄中兩筆的 `tx_order` 都是 A 的 ID，送達順序是 1、2。
9. **通知模式**：
   - `a_stale_reading_never_overwrites_a_newer_one`：新讀數先存、舊讀數晚到被拒；兩個副本競爭時（一方持有交易、另一方必須等待，測試確認它在等），兩種先後順序最後都是新版本。
   - `late_and_replayed_events_converge_on_the_current_state`：3 筆事件在狀態已經是第 3 版時才處理，只寫入一次（版本 3）；第 4 版寫入一次；`Reprocess` 重播 4 筆不再寫入；連版本紀錄都清掉再重播，結果仍是目前狀態。
10. 其他：重試留在原位、永久失敗進死信並跳過（`failures_are_retried_in_place_or_dead_lettered`）；`Handler::begin` 設定的交易層級設定在 `handle` 仍有效（`begin_runs_in_the_delivery_transaction`，給決策 29 用）；handler 尚未寫入時不拖住其他訂閱，另一個副本得到 `Busy`（`a_slow_handler_that_has_not_written_does_not_hold_back_other_consumers`）；收尾時只做完進行中的事件，同批其餘事件留到下次（`shutdown_finishes_the_event_in_flight_and_leaves_the_rest_of_the_batch`）；只用 README 列出的權限，產生端與消費端角色都能運作，消費端角色讀不到產生端其他資料表、不能刪事件（SQLSTATE 42501，`services_need_only_the_documented_grants`）；`StartFrom::Latest` 只略過讀取上限之前的事件；訂閱不能換產生端。
11. 讀取上限的佐證：在 Postgres 上手動確認，唯讀的 `REPEATABLE READ` 交易不會壓住 `pg_snapshot_xmin`，有交易 ID 的寫入交易會（README「順序與不漏讀」的代價說明以此為據）。

合併 main 之前，service-kit 的 `lifecycle` 測試在平行執行時偶爾失敗（`invalid_configuration_names_the_key_without_its_value`、`sigterm_fails_readiness_at_once_and_drains_requests_in_flight`，都是在日誌或連線狀態到位前就斷言），重跑即通過；本分支沒有改這些測試與它們測的程式路徑。main 的 Laysi/trustiot-v2#245 修正了這類時序，合併後的整套測試全部通過。

| 交易回滾時不產生事件（測試） | 通過 | 結果第 1 點 |
