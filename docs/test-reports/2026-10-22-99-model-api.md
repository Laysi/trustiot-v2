# 設備型號 API 的驗收證據（2026-10-22）

### 本次修正（2026-10-22）

2026-10-21 的實作在建置主機無法使用時寫成，當時 `tests/device_models.rs` 沒有在最終程式碼上跑過。2026-10-22 執行時發現並修正：

1. **共用的 product 資料庫並行設定 LOGIN 失敗**：`testkit::product::product_postgres` 在對角色執行 `ALTER ROLE ... LOGIN` 前就放開鎖，同一個測試執行檔的測試同時啟動時，Postgres 以 `tuple concurrently updated` 拒絕其中之一。改為設定完 LOGIN 才放開鎖（commit `2c911c2`）。
2. **刪除仍被使用的型號回 503 而不是 409**：`ON DELETE RESTRICT` 的外鍵拒絕刪除時，Postgres 回 SQLSTATE 23001（`restrict_violation`），不是 `NO ACTION` 的 23503。在 Postgres 18.6 以一次性容器確認：`ERROR: 23001: update or delete on table "p" violates RESTRICT setting of foreign key constraint "c_pid_fkey" on table "c"`。兩個代碼現在都對應到 409 `in_use`（commit `78f34a1`）。
3. **401 沒有 `cache-control: no-store`**：身分 extractor 回的 401 不經過 handler，沒有這個標頭。型號的路由改以 route layer 為每個回應加上它（commit `78f34a1`）。
4. **migration 測試的順序**：`assets` 成為 outbox producer 後，image 預期的檔案清單依套用順序把 outbox 檔案排在前面，資料庫讀出的紀錄則依名稱排序。測試改為兩邊都排序後比較（commit `78f34a1`）。
