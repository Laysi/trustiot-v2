# 日誌擷取測試偶發收不到事件：原因與修正後的重複執行

對應 issue：Laysi/trustiot-v2#581

## 環境

- 機器：開發者工作站（x86_64 Linux），8 核心，同時有其他建置在跑。
- Rust 1.99.0（`rust-toolchain.toml`）；tracing 0.1.44、tracing-core 0.1.36、tracing-subscriber 0.3.23（`Cargo.lock`）。
- 程式碼：分支 `fix/581-assistant-log-capture`，基於 main `c96d059d`。
- 「修正前」的數據跑在 main 的測試上；`service-kit` 那組是先把 2026-10-15 拿掉的 INFO 斷言加回來、還沒加鎖時跑的。
- 每次 `cargo test` 都用預設的並行方式，同一個測試執行檔裡的測試同時在不同執行緒上跑。

## 原因

`tracing::subscriber::set_default`（或 `with_default`）裝的 subscriber 只看得到自己執行緒的事件，但每個日誌敘述（callsite）是否啟用，整個行程只決定一次，結果會快取起來。tracing-core 0.1.36 的 `src/callsite.rs`：

- `Dispatchers::register_dispatch` 在 `dispatchers.len() <= 1` 時把 `has_just_one` 設為 true。只有一個 scoped dispatcher 存在時（也就是只有一個測試在擷取時），它一直是 true。
- 這時 `DefaultCallsite::register` 拿到 `Rebuilder::JustOne`，只用 `dispatcher::get_default` 問「第一個執行到這個敘述的執行緒」的 subscriber。這條路徑不拿鎖。
- 第一個執行到的若是另一個沒有擷取的測試的執行緒，它的預設是 `Dispatch::none()`（`NoSubscriber::register_callsite` 回傳 `Interest::never()`），這個敘述就被快取成「永不啟用」。擷取中的測試之後在自己的執行緒上執行同一個敘述，事件根本不會產生。下一次有測試建立 dispatcher 時快取才重算，所以擷取到的筆數可能是 0 到全部之間的任何數（CI 是 0 筆，本機一次是 2 筆）。

## 指令

修正前，可確定重現的最小案例（`repro_581.rs`，只在修正前暫時放在 `services/assistant/tests/`，原始碼見 [repro_581.rs.txt](data/2026-10-23-581-log-capture/repro_581.rs.txt)）：

```sh
cargo test -q -p assistant --test repro_581 -- --nocapture
REPRO_ORDER=before cargo test -q -p assistant --test repro_581 -- --nocapture
```

重複執行（以迴圈跑；`count.sh` 每次執行 `cargo test`，失敗就記下，最後印出失敗次數）：

```sh
# 修正前
for i in $(seq 1 100); do cargo test -q -p assistant --test agent || echo "run $i failed"; done
for i in $(seq 1 100); do cargo test -q -p service-kit --lib || echo "run $i failed"; done
# 修正後
for i in $(seq 1 300); do cargo test -q -p assistant --test agent --test agent_logs || echo "run $i failed"; done
for i in $(seq 1 200); do cargo test -q -p service-kit --lib || echo "run $i failed"; done
for i in $(seq 1 10); do CI=1 cargo test -q -p service-kit --test job_lock || echo "run $i failed"; done
```

## 結論

- 原因有程式碼證據（上面「原因」一節）與可確定的重現（0 筆對 3 筆），並在修正前的迴圈中重現了 CI 的失敗：通過。
- 修正後擷取日誌的測試連續重複執行都通過，執行時同一個行程裡的其他測試照常並行：assistant 300 次、service-kit 單元測試 200 次、job_lock 10 次，0 失敗：通過。
- 其他以 `set_default` 或 `with_default` 擷取日誌的測試已逐一檢查：
  - `crates/service-kit/src/migrations.rs`：有同樣的風險。2026-10-15 拿掉的 INFO 斷言就是因此偶發失敗；加鎖後把斷言加回（修正前 9/100 失敗，修正後 0/200）。
  - `crates/service-kit/tests/job_lock.rs`：有風險，但要先有條件才會觸發：多執行緒的 `periodic_runs_on_two_replicas_never_overlap` 遇到取鎖錯誤時，會在 worker 執行緒上執行 `scheduled job lock failed`，這正是擷取測試檢查的敘述。現在執行 `run_periodically` 的四個測試互相排隊。這個情況沒有在本機重現，修正依據是程式碼。
  - `crates/contract/tests/client_logging.rs`：沒有風險。這個執行檔只有這一個測試，被檢查的事件只在測試自己的執行緒上產生。
  - `crates/service-kit/src/telemetry/log_layer.rs`：沒有風險。每個測試檢查的都是自己函式裡的 `tracing::*!` 敘述，別的執行緒不會執行到；經 `tracing-log` 轉送的事件（`dispatch_record`）直接呼叫 `get_default` 與 `Dispatch::enabled`，不經過 callsite 的快取。
