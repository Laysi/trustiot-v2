# AI 儀表板：合併 main 之後的 API、遷移編號、清除、權限矩陣與軟刪除的對話

對應 issue：Laysi/trustiot-v2#150（AI 儀表板）。測試日期：2026-10-30 至 2026-10-31（Asia/Taipei）。

main 在 Laysi/trustiot-v2#774 加入了 assistant 的 API 骨架（對話串的 API、每 30 天的清除、權限矩陣）。這份報告是把 main 合併進 #150 的整合分支之後的證據：儀表板的 API 改用 main 的骨架、遷移改編號、對話的清除連同草稿刪除、儀表板的操作宣告進權限矩陣、跨租戶的負向測試併進 main 的套件，以及刪除（軟刪除）的對話的草稿隱藏。驗收條件的總表仍是 [2026-10-27-150-dashboards.md](2026-10-27-150-dashboards.md)，這份不改寫它。沒有原始資料目錄：輸出含本機路徑，摘要直接寫在「結果」。

## 結果

### 合併與 API 骨架

- 29 個衝突的檔案逐一合併兩邊的內容；main 的測試沒有改動就通過（`tests/api.rs` 10 個、`tests/conversation_threads.rs` 12 個、`tests/purge_job.rs` 1 個、`tests/purge_locks.rs` 2 個、`tests/history_store.rs` 5 個）。main 的 `tests/startup.rs` 只加上檢查服務的位址（指向關閉的埠）與儀表板的工具數、資料集執行，`tests/permissions.rs` 加上儀表板的操作（見下方「權限矩陣」）。
- 儀表板的路由併進 main 的 `api::routes`：一個 router、一份 OpenAPI 文件（main 的 tag，描述加上儀表板），每個回應都是 `no-store`；交易用 main 的 `begin`（2 秒的鎖等待），儀表板的 404 就是 main 的 `api::not_found`（`tests/dashboards_api.rs` 比對每個路由的 404 與不存在的 ID 逐位元組相同）。
- 合併時兩邊的數字要一起調整的地方：nightly 的時限（main 加的時間與 #150 的檢查服務合計 130 分鐘）、chart 的呼叫矩陣測試（main 改了結構，加上 assistant 呼叫 `dashboard-check`）、assistant 的連線數（main 的 8 個加清除角色的 2 個，`tests/chart_connections.rs` 用 main 的數字）、設定測試裡重複的金鑰檔變數、nightly 映像清單的順序。
- `api/openapi.json` 與 `frontend/src/api/schema.gen.ts` 由程式重新產生，`cargo run -p openapi -- --check` 與 `api:check` 都相同。

### 遷移的重新編號

- `0002_dashboards.sql` 以 `git mv` 改成 `0003_dashboards.sql`，排在 main 的 `0002_conversation_threads.sql` 之後；`src/schema.rs` 說明舊的名稱只在這個分支上、沒有任何發行版套用過。
- `0003` 在對話表加的唯一限制 `conversations_owner (tenant_id, conversation_id, user_id)` 與 `0002` 不衝突：主鍵已是 `(tenant_id, conversation_id)`，`0002` 給服務角色的欄位 UPDATE 不含 `user_id`，所以草稿指向對話的外鍵所參照的值不會變。
- `0003` 加上與 `0002` 相同、只在交易內有效的 `lock_timeout = '5s'`（`43f66a2`）：對話表在每個請求都會讀寫，migration Job 等不到鎖時失敗重試，而不是讓請求排在它後面。
- `cargo test -p migrate`：`registry` 6 個、`fresh_database` 1 個與其餘的 migration 測試通過；唯一的失敗是 `mqtt_broker` 的 `gateways_need_a_current_certificate_of_our_ca`，main 在同一台工作站上也失敗（與本分支無關，見「最後的檢查」）。

### 清除連同草稿（`21b1a80`）

`tests/dashboards_store.rs` 的 `the_purge_removes_an_expired_conversations_drafts_and_keeps_what_was_published` 經 main 真的 `purge::round` 執行：

| 檢查 | 結果 |
| --- | --- |
| 版本之間的兩個外鍵（前一版、還原指向的內容）的刪除動作 | 都是 `NO ACTION`（`confdeltype` 為 `a`），在敘述結束時才檢查，串聯刪除一個草稿的所有版本不會中途被拒 |
| 第一輪：一個過期的對話（兩個草稿，各有還原的列），另一個過期對話的草稿列被另一個工作階段 `FOR UPDATE` 鎖住，第三個對話已刪除但未過期 | `Round { purged: 1, skipped: 1 }`，一行 WARN，欄位只有 `job`、`purged`、`skipped`；清除的對話的草稿與版本都不在了，從它發布的已儲存儀表板逐列不變，被鎖住的那個完整留著，未過期的不受影響 |
| 鎖放開後的第二輪 | `Round { purged: 1, skipped: 0 }`，一行 INFO；已儲存的儀表板仍逐列不變 |

### 權限矩陣（`2d46d77`）

- 儀表板的 9 個操作宣告進 [docs/architecture/permissions.md](../architecture/permissions.md) 的「assistant」：發布、封存、取消封存要租戶 editor，其他是租戶 viewer。handler 在讀 body 與資料庫之前以 service-kit 的 `UserIdentity::require` 檢查；store 以 `UserIdentity::meets` 再檢查一次發布與封存的 editor。
- `cargo test -p assistant --test permissions -- --nocapture`：宣告檢查 32 個、探測 192 個，0 個失敗。16 個操作各以沒有 token、偽造的 token、別的受眾、沒有租戶、沒有租戶的 platform admin、每個角色、不認得的角色與換出的 token 呼叫真的執行檔；探測前後對話、訊息、捨棄的回合、提問紀錄、儀表板與版本的列數相同；身分服務的 token 交換、telemetry-query、assets 與檢查服務的位址都指向只計算連線數的本機埠，探測後都是 0；三個 editor 操作的拒絕各有 `role_too_low` 與 `no_tenant` 的 INFO 記錄。
- `cargo test -p testkit` 的 `the_matrix_covers_every_operation_of_the_api_spec` 通過（矩陣涵蓋 `api/openapi.json` 的每個操作）。

### 跨租戶（合併 commit 與 `135fd49`）

`cargo test -p assistant --test cross_tenant -- --nocapture`：3 個測試通過，148 個探測，0 個失敗（main 合併前是 79 個）。儀表板依 main 的 `World::user` 模型併入：已儲存的儀表板屬於租戶，草稿放在套件的使用者擁有的對話裡，所以發布也探測得到；新的 `a_conversations_drafts_stay_in_their_tenant` 以同一個使用者在兩個租戶各自的對話與草稿確認：在租戶 A 讀租戶 B 的草稿列表、草稿與版本列表，回應與不存在的 ID 逐位元組相同（404），沒有任何 B 的 ID、標題或租戶；沒有租戶時是 403；租戶 B 經同樣的路由照常讀得到自己的草稿。

### 軟刪除的對話的草稿（`7a6cb7a`）

決定誰看得到草稿的唯一查詢（`dashboards::store` 的 `CONVERSATION_OWNER`）加上 `deleted_at IS NULL`；寫草稿或從草稿寫版本的函式（工具的三種寫入、發布、還原）在自己的短交易裡以 `FOR SHARE` 鎖住對話那一列，與 main 的刪除（`FOR NO KEY UPDATE`）排隊。

| 測試 | 結果 |
| --- | --- |
| `dashboards_store`：`a_soft_deleted_conversations_drafts_are_hidden_until_it_is_restored`（原本 `#[ignore]` 的測試，改用 main 的 `store::delete` 與 `store::restore`） | 刪除後，對這個草稿（已儲存儀表板的草稿，最新版是 2）每個函式都回 `NotFound`：開啟、版本列表、資料集、草稿列表、工具的寫入、建立草稿、取用已儲存的儀表板、發布、還原、封存；每個呼叫在刪除前都是有效的。草稿的列不變；從它發布的已儲存儀表板逐列不變，擁有者與 viewer 都照常開啟，列表不變。還原後草稿原樣回來（版本 2、標題、擁有者的存取），可以再寫入版本 3 |
| `dashboards_store`：`a_conversations_delete_and_a_drafts_write_wait_for_each_other` | 寫入先：刪除等寫入的交易（以 `pg_blocking_pids` 確認在等鎖，不靠時間），寫入 commit 後刪除完成，草稿連新版本一起隱藏。刪除先：寫入等刪除，刪除 commit 後寫入回 `NotFound`，草稿的列不變 |
| `dashboards_api`：`a_deleted_conversations_drafts_answer_404_until_it_is_restored` | 以 API 刪除對話（204）後，草稿列表、開啟、版本列表、資料集、還原、發布、封存與取消封存 8 個請求的狀態、`cache-control`、`content-type` 與本文，與不存在的儀表板與對話逐位元組相同（404、`no-store`），版本數不變；已儲存儀表板的列表本文不變；以 API 還原（200）後，開啟、版本列表與草稿列表的本文與刪除前相同 |
| `dashboard_tool`：`a_write_to_a_conversation_deleted_meanwhile_is_refused_like_a_missing_dashboard` | 寫入停在檢查時以 API 刪除對話：刪除立即回 204，寫入還沒結束（工具在檢查回答之後才開交易）；放行檢查後寫入被拒，模型拿到的文字與不存在的儀表板完全相同；還原對話後草稿仍是原本的版本 1 |

反例（見「指令」）：去掉 `deleted_at IS NULL` 時，四個測試都失敗（API 的測試裡 8 個請求分別回 200、201、422 與 503，沒有一個是 404；工具的寫入存成了新版本）；去掉 `FOR SHARE` 時，`a_conversations_delete_and_a_drafts_write_wait_for_each_other` 在等鎖的上限（120 秒）後失敗，刪除沒有等寫入。
