# assets 服務：設備 API（2026-10-24）

Laysi/trustiot-v2#100（rebuild checklist C2）：租戶的設備 API。每台設備屬於一台目前綁定到該租戶的閘道器與租戶的一個型號；連線設定與取樣間隔先經欄位規則，再經 `crates/protocol` 的閘道器設定檢查；建立、更新、刪除各寫出 `assets.device_*` 事件。規則、選定的數值與理由在 [services/assets/README.md](../../services/assets/README.md) 的「設備」。這份報告是四條驗收條件的證據。

### 跨租戶負向測試（`tests/cross_tenant.rs`）

`assets.devices` 以 `pg_table!` 宣告（每個租戶 9 列，每列有自己的閘道器、綁定與型號，canary 是主機名稱）；設備的列表、讀取、更新、刪除四個端點宣告為探測對象。157 個探測全部通過，其中 `assets.devices` 與設備端點：

| 探測 | 結果 |
| --- | --- |
| read as tenant A / B | 只看得到自己的 9 列，看不到對方的 |
| read without a tenant | 一列都看不到 |
| update own rows | 只碰到自己的 9 列 |
| move own rows into the other tenant | 被拒（42501） |
| insert into the other tenant | 被拒（42501） |
| `GET /api/assets/v1/devices` | 200，自己的 9 列都在、沒有對方的；沒有租戶 403 |
| `GET`、`PUT`、`DELETE /api/assets/v1/devices/{device_id}` | 對方的設備 404、回應沒有對方的資料；沒有租戶 403；正向對照：自己的設備 200、200、204 |

建立設備（`POST /api/assets/v1/devices`）以理由豁免：body 必須指向呼叫者租戶已綁定的閘道器與型號，suite 的 body 範本只能代入 `{id}`、`{tenant}`、`{canary}`，做不到；body 沒有租戶欄位，服務只寫進呼叫者的租戶，`names_gateways_and_models_are_checked` 測別的租戶的閘道器與型號都被拒、兩個租戶都沒有寫入。既有的表與端點照舊通過。完整報告：[cross-tenant-report.txt](data/2026-10-24-100-device-api/cross-tenant-report.txt)。
