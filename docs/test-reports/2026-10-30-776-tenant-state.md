# 租戶狀態機：停權、恢復與版本化狀態事件（2026-10-30）

Laysi/trustiot-v2#776：身分服務的 `identity.tenants` 加上狀態、停權原因、版本與進入狀態的時間（`0008_tenant_state.sql`），平台管理者本人以 `GET`/`PUT /api/identity/v1/platform/tenants/{tenant_id}/state` 讀取、停權與恢復，每次改變經 outbox 發出帶快照的 `identity.tenant_state_changed` v1（`{state, reason, state_version}`）。這份報告是驗收條件的證據：全部由自動化測試以 `CI=1` 實際執行，需要容器的測試不略過。

## 環境

- **程式碼**：分支 `issue-776-tenant-state`，commit `8b2492bd`（rebase 到 main `1bf6759e` 之後，沒有衝突）。
- **機器**：建置主機（arm64 Linux VM），經檢查佇列執行。容器測試由 podman 起 `testkit::product` 的拋棄式 TLS Postgres，以 migration Job 的程式套用整個產品的 schema（含 `0008_tenant_state.sql`），再以真的 `identity` 執行檔（服務角色 `identity_app`、平台角色 `identity_platform`）回應請求。
- **工具**：`.prototools` 與 `rust-toolchain.toml` 釘選的 Rust 1.99.0、Bun 1.4.2。
- **設定**：`CI=1`。

## 指令

在 repo 根目錄：

```sh
cargo fmt --all --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo run --locked -p openapi -- --check
CI=1 cargo test --locked --no-fail-fast --workspace --exclude agent
bun install --cwd frontend --frozen-lockfile
bun run --cwd frontend api:check
bun run --cwd frontend typecheck
bun run --cwd frontend lint
bun run --cwd frontend test
```

驗收證據可以單獨重跑：

```sh
CI=1 cargo test -p identity --test tenant_state
CI=1 cargo test -p identity --test permissions --test cross_tenant -- --nocapture
cargo test -p identity --lib tenant_state
cargo test -p contract --test events tenant_state_changed
```

全部在建置主機（arm64 Linux VM）上執行，`exit 0 at 14:10:38 (build host)`。

開發中的測試執行找到兩個問題，都已修正並由上面的執行涵蓋：trigger 的 IF 條件裡的 `CASE ... THEN` 讓 PL/pgSQL 提早結束條件（migration 套用失敗，`syntax error at end of input`）；`deleted` 的原因 CHECK 原本寫成 `= 'contract_terminated'`，原因是 NULL 時 CHECK 結果是 NULL 而被放行，改成 `IS NOT DISTINCT FROM` 後步驟 10 的「刪除時拿掉原因」得 23514。

`tests/tenant_state.rs`（`platform_administrators_suspend_and_resume_tenants_with_versioned_events`）依序驗證：

| 步驟 | 驗證的行為 |
| --- | --- |
| 1 | 新租戶是 `active`、版本 1，`state_changed_at` 等於建立時間 |
| 2 | 停權（`non_payment`）得版本 2，`state_changed_at` 晚於建立時間；同狀態同原因再送一次回原本的快照，資料庫不變；換原因（`security_or_abuse`）得版本 3；恢復（`{"state": "active"}` 與 `"reason": null` 兩種寫法）得版本 4 |
| 3 | 4 個相同的停權請求同時送出：每個回應都是同一個快照（版本 5），資料庫的版本是 5，outbox 只多一個事件 |
| 4 | 合約終止得版本 6；之後恢復、換成 `non_payment` 或 `security_or_abuse` 都回 409 `conflict`、訊息 key `tenant.state_final`，資料庫完全不變；同樣的合約終止再送一次回原本的快照 |
| 5 | 租戶 B 由超級使用者先合約終止、再設成 `deleted`（Laysi/trustiot-v2#109 的動作）：讀到 `deleted`、`contract_terminated`、版本 3；恢復、停權、合約終止都回 409，資料庫不變 |
| 6 | 租戶 A 的 outbox 有序列 2 到 6 的五個 `identity.tenant_state_changed`，各帶當時的快照與平台管理者為 `actor`；租戶 B（只由資料庫直接修改）沒有事件 |
| 7 | 403 `permission_denied`：租戶 C 的 admin、租戶 A 的 viewer、沒有租戶的使用者、平台管理者由 Assistant 或 Assets 換發的 token（帶 `act`），對 `GET` 與 `PUT` 都一樣；不存在的租戶、不是 UUID 的路徑、`text/plain` 與超過上限的 body 也一樣得 403，證明在讀路徑、body 與資料庫之前就拒絕。沒有 token 與給其他服務的 token 得 401。拒絕前後資料庫與 outbox 不變 |
| 8 | 不存在的租戶 404、路徑不是 UUID 400、沒有或不是 JSON 的 `Content-Type` 400、不是正確形狀的 JSON body 400、`deleted`／不認得的狀態、停權沒有原因、恢復帶原因、不認得的原因 422（欄位 `/state`、`/reason`）；什麼都沒寫 |
| 9 | 後台以 `GET /api/identity/v1/platform/tenants/{tenant_id}/event-log` 讀到租戶 A 的五次改變（含原因、版本與操作者），新到舊 |
| 10 | 超級使用者直接改 `state_changed_at`：trigger 保留原值。服務角色：`state`、`suspension_reason`、`state_version` 的更新與 `FOR NO KEY UPDATE` 可以；改 `name`、`created_at`、`tenant_id`、`state_changed_at`、INSERT 帶 `state` 或 `state_version`、DELETE 都得 42501；trigger 拒絕（42501）改變不升版本、跳號、升版本卻沒改變、版本倒退、合約終止後恢復或換原因、`active` 直接變 `deleted`；CHECK 拒絕（23514）停權沒有原因、刪除時拿掉原因；合約終止變 `deleted` 可以；另一個租戶的列更新 0 列 |
| 11 | 日誌有 `changed a tenant's state`、`refused to change a tenant's state`、`refused to read a tenant's state` |

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 併發停權只產生一個新版本（測試） | 通過：步驟 3，4 個同時的相同停權都回版本 5，資料庫版本 5，outbox 一個事件（步驟 6 對照序列） |
| 停權與恢復（含原因）寫進操作紀錄（測試） | 通過：步驟 6 與 9，outbox 的事件帶快照與操作者，事件層記進租戶 A 的操作紀錄，後台讀得到 |
| 不是平台管理員、或 token 帶 `act`，在讀本文之前就回 403（測試） | 通過：步驟 7；另有 `tests/permissions.rs` 對兩個操作的每種呼叫者探測 |
| 合約終止與 `deleted` 的恢復回 409，版本號不變（測試） | 通過：步驟 4 與 5，資料庫快照前後相同；資料庫的 trigger 也擋（步驟 10） |
