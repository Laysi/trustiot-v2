2026-10-09 PoC 的攻擊直接以租戶帳號執行：全部被資料庫拒絕，或答案裡沒有其他租戶的讀數；超過讀取列數、記憶體、時間上限的查詢分別以 `TOO_MANY_ROWS`、`MEMORY_LIMIT_EXCEEDED`、`TIMEOUT_EXCEEDED` 中止（[tenant-accounts.txt](data/2026-10-26-143-ai-sql/tenant-accounts.txt)，在 `829cfc8` 上重跑，39.08 s 通過）。同一個測試也確認帳號被改時的處理：

- 密碼被改：下一個 API 呼叫自動改回；
- 查詢上限在帳號上被改寬、或帳號被改成別的租戶：API 回 503、不執行查詢，回不出別的租戶；
- 租戶角色不再是帳號的 default role（`ALTER USER … DEFAULT ROLE NONE`，依 2026-10-26 的決定維持現行處理）：兩次呼叫都回 503、沒有該租戶的讀數，每次都記一筆錯誤日誌（原因 `other roles`）；之後帳號的 default role 仍是空的，服務沒有自動改回；管理者改回後下一個呼叫恢復，可查期間沒有被動到。在工作站上把服務的角色檢查暫時拿掉時，這個案例失敗在「第 1 次呼叫的錯誤日誌」（之後已還原，未提交）。

## 結論

1. **2026-10-09 PoC 的攻擊類型全部被解析器拒絕或讀到 0 筆**：通過。經入口的 43 種攻擊（`sql_api.rs`）都被檢查拒絕，或只回 A 自己的讀數；直接以租戶帳號執行時（`tenant_accounts.rs`）也都被資料庫拒絕或讀不到其他租戶。
2. **繞過可查期間的查詢無法讀到鎖住的期間**：通過。84 種繞過以租戶帳號直接執行（`queryable_period.rs`，另加 9 項只能直接對資料庫做的）與經入口執行（`sql_api.rs`）都讀不到窗外的列；帳號改不了自己的時間窗；方案改窗後下一個查詢生效。
3. **解析器拒絕的語法回傳通用錯誤類別給 agent**：通過。入口回 422 與封閉的類別（`sql_api.rs`），工具把類別換成固定說明給模型，服務多給的文字或不認得的類別都不會進到模型（`assistant/tests/telemetry_sql.rs`）。
4. **`SET ROLE`、`SET DEFAULT ROLE` 與其他不是 SELECT 的敘述都被解析器拒絕，不會送到 ClickHouse**：通過。15 種敘述都回 422，`system.query_log` 裡租戶帳號只執行過 `Select`、探測標記 0 筆；工具對真正的路由送出的拒絕敘述，Postgres 與 ClickHouse 的連線數都是 0。
5. **同一段 SQL 以另一個租戶的身分執行時，只讀到該租戶的資料**：通過（A、B 各 10 列，全是自己的標記）。
6. **歷史 API 的彙總序列改讀 1 分鐘與 1 小時彙總表，路徑、參數與欄位不變**：通過（`history.rs`，與參考值相同；邊界差異寫在 `services/telemetry-query/README.md`）。
7. **SQL 入口只接受 AI 助理的呼叫，入口閘道擋下 `/internal` 路徑**：通過。入口只接受 assistant 換出、帶租戶角色的 token（使用者自己的、別的服務的、沒有租戶的都 403）；chart 的 DENY policy 與 mesh 的路徑正規化以 `bun test deploy/chart` 確認。這次沒有在叢集上以這條路由實測 gateway：通用的 `/internal*` 拒絕已在 2026-10-10 的入口 e2e（[2026-10-10-62-ingress-e2e.md](2026-10-10-62-ingress-e2e.md)）實測過，針對 `/internal/telemetry/v1/sql` 的叢集探測列為後續的進階驗證。

範圍裡的「租戶帳號的預設角色若被改掉，維持回 503 與錯誤紀錄、不自動修復」：通過（`tenant_accounts.rs`，見「租戶帳號」一節）。
