### 租戶帳號（`services/telemetry-query/tests/tenant_accounts.rs`）

2026-10-09 PoC 的攻擊直接以租戶帳號執行：全部被資料庫拒絕，或答案裡沒有其他租戶的讀數；超過讀取列數、記憶體、時間上限的查詢分別以 `TOO_MANY_ROWS`、`MEMORY_LIMIT_EXCEEDED`、`TIMEOUT_EXCEEDED` 中止（[tenant-accounts.txt](data/2026-10-26-143-ai-sql/tenant-accounts.txt)，在 `829cfc8` 上重跑，39.08 s 通過）。同一個測試也確認帳號被改時的處理：

- 密碼被改：下一個 API 呼叫自動改回；
- 查詢上限在帳號上被改寬、或帳號被改成別的租戶：API 回 503、不執行查詢，回不出別的租戶；
- 租戶角色不再是帳號的 default role（`ALTER USER … DEFAULT ROLE NONE`，依 2026-10-26 的決定維持現行處理）：兩次呼叫都回 503、沒有該租戶的讀數，每次都記一筆錯誤日誌（原因 `other roles`）；之後帳號的 default role 仍是空的，服務沒有自動改回；管理者改回後下一個呼叫恢復，可查期間沒有被動到。在工作站上把服務的角色檢查暫時拿掉時，這個案例失敗在「第 1 次呼叫的錯誤日誌」（之後已還原，未提交）。

- **對 telemetry-query 真正的路由**（Postgres 與 ClickHouse 是只計數的 loopback 埠）：系統表、`url()`、`dictGet`、`SET DEFAULT ROLE NONE TO CURRENT_USER`、`SET ROLE NONE`、兩個敘述、`SETTINGS readonly = 0`、`CAST` 成 `Array`、沒寫時區的 `toStartOfDay`、沒讀 view、引號識別字、反斜線、語法錯誤、300 層括號：模型各自拿到該類別固定的英文說明，例如「`system.tables` is not a table you may read. …」「Only a SELECT (or WITH … SELECT) may run …」；兩個資料庫的連線數都是 0，模型的文字與日誌都沒有 SQL。超過 16 KiB 的 SQL 由工具自己拒絕、不送出。通過檢查的查詢（對照組）會連到 Postgres，失敗後模型拿到固定的失敗訊息。
- **對替身**：答案（長文字截到 256 個字元）、`too_many_rows`、`query_error`、`query_too_heavy`、`result_too_large` 各自是固定說明；多一個欄位、不認得的類別、子句或 `kind`、不是識別字的名稱、不是拒絕的 422、不是 JSON 的 422 都當成失敗；429、504、404、403、400 各自是固定訊息，5xx 與不是 JSON 的 200 是失敗。替身放在錯誤本文的字串不在模型的文字與日誌裡；每次呼叫都換新 token（受眾 telemetry-query、`act` 是 assistant），請求正好是 `{"sql": …, "max_rows": 200}`。

#### H1 的上限與理由

- **在 lexer 拒絕**：解析開始後就停不下來，所以會讓解析超線性成長的寫法要在解析前拒絕。lexer 已經把文字讀成 token，數括號是線性的。
- **`position(` 只能一層**：sqlparser 0.63 遇到 `position(` 先試 `POSITION(a IN b)`，失敗後再當函式重讀，而且不記住這次失敗（`parse_position_expr`）。ClickHouse 慣用的逗號寫法要讀完整個第一個參數才失敗，所以每多一層加倍。lexer 看 `position` 後面緊接 `(`（中間的空白與註解不算，`t.position(` 也算），已經開著一個 `position(` 時再出現就拒絕；並排的、不同子句裡的各一個都可以。
- **16 層**：測試接受的查詢（`tests/data/model-queries.sql` 的模型查詢、單元測試、`tests/sql_api.rs` 跑的查詢）最深 3 層（在測試執行時以暫時的量測程式碼記錄，之後移除），其中模型查詢最深 2 層（掃描查詢檔）。審查建議 16 到 20，取下限：比實際用到的多 13 層，更深的查詢可以用 `WITH` 拆開；Laysi/trustiot-v2#150 的儀表板 SQL 讀同樣的 view。其他會試讀的寫法 sqlparser 會記住失敗的位置，每層最多重讀一次，代價約是巢狀層數乘以 token 數，所以 16 層也限住了它們。
- **讀回**：印出的文字多了檢查加上的括號（一條路徑最多 24 層，`MAX_ADDED_NESTING`），讀回的巢狀上限是 16 + 24 + 8 = 48；`position(` 的規則照樣適用，印回不會多出 `position`。

#### sqlparser 會試讀的地方

`sqlparser` 0.63.0 的 `src/parser/mod.rs` 裡 55 處 `maybe_parse`、`try_parse` 與重設讀取位置的地方逐一看過，清單與每處的判斷在 parser-survey.txt：

- 只有其他語句會走到的（`RAISE`、`EXPLAIN`、`SET`、`COPY`、DDL 等）：lexer 只讓 `SELECT`、`WITH`、`(` 開頭，走不到。ODBC 的 `{d …}`、`{fn …}`：lexer 拒絕 `{`。CTE 的試讀只在 `supports_cte_without_as` 時，ClickHouse 是 false。
- 只讀資料型別、名稱或幾個關鍵字的試讀：在任何運算式之前就失敗。
- 讀到運算式之後才可能失敗的：保留字開頭的寫法（`CAST`、`EXTRACT`、`SUBSTRING`、`OVERLAY`、`TRIM`、`CEIL`、`CASE` 等）、非保留字當運算式、`(…)` 衍生表，sqlparser 都以 token 位置記住失敗，每層最多重讀一次；`IN (查詢)` 在第一個不能開始查詢的 token 就失敗；具名參數 `name => value` 的值在最後讀。
- 唯一不記住失敗、又在讀完參數之後才失敗的是 `parse_position_expr`，由 lexer 的規則擋下。

release build；時間是多次中最好的一次，會隨機器負載變動，用來看成長，不是上限。

#### 每租戶的檢查名額

審查要求評估是否限制單一租戶能佔的檢查名額。不加，理由：

1. 修正後一次檢查在上限內最多約 10 ms，名額被佔的時間短。名額是 `tokio::sync::Semaphore`，依請求的先後發放，一個租戶送再多，其他租戶的請求也只排在已經在等的請求之後。
2. 會長時間佔住名額的正是 H1 的寫法，已在解析前拒絕；每租戶的上限只會在毫秒級的佇列裡重新排序，卻要多一份依租戶計數的共享狀態。
3. 能呼叫的只有 AI 助理，每個問題的工具呼叫受它的預算與每一步的上限限制（`services/assistant/src/budget.rs`、`config.rs`）。

Laysi/trustiot-v2#150 的儀表板成為呼叫者、量變大時應再評估。

#### 沒有涵蓋的

建議加入 Laysi/trustiot-v2#693 的 fuzzing 範圍：三種以上寫法的組合；子句層級的寫法（`WINDOW`、`SETTINGS`、`ARRAY JOIN`、`PREWHERE`、`LIMIT BY`、`WITH FILL`、`INTERPOLATE`、`SAMPLE`、各種 `JOIN`）的解析時間；需要時以 dialect 的 `parse_prefix` 計數為解析加上工作量的上限。升級 sqlparser 時要重做這份調查（計數測試抓得到既有寫法新出現的加倍，抓不到只有新寫法才會走到的），由 L4 的測試強制。
