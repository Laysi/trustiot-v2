### 資料庫強制可查期間（`services/telemetry-query/tests/queryable_period.rs`）

以租戶帳號直接對 ClickHouse 執行，不經 SQL 檢查（[queryable-period.txt](data/2026-10-26-143-ai-sql/queryable-period.txt)）：上一節同一份 84 種繞過，加上只能直接對資料庫做的 9 項（session 裡的 `SET` 與 `SET ROLE NONE`、沒有時間窗設定、時間窗設定值不合法），共 93 項。改寫時間條件（`OR true`、從 1970 起、`toDate`、`BETWEEN`、別名蓋過 `ts`、`WITH` 常數）、子查詢、CTE、各種 JOIN、`IN`、`UNION`、`INTERSECT`、視窗函式、`WITH TOTALS`、`view()`、`merge()`、`SAMPLE`、讀彙總 view，以及在 `WHERE`、`SELECT` 用 `throwIf` 或失敗的轉型探測窗外的列：每一種不是被資料庫拒絕（`ACCESS_DENIED`、`READONLY`、`ILLEGAL_PREWHERE`、`SET_NON_GRANTED_ROLE` 等），就是答案裡沒有窗外的標記。帳號改不了自己的時間窗（`SETTINGS`、URL 參數、`SET`、`ALTER USER`、設定 profile、row policy 都被拒）。服務改帳號的時間窗後，下一個查詢就照新的窗（放寬成 365 天與 12 個月、把 1 小時窗縮成 1 個月、再改回 7 天與 3 個月）。帳號沒有時間窗設定時三個 view 都回 `UNKNOWN_SETTING`；設定值是 -1、70000 或文字時查詢失敗。

### 租戶帳號（`services/telemetry-query/tests/tenant_accounts.rs`）

2026-10-09 PoC 的攻擊直接以租戶帳號執行：全部被資料庫拒絕，或答案裡沒有其他租戶的讀數；超過讀取列數、記憶體、時間上限的查詢分別以 `TOO_MANY_ROWS`、`MEMORY_LIMIT_EXCEEDED`、`TIMEOUT_EXCEEDED` 中止（[tenant-accounts.txt](data/2026-10-26-143-ai-sql/tenant-accounts.txt)，在 `829cfc8` 上重跑，39.08 s 通過）。同一個測試也確認帳號被改時的處理：

- 密碼被改：下一個 API 呼叫自動改回；
- 查詢上限在帳號上被改寬、或帳號被改成別的租戶：API 回 503、不執行查詢，回不出別的租戶；
- 租戶角色不再是帳號的 default role（`ALTER USER … DEFAULT ROLE NONE`，依 2026-10-26 的決定維持現行處理）：兩次呼叫都回 503、沒有該租戶的讀數，每次都記一筆錯誤日誌（原因 `other roles`）；之後帳號的 default role 仍是空的，服務沒有自動改回；管理者改回後下一個呼叫恢復，可查期間沒有被動到。在工作站上把服務的角色檢查暫時拿掉時，這個案例失敗在「第 1 次呼叫的錯誤日誌」（之後已還原，未提交）。

### AI 助理的 `telemetry_sql`（`services/assistant/tests/telemetry_sql.rs`）

經工具組（模型實際用的路徑）呼叫，全部通過（[assistant-tool.txt](data/2026-10-26-143-ai-sql/assistant-tool.txt)，每一行是模型拿到的文字）：

- **對 telemetry-query 真正的路由**（Postgres 與 ClickHouse 是只計數的 loopback 埠）：系統表、`url()`、`dictGet`、`SET DEFAULT ROLE NONE TO CURRENT_USER`、`SET ROLE NONE`、兩個敘述、`SETTINGS readonly = 0`、`CAST` 成 `Array`、沒寫時區的 `toStartOfDay`、沒讀 view、引號識別字、反斜線、語法錯誤、300 層括號：模型各自拿到該類別固定的英文說明，例如「`system.tables` is not a table you may read. …」「Only a SELECT (or WITH … SELECT) may run …」；兩個資料庫的連線數都是 0，模型的文字與日誌都沒有 SQL。超過 16 KiB 的 SQL 由工具自己拒絕、不送出。通過檢查的查詢（對照組）會連到 Postgres，失敗後模型拿到固定的失敗訊息。
- **對替身**：答案（長文字截到 256 個字元）、`too_many_rows`、`query_error`、`query_too_heavy`、`result_too_large` 各自是固定說明；多一個欄位、不認得的類別、子句或 `kind`、不是識別字的名稱、不是拒絕的 422、不是 JSON 的 422 都當成失敗；429、504、404、403、400 各自是固定訊息，5xx 與不是 JSON 的 200 是失敗。替身放在錯誤本文的字串不在模型的文字與日誌裡；每次呼叫都換新 token（受眾 telemetry-query、`act` 是 assistant），請求正好是 `{"sql": …, "max_rows": 200}`。

### 安全審查後的修正

2026-10-26 的安全審查提出 11 項。修正前的失敗輸出摘錄在 [security-fixes.txt](data/2026-10-26-143-ai-sql/security-fixes.txt)；修正後的結果在下一節合併後的全部測試裡。

| 項目 | 修正 | 新測試在修正前的結果 |
| --- | --- | --- |
| 1. 運算元的分組 | sqlparser 與 ClickHouse 的運算子優先順序不同（例如 `1 + 2 \|\| 3`、`'a' LIKE 'a' = 0`、`1 BETWEEN 0 AND 2 = 0`），原樣印回的文字會被 ClickHouse 以另一種方式分組。印回時每個是運算的運算元都加上括號 | 單元測試 3 個失敗（`SELECT 1 + 2 \|\| 3` 印成原樣，sqlparser 的分組是 `1 + (2 \|\| 3)`）；`sql_api` 以 ClickHouse 的 `EXPLAIN AST` 比對，ClickHouse 對印回的 `SELECT 1 + 2 \|\| 3` 分組與 sqlparser 不同，失敗 |
| 2. 印回的文字在上限內 | 加上括號後再以解析上限讀一次印回的文字，超過時拒絕成 `too_complex`（最多多 24 層）；sqlparser 讀不成運算式、退回當成名稱的 31 個關鍵字（例如沒有 `WHEN` 的 `case`）拒絕成 `syntax` | `sql_check` 的 `a_query_over_the_limits_only_as_printed_is_refused_as_such`（寫的時候在上限內、印回後超過的查詢得到內部錯誤，入口會回 500）與單元測試 `a_keyword_the_parser_fell_back_to_a_name_for_is_refused` 失敗 |
| 3. 寫成字串的名稱 | sqlparser 把 `AS 'x'`、`WITH 'x' AS`、`WINDOW 'w'`、`OVER 'w'` 的字串當成名稱，拒絕成 `syntax` | `a_string_where_a_name_belongs_is_refused` 失敗 |
| 4. 括號查詢後的 `ORDER BY`、`LIMIT` | ClickHouse 不接受，拒絕成 `clause_not_allowed`（`set_operation_order`），工具的說明改成寫成子查詢 `SELECT * FROM (...) ORDER BY ...` | `sql_api` 回 `query_error`（ClickHouse 的語法錯誤），不是 `set_operation_order` |
| 5. 以錯誤當探針 | 只加測試：20 條路線以 `intDiv`、`toInt64` 對別的租戶與窗外的原始讀數、1 分鐘格、1 小時格探測（`WHERE` 與 `SELECT`），4 條對照組對自己的列 | 沒有程式修正，所以沒有修正前的失敗；`queryable_period.rs` 與 `sql_api.rs` 都通過：row policy 先濾掉列，探針都正常回答，對照組照樣得到 `division_by_zero`、`cannot_parse_value` |
| 6. 帳號改得了被檢查的設定 | 帳號檢查以 `system.settings` 的 `readonly` 確認 `SQL_tenant_id`、`readonly` 與 7 個查詢上限都是 `CONST`，改得了時回 503、記錯誤、不修復；三個時間窗改得了時寫回 | 時間窗被改成 `CHANGEABLE_IN_READONLY` 後沒有寫回（寫回次數 2，應為 3）；`SQL_tenant_id` 改得了時 API 仍回 200（應為 503） |
| 7. 月底的裁切起點 | 月份減法在較短的月份會往前或往回跳。起點取「5 分鐘後的時間窗」與「5 分鐘跨過 UTC 午夜時，午夜前一刻的時間窗」中較晚的一個 | 修正前的程式在逐分鐘走過 2027、2028 年每個月底（1、3、12 個月的窗）時失敗，例如 2027-02-28 23:55、1 個月的窗：資料庫的窗從 02-01 開始，裁切起點卻是 01-29；只用「5 分鐘後的窗」也在往回跳的午夜失敗（2027-05-30T23:56Z 時應為 2027-03-01T00:00Z，得到 2027-02-28T00:01Z） |
| 8. SQL 路由上帳號檢查失敗 | 與歷史 API 相同地對應 ClickHouse 的錯誤（`497`、`164` → 503 `unavailable`） | 替身 ClickHouse 回 `497` 時入口回 500 `internal` |
| 9. 日誌的 SQL 指紋 | 改成每個程序啟動時隨機產生金鑰的 HMAC-SHA-256（前 8 bytes），同一段 SQL 在不同程序得到不同的值，無法拿常見的查詢比對 | 指紋等於不帶金鑰的雜湊 |
| 10. 工具結果的物件 key | 物件的 key 也截到 256 個字元（例如 `Map` 的 key），截斷後相同時加 `#2`、`#3`，不丟掉值 | `long_keys_are_cut_and_keys_cut_alike_are_kept_apart` 失敗 |
| 11. 文件 | README 寫明租戶的 quota 由歷史 API、語意查詢與 AI 的 SQL 共用（2026-10-26 決定維持，Laysi/trustiot-v2#694），以及多個副本在滾動部署時會互相改寫時間窗 | 只改文件 |

## 結論

1. **2026-10-09 PoC 的攻擊類型全部被解析器拒絕或讀到 0 筆**：通過。經入口的 43 種攻擊（`sql_api.rs`）都被檢查拒絕，或只回 A 自己的讀數；直接以租戶帳號執行時（`tenant_accounts.rs`）也都被資料庫拒絕或讀不到其他租戶。
2. **繞過可查期間的查詢無法讀到鎖住的期間**：通過。84 種繞過以租戶帳號直接執行（`queryable_period.rs`，另加 9 項只能直接對資料庫做的）與經入口執行（`sql_api.rs`）都讀不到窗外的列；帳號改不了自己的時間窗；方案改窗後下一個查詢生效。
3. **解析器拒絕的語法回傳通用錯誤類別給 agent**：通過。入口回 422 與封閉的類別（`sql_api.rs`），工具把類別換成固定說明給模型，服務多給的文字或不認得的類別都不會進到模型（`assistant/tests/telemetry_sql.rs`）。
4. **`SET ROLE`、`SET DEFAULT ROLE` 與其他不是 SELECT 的敘述都被解析器拒絕，不會送到 ClickHouse**：通過。15 種敘述都回 422，`system.query_log` 裡租戶帳號只執行過 `Select`、探測標記 0 筆；工具對真正的路由送出的拒絕敘述，Postgres 與 ClickHouse 的連線數都是 0。
5. **同一段 SQL 以另一個租戶的身分執行時，只讀到該租戶的資料**：通過（A、B 各 10 列，全是自己的標記）。
6. **歷史 API 的彙總序列改讀 1 分鐘與 1 小時彙總表，路徑、參數與欄位不變**：通過（`history.rs`，與參考值相同；邊界差異寫在 `services/telemetry-query/README.md`）。
