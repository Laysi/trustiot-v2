# 對話頁的追問與串流回答留在頂端列與輸入框之間：瀏覽器實測（2026-11-07）

對應 issue：Laysi/trustiot-v2#1182（送出追問後，等待與串流中的回答被黏住的輸入框蓋住）。問題的來源是 Laysi/trustiot-v2#1179 的投影走查（`docs/test-reports/2026-11-07-1179-projector-walkthrough.md` 的問題 1）。

## 環境

- 建置主機（x86_64 Linux）。測的程式是分支 `fix/1182-follow-up-scroll` 的 commit `549f7c32`（從 main `bcadc8e2` 開始）；瀏覽器檢查跑的工作目錄與這個 commit 的程式相同，只多了本報告的 data 目錄。
- Bun 與其他工具是 `.prototools` 釘選的版本；`bun install --cwd frontend --frozen-lockfile` 之後啟動 UI 預覽：`bun --bun vite --mode ui-preview --host 127.0.0.1 --port 5194 --strictPort`（埠已有回應時拒絕執行）。沒有後端，所有 API 由預覽的假服務在頁面裡回答。
- 瀏覽器：`frontend/e2e/image.ts` 釘選的 Playwright 映像（`mcr.microsoft.com/playwright:v1.64.1-noble`，以 digest 釘選）裡的 Chromium，`--network host`、`--shm-size 1g`、`--cap-drop ALL`、`--security-opt no-new-privileges`。語言 zh-TW（`navigator.languages` 是 `["zh-TW"]`，頁面 `lang="zh-TW"`）、時區 Asia/Taipei；每個視窗的 `language` 行記錄了這些值與主題。
- 視窗：1920×1080、1280×720、853×400（`deviceScaleFactor` 1.5，即 1280×720 一般視窗放大 150 %）淺色，以及 1280×720 深色。
- 與走查一樣隱藏只有預覽才畫的東西（預覽工具列、對話頁「讀不到這段對話的草稿」的提示、輸入框的灰字補全提示與「問句範本」按鈕、首頁的設定清單與建議問題），量到的是正式版的版面。

### 和走查不同的做法

- **長對話**：走查用的預覽對話（回答裡有儀表板卡）要 PR Laysi/trustiot-v2#1178 的預覽資料，main 還沒有。本次打開預覽的「Line 2 energy this week」，先問幾個一般問題（預覽 2.5 秒後回答），直到頁面比視窗高 600 px 以上（1920×1080 問 5 個、1280×720 問 3 個、853×400 問 2 個），再捲到底送出追問。這就是 issue 重現步驟的情境：已有回答的對話、捲在底部、送出追問。
- **讓回答變長**：預覽的 `!slow` 問題只在 1.25 秒時串流出第一段，之後不再有新的段落。為了測串流中的跟隨，腳本在頁面載入前包住頁面的 `fetch`，回答串流（`.../runs/{id}/stream`）的事件原樣通過，同時記住回答的結尾位置；`__appendParagraph` 在那個位置加一個 `text` 事件。app 照一般的段落接收與畫出（`useAnswerStream`、`StreamingAnswer`），所以跟隨是由真正的 React 畫面變化觸發的。
- **出現當下的取樣**：「正在查詢讀數…」只在問題送出後到第一段到達前（約 1.25 秒）存在。腳本在送出前開始每個 animation frame 取樣一次，記錄第一個樣本（頁面還沒捲）與最後一個樣本（第一段到達前），以及最後有幾個 frame 的捲動位置沒有再變（`stillFramesAtEnd`）。

## 指令

```sh
# repo 根目錄
bun install --cwd frontend --frozen-lockfile
bash docs/test-reports/data/2026-11-07-1182-follow-up-scroll/run.sh
# 只跑部分視窗：VIEWPORTS=853x400,1280x720；截圖（只給作者自己看，不提交）：SHOTS=1
```

[`run.sh`](data/2026-11-07-1182-follow-up-scroll/run.sh) 啟動預覽、等它回應、在 Playwright 容器裡執行 [`browser-check.mjs`](data/2026-11-07-1182-follow-up-scroll/browser-check.mjs)，最後停掉預覽；兩者改自走查的同名檔案。等待都以條件為準（上限 60 秒，逾時的訊息寫明在等什麼）；「頁面停止捲動」也是條件：捲動位置連續 20 個 frame 不變。唯一以時間為準的是「往上捲之後頁面不動」：新段落畫出來之後，觀察 1.5 秒（比頁面的滾輪靜止判斷 200 ms 加一次平滑捲動長）捲動位置有沒有變。原始輸出（45 行）：[browser-check.jsonl](data/2026-11-07-1182-follow-up-scroll/browser-check.jsonl)，結尾的 `summary` 行 `failures` 是空陣列，每一行的 `consoleErrors` 都是空陣列。

可見帶（下稱「帶」）= 頂端列下緣到輸入框上緣；沒有輸入框蓋在視窗下緣時（頁面不夠長，輸入框停在原位）是到輸入框實際的上緣。頁面發布的 `scroll-padding` 在每個視窗都是 `57px`／`130px`，與量到的頂端列（57）與輸入框（130）高度相同。

### 單元測試與檢查

- `frontend/src/pages/conversations/follow.test.ts`（跟隨的決定，純函式）：出現時跟隨；在底部（含 32 px 的門檻內）跟隨；往上捲離開底部就不跟、答案變長也不拉回、往下捲但還沒到底不恢復；回到底部（任何方式）恢復；頁面自己的平滑捲動途中保持跟隨；手指在螢幕上或滾輪還沒停時不捲；最新段落已在輸入框上方時不捲；偏好減少動態效果時 `instant`，否則 `smooth`。
- `frontend/src/lib/sticky-bars.test.tsx`：列發布自己的高度（取整數 px）、跟著大小變、離開時移除；上下兩邊分開，同一邊以最後掛上的為準。
- `frontend/src/pages/conversations/ConversationTurn.test.tsx`「keeping the question being answered in view」：送出的問題以 `{ block: "nearest", behavior: "smooth" }` 捲進來，減少動態效果時是 `"instant"`；對話頁打開時頂端列與輸入框發布了 `--sticky-top`、`--sticky-bottom`，離開後移除。
