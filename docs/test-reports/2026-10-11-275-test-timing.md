# 測試在高負載下的時間假設（Laysi/trustiot-v2#275）

## 環境

- 機器：本機（Fedora，8 核，podman 6.1.3），另以建置主機 `ruisi-wsl`（Ubuntu on WSL2，20 核，Docker，閒置）確認全套測試。
- 工具：bun 1.4.2、helm 4.3.0、kubeconform（皆 `.prototools` 釘選版本）、Rust 工具鏈依 `rust-toolchain.toml`。
- 測試對象：分支 `fix/275-test-timing`（基於 `e8f180b`），修正前的對照是同一個 `e8f180b`。
- 負載方式：`load.sh start 24..28 <秒>`，也就是 24 到 28 個 `timeout` 包住的 CPU 忙迴圈（`sh -c 'while :; do :; done'`），疊加其他 agent 當時的負載。測試期間 load average 為 28–38（`repeat.sh` 每次輸出都記了當時的值）。每次負載都有秒數上限，結束後以 `load.sh stop` 停掉；報告時機器 load 為 0.2。原始腳本見 data 目錄。
- 閒置基準：建置主機上 `bun test deploy/chart/tests/chart.test.ts` 單項最久 1.4 秒（四次 render 加 kubeconform 的那類測試），多數 helm 測試 0.1–0.2 秒。

## 指令

```sh
# 負載
bash load.sh start 28 2400
# 連跑（repeat.sh <標籤> <次數> <指令...>）
CI=1 bash repeat.sh before-tenant 10 cargo test --locked -p service-kit --test tenant_db
bash repeat.sh after-chart 5 bun test deploy/chart
CI=1 bash repeat.sh after-kit 3 cargo test --locked -p service-kit --no-fail-fast --lib \
  --test errors --test identity --test identity_adversarial --test job_lock --test lifecycle --test logging --test otlp
bash load.sh stop
# 建置主機（閒置）
bash rcheck.sh 275 'cargo fmt --all --check; cargo clippy --locked --workspace --all-targets -- -D warnings; CI=1 cargo test --locked --workspace'
```

## 根因

- chart 測試：近 150 項測試各自呼叫 `helm template`，沿用 bun 預設的每項 5 秒。`Bun.spawnSync` 在逾時時殺掉 helm，日誌只剩空 stderr 的 `helm template failed:`，看不出是被殺的。kubeconform 要從網路下載 schema，卡住時沒有自己的時限（協調者觀察到兩次整整等到 120 秒測試上限）。
- `tenant_db` 拒絕 session：sqlx 取得連線的逾時是 2 秒，連線建立（TLS 加 session 檢查）高負載下超過它時，kit 還沒記錄任何拒絕，只能回報 `PoolTimedOut`。
- `tenant_db` 就緒等待：example service 的就緒檢查自己有 800 ms 上限（`health.rs` 的 `CHECK_TIMEOUT`），冷的連線池要在 800 ms 內建好連線，負載高時要試很多次才成功；測試只給 20 秒。
- e2e 單元測試（`deploy/chart/tests/e2e`）：「連線失敗發生在行程結束之前」靠 fake 行程 500 ms 的計時器；「回應 head 之後卡住」的 300 ms 客戶端逾時若早於 head 被讀到，就變成 `ConnectionError`。兩者都是競態。
- `lifecycle.rs`：`ready_checked < 1s` 與 1 秒的 drain delay 綁在一起，測試執行緒晚 1 秒拿到 CPU，監聽就已關閉。

## 修正

- `deploy/chart/tests/timing.ts`（新）：`COMMAND_TIMEOUT_MS`（單一行程 60 秒）、`TEST_TIMEOUT_MS`（預設 60 秒）、`SLOW_TEST_MS`（多指令測試 120 秒，沿用 Laysi/trustiot-v2#277 的名稱與數值）、`useProcessTestTimeouts()`、`throwIfTimedOut()`。bun 1.4.2 的 `setDefaultTimeout` 以檔案為單位，bunfig 的 `[test] timeout` 無效（實測），所以每個測試檔呼叫一次。
- `chart.test.ts`：所有 `Bun.spawnSync` 都帶 `timeout`，被殺時丟出帶指令名稱的訊息；kubeconform 的訊息指出可能是 schema 下載卡住。不重試、不繞過網路。
- e2e 單元測試：fake 行程新增 `on-stdin` 模式，由測試在看過失敗後才叫它結束，不再賭計時器；等待逾時改成「事件一發生就結束」的寬鬆上限；「不必等 grace」的測試以 grace 的一半為上限；head 後卡住的逾時固定為 `HEAD_STALL_TIMEOUT_MS`（2 秒，測試本來就要等完）；`waitListening` 在 fake 行程提前結束時立刻失敗。
- `tenant_db.rs`：`refusal_through_pool` 依序用 2、4、8、16、32 秒的取得逾時嘗試，只有「沒有任何拒絕可報」的 `PoolTimedOut` 才換下一個預算，出現拒絕原因就斷言它是 `OwnsRelation`；`wait_until_ready` 最多等 120 秒，服務停止回應立即失敗，失敗訊息附上最後回應與 stdout/stderr。拒絕後的訊息等待改用既有的 `OUTPUT_DRAIN_TIMEOUT`。沒有改產品程式。
- `lifecycle.rs`：SIGTERM 測試的 drain delay 改 4 秒、drain timeout 60 秒，斷言改為相對於這兩個設定值；其餘測試的事件等待用 `EVENT_TIMEOUT`（10 秒），上限斷言對照測試自己設定的數值（8 秒的慢請求、30 秒的 drain delay）。

### 建置主機（閒置）

- `cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo clippy -p service-kit --no-default-features --all-targets -- -D warnings`：通過。
- `CI=1 cargo test --workspace`、`CI=1 cargo test -p service-kit --no-default-features`：全部通過。
- `bun run --cwd scripts typecheck`：通過。
- `bun test deploy/chart`：`chart.test.ts` 與 `raw-client.test.ts` 全過；`tunnel-recovery.test.ts` 在該主機（WSL）失敗是已知差異。修正前同一檔在該主機失敗 5 項，修正後失敗 6 項（`rcheck-base-tunnel.log` 與 `rcheck-chart-wsl.log`），多出的一項是 `retries at most once`。這些測試在該主機上本來就無法正常運作（原因未深究，屬 WSL 環境差異），結果取決於各項逾時長短，新版逾時較長，所以失敗的項目略有不同。本機同一檔 22 項全過。

### 合併 main（`e21ff41`）後，建置主機（閒置）

- fmt、clippy（含 `--no-default-features`）、`CI=1 cargo test --workspace`、`--no-default-features` 測試、typecheck：通過。
- `bun test deploy/chart`：202 項中 201 過。`tunnel-recovery.test.ts` 在合併 Laysi/trustiot-v2#300 後於該主機也通過。
- 失敗的 1 項是 `saas shape > rendered manifests pass kubeconform -strict for Kubernetes 1.36.0`：kubeconform 在 60.9 秒時被 `COMMAND_TIMEOUT_MS` 殺掉。同一項隨後重跑 3 次、每次 4 項皆在約 1 秒通過（`data/2026-10-11-275-test-timing/rcheck-merged.log`、`rcheck-kubeconform-rerun.log`）。這與協調者在同一主機看到的「kubeconform 無輸出，等到測試上限」是同一現象：偶發的 schema 下載停滯。本 issue 只讓它在 60 秒內失敗並指出是 kubeconform 的 schema 下載；停滯的原因（網路或 DNS）沒有處理，也沒有繞過網路。

## 結論

- 高負載連跑：`tenant_db` 10 次、`bun test deploy/chart` 5 次，皆 0 次失敗：通過。
- 回歸驗證：`tenant_db` 修正前 10 次失敗 3 次、chart 失敗 1 次（真實高負載），其餘競態以注入延遲證明：通過。
- 測試仍驗證原本行為：拒絕原因仍斷言為 `UnsafeSession::OwnsRelation`、服務仍只回使用者自己租戶的資料（斷言未改）、chart 規則未改；`lifecycle`、tunnel 的斷言依然對照被測的設定值：通過。
- 證據存檔：本報告與 `data/2026-10-11-275-test-timing/`：通過。

## 後續建議

- 產品：example service 的就緒檢查在冷連線池上要於 800 ms 內建好連線，高負載下可能長時間不就緒。可讓連線池在背景先暖機，檢查只對已建立的連線做 ping。這會改變 kit 行為，故不在本 issue。
- 產品：被拒絕的 session 目前要等到取得逾時才回報（預設 30 秒）。第一個拒絕出現時就讓 `TenantDb::begin` 立即回傳 `UnsafeSession` 較合理。
