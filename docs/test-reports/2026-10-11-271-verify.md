# outbox 消費端租戶隔離的獨立驗證（Laysi/trustiot-v2#271）

對 Laysi/trustiot-v2#271 的實作（`feat/271-outbox-platform-pool`，`b4c748b`）做獨立驗證：驗證者沒有參與實作，目標是找出它會壞掉的地方。實作者自己的報告見 [2026-10-11-271-outbox-consumer-tenancy](2026-10-11-271-outbox-consumer-tenancy.md)。

本次只新增測試、探測與報告，沒有改實作。新增的測試在 `crates/outbox/tests/verify_271.rs`。這個檔案的 handler 會故意執行 `SET ROLE`、`RESET ALL` 與設定租戶的 `set_config`，用來確認這些攻擊會失敗，或重現發現的問題。所以 `tools/sql-check` 的 `EXCEPTIONS` 加了這個檔案，免除的規則與 `services/ingest/tests/clickhouse.rs` 相同（含 `SessionSetting`），理由寫在清單與 sql-check README。

會重現問題的測試斷言的是**應有的行為**，並標成 `#[ignore = "Laysi/trustiot-v2#271 F-n: …"]`，所以分支仍是綠的；加 `--ignored` 執行就會看到它們失敗。

### 3.2 發現

#### F-1（中）：session 層級的租戶會帶進之後「沒有租戶」的交易

- 測試：`f1_a_platform_wide_event_never_runs_in_a_leaked_tenant`（ignored）
- 重現：租戶 A 事件的 handler 執行 `SELECT set_config('trustiot.tenant_id', <B>, false)`（第三個參數是 false，所以是 session 層級，不是交易層級）。交易 commit 後，這個設定留在 pool 的連線上。同一條連線上下一個以 `BackgroundTenantDb::begin_without_tenant` 開的交易就在租戶 B 裡執行。消費端以這種交易處理全平台事件、寫死信、建立訂閱、查位置。`TenantDb::pool()` 上「沒有租戶」的查詢也一樣受影響。
- 證據：

  ```
  ledger after the leak: [(<A 的事件>, Some("…0a"), Some("…0b"), 1), (<全平台事件>, None, Some("…0b"), 1)]
  assertion failed: the platform-wide event's transaction must have no tenant and see no tenant row
    left: (Some("01928f6e-7a3c-7d4e-8f00-00000000000b"), 1)
   right: (None, 0)
  ```

  全平台事件的 handler 看到 `trustiot.tenant_id = B`，也看得到租戶 B 的一列。
- 原因：service-kit 只在**新連線**檢查有沒有預設租戶（`TenantPreset`，`after_connect`）。`begin_without_tenant` 直接 `pool.begin()`，沒有清掉租戶。`TenantDb::begin` 與 `BackgroundTenantDb::begin` 不受影響，因為它們每次都以 `SET LOCAL` 覆寫。這與 `begin_without_tenant` 文件、outbox README「全平台事件……看不到也寫不進任何租戶的列」的保證不符。
- 觸發條件：程式碼要設定 session 層級的 `trustiot.*`。sql-check 擋下字面寫法，但擋不到 PL/pgSQL `EXECUTE` 字串裡組出來的寫法（sql-check README 已列為限制）。一旦發生，影響會延續到該連線結束，波及同一個 pool 上之後所有「沒有租戶」的工作，所以列為中。
- 建議修正：`begin_without_tenant` 在交易開頭執行 `SELECT set_config('trustiot.tenant_id', '', true)`，與 `begin_in` 對稱。另外在 pool 的 `after_release`（或 `before_acquire`）檢查 session 層級的租戶是空的，不是空的就關掉這條連線，連 `TenantDb::pool()` 的直接查詢也一起保護。修正後拿掉 `f1_` 的 `#[ignore]`。

#### F-2（低）：handler 可以把自己的交易切到別的租戶，消費端照樣 commit

- 測試：`f2_a_handler_that_switches_the_tenant_is_not_committed`（ignored）
- 重現：租戶 A 事件的 handler 執行 `SELECT set_config('trustiot.tenant_id', <B>, true)`，或執行 `DO $$ BEGIN EXECUTE 'SELECT set_' || 'config(…)'; END $$`，再寫一列租戶 B 的資料。
- 證據：`tenant switches: [("set_config local", 1, "CaughtUp, delivered 1"), ("set_config hidden in PL/pgSQL EXECUTE …", 1, "CaughtUp, delivered 1")]`：兩種寫法都寫進租戶 B，投遞也算成功。
- 評估：決策 29 的威脅模型本來就接受「SQL 能改設定值」，靠 sql-check 擋。第二種寫法沒有被 sql-check 檢查到，這是 sql-check README 已列的限制；本測試檔已被免除檢查，所以本次沒有另外驗證 sql-check 會不會報它。消費端只需要一個查詢就能偵測，所以列為低、建議加強。
- 建議修正：`handle` 回來後、寫 inbox 前，在同一筆交易查 `NULLIF(current_setting('trustiot.tenant_id', true), '')`，與 `Delivery::tenant()` 比對；不同就 rollback，以 ERROR 記錄並進死信（或重試）。README 的 handler 規則補上「不得改租戶與角色設定」。

#### F-3（低）：handler 自己送出 `COMMIT` 會把投遞拆開，事件被處理兩次

- 測試：`f3_a_handler_commit_does_not_split_the_delivery`（ignored）
- 重現：handler 寫入後執行 `sqlx::raw_sql("COMMIT")`，接著回 `HandlerError::retry`。
- 證據：`tenant A notes after the failed attempt: 1; after retry: 2`。失敗的那次已經 commit 寫入，重試又寫一次。
- 評估：README 說 handler 的寫入與「已處理」同時生效，但這要靠 handler 不自己控制交易，消費端沒有檢查。`COMMIT` 之後的陳述會在 autocommit 下執行，交易層級的租戶設定與 advisory lock 也都已經釋放。
- 建議修正：與 F-2 合併成同一個檢查。開交易後先記下 `transaction_timestamp()`（或 `pg_current_xact_id_if_assigned()`），`handle` 之後再查一次：值不同代表交易已被結束或替換，就當成失敗處理。README 也寫明 handler 不得執行交易控制陳述。

#### F-4（低）：`PlatformReader` 的 `READ ONLY` 可以被呼叫端解除

- 測試：`f4_a_platform_reader_transaction_stays_read_only`（ignored）
- 重現：`PlatformDb::reader(...).begin()` 之後，第一個陳述是 `SET TRANSACTION READ WRITE`，再寫一張平台角色有 INSERT 權限的表。
- 證據：`SET TRANSACTION READ WRITE: Ok(()); insert: Ok(()); commit: Ok(()); rows: 1`
- 原因：`begin_with("BEGIN READ ONLY")` 之後還沒有執行任何查詢，Postgres 允許在第一個查詢之前改回讀寫。outbox 消費端自己不會這樣做，而且它讀的產生端 log 沒有寫入權限，所以目前沒有實際影響。但 service-kit README 與 doc comment 寫「資料庫拒絕任何寫入」，`PlatformReader` 又是公開 API，日後的使用者可能依賴這個保證。
- 建議修正：`PlatformReader::begin` 在 `BEGIN READ ONLY` 之後立刻執行一個會取得快照的查詢（例如 `SELECT 1`）。之後 Postgres 會以「transaction read-write mode must be set before any query」拒絕改回讀寫。再以 `f4_` 測試確認。

#### F-5（中，#271 之前就存在）：handler panic 會永久停掉 `Consumer::run`，lag 指標也停在最後一次的值

- 測試：`f5_a_handler_panic_does_not_stop_the_consumer`（ignored）
- 重現：handler 對第一個事件 panic 一次，之後正常。
- 證據：`processed 0; run task finished on its own: true (Err(true)); lag gauge None, measured now 1`。`run` 的工作因 panic 結束，事件一直沒有處理。lag 指標從來沒有更新（`None`），實際落後是 1。
- 評估：panic 從 `process` 經 `tokio::join!` 帶走 `monitor_lag`，訂閱在該副本停住，而且指標不再更新，所以依 lag 設的告警也不會觸發。每個副本遇到同一個事件都會 panic，最後全部停住。這不是 #271 引入的（`run` 的結構來自 Laysi/trustiot-v2#54），但屬於這次驗證範圍「失敗時的投遞語意」。好的一面：P8 證實 panic 不會留下部分寫入，也不會讓租戶殘留到下一個交易。
- 建議修正（建議另開 issue）：把 handler 的呼叫包在 `catch_unwind`（`futures::FutureExt::catch_unwind` 加 `AssertUnwindSafe`）裡，panic 當成重試，記 ERROR；或讓 `monitor_lag` 與 `process` 分開執行，處理停住時 lag 與 age 仍會上升。

### 3.3 觀察（不列為問題）

- 消費端只比對信封與 log 列的**租戶**，沒有比對信封 `id` 與 log 列的 `event_id`（inbox 以後者去重）。兩者不同只有直接寫 SQL 的產生端做得出來，也不影響租戶隔離，列為觀察。
- handler 物件本身可以持有其他 pool（例如另一個 `BackgroundTenantDb`），在任何租戶開交易。這是程式結構的問題，不屬於消費端能管的範圍；handler 拿到的只有該事件的交易，拿不到消費端的 pool。

## 4. 結論

| 驗收條件（Laysi/trustiot-v2#271） | 獨立驗證結果 |
| --- | --- |
| 消費端以平台角色讀取 RLS 下的 `outbox_event`，讀得到所有租戶的事件；以服務角色連線時被 service-kit 拒絕 | 通過。P5：平台角色讀得到全部事件，其他都讀不到、寫不了。P7：各種不安全的角色組合都被拒。P11：設定錯誤時不會處理任何事件，也沒有改用其他角色。另發現 F-4（`PlatformReader` 的唯讀可被解除，目前不影響消費端） |
| handler 的寫入只落在事件的租戶；handler 試圖寫入其他租戶時失敗 | 以一般 SQL 與角色手法嘗試時通過（P1 的 11 種手法都失敗，P4、P9 都在正確租戶）。handler 以 SQL 改租戶設定時**不成立**：F-2（同一筆交易）、F-1（session 殘留到之後沒有租戶的交易）。決策 29 把這類寫法交給 sql-check 擋，但 PL/pgSQL `EXECUTE` 是已知盲點 |
| 既有的 outbox 有序、冪等遞送測試全部仍通過 | 通過（`cargo test -p outbox` 全綠）。另以 P8、P9、P10 從失敗、並行、資料庫重啟三方面驗證，都只處理一次、順序正確。F-3（handler 自己 `COMMIT`）與 F-5（panic 停掉消費端）是保證成立的前提，目前沒有被強制 |

整體：#271 的主要路徑成立，資料庫層的隔離（角色、grant、RLS、session 檢查）經得起直接攻擊。剩下的問題都出在「handler 程式本身不守規則」時，消費端與 service-kit 沒有第二道防線，其中 F-1 會跨交易延續，嚴重度最高。
