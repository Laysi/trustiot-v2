對應 issue：Laysi/trustiot-v2#63。原始資料在 [data/2026-10-10-63-mesh-authz/](data/2026-10-10-63-mesh-authz/)。

## 環境

- **commit**：分支 `feat/63-mesh-authz`。lab 的 e2e 以 `efa3ffd` 加上之後提交的 `mesh.e2e.ts` 修改執行（測試順序改為先測只有 NetworkPolicy 的階段、加入 imposter，見「結果」的第一次執行）；chart 的樣板與 values 在兩次執行之間沒有變動。
- **本機**：x86_64 的 Fedora；bun 1.4.2、helm 4.3.0、kubeconform 0.8.0、kubectl 1.36.5，都由 `.prototools` 鎖定、以 proto 安裝。
- **lab 的 Mac mini M1**（`trustiot-mac-m1`）：Fedora Linux Asahi Remix 44、aarch64、k3s v1.36.5+k3s1（NetworkPolicy 由 k3s 內建的控制器執行）、Istio 1.30.5 ambient、Gateway API v1.6.1，見 [environment-lab.txt](data/2026-10-10-63-mesh-authz/environment-lab.txt)。
- **叢集**：issue 寫 k3d，依 2026-10-10 的決定改在 lab 的 k3s 執行。測試只用 kubeconfig 與 context，不綁定叢集種類，nightly 的 k3d（Laysi/trustiot-v2#69）可以直接沿用。
- **命名空間**：`e2e-63`，Pod Security Admission 為 `restricted`。執行身分是 `e2e-63` 裡的 ServiceAccount，以 RoleBinding 綁 ClusterRole `admin`，另加只在 `e2e-63` 有效的 Role，允許 Gateway、HTTPRoute 與 AuthorizationPolicy；token 2 小時，kubeconfig 只放在本機暫存目錄，測完刪除。本機經 `ssh -L 127.0.0.1:16463:127.0.0.1:6443` 連 API server。
- **替身**：`deploy/chart/tests/e2e/identity-double/`（Bun）在 lab 以 podman 建 arm64 映像、匯入 k3s 的 containerd，以 digest `sha256:62dcce6d…` 引用（`imagePullPolicy: Never`）。服務間授權測試的五個服務與三個測試 pod 都用這個映像；入口測試沿用 `values-e2e.yaml`（其他後端是 `traefik/whoami`）。
- **ext_authz provider**（只有入口測試需要）：以 k3s 的 `HelmChartConfig` 暫時在 istiod 加上 `trustiot-e2e-63`，PoC 原有的 provider `identity` 原樣保留（[lab-istiod-helmchartconfig.yaml](data/2026-10-10-63-mesh-authz/lab-istiod-helmchartconfig.yaml)）；測完刪除，istiod 回到只有 `identity` 的設定。

## 結果

### 本機

| 檢查 | 結果 |
| --- | --- |
| `bun test deploy/chart` | 合併 main（含 Laysi/trustiot-v2#253 的叢集內 ClickHouse）後 173 項通過、0 失敗。本 issue 新加 24 項：每個服務自己的 ServiceAccount、兩種型態的 namespace 預設拒絕、呼叫清單與入口路由產生的 AuthorizationPolicy、兩種型態下每個服務的 NetworkPolicy 與 AuthorizationPolicy 列同一批呼叫端（只開 15008 與 kubelet 探測來源）、未啟用的服務略過、預設清單、trust domain、沒有 waypoint；叢集內 ClickHouse 只放行 `ingest` 與 `telemetry-query`（兩種型態）、呼叫端都關閉時拒絕所有連線、`external` 時沒有政策、未列的服務連不到；每個 Deployment 與 StatefulSet 的 pod 都有自己的 NetworkPolicy 與 AuthorizationPolicy（兩種型態，故意把 ClickHouse 拿掉時這項會失敗）；4 種在跳過 schema 時仍由樣板擋下的清單，以及 4 種由 schema 擋下的設定 |
| kubeconform（1.30.0 與 1.36.0，`-strict`） | 含 e2e 後端與所有服務的渲染結果全部有效、0 略過（同一組測試內） |

### lab：服務間授權（`mesh.e2e.ts`）

5 項全部通過（[mesh-e2e.junit.xml](data/2026-10-10-63-mesh-authz/mesh-e2e.junit.xml)），每次呼叫的結果在 [mesh-e2e.json](data/2026-10-10-63-mesh-authz/mesh-e2e.json)。呼叫圖：清單只有 assets → certs；入口路由到 identity、assets、certs、mqtt-bridge；沒有人可以呼叫 alerts。

| 呼叫 | 兩層都在 | 只有 NetworkPolicy | 都沒有 | 只有 AuthorizationPolicy | 兩層恢復 |
| --- | --- | --- | --- | --- | --- |
| assets → certs（清單內） | 200 | 200 | 200 | 200 | 200 |
| 入口 → identity、certs、mqtt-bridge | 200 | 200 | — | 200 | 200 |
| certs → assets | 重置 | 重置 | 200 | 重置 | 重置 |
| assets → alerts | 重置 | 重置 | 200 | 重置 | 重置 |
| mqtt-bridge → identity | 重置 | 重置 | 200 | 重置 | 重置 |
| stranger（mesh 內、`default` SA）→ certs | 重置 | 重置 | 200 | 重置 | 重置 |
| outsider（不在 mesh）→ certs 的 Service | 拒絕 | 拒絕 | 200 | 重置 | 拒絕 |
| outsider → certs 的 pod IP:8080 | 拒絕 | 拒絕 | 200 | 重置 | 拒絕 |
| imposter（assets 的 label、`default` SA）→ certs | 重置 | **200** | — | 重置 | 重置 |
| outsider → 入口 pod | 拒絕 | 拒絕 | 200 | 200 | 拒絕 |

「重置」是 `ECONNRESET`、「拒絕」是 `ConnectionRefused`，被拒的呼叫都在 3 ms 內結束。mesh 內的呼叫端被 NetworkPolicy 擋時也看到重置：k3s 的 NetworkPolicy 控制器拒絕 ztunnel 往對方 15008 的連線，ztunnel 再重置呼叫端。

- **兩層各自生效**：只有 NetworkPolicy 時，imposter 通過，證明 AuthorizationPolicy 確實已不在；此時 mesh 內與 mesh 外的清單外呼叫仍全部被拒，擋下的是 NetworkPolicy（15008 只對呼叫端的 pod 開）。只有 AuthorizationPolicy 時，outsider 連得到入口 pod，證明 NetworkPolicy 確實已不在；清單外的呼叫與 imposter 全部被 ztunnel 重置。兩層都拿掉後同樣的呼叫全部 200，所以被拒是政策造成的。
- **健康檢查**：兩層都在時（安裝後與最後），五個服務與入口兩個副本共 7 個 pod 全部就緒、0 次重啟；kubelet 的探測經 `169.254.7.127/32` 照常通過。
- **入口照常**：四個階段入口到 identity、certs、mqtt-bridge 都是 200。

第一次執行（[mesh-e2e-first-order.json](data/2026-10-10-63-mesh-authz/mesh-e2e-first-order.json)）的順序是先拿掉 NetworkPolicy、再兩層都拿掉、最後只恢復 NetworkPolicy。前三個階段的結果與上表相同，但只恢復 NetworkPolicy 之後，certs → assets 在 90 秒內 112 次呼叫全部 200：第 3 階段放行時 ztunnel 已在兩個 pod 之間建好 HBONE 連線並重複使用，NetworkPolicy 不切斷已建立的連線，測試的持續呼叫又讓連線一直保持在使用中。所以測試改成先測只有 NetworkPolicy 的階段，並把這個限制寫進 chart README 與決策 27。這和 Laysi/trustiot-v2#62 獨立驗證（PR Laysi/trustiot-v2#254 的 F4）看到「對身分服務加 deny-all NetworkPolicy 對 HBONE 沒有作用」一致：入口到身分服務的連線在加上政策前就已建立。

### lab：入口（`ingress.e2e.ts`，預設拒絕下的回歸）

44 項全部通過（[ingress-e2e-saas.junit.xml](data/2026-10-10-63-mesh-authz/ingress-e2e-saas.junit.xml)、[ingress-e2e-saas.json](data/2026-10-10-63-mesh-authz/ingress-e2e-saas.json)），SaaS 型態、經 `ssh -L` 由 lab 主機連入口的 ClusterIP。新的預設拒絕、服務的 NetworkPolicy 與 AuthorizationPolicy 都在：cookie 驗證（ext_authz 經 HBONE 呼叫身分服務）、例外路徑、標頭、28 種路徑繞過（27 個 401、1 個 404）、身分服務延遲與停機時的 503 都與 Laysi/trustiot-v2#62 相同；偽造的身分標頭沒有一次到達後端。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 未列在清單的服務呼叫被重置、列在清單的放行（k3d 測試） | 通過：lab 的 k3s（依 2026-10-10 的決定取代 k3d），`mesh.e2e.ts` 第 1、5 階段；測試不綁叢集種類，nightly 的 k3d 可直接沿用 |
| 拿掉 NetworkPolicy 時 AuthorizationPolicy 仍擋、拿掉 AuthorizationPolicy 時 NetworkPolicy 仍擋（兩層各自生效的測試） | 通過：第 2、4 階段，各有證明另一層已失效的對照（imposter、outsider → 入口 pod），第 3 階段證明呼叫本身可行。限制：NetworkPolicy 只擋新的連線，且依 label 選來源；主要防線是 AuthorizationPolicy（見上） |
| 所有 pod 的健康檢查在預設拒絕下仍通過 | 通過：7 個 pod 全部就緒、0 次重啟；入口回歸測試 44 項通過 |

叢集內 ClickHouse（Laysi/trustiot-v2#253 在 lab 執行之後才合併進 main）：它的 AuthorizationPolicy 與 NetworkPolicy 由同一份清單產生，只放行 `ingest` 與 `telemetry-query`，以 chart 測試驗證；在叢集上「其他服務連不到 ClickHouse、它的 `/ping` 探測在預設拒絕下通過」**待測**：lab 測試的 `values-e2e.yaml` 用 `external`、沒有部署 ClickHouse。規則與上表的服務完全相同（同一個樣板、同樣以 `169.254.7.127/32` 放行探測），下一次 lab 或 nightly（Laysi/trustiot-v2#69）以 `bundled` 安裝時應補測。
