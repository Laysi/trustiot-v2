# service-kit 與 chart：健康檢查改用獨立的埠（2026-10-11）

對應 issue：Laysi/trustiot-v2#286。原始資料在 [data/2026-10-11-286-health-port/](data/2026-10-11-286-health-port/)。

## 目的

1. service-kit 在獨立的健康埠（`http.health_listen_addr`，預設 `0.0.0.0:8081`）只提供 `/healthz`、`/readyz`，其他路徑一律 404。
2. SIGTERM 後兩個埠的 readiness 行為一致，與 Laysi/trustiot-v2#51 的既有測試相同：立刻回 503 `draining`，`/healthz` 照常 200。
3. 兩份 values 與各種疊加渲染出的每個服務 NetworkPolicy，節點來源 `169.254.7.127/32` 只放行健康埠 8081，不放行 API 埠 8080；Service 不開健康埠，入口路由指不到它。
4. 回歸：同一份 chart 測試在修正前的 main（`37d81aa`）失敗（節點來源拿到 8080），修正後通過。

## 環境

- **建置主機** `ruisi-wsl`（Ubuntu on WSL2，x86_64，Docker），以 `rcheck.sh 286 '…'` 執行，`CI=1`：Rust 由 `rust-toolchain.toml` 鎖定，bun、helm、kubeconform 由 `.prototools` 鎖定。容器測試（`container`、`verify_container`、`tenant_db`、`job_lock`、outbox）用 Docker。
- **本機**：x86_64 Fedora（Linux 7.2.8-300.fc45），bun 1.4.2、helm 4.3.0（`.prototools`）。執行 `deploy/chart/tests/e2e` 的單元測試（`tunnel-recovery.test.ts` 在 WSL 上已知會失敗，所以在本機跑）與回歸比對。
- **受測版本**：分支 `feat/286-health-port`，最後一次完整執行在合併 main `e21ff41` 之後的 `46fe595`。「修正前」是以 `git archive origin/main deploy .prototools .proto docs/architecture/deployment.md` 取出的 `37d81aa`，只換上本分支的 `deploy/chart/tests/chart.test.ts`。

service-kit 的測試內容：

- `lifecycle::health_port_serves_only_the_probe_endpoints`：健康埠的 `GET /healthz`、`GET /readyz` 回 200（帶 `Cache-Control: no-store`）；`/`、`/v1/hello`、`/v1/slow`、`/v1/panic`、`/v1/whoami`、`/v1/items`、`/internal/anything`、`/healthz/`、`/readyz/`、`/healthz/../v1/hello`、`/HEALTHZ`、`/healthzx`、`//healthz`、`/%68ealthz` 都回 404；`POST /v1/echo`、`PUT /internal/anything`、`DELETE /v1/hello` 回 404；`POST /readyz` 回 405。API 埠照常服務，兩個埠都不記探針的存取日誌。
- `lifecycle::sigterm_fails_readiness_at_once_and_drains_requests_in_flight`：SIGTERM 後兩個埠的 `/readyz` 立刻都回 503 `draining`（最後一次執行為 2 ms），兩個埠的 `/healthz` 仍回 200；drain delay 結束後 API 埠拒絕新連線，健康埠仍回應（readiness 503、liveness 200），進行中的請求完成，行程在 2222 ms 以 exit code 0 結束，之後健康埠也關閉。
- `lifecycle::listen_address_in_use_stops_startup`：API 埠或健康埠被占用都以 exit code 1 結束，不記 `listening`。`lifecycle::health_port_equal_to_the_api_port_stops_startup` 與 `http::tests::the_health_port_must_differ_from_the_api_port`：兩個埠號相同是設定錯誤（`0` 除外），錯誤訊息不含設定值。
- `container`：範例服務以 PID 1 在唯讀容器內執行，readiness 經健康埠 8081 輪詢，`stop` 時健康埠回 503 後正常收尾。
- `chart_contract`：kit 的預設健康埠等於 `serviceDefaults.healthPort`，三個探針的 `port` 都是 `health`。

chart 的測試內容：

- `service-to-service authorization (decision 27) > <shape>: the node source reaches every service on its health port only, never its API port`：兩種部署型態，各自疊加不加、`tests/values/smoke.yaml`、smoke 加上啟用全部服務、`tests/e2e/values-e2e.yaml` 加上 `mesh.calls`，以及只啟用全部服務。每個服務的 Deployment：節點來源規則恰好是 TCP 8081；所有 ipBlock 規則的埠只有 8081；container port 是 `http` 8080 與 `health` 8081；三個探針都連 `health`；Service 只開 `http` 8080。每個規劃中的服務都被檢查到。traefik/whoami 替身（smoke-echo，e2e 的 assets、certs、mqtt-bridge）只能聽一個埠，探針由測試 overlay 改連 `http`，測試明列它們是 8080。
- `healthPort moves the health port…`、`no ingress route can reach the health port`、驗證表的 `a port named health`、`a port on the health port's number`、`health port below 1024`、`health port as a string`、`no health port`。
- 原本的 `the host source reaches only each workload's probe ports` 與 `each service's NetworkPolicy admits HBONE from the same callers…`（改為預期健康埠）照常通過；AuthorizationPolicy 與 mesh 計畫的測試沒有改動，仍然通過。
