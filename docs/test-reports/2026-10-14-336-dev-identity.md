新增的單元測試（`bun test scripts`）：

- `tests/identity.test.ts`：簽章金鑰（PKCS#8 PEM、Ed25519、0600 檔案與 0700 目錄、沿用、其他使用者讀得到時拒絕、不是金鑰與 RSA 金鑰拒絕，錯誤訊息不含檔案內容）、公鑰 JWK Set（只有 `kty`、`crv`、`kid`、`x`，不含私鑰，簽章以 JWK 驗得過，`kid` 跟著金鑰）、路由表、cookie（43 字元、雜湊是 32 bytes 的 SHA-256 而不是文字的）、SQL 只含雜湊不含 cookie、seed 檔與常數一致、`status` 的金鑰檢查。
- `tests/secret-api.test.ts`：Secret API 替身對 Job 會送的每種請求的回應（`GET`、帶 `resourceVersion` 的 merge `PATCH`、409、`null` 移除、401、404、405、415、400）、只聽 127.0.0.1，以及 PATCH 的原子性：部分無效的 patch（有效的 annotation 加無效的 data 值、有效的 data 加無效的 label 等）回 400、過期的 resourceVersion 回 409，之後 GET 的 annotations、labels、data 與 resourceVersion 都與之前相同。
- `tests/migrate.test.ts`：Job 的環境（平台設定、不繼承呼叫者的 `TRUSTIOT*`）、失敗時日誌的遮蔽、migration 角色的 SQL（`$$` 區塊、屬性、`ALTER DATABASE ... OWNER`）。
- `tests/env.test.ts`、`tests/secrets.test.ts`、`tests/state.test.ts`：`env` 的身分服務變數（含 `sh` 的 `eval` 讀回 JSON）、單引號輸出、`down` 保留的項目。

端對端測試（`tests/e2e.test.ts`）在真的 podman 環境裡驗證，順序：

1. `up`：執行 migration Job（全新資料庫上手動跑 `up` 時日誌是 `10 change(s)`），日誌含 `running the migration Job (tools/migrate)` 與 `migration Job finished`；`pg_roles` 是 `identity_app`（可登入）、`identity_owner`（不可登入）、`trustiot_owner`（可登入，皆非 superuser），資料庫 `trustiot` 的擁有者是 `trustiot_owner`；`state.json` 的 `identity_app` 密碼是 64 個十六進位字元（Job 產生）。
2. 私鑰：狀態目錄裡含 `PRIVATE KEY` 的檔案只有 `identity/signing-key.pem`（0600，目錄 0700）；`env` 與 `status` 的輸出不含它的內容。
3. `env`：印出公鑰 JWK Set（一把 key）、私鑰路徑、路由、`identity_app` 帳密；`status` 多一項 `identity: signing key`。
4. `seed` 兩次：兩次印出同一個 cookie，只建立一筆 session（`identity.sessions` 一列），cookie 檔 0600。
5. 在主機上以 `env` 的設定啟動 `identity`（`/readyz` 回 200），呼叫 `GET /internal/ext-authz/api/anything`（`Host: localhost`，帶 seed 的 cookie）：
   - 回 200，剛好一個 `x-internal-identity`；以 `env` 的公鑰驗證 EdDSA 簽章通過；標頭是 `{"alg":"EdDSA","typ":"internal-identity+jwt"}`；claims 是 `iss=identity`、`sub=<開發使用者>`、`aud=assets`、`tenant={<開發租戶>, admin}`、`exp-iat=60`。
   - 另一個格式正確的 cookie、沒有 cookie、格式錯誤的 cookie 都回 401，沒有 `x-internal-identity`；沒有路由的主機回 403。
   - 身分服務的日誌不含私鑰內容、`identity_app` 密碼與 cookie 值。
6. `up`、`status`、`seed` 的輸出不含任何資料庫密碼與私鑰內容（`seed` 只印 cookie）。
7. `down`：狀態目錄只剩 `identity/`，私鑰內容不變、權限仍是 0600；資料磁碟區保留。
8. 第二次 `up`：`identity signing key: kept`、私鑰不變、`identity_app` 換了新密碼、公鑰不變；`seed` 印出同一個 cookie（`kept the identity dev session`）；再啟動一次身分服務，同一個 cookie 通過同一組檢查。
9. `purge`：`identity/` 與私鑰已刪除、實例的容器、網路、磁碟區與映像都沒了；repo 的工作目錄沒有多出任何檔案。
