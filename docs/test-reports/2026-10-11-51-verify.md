# service-kit 獨立驗證（2026-10-11）

對應 issue：Laysi/trustiot-v2#51 service-kit：服務共用骨架（設定、health、SIGTERM、tracing），實作 PR Laysi/trustiot-v2#239，後續修正 Laysi/trustiot-v2#244（PR Laysi/trustiot-v2#245）。原始資料與失敗探測在 [data/2026-10-11-51-verify/](data/2026-10-11-51-verify/)。

## 目的

不是重跑實作者的測試，而是從安全與維運意圖找破口：日誌與遙測是否可能帶出請求資料或設定值；設定來源、優先順序與錯誤處理；SIGTERM 下的 readiness、排空與退出行為（含 keep-alive 與慢速客戶端）；advisory lock 在連線中斷時是否仍保證「同時只有一個副本執行」、是否漏鎖；`--no-default-features` 是否真的不依賴 `contract`。

### 3. Health、readiness 與關閉

| 檢查 | 結果 |
| --- | --- |
| 100 個進行中請求（各 2 秒，同時 SIGTERM） | 全部回 200；SIGTERM 後 1.84 秒退出，退出碼 0；之後連線被拒 |
| readiness 在 SIGTERM 後立即轉 503（量到 < 400 ms 內，容器內量到約 3 ms），`/healthz` 在排空延遲內仍回 200 | 通過 |
| 50 條閒置 keep-alive 連線 | SIGTERM 後 358 ms 退出（退出碼 0），連線被伺服器關閉 |
| keep-alive 連線在排空延遲內再送請求 | `/readyz` 回 503、一般請求回 200，隨後正常退出 |
| 半個請求標頭就停住的客戶端、宣告 1000 位元組只送 10 位元組的上傳 | 在 `drain_timeout`（2 s）後約 2.7 秒、2.3 秒退出，退出碼 1（文件規定的排空逾時失敗），沒有卡住 |
| 閒置服務 SIGTERM | 排空延遲後約 0.3 秒退出，退出碼 0 |
| PID 1 容器：`kill --signal TERM`，排空延遲 3 s，進行中請求 5 s | 通過：readiness 立即 503；延遲後新連線被拒；進行中請求完整回 200（`waited_ms=5000`）；`podman wait` 退出碼 0，6.6 s（寬限期 15 s） |
| 既有 `container.rs`（`podman stop`） | 在負載高時以及 `--no-default-features` 下各失敗過一次（`readiness fails within the drain delay`），重跑即過。`podman stop` 在這台機器要約 3.5 秒才送出 SIGTERM，超過測試的 1 秒視窗，即 Laysi/trustiot-v2#259 的已知不穩定，與 feature 無關；我沒有改那個檔案 |
| 超長 `drain_delay`（5000 億年） | 不會退出（要第二個訊號），測試以 SIGKILL 結束；屬 F-1 的同類問題，沒有上限驗證 |

## 發現

嚴重度依對「近乎產品環境」的影響判斷；重現的程式與輸出都在 data 目錄。

**F-1（低）設定的時間值沒有上限，極端值讓 SIGTERM 變成 panic。** `shutdown.drain_timeout` 是 `5000 億年` 這類 humantime 可解析的值時，啟動通過驗證；SIGTERM 後 `tokio::time::Instant + Duration` 溢位，行程 panic，退出碼 101，沒有排空。`292000000000y` 以下沒問題。`shutdown.drain_delay` 同樣的極端值則永遠不退出（要第二個訊號，或被 SIGKILL）。重現：`TRUSTIOT__SHUTDOWN__DRAIN_TIMEOUT=500000000000y`，啟動後送 SIGTERM；證據 `probe-extreme-durations.txt`、`probe-huge-drain-timeout.rs.txt`。建議：`ShutdownConfig::validate` 對兩者設合理上限（例如 1 小時），並驗證 `drain_delay + drain_timeout` 不超過合理的寬限期。這需要人為設定荒謬的值，風險低。

**F-2（中）鎖持有者與資料庫之間的網路分割時，兩個副本可以同時執行同一個工作。** `JobLockGuard::watch` 每次 heartbeat 對 session 做 `ping()`，沒有逾時。當封包被丟棄而連線沒有被重設時，持有者的 `ping()` 會一直等到 TCP 層放棄（Linux 預設要十幾分鐘），期間工作照常執行；而 server 端若先殺掉該 session（failover、`pg_terminate_backend`、idle 逾時、keepalive 判定），鎖被釋放，別的副本取得鎖並執行。重現（`probe-job-lock-partition-panic-pool1.rs.txt`，輸出 `probe-job-lock-output.txt`）：以 TCP 代理連線，代理改黑洞後由 admin 殺掉持有者的 backend；副本 B 在 36 ms 內取得鎖，A 的工作在之後 10 秒內又跑了 449 個 tick，`run` 未結束。已知限制是連線被乾淨關閉或重設時（測過，186 ms 偵測）沒有問題。建議：heartbeat 的 `ping()` 與 `release`、`try_acquire` 的查詢加逾時（例如 2 個 heartbeat），逾時視為 `Lost`；README 補上「工作必須冪等」之外的這個前提。

**F-3（低）工作 panic 會讓 `run_periodically` 的排程默默結束。** 迴圈直接 `await` 工作，panic 一路往上讓 `context.spawn` 的任務結束，這個副本從此不再排該工作（直到重啟）；readiness 與 liveness 都不受影響，只有一行 ERROR `thread panicked`。重現：第一次執行就 panic 的工作，2 秒內只執行 1 次，任務已結束（`probe-job-lock-output.txt`）。建議：以 `catch_unwind` 或在子任務執行工作並把 panic 記成 WARN 後繼續下一輪，或在 README 明寫工作不得 panic。

**F-4（低）OTLP 端點的路徑在 debug 以下的等級會出現在 stdout。** kit 刻意在啟動日誌只記錄「匯出是否開啟」，因為路徑可能帶 token；但 `log_filter=debug` 或 `trace` 時，OpenTelemetry SDK 的診斷日誌（`target=opentelemetry-otlp`，只寫 stdout）在每次匯出失敗時記錄完整 URL，36 行含路徑。預設 `info` 沒有（16 行，0 行含）。重現：`TRUSTIOT__TELEMETRY__OTLP_ENDPOINT=http://127.0.0.1:9/<secret>`、`LOG_FILTER=debug`，collector 連不上；證據 `probe-otlp-endpoint-path-in-sdk-diagnostics.txt`。建議：在 README 的遮蔽規則註明端點路徑不得放 token，或對 `opentelemetry-otlp` 目標的 `url` 欄位也遮蔽。

**觀察（不算缺陷）**

- O-1：panic 訊息原樣記錄（`payload` 欄位不在遮蔽名單），README 已寫明 panic 與 `expect` 的訊息不能放資料；sqlx 的慢查詢 WARN 會帶 SQL 文字，README 規則 4 已要求用綁定參數。
- O-2：pool 只有一條連線時，工作若使用同一個 pool 會死結（README 規則 4 已寫佔用一條連線）。
- O-3：標頭只收到一半或上傳停住的客戶端會讓服務在 `drain_timeout` 後以退出碼 1 結束（文件規定的行為），在寬限期之內，沒有卡住。

## 結論（逐條驗收）

- 容器內 PID 1：SIGTERM 後進行中請求完成、寬限期內退出（整合測試）：**通過**（既有測試與新增 `kill --signal TERM` 版本；既有 `container.rs` 的 1 秒視窗在高負載下不穩定，已知 Laysi/trustiot-v2#259）。
- SIGTERM 後 readiness 立即失敗：**通過**。
- 日誌為 JSON、帶 trace id、request body 不進日誌：**通過**，並擴大到標頭、查詢字串、路徑、錯誤路徑、設定值與 OTLP 匯出；F-4 是 debug 等級下端點 URL 的例外，不涉及請求資料。
- advisory lock 兩個副本只有一個執行：**通過**（乾淨關閉或重設連線，含 8 副本壓力測試）；**但網路分割下不成立**，見 F-2。
- 關閉 feature 時不依賴 contract：**通過**。
