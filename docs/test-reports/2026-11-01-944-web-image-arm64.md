# web 映像：arm64 實建、重現性與量測

對應 issue：Laysi/trustiot-v2#944（父 issue Laysi/trustiot-v2#498）。補上 [2026-10-21 的報告](2026-10-21-123-web-service.md) 結論中兩項「待測」：在 arm64 主機以發佈流程實際建置 `web` 映像並啟動，以及同一個 commit 重建兩次的重現性；另外量測記憶體、啟動時間與建置輸出大小。

測試日期為 2026-11-01。下方時間除非另外註明都是 UTC；`tar -tv` 列出的時間是建置主機的本地時間（UTC+8），所以 commit 時間 `11:48:59Z` 在那裡顯示為 `19:48:59`。

## 環境

- **主機**：建置主機（arm64 Linux VM）。aarch64，Fedora Linux 44，kernel 6.19，12 vCPU，19.5 GiB 記憶體。rootless podman 5.8.9（buildah 1.43.5）。各次量測時的負載寫在結果旁邊。
- **工具**：`.prototools` 釘選的 Bun 1.4.2、Rust 1.99.0、zig、cargo-zigbuild、cargo-auditable、syft、helm。主機沒有安裝 skopeo（發佈流程用它讀 OCI 壓縮檔的 manifest 與 config），腳本以 `dnf download` 取得 Fedora 的 `skopeo-1.22.3-1.fc44.aarch64` 套件，解開在這次執行的工作目錄裡使用，不安裝到主機。
- **受測程式碼**：本分支 tree `b89d7b77c832b4b39e698cb6997375d78718a46a`（以 main `d2e47c2f` 為基底，加上量測腳本的兩個 commit）。每次執行是該 tree 的一份乾淨複本，以一個新的 commit 建置，所以映像的 `org.opencontainers.image.revision` 標籤與時間戳（commit 時間）每次執行不同、digest 也跟著不同；同一次執行內的兩次建置是同一個 commit。
- **發佈流程**：`scripts/release/plan.ts --dry-run`（tag `v0.0.0-rc.944`，registry 寫本機的 `127.0.0.1:5068/laysi/trustiot-v2`，不推送），把 plan 的映像清單縮成只有 `web`，再以 `scripts/release/build.ts` 建置：交叉編譯 `web`（`aarch64-unknown-linux-musl`）、建置並檢查 `frontend/`（`[static]`）、以 vfs store 的 podman 打包、syft 產生 SBOM。與 release.yml 的 build job 相同的程式碼與指令；不同的是主機上的 podman 版本（release.yml 的 arm64 runner 用 Ubuntu 套件的 podman），所以這裡的 digest 不會等於正式發佈的 digest，見 [CI 與發佈](../architecture/ci-release.md)「交叉編譯與可重現建置」。
- **容器**：映像從 OCI 壓縮檔拉進這次執行自己的 vfs store（不動使用者的 store），以 `podman run --read-only --cap-drop=all --security-opt=no-new-privileges` 啟動，兩個埠只發佈在 127.0.0.1。沒有在任何叢集或環境開啟 `services.web`。

## 指令

從 repo 根目錄執行，HEAD 要是受測的 commit（發佈流程要求）。腳本在 [data 目錄](data/2026-11-01-944-web-image-arm64/web-image.ts)，每次執行自成一體：建置、檢查、啟動與量測都在同一次執行裡完成，結束時刪除工作目錄、容器與映像。

```sh
# 重現性、/srv/www 的擁有者與模式、啟動並請求深連結與每個檔案
bun docs/test-reports/data/2026-11-01-944-web-image-arm64/web-image.ts repro

# 啟動時間、記憶體與大小；量測時主機上沒有其他建置工作
bun docs/test-reports/data/2026-11-01-944-web-image-arm64/web-image.ts measure --runs 5
```

`repro` 的第二次建置刻意與第一次不同：在另一個目錄的新 clone（`git clone --no-checkout` 後 checkout 同一個 commit）、自己全新的 Cargo target 目錄、umask 027，並晚於第一次建置；Bun 的套件快取與 Cargo 的 registry 快取共用。

### 2. 啟動映像與請求

`/readyz` 在 `podman run` 之後 108 ms 回 200。每個請求的結果（`PASS` 表示狀態、Content-Type、body 與 9 個安全標頭都符合）：

| 請求 | 結果 |
| --- | --- |
| 深連結 `GET /devices/42?tab=data`、`/`、`/settings/users`、`/a/b/c/d` | 200 `text/html; charset=utf-8`、`cache-control: no-cache`，body 與 `dist/index.html` 逐位元組相同 |
| `dist/` 的 12 個檔案逐一 `GET` | 200，body 與 `dist/` 的檔案逐位元組相同；`/static/` 底下的 `cache-control: public, max-age=31536000, immutable`，其他 `no-cache`；`.js` 是 `text/javascript; charset=utf-8`、`.css` 是 `text/css; charset=utf-8`、`.svg` 是 `image/svg+xml` |
| `index.html` 引用的資源（`/favicon.svg`、`/static/B1Kiyeui.js`、`/static/DDEsU6_R.css`） | 都在 `dist/` 裡，也都在上一列請求過 |
| `HEAD /devices/42` | 200，沒有 body |
| `GET /static/missing.js`、`GET /static/..%2Findex.html` | 404 `text/plain; charset=utf-8`、`cache-control: no-store` |
| `POST /` | 405、`cache-control: no-store` |

深連結回應的安全標頭與 2026-10-21 本機實測的值相同（CSP、`content-security-policy-report-only`、`x-content-type-options: nosniff`、`referrer-policy: strict-origin-when-cross-origin`、`permissions-policy`、COOP、CORP、`x-frame-options: DENY`、HSTS），逐項列在 repro.txt。`podman stop` 送 SIGTERM 後依 service-kit 的流程結束：readiness 先失敗、5 秒後停止接受連線、`shutdown complete`，exit code 0。

### 3. 重現性

同一次執行、同一個 commit 的兩次建置（條件見「指令」）：

| 比較 | 結果 |
| --- | --- |
| SPA `frontend/dist/` 每個檔案的 sha256 與大小 | 相同（清單的 sha256 `1be3b66c…`）；同一天另外兩次 `repro` 執行（較早的 tree，`frontend/` 相同）的 4 次建置也得到同一份清單 |
| `web` 執行檔 | 相同（sha256 `29f8be58…`） |
| 映像 digest（`build.json`） | 相同：`sha256:529e94b981bcf621be506c93a1a6f3849fd32bae6513fe192d4bc195b6b2d147` |
| config digest、15 個 layer digest | 相同 |
| OCI 壓縮檔的內容：`index.json`、`oci-layout` 與每個 blob | 相同 |
| OCI 壓縮檔這個檔案本身的 sha256 | 不同，只差外層 tar 每個項目的時間（podman 寫出壓縮檔的當下時間，主機本地時間 19:49:11 與 19:49:44）；publish 以 `skopeo copy --preserve-digests` 推送的是裡面的 blob，不是這個 tar，所以不影響發佈的 digest |
| SBOM（`web.spdx.json`） | 檔案不同：syft 每次產生新的 `documentNamespace`（含隨機 UUID）與 `creationInfo.created`（產生時間）；列出的套件（名稱與版本，216 個）相同。SBOM 以 attestation 附在映像旁，不在映像 digest 裡 |

所以映像 digest 可以重現，不需要修改。Vite 的輸出在不同目錄的 clone 也相同，表示建置輸出沒有寫入 checkout 的路徑。

### 4. 量測

在建置主機（arm64 Linux VM）上執行，量測期間主機上沒有其他建置工作；每次啟動前的負載列在表裡，結束時 0.60 1.25 1.95。網站是上面的 `frontend/dist`（12 個檔案、1,345,424 bytes）。

**啟動時間**（5 次）：

| 次 | 負載（1/5/15 分鐘） | `podman run` → `/readyz` 200 | 容器啟動 → `loaded the site` | 容器啟動 → `listening` |
| --- | --- | --- | --- | --- |
| 1 | 1.39 1.48 2.06 | 139 ms | 5.8 ms | 5.9 ms |
| 2 | 1.18 1.43 2.04 | 127 ms | 6.1 ms | 6.2 ms |
| 3 | 0.92 1.36 2.01 | 134 ms | 5.3 ms | 5.4 ms |
| 4 | 0.77 1.32 1.99 | 125 ms | 5.6 ms | 5.7 ms |
| 5 | 0.65 1.27 1.97 | 128 ms | 4.9 ms | 5.0 ms |

- 「容器啟動」是 podman 記錄的 `State.StartedAt`，後兩欄是服務自己的日誌時間戳；兩者都是主機的同一個時鐘。服務從啟動到開始監聽約 5–6 ms，讀網站本身占其中一小部分（`loaded the site` 之後 0.1 ms 就 `listening`）。
- `podman run` → `/readyz` 200 是用戶端從執行 `podman run` 到第一次讀到 200 的時間（每 5 ms 問一次），包含 podman 建立容器與埠轉送，約 125–139 ms。

**記憶體**（同 5 次；`VmRSS`、`VmHWM`、`RssAnon`、`RssFile` 來自 `/proc/<pid>/status`，`memory.current`、`memory.peak` 來自容器的 cgroup，cgroup 的數字含映像檔案的 page cache，約 5.2 MB）：

| 時點 | VmRSS | RssAnon | RssFile | cgroup memory.current | cgroup memory.peak |
| --- | --- | --- | --- | --- | --- |
| 就緒 2 秒後 | 4456–4472 kB | 1832–1848 kB | 2624 kB | 7.9–8.4 MB | 10.2–10.5 MB |
| 5000 個請求之後 | 6484–7448 kB | 3860–4824 kB | 2624 kB | 11.4–12.7 MB | 13.8–15.1 MB |

- 5000 個請求：32 個同時，輪流請求兩個深連結與 12 個檔案，共 480,733,080 bytes，每個回應的狀態與長度都正確（用戶端在同一台主機，0.12–0.16 s）。`VmHWM` 與請求後的 `VmRSS` 相同，執行緒 14 個。
- 網站以 `Bytes` 放在 heap（`services/web/src/site.rs`），所以 `RssAnon` 在就緒時約是網站大小（1.3 MiB）加上約 0.5 MiB；網站變大時，記憶體大致隨網站大小線性增加，上限是服務接受的 32 MiB（`MAX_SITE_BYTES`）。
- chart 的 `serviceDefaults.resources`（`services.web` 沿用）是 requests 32Mi、limits 256Mi，量到的峰值（cgroup 15.1 MB）遠低於兩者。

**大小**：

| 項目 | 大小 |
| --- | --- |
| SPA 建置輸出 `frontend/dist` | 12 個檔案、1,345,424 bytes；以 gzip -9 壓縮合計 410,123 bytes |
| 其中主程式 `static/B1Kiyeui.js` | 718,499 bytes（gzip -9：217,466） |
| 其中 `static/DDEsU6_R.css` | 36,518 bytes（gzip -9：7,681） |
| 其中 `sandbox/`（儀表板沙箱的頁面與程式） | 7 個檔案、587,466 bytes |
| `web` 執行檔（aarch64、musl、靜態連結） | 3,804,104 bytes |
| 映像（OCI 壓縮檔） | 3,226,112 bytes；15 層壓縮後合計 3,201,658 bytes（measure.txt）。各層大小在 repro.txt 那次建置：執行檔那層 1,878,561、`/srv/www` 那層 426,935、其餘 13 層是 distroless 基底共 896,167，合計 3,201,663；兩次執行的 commit 時間不同，這兩層 tar 裡的時間跟著不同，壓縮後的大小差幾個 bytes |

每個檔案的大小與 gzip -9 大小在 measure.txt。`web` 回應時不壓縮（沒有 `content-encoding`），gzip 的數字只是對照。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 在 arm64 實際建置 `web` 映像，`/srv/www` 的擁有者與模式正確，映像能啟動並回應深連結 | 通過：建置主機（arm64 Linux VM）以發佈流程的 `build.ts` 建置；檔案 0644、目錄 0755、全部 0:0，映像以 65532:65532 執行、根檔案系統唯讀；深連結回 `index.html`，每個檔案逐位元組相同，404、405、HEAD 與安全標頭正確（結果第 1、2 項） |
| 兩次建置的 SPA `dist/` 與 `web` 映像 digest 相同，或記下不同的原因與處理方式 | 通過：`dist/`、執行檔、映像 digest、每一層與 config 都相同。OCI 壓縮檔外層 tar 的時間與 SBOM 的 namespace、產生時間不同，都不進映像 digest，不需處理（結果第 3 項） |
| 記憶體、啟動時間與建置輸出大小的量測 | 通過：啟動到監聽約 5–6 ms、`podman run` 到就緒約 125–139 ms；就緒時 VmRSS 約 4460 kB、5000 個請求後最多 7448 kB，cgroup 峰值 15.1 MB；`dist` 1,345,424 bytes、映像 3,226,112 bytes（結果第 4 項） |
| 與正式發佈（release.yml 的 arm64 runner）的 digest 比對 | 待測：本次的 podman 版本與 runner 不同，digest 本來就不會相同；要以 runner 的 podman 版本重建某個 tag 的 `web` 映像比對，屬於跨環境的重複驗證，延後 |
