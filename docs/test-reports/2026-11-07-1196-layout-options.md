# 有草稿的對話頁：版面選項的原型與量測（2026-11-07）

對應 issue：Laysi/trustiot-v2#1196（有草稿的對話頁在 1280 px 以上是兩欄：對話欄只剩 520 px，看最新回答時右半邊是空的；等維護者在選項 1–4 之間決定）。

這份報告只提供決定用的數字與取捨，不做決定，也不實作：選項 1、2、1+2 與 3 各做了一個拋棄式的原型（報告資料目錄裡的 patch），在 UI 預覽量完就還原，產品程式沒有任何改變。選項 4（不改版面）就是現在的程式，當作基準量測。

## 環境

- 建置主機（arm64 Linux）。測的程式是分支 `test/1196-layout-options`，從 Laysi/trustiot-v2#1195 的分支 `feat/1195-two-column-walkthrough`（`e976c301019361c15bc0bb091b599a5b654d803b`）開出，沒有合併 main。所以和 Laysi/trustiot-v2#1195 的走查一樣，這個樹沒有 PR Laysi/trustiot-v2#1190（頁首與輸入框的高度寫成 `scroll-padding`，`visibleBand()`）與 Laysi/trustiot-v2#1184 的 `revealInBand`；它們和各選項的關係寫在「實作還需要的」。
- Bun 與其他工具是 `.prototools` 釘選的版本；`bun install --cwd frontend --frozen-lockfile` 之後啟動 UI 預覽：`bun --bun vite --mode ui-preview --host 127.0.0.1 --port 5196 --strictPort`（建置主機是共用的，所以用自己的埠，埠已有回應時拒絕執行）。沒有後端，所有 API 由預覽的假服務在頁面裡回答。
- 瀏覽器：`frontend/e2e/image.ts` 釘選的 Playwright 映像（`mcr.microsoft.com/playwright:v1.64.1-noble`，以 digest 釘選，linux/arm64）裡的 Chromium。語言 zh-TW、時區 Asia/Taipei、淺色、放大 100 %（`deviceScaleFactor` 1）。Chromium 的捲軸佔 15 px，`xl`、`2xl` 的媒體查詢以含捲軸的視窗寬度判斷。
- 預覽的對話與 Laysi/trustiot-v2#1195 相同：「Line 2 energy this week」兩輪問答，第一則回答寫出草稿「Line 2 power draft」的第 1 版，追問的回答寫出第 2 版，草稿面板畫最新的第 2 版。資料是虛構的英文名稱，介面文字是繁體中文。

### 原型

每個選項是一個對分支產品程式的 patch，只當作證據：[`option-1.patch`](data/2026-11-07-1196-layout-options/option-1.patch)、[`option-2.patch`](data/2026-11-07-1196-layout-options/option-2.patch)、[`option-1-2.patch`](data/2026-11-07-1196-layout-options/option-1-2.patch)（前兩者合在一起）、[`option-3.patch`](data/2026-11-07-1196-layout-options/option-3.patch)。類別名稱照真的實作會寫的樣子挑（Tailwind 的斷點、`focusRing`、`useMediaQuery`），讀過 `docs/design/chat-dashboards/design.md` 的「對話裡的草稿」「和設計稿不同的實作」、`draft.html` 與它的 `assets/base.css`。

| 選項 | 改了什麼 | 檔案 |
| --- | --- | --- |
| 1：面板 sticky | 兩欄時（`xl` 以上）草稿面板的容器 `sticky`，貼在頂端列下方 32 px（與 `main` 的上內距相同，所以頁面頂端時位置不跳）；高度到視窗底留 16 px（`max-h: calc(100dvh − 頂端列 − 3rem)`），內容超過時在面板裡捲動（`overflow-y: auto`）。頂端列高度讀 PR Laysi/trustiot-v2#1190 會發布的 `--sticky-top`，這個樹沒有，所以用後備值 57 px。兩欄時面板是有名稱的 `region`（「儀表板草稿」，新的訊息鍵 `draft.panel`）、`tabIndex=0`、套用 `focusRing`，鍵盤可以進到面板再用方向鍵捲動；單欄時不是 region、不在 Tab 順序裡（`useMediaQuery` 判斷）。因為面板元件本身帶這些類別，對話頁與唯讀的分享頁都套用。 | `DraftPanel.tsx`、兩個語系檔 |

## 指令

```sh
# repo 根目錄；frontend/ 必須沒有未提交的變更（腳本會套用再還原 patch，有變更時拒絕執行）
bun install --cwd frontend --frozen-lockfile
SHOTS_DIR="$(mktemp -d)" bash docs/test-reports/data/2026-11-07-1196-layout-options/run.sh
# 只跑部分選項或視窗：OPTIONS="baseline option-1"、VIEWPORTS=1280x720；不截圖：SHOTS=0
```

[`run.sh`](data/2026-11-07-1196-layout-options/run.sh) 對 `OPTIONS` 裡的每個名稱（預設 `baseline option-1 option-2 option-1-2 option-3`）：`git apply` 套用 patch（`baseline` 不套）、啟動預覽、在 Playwright 容器裡執行 [`browser-check.mjs`](data/2026-11-07-1196-layout-options/browser-check.mjs)、停掉預覽、`git apply -R` 還原（失敗或中斷也還原）。每個選項的紀錄寫到同一個目錄的 JSONL：[baseline](data/2026-11-07-1196-layout-options/baseline.jsonl)、[option-1](data/2026-11-07-1196-layout-options/option-1.jsonl)、[option-2](data/2026-11-07-1196-layout-options/option-2.jsonl)、[option-1-2](data/2026-11-07-1196-layout-options/option-1-2.jsonl)、[option-3](data/2026-11-07-1196-layout-options/option-3.jsonl)，每個 41 行（四個視窗各 10 行與一行 `summary`）。每個視窗的最後一行 `summary row` 是下面各表的數字來源。截圖只在設了 `SHOTS_DIR` 時寫成 JPEG，不進 repo。

紀錄之後只在腳本加了兩個輸入檢查（`VIEWPORTS` 有不認得的名稱時失敗；`frontend/` 與 `HEAD` 不同時，包括已 stage 的變更，`run.sh` 拒絕執行），量測的步驟沒有改。

本次在建置主機上一次跑完五種版面（四個 patch 都套得上分支頭，預覽在每個 patch 下都能啟動並畫出頁面）；五個 `summary` 行的 `failures` 都是空陣列，所有步驟的主控台錯誤都是空的，頁面頂端時沒有橫向捲動、沒有超出視窗的元素、沒有被截斷的文字。等待都以條件為準（上限 60 秒，逾時的訊息寫明在等什麼）；滾輪的每一下等到捲動停下（連續五個畫格位置不變，上限 10 秒）。

### 每個視窗做的事

腳本由 Laysi/trustiot-v2#1195 的 `browser-check.mjs` 改來，走同樣的步驟、同樣的視窗。每個視窗：

1. **頁面頂端**：打開預覽對話，等兩則回答的卡片、面板、圖與 KPI 都畫好，捲回頂端（頁面與面板自己的捲動都歸零），量兩欄、回答的卡片與圖、面板與圖的寬度與位置，面板是不是 sticky、自己會不會捲動。
2. **最新的回答**：把第二則回答的卡片標題列捲到頂端列下方（劇本步驟 3、4 的動作都在這裡），量面板露出多少、面板的標題卡與狀態標籤（「草稿・第 2 版・未儲存」）是否完整在視窗內、面板的圖露出多少。
3. **滾輪**：同一個位置，滑鼠放在面板的中間（面板不在視窗內時是同一個 x、視窗高度的一半），往下四下、往上四下，每下 200 px；連續送一次、每下間隔 1.2 秒再送一次。每一下之前記錄滑鼠下面是不是圖的繪圖區（canvas），之後記錄頁面與面板的捲動位置，以及事件有沒有被頁面裡的程式取消（`preventDefault`）。這是 Playwright 送的合成滾輪事件，不是實體滑鼠或觸控板。
4. **Tab**：同一個位置，焦點放在輸入框，連按 Tab 直到焦點進入面板又離開（最多 14 下），記錄每一站在哪裡、是否完整看得到、頁面與面板的捲動，以及焦點外框的計算樣式。
5. **面板的內容比面板高時**：面板自己會捲動時，把它捲到底，看面板的圖是否完整。
6. **資料來源**：先把元件的上緣捲到「顯示它的地方」的頂端（面板自己會捲動時捲面板，否則捲頁面到頂端列下方），再打開資料來源：最新回答的 KPI、面板的 KPI、面板的圖（元件右上的「資料來源」）。記錄面板打開時的寬高、露出多少、剩下的要靠頁面還是面板捲動才看得到。
7. **儲存**：頁面與面板都捲回頂端，再把最新回答的卡片標題列捲到頂端列下方，按卡片的「儲存到儀表板列表」，記錄兩處的狀態標籤（「已發布・第 1 版」）與通知（「已儲存為儀表板列表裡的第 1 版」）是否都完整在視窗內。

「完整在視窗內」是指方塊在頂端列下緣與視窗底之間，而且沒有被任何會裁切它的祖先（例如自己捲動的面板）裁掉；左欄的方塊另外要在輸入框上緣之上（輸入框只擋與它左右重疊的方塊，不擋右欄）。

### 7. 各選項真的實作還需要的

共同：

- `design.md` 的「對話裡的草稿」位置一段與「和設計稿不同的實作」的表格依決定改寫，並更正「兩欄各至少約 560 px」；劇本（PR Laysi/trustiot-v2#1146 的 `docs/runbooks/demo-presentation.md`）步驟 3、4 的面板說明依決定改。
- `frontend` 的 `api:check`、`typecheck`、`lint`、`test`、`build`、`check:dist`，以及在 1280×720、1536×768、1920×1080 重跑本報告的 `run.sh`（或它的改版）。原型沒有跑這些檢查：patch 只證明能套用、預覽能畫。
- 手機與窄螢幕：四個原型在 1279×720 都沒有改變單欄的版面（選項 2 例外：單欄的面板寬度跟著內容欄變成 1232 px），但沒有量手機寬度。

選項 1：

- 頂端列的高度：原型讀 `--sticky-top`（PR Laysi/trustiot-v2#1190 會發布）並用 57 px 當後備；要等 #1190 合併後改成只讀變數，並測頂端列高度改變時面板跟著動。
- PR Laysi/trustiot-v2#1190 的 `visibleBand()` 與 Laysi/trustiot-v2#1184 的 `revealInBand()` 都以「頁面的捲動、頂端列與輸入框之間」為可見範圍，選項 1 多了第二個捲動容器：
  - 輸入框只在左欄，右欄面板的可見下緣是面板自己的下緣（視窗底留 16 px），不是輸入框上緣；以頁面的可見帶判斷面板裡的元素，下緣會多算 130 px 被遮住。
  - 面板裡的元素被面板的框裁掉時，`revealInBand` 只看它的位置在不在頁面的可見帶裡，可能判斷為「已經看得到」而不捲動；要改成同時看最近的捲動容器的框。它呼叫的 `scrollIntoView` 本身會捲動面板與頁面，所以補上判斷之後，本報告 4. 的「從面板的圖打開資料來源只露出 44 px」才會被捲到看得到。
  - 面板的捲動容器沒有 `scroll-padding`；Tab 到面板裡的元素時由瀏覽器捲進面板（本次的 Tab 每一站都完整看得到）。
- 滾輪：面板裡的圖會把滾輪當縮放（見 5.），面板矮時更容易停在圖上。要決定是否接受、或面板裡的圖不用滾輪縮放；另外要決定面板捲到底之後滾輪是否接著捲頁面（`overscroll-behavior`，原型沿用預設：接著捲）。
- 面板的標題卡（名稱、狀態、儲存鈕、儲存後的通知）會隨面板內容捲走；可以考慮像 `conversation.html` 的 `.panel-head` 那樣在面板裡黏在上面，讓 3. 的「兩處同時看得到」不受面板捲動影響。多份草稿的下拉選單也在同一個捲動範圍裡。
- 焦點外框：見 5. 的既有問題，region 的外框要等它修好才看得到。
- 測試：`DraftPanel` 的單元測試（兩欄時是有名稱、可聚焦的 region，單欄時不是；`useMediaQuery` 以 `matchMedia` 模擬），以及瀏覽器端對端測試量 sticky 與面板自己的捲動（jsdom 量不到版面）。
- 斷點一致：原型的 `xl:` 與 `(min-width: 80rem)` 寫在 `DraftPanel` 裡，要和兩頁的兩欄斷點一致；若和選項 3 一起用，要一起改成 `2xl`。

選項 2：

- 依路徑決定內容欄寬（原型在 `Layout.tsx` 以 `isConversationPath` 與分享頁的前綴判斷）要有測試；`docs/design/app-shell.md` 提到內容欄的 `max-w-6xl`，要補寫對話頁的例外。
- 回答卡片跨過容器查詢的門檻（見 4.）：回答裡的 KPI 變成半格，資料來源面板變成 207×2385。要和 Laysi/trustiot-v2#1197 一起處理，或先處理 #1197，否則劇本「從左欄的回答卡片點數字」的建議不再成立。

## 結論

issue 的四條驗收條件（決定寫進 `design.md`、實作後重跑、劇本、`frontend` 檢查）都在決定之後，本報告不改變它們：**待決定**。這份報告是決定用的證據；各選項的事實：

- 1280×720 的對話欄：現在 520 px；選項 1 520 px；選項 2 與 1+2 633 px；選項 3 單欄 768 px。
- 看最新的回答時面板看得到：只有選項 1 與 1+2（1280×720 露出 615 px，含標題卡與狀態標籤）。
- 儲存後兩處的狀態同時看得到：只有選項 1 與 1+2（三個兩欄的視窗都是）。
- 量到、原本沒有預期的：選項 2 讓回答裡的 KPI 資料來源從 358×725 變成 207×2385；選項 1 的面板裡打開資料來源時被面板的框裁掉（從圖打開只露出 44 px），圖的滾輪縮放在矮的面板裡更容易擋住捲動；所有版面的焦點外框都看不到（既有問題，與版面無關）。
- 沒有做的：Laysi/trustiot-v2#1198 的第一份草稿那一刻（要另一個腳本，數字由欄寬推論）、分享頁、手機寬度、實體滑鼠與觸控板、真的投影機。決定由維護者做。
