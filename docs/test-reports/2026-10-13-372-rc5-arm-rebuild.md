# 在 arm64 模擬容器重建 `v0.0.0-rc.5`，與 arm64 runner 發佈的產出比對

對應 issue：Laysi/trustiot-v2#372。前置評估見 [release.yml 改用 arm64 runner 的測試報告](2026-10-12-310-release-arm-runner.md)（Laysi/trustiot-v2#310），規則見 [CI 與發佈](../architecture/ci-release.md) 的「交叉編譯與可重現建置」。原始資料與腳本在 [data/2026-10-13-372-rc5-arm-rebuild/](data/2026-10-13-372-rc5-arm-rebuild/)。

## 指令

腳本都在 data 目錄，由 rcheck 在 worktree 根目錄（build host 上的快照）執行：

```sh
# 1. 重建：arm64 容器內兩個新 clone 各跑一次 plan.ts --tag v0.0.0-rc.5 與 build.ts，再比對（inner.sh、images.sh）
rcheck.sh 372 'bash docs/test-reports/data/2026-10-13-372-rc5-arm-rebuild/arm-eval.sh rebuild'
# 2. COPY 層的 tar 標頭（tarhdr.ts），以及在 x64 容器內以 root 與 rootless podman 重新打包發佈的執行檔（layer-inner.sh）
rcheck.sh 372 'bash docs/test-reports/data/2026-10-13-372-rc5-arm-rebuild/arm-eval.sh layers'
# 3. root 與 rootless、--layers=false、vfs 的組合，每次都是新的 storage（variants.sh）
rcheck.sh 372 'bash docs/test-reports/data/2026-10-13-372-rc5-arm-rebuild/arm-eval.sh variants'
# 4. 上面各次產生的映像 config 的 COPY 步驟與 history 註解
rcheck.sh 372 'bash docs/test-reports/data/2026-10-13-372-rc5-arm-rebuild/arm-eval.sh configs'
# 5. 以 runner 的方式（一般使用者、rootless podman）打包第 1 步重建的執行檔，x64 與 arm64 容器各一次（pack-rootless.sh）
rcheck.sh 372 'bash docs/test-reports/data/2026-10-13-372-rc5-arm-rebuild/arm-eval.sh rootless'
# 刪除 build host 上的評估目錄
rcheck.sh 372 'bash docs/test-reports/data/2026-10-13-372-rc5-arm-rebuild/arm-eval.sh cleanup'
```

`rcheck.sh` 是 coordinator 的 check queue 指令，不在 repo 內：它把 worktree 的快照同步到 build host，以單一佇列執行引號內的指令。不經它時，在有 Docker 與 aarch64 qemu-user binfmt handler 的 x86_64 主機上，從 repo 根目錄直接執行引號內的指令即可；評估目錄是腳本開頭的 `E`（`$HOME/tv2/agents/372-eval`），換位置時改它。每一步的完整輸出存成 [run-rebuild.txt](data/2026-10-13-372-rc5-arm-rebuild/run-rebuild.txt)、[run-layers.txt](data/2026-10-13-372-rc5-arm-rebuild/run-layers.txt)、[run-variants.txt](data/2026-10-13-372-rc5-arm-rebuild/run-variants.txt)、[run-configs.txt](data/2026-10-13-372-rc5-arm-rebuild/run-configs.txt)、[run-rootless.txt](data/2026-10-13-372-rc5-arm-rebuild/run-rootless.txt)，其中 build host 的名稱與家目錄路徑已換成「the build host」與 `<eval dir>`。`arm-eval.sh` 的 `layers`、`variants`、`configs`、`rootless` 模式是在第 1 步之後才加上的；`rebuild` 模式除了註解與 `trap` 的位置，與第 1 步執行時相同。第 3 步的 rcheck 結束碼是 1，因為腳本最後一個指令 `diff` 找到差異（那是預期的輸出），所有變體都有結果。

重建的兩次建置：

| 建置 | clone 位置 | `CARGO_HOME` |
| --- | --- | --- |
| runner 路徑 | `/home/runner/work/trustiot-v2/trustiot-v2`（runner 的 checkout 路徑） | `/home/runner/.cargo` |
| 其他路徑 | `/work/repo` | `/work/cargo-alt` |

兩次都跑 release.yml 的 plan 指令 `plan.ts --tag v0.0.0-rc.5`（不加 `--dry-run`，所以 tag 必須指向 checkout 的 commit），再以 plan 跑 `build.ts`。plan 拿掉了 `postgres`：它的 Containerfile 有 `RUN`，qemu-user 下的 podman 無法執行（見 Laysi/trustiot-v2#310 的報告），也不在本 issue 範圍。容器以 root 執行，與 Laysi/trustiot-v2#310 相同。

## 結果

### 1. 重建：執行檔相同，映像 digest 不同

| 項目 | runner 路徑 | 其他路徑 | rc.5 發佈 |
| --- | --- | --- | --- |
| plan | `0.0.0-rc.5`，commit `716740a`，`sourceDateEpoch` 1791832004 | 同左 | `[release:plan]` 輸出相同 |
| Cargo（模擬） | 22 分 19 秒 | 20 分 30 秒 | runner 上約 1 分 16 秒 |
| `identity` 執行檔 | `ea8f655b…`，6,378,112 bytes | `ea8f655b…` | 從 GHCR 映像取出：`ea8f655b…`，**相同** |
| `release-selftest` 執行檔 | `78769ece…`，377,264 bytes | `78769ece…` | 套件私有，未取出；見第 3 節 |
| `identity` 映像 | `sha256:4bb4177e…` | `sha256:4bb4177e…` | `sha256:7a042972…`，**不同** |
| `release-selftest` 映像 | `sha256:6f37a60c…` | `sha256:6f37a60c…` | `sha256:bc2b33e0…`，**不同** |
| SBOM 套件數 | 213 / 13 | 213 / 13 | 213 / 13 |

- 兩次重建完全相同：checkout 路徑與 `CARGO_HOME` 不影響執行檔與映像（`--remap-path-prefix` 有效）。
- `identity` 的執行檔與 runner 發佈的逐位元組相同（`images.sh` 從 GHCR 的映像取出 `usr/local/bin/identity` 比對）。所以 Rust 建置在 qemu-user 模擬的 arm64 容器與真正的 arm64 runner 上結果相同：模擬環境、容器內的 rustup 與 Rust 版本都不是差異來源。
- 映像不同。`identity` 的 manifest 中，distroless 的 13 層完全相同，只有最後的 COPY 層不同（重建 `1196df77…`，3,277,753 bytes；發佈 `b0779185…`，3,278,126 bytes）。config 的差異只有 COPY 層的 `diff_id`（`fe0509b6…` 對 `8b3d9619…`），以及 history 裡三個 `FROM <中間映像 ID>` 註解；COPY 步驟本身（`COPY file:f48d364a…`）、標籤、時間戳都相同。

### 2. 找出原因：podman 以 root 或 rootless 執行

`tarhdr.ts` 列出兩個 COPY 層的每個 tar 標頭（[run-layers.txt](data/2026-10-13-372-rc5-arm-rebuild/run-layers.txt)）：

- 兩者的 `usr/`、`usr/local/`、`usr/local/bin/`、`usr/local/bin/identity` 標頭逐位元組相同（mode、uid/gid 0、mtime 1791832004，內容相同）。
- 發佈的層多了一個 PAX 標頭：`usr/` 帶 `SCHILY.xattr.user.overlay.origin=`（空值）。這是 rootless podman 的 overlay storage 寫入的 xattr：沒有 root 權限時，overlay 用 `user.overlay.*` 而不是 `trusted.overlay.*`，匯出層時 `user.*` 的 xattr 跟著進了 tar。

runner 上的 build.ts 以 runner 的使用者 `runner` 直接呼叫 podman，所以是 rootless；本次與 Laysi/trustiot-v2#310 的容器都以 root 執行 podman。驗證（x64 容器，同版本的 podman，打包從 GHCR 取出的執行檔，指令與 build.ts 相同）：

| podman | COPY 層 `diff_id` | 映像 |
| --- | --- | --- |
| root（x64 容器） | `fe0509b6…` | `4bb4177e…`，與 arm64 模擬容器內的重建相同 |
| rootless，使用者 uid 1001（x64 容器，[run-layers.txt](data/2026-10-13-372-rc5-arm-rebuild/run-layers.txt)） | `8b3d9619…`，與發佈的 COPY 層逐位元組相同 | `7f10672d…`，仍不同 |

rootless 重現了發佈的 COPY 層，但 digest 仍不同：history 的 `COPY file:<hash>` 不同（[run-configs.txt](data/2026-10-13-372-rc5-arm-rebuild/run-configs.txt)）。buildah 的這個 hash 是 COPY 來源的 tar 串流，時間戳歸零，但保留來源檔案的 uid、gid、使用者與群組名稱、xattr。rootless podman 在 user namespace 內看來源檔案：

- build.ts 在 runner 上自己建立 build context（暫存目錄裡的執行檔），檔案屬於 `runner` 的使用者與群組，在 namespace 內是 0:0，與 root 打包時相同，所以發佈的 hash 是 `f48d364a…`，與 root 的相同；
- 上表的 rootless 只把擁有者改成使用者，群組仍是 root，在 namespace 內是 0:65534，hash 成了 `d4920a6a…`；
- 第 3 步的 rootless 變體 context 屬於 root，在 namespace 內是 65534:65534，hash 是 `1d93dd5b…`。

後兩項的 namespace 內 uid/gid 是依 buildah 的 hash 規則推得的，沒有逐一印出；第 3 節讓使用者以自己的使用者與群組建立 context，hash 就與發佈的相同，印證這個解釋。這個 hash 改變中間映像的 config，於是 history 裡 `FROM <ID>` 的 ID 跟著變。

第 3 步的其他觀察（[run-variants.txt](data/2026-10-13-372-rc5-arm-rebuild/run-variants.txt)，每次都是新的 storage）：

- 同一設定重跑兩次，digest 相同（root：`4bb4177e…` 兩次；rootless：`b575b122…` 兩次），所以差異不是隨機的。
- rootless 改用 vfs storage driver 時，COPY 層沒有 xattr，`diff_id` 與 root 相同（`fe0509b6…`）。
- `--layers=false` 不留中間映像，history 沒有 `FROM <ID>` 註解；root 加 `--layers=false` 時，overlay 與 vfs 的 digest 相同（`a7a216fb…`）。

### 3. 以 runner 的方式打包：digest 與發佈的相同

`pack-rootless.sh` 建立 uid 1001 的使用者 `runner`（有自己的群組與 subordinate id），以這個使用者照 build.ts 的步驟建立 build context，放入第 1 步重建的執行檔，以 rootless podman（預設 storage，overlay）打包。每個映像打包兩次，每次都是新的 context（不同的 mtime）與重設過的 storage（[run-rootless.txt](data/2026-10-13-372-rc5-arm-rebuild/run-rootless.txt)）：

| 映像 | 第 1 次 | 第 2 次 | rc.5 發佈 |
| --- | --- | --- | --- |
| `identity` | `sha256:7a042972…` | `sha256:7a042972…` | `sha256:7a042972…`，**相同** |
| `release-selftest` | `sha256:bc2b33e0…` | `sha256:bc2b33e0…` | `sha256:bc2b33e0…`，**相同** |

`release-selftest` 的套件是私有的，沒有取出它的執行檔；映像 digest 涵蓋 COPY 層的內容，digest 相同表示執行檔也逐位元組相同，所以不必再請 coordinator 拉取。

這一步在 x64 容器內原生執行。同一個腳本在 arm64 模擬容器內失敗：rootless podman 要以 `/proc/self/exe` 重新執行自己進入 user namespace，在 qemu-user 下得到 `cannot clone: Invalid argument`、`Error: cannot re-exec process`，與 Laysi/trustiot-v2#310 記錄的 chroot isolation 是同一類限制。打包不執行映像平台的程式，而且 root 打包在 x64 與 arm64 模擬容器內得到同一個 digest（`4bb4177e…`），所以主機架構不影響打包。

### 已排除的因素

| 因素 | 結論與證據 |
| --- | --- |
| qemu-user 模擬 | 不影響：模擬容器建出的 `identity` 執行檔與 runner 的逐位元組相同 |
| rustup、Rust、zig 等工具版本 | 不影響：同上；版本都依釘選安裝（rustup 1.29.1、Rust 1.99.0、`.prototools`） |
| checkout 路徑、`CARGO_HOME` | 不影響：runner 路徑與其他路徑的兩次重建，執行檔與映像都相同 |
| podman、buildah 版本 | 不是本次的差異來源：版本與 runner 映像列出的相同，rootless 打包得到與發佈相同的 digest。但 runner 上的版本不由本 repo 釘選，見下方建議 |
| 打包主機的架構 | 不影響：root 打包在 x64 與 arm64 模擬容器內 digest 相同；rootless 在 x64 上重現了 runner（arm64）的 digest |
| **podman 以 root 或 rootless 執行** | **差異來源**：COPY 層的 `user.overlay.origin` xattr，以及 build context 擁有者在 user namespace 內的 uid/gid 進入 COPY hash 與中間映像 ID |

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 從乾淨 clone 重建 `716740a` 的 `identity` 與 `release-selftest`，與 rc.5 的執行檔及映像 digest 的比較寫進 `docs/test-reports/`，包含指令、工具版本與 digest | **通過**：本報告。執行檔：`identity` 與 GHCR 上 rc.5 的逐位元組相同；`release-selftest` 由映像 digest 相同推得相同。映像：以 build.ts 在 root 容器內打包時不同，以 runner 的方式（rootless podman）打包時兩個 digest 都與 rc.5 相同 |
| 結果相同時，`ci-release.md` 的可重現建置段落註明已與 arm64 runner 的產出比對並連到報告；不同時寫出原因或已排除的因素，並開後續 issue | **通過**：結果相同，條件是打包時 podman 以 rootless 執行；[CI 與發佈](../architecture/ci-release.md) 的「交叉編譯與可重現建置」已註明比對結果、連到本報告，並寫明打包的條件。原因與已排除的因素見上方。後續 issue 的提議見下方，由 coordinator 決定是否建立 |

後續建議：

- **讓映像 digest 不受 podman 以 root 或 rootless 執行影響**。目前以 root 執行 build.ts（例如容器內、`sudo`）會得到與發佈不同的服務映像 digest，執行檔卻相同。可能的做法，都需要在 runner 上再驗證一次：
  - build.ts 對 podman build 加 `--layers=false`（`containerBuildArgs` 已允許這個選項），history 不再有中間映像 ID；
  - 固定 storage driver（例如 `vfs`），讓 rootless 的 COPY 層不帶 `user.overlay.origin`；
  - 或者 build.ts 偵測到以 root 執行時拒絕或警告，並在文件寫明。

  改了之後，下一個 rc 的 digest 會與先前的規則不同，但只要 runner 與本機都照新規則，就能一致。
- runner 上的 podman 版本不由本 repo 釘選，Ubuntu 套件更新可能改變打包結果。若要長期保證能重現，可以考慮在 release 記錄 `podman --version` 與套件版本（release.yml 的 build job 已印出 `podman --version`）。
