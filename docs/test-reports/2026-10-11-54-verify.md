# outbox crate 獨立混沌驗證（Laysi/trustiot-v2#54）

## 目的

獨立驗證已合併的 `crates/outbox`（Laysi/trustiot-v2#54，PR Laysi/trustiot-v2#249，main commit `9132855`）在混亂條件下仍成立的保證：

- 同交易寫入：回滾的交易不產生事件、已 commit 的事件不遺失。
- 每個事件 ID 只處理一次（含重播、副本競爭、行程被 SIGKILL）。
- 同一聚合依序。
- 不漏讀：長時間寫入交易（README「順序與不漏讀」的 xmin 讀取上限）、Postgres 重啟與崩潰、連線被終止。
- 重播（`Reprocess`、`SkipProcessed`）、死信（永久失敗的 handler）、lag 回到 0。
- README「資料庫權限」的最小授權。

本次只驗證、不修改產品程式碼。

## 2. 測試計畫與 harness

### 混沌 run 1（20 分鐘混沌 + 排空）

- 3 個產生端行程，各 3 個並行任務，寫入 24 個聚合（熱點聚合較多）；每筆交易 1–3 個事件（可同一聚合寫兩次）；12% 的交易寫完後故意回滾；35% 的交易先取得交易 ID、睡 0–60 ms 再寫入（讓交易 ID 順序與 commit 順序相反）；3% 的事件為 poison。
- 每個事件同時寫一列業務 `ledger`（在 `publish` 之後、同一交易），作為獨立的 commit 順序與存在證據；產生端另記 `R`（即將回滾）、`P`（即將 commit）、`C`（commit 成功）日誌。
- 3 個消費端副本（`c1` 用 `Consumer::run`，`c2`、`c3` 用 `poll_once` 迴圈以取得 `Progress` 計數）。handler：先讀 generation，寫 `handled_log`（附 generation、聚合序號）、依序檢查（`aggregate_state` 的 `last_seq` 必須小於新序號，否則寫 `violations`）、poison 事件在寫入後回傳 `permanent` 錯誤（handler 的寫入必須隨之回滾）；另外 3% 在寫入前、3% 在寫入後回傳 `retry`。
- 故障：隨機 SIGKILL 產生端與消費端（每 2.5–9 秒一次，15% 同時殺兩個），0.3–4 秒後重啟；`pg_terminate_backend` 殺掉全部或一半的連線；每 40–75 秒一個 15–35 秒的長寫入交易（在 `other` schema，持有交易 ID）；Postgres 優雅重啟 2 次與 `podman kill`（SIGKILL，崩潰復原）3 次；其中一次崩潰時有一個 `PREPARE TRANSACTION` 的交易（在 `other`）被持有，復原後 36 秒才 `COMMIT PREPARED`；第 455 秒做 `replay_from(START, Reprocess)`（同交易遞增 generation 並清空消費端狀態，依 README 的順序），第 864 秒做 `replay_from(START, SkipProcessed)`。
- 結束：停止產生端，不再注入故障，重啟所有消費端並等到 lag 為 0，停止消費端，執行 `verify`。

`verify` 檢查（全部以資料庫內容與日誌獨立計算）：

1. outbox 事件集合 == `ledger` 集合（同交易）。
2. 回滾日誌中的事件不在 outbox 也不在 `ledger`；已確認 commit 的事件都在 outbox。
3. 每個聚合：`aggregate_seq` 與 `ledger` 的 commit 順序一致、無缺號、`tx_order` 與 `id` 不比前一筆小。
4. 每個 generation：每個事件 ID 在 `handled_log` 至多一次；每個聚合的處理序號嚴格遞增，且是該聚合事件序列的前綴（不跳過）；poison 事件不得留下 handler 的寫入；最後一個 generation 必須涵蓋全部非 poison 事件。
5. `aggregate_state` 等於產生端事件推得的狀態；`violations` 為 0。
6. 死信集合 == poison 事件集合；`outbox_inbox` == 非 poison 事件集合；訂閱位置 == 最後一筆事件；以 SQL 計算的 lag == 0。

### 停滯探針 run 2（約 4 分鐘）

單一產生端與兩個副本，先讓消費端追上，再依序開 30 秒的長寫入交易與長唯讀交易（`pg_sleep`，無交易 ID），逐點記錄處理進度與 lag，最後同樣執行 `verify`。

### 權限檢查

在 run 1 的資料庫上，用 `consumer_role`、`producer_role` 執行 23 個語句，期望允許或被拒（SQLSTATE 42501）。

### 3.2 run 1 的過程紀錄（誠實揭露，不影響結論）

1. 煙霧測試（2 分鐘）發現 harness 的錯誤，不是 outbox 的：`ledger` 寫在 `publish`（取得聚合鎖）之前，所以 `ledger.id` 順序不等於 commit 順序，`verify` 誤報順序違反。已改為先 `publish` 再寫 `ledger`。
2. run 1 協調器的排空等待只有 2 分鐘，但積壓有約 2 萬個事件，所以協調器第一次執行 `verify` 時 lag 未歸零，報了「最終 generation 未涵蓋全部事件」「lag 17 763」等預期中的失敗；同一次還報了「6 筆已確認 commit 的事件不在 outbox」，經查是日誌檔的問題：同一行程的並行任務用兩次 `write` 寫一行，記錄黏在同一行（例子見 [`run1-glued-log-lines-example.txt`](data/2026-10-11-54-verify/run1-glued-log-lines-example.txt)、逐筆對照見 [`run1-first-verify-false-alarm-tokens.txt`](data/2026-10-11-54-verify/run1-first-verify-false-alarm-tokens.txt)），解析時把 token 讀錯，不是遺失。已改為一次 `write_all` 並讓解析器容忍黏行。
3. 之後以 `finish.ts` 重啟消費端（資料庫保持原樣）、排空到 lag 0，再用修正後的 `verify` 驗證整個資料庫：全部通過。協調器第一次（失敗）的輸出完整保留在 [`run1-orchestrator-output.txt`](data/2026-10-11-54-verify/run1-orchestrator-output.txt)，最終結果在 [`run1-finish-output.txt`](data/2026-10-11-54-verify/run1-finish-output.txt)。
4. 若要完全乾淨地重現，應在協調器裡把排空等待設為 25 分鐘（`chaos.ts` 的目前版本已是），或降低產生端速率；本次沒有為此重跑 20 分鐘。`Reprocess` 重播只做了一次，所以「兩個 generation 各自的 once-only」是以一次重播驗證的。

### 3.3 run 2：長交易讓 horizon 停滯（探針）

消費端追上後開 30 秒長寫入交易。注意：`stall.ts` 的取樣因機器擁擠比預期慢，原始 CSV 的 `phase` 欄位在交易結束後仍標成 `write_tx_open`／`readonly_tx_open`，其 timeline 的「during write tx」終點（t = 117 秒）也已在交易結束之後，所以以下只採用交易仍開著的區間（長寫入交易 t ≤ 82 秒，長唯讀交易 t ≤ 192 秒），並提供重新標記的 [`run2-stall-corrected-phases.csv`](data/2026-10-11-54-verify/run2-stall-corrected-phases.csv)（原始檔 [`run2-stall.csv`](data/2026-10-11-54-verify/run2-stall.csv) 未改）。交易的實際結束時間以處理恢復的時間點推得（t = 86.5 秒的取樣已恢復），不是直接量測：

| 階段 | 觀察 |
| --- | --- |
| 長寫入交易開啟中（t = 63.9–82.0 秒） | 已處理數固定在 344；事件 475 → 675，lag 115 → 315，函式庫的 lag 指標到達 332 個事件、年齡 29 秒（[`run2-stall-replica-c2-stat.txt`](data/2026-10-11-54-verify/run2-stall-replica-c2-stat.txt)） |
| 交易結束後（t ≥ 86.5 秒） | 處理恢復（379 → 912 直到 t = 117 秒，之後繼續），約 60 秒內 lag 降到個位數，之後維持低值 |
| 長唯讀交易仍開著（t = 167–192 秒，無交易 ID） | 處理數持續增加（1 567 → 1 803），沒有停滯 |
| 最後 `verify` | `failures: []`：2 436 個事件、87 個死信、處理 2 349 個，順序違反 0（[`run2-stall-verify.json`](data/2026-10-11-54-verify/run2-stall-verify.json)） |

這與 README 的說法一致：長寫入交易（任何 schema）會暫停所有訂閱、唯讀交易不會，指標也反映停滯。run 1 在積壓期間的長交易看不出消費速率差異（15.5 對 16.4 事件／秒），因為積壓的舊事件都在 horizon 之下，不受影響；這不是矛盾，只是 run 2 才是專門量測停滯的實驗。

### 3.4 權限（README「資料庫權限」）

23 個語句全部符合預期（[`grants.out.txt`](data/2026-10-11-54-verify/grants.out.txt)）：

- `consumer_role` 可 SELECT 產生端的 `outbox_event`；不能讀產生端的業務資料表（`ledger`）、`outbox_aggregate`、其他產生端 schema 的任何表（`permission denied for schema`）、無關 schema；不能對產生端的 `outbox_event` 做 INSERT、UPDATE、DELETE、TRUNCATE、`SELECT … FOR UPDATE`；不能寫產生端的 `outbox_aggregate`（所以不能對產生端呼叫 `publish`）；不能在產生端或自己的 schema 建表。
- `producer_role` 對自己的 `outbox_event` 只能 INSERT（SELECT、UPDATE、DELETE 都被拒）；讀不到消費端的表與無關 schema。
- 全部被拒的錯誤都是 42501。

## 5. 發現

沒有發現 outbox crate 的缺陷。本次發現的兩個問題都在 harness（見 3.2），已修正並重新驗證。

觀察（不是缺陷，供後續決定）：

1. **吞吐量**：每個事件一筆交易、同一訂閱同時只有一個副本在處理，在這台擁擠的機器上約 16 事件／秒。README 已寫明適合控制面的低頻事件；若某訂閱的事件量長期超過這個量級，lag 會持續累積（本次產生端 27 事件／秒時就是如此）。建議 #130 決定保留期限時，一併留意積壓後的排空時間與告警門檻（lag 與 age）。
2. **lag 指標上限 10 000**：積壓超過上限時，數值不再增加，只有 age 能看出惡化（本次 age 達 1 113 秒）。README 建議的告警是 age，這個建議是對的；可在 README 補一句「count 到上限後以 age 判斷」。
3. 長寫入交易的影響範圍是整個 Postgres 叢集（run 1 的 20 次與 prepared transaction 都有影響，run 2 精確量到），與 README 描述相符；任何其他 schema 的長寫入交易（包含 `PREPARE TRANSACTION` 沒人收尾）都會讓所有訂閱停住，上線後值得有告警（age）與監控。

## 6. 未涵蓋

- 沒有測 transaction ID 週期（xid wraparound、epoch）；`tx_order` 使用 `xid8`（64 位元），理論上不受影響，未實測。
- 只有一次 `Reprocess` 重播；沒有在重播進行中同時殺行程的專門場景（隨機 SIGKILL 可能碰到，但沒有統計）。
- 沒有測多個訂閱、多個產生端 schema 同時運作；沒有測 RLS（由 Laysi/trustiot-v2#53 處理）。
- 通知模式（`notify::store_if_newer`）沒有在混沌下測。
- 吞吐量與延遲數字只在擁擠的機器上取得，不具效能基準的意義。
- 沒有讀 CI 結果（MCP token 對 check runs 回 403）。
- 沒有新增進測試套件的測試：harness 需要多行程、數分鐘的執行與 podman 容器的啟停，不適合放進有界限的 `cargo test`；程式碼與腳本以 `.txt` 附在 data 目錄。
