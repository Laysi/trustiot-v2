  - PID 1 測試的基底：`gcr.io/distroless/cc-debian13:nonroot@sha256:e792ab3d241a468a4fd7519ddbbebe66b49b5f365771716ea688ad40b6c6f1c2`。映像裡沒有 shell，服務本身就是 PID 1；容器以唯讀根目錄、UID 54321、拿掉所有 capability、`no-new-privileges` 執行，與 Helm chart 給服務的執行環境相同。

- 範例服務 `example-service` 是 debug 建置，以預設的 `contract` feature 編譯，另以 `--no-default-features` 跑一次全部測試。

### PID 1 與 SIGTERM

容器測試 `pid_1_in_a_container_drains_and_exits_within_the_grace_period`（[container.txt](data/2026-10-10-51-service-kit/container.txt)）以 chart 的執行限制跑範例服務，drain delay 1 秒、drain timeout 10 秒，`podman stop` 的寬限期 15 秒：

| 項目 | 結果 |
| --- | --- |
| PID 1 | `starting` 日誌的 `process.pid` 是 1；映像沒有 shell，服務本身就是 PID 1 |
| 進行中的請求 | SIGTERM 前 0.5 秒送出的 `GET /v1/slow?ms=3000` 回 200，`waited_ms` 3000，日誌的 `duration_ms` 3016.217 |
| readiness | SIGTERM 後 1 秒內（drain delay 內）`/readyz` 回 503，`status` 為 `draining` |
| 結束 | `podman stop --time 15` 在 2606 ms 後返回，容器 exit code 0（被 SIGKILL 會是 137）；日誌依序為 `shutdown requested; readiness now fails`（`signal` SIGTERM）、`stopped accepting connections; draining requests and background tasks`、慢請求的 `request completed`、`shutdown complete` |
| 對照組 | Alpine 的 `sleep` 當 PID 1，`podman stop --time 5` 在 5.23 秒後返回，podman 警告 SIGTERM 沒有停下容器、改送 SIGKILL，exit code 137（[pid1-baseline.txt](data/2026-10-10-51-service-kit/pid1-baseline.txt)） |

本機行程的生命週期測試（[lifecycle.txt](data/2026-10-10-51-service-kit/lifecycle.txt)），訊號與 HTTP 請求都是真的：

| 測試 | 結果 |
| --- | --- |
| `sigterm_fails_readiness_at_once_and_drains_requests_in_flight` | SIGTERM 後 4 ms `/readyz` 回 503；drain delay 內 `/healthz` 與 `/v1/hello` 仍回 200；drain delay 結束後新連線被拒絕；SIGTERM 前送出的 2.5 秒請求回 200；行程在 SIGTERM 後 2222 ms 以 exit code 0 結束 |
| `drain_timeout_bounds_shutdown` | drain timeout 500 ms、請求要 8 秒：還在執行的請求回 504（入口不會重試），有 WARN `request cut off by the drain timeout`，ERROR `drain timed out; cut off the work still in flight`，行程在 3 秒內以 exit code 1 結束 |
| `second_signal_exits_without_draining` | 收尾中再送一次 SIGTERM，2 秒內以 exit code 1 結束 |
| `sigint_drains_like_sigterm` | SIGINT 的收尾與 SIGTERM 相同，exit code 0 |
| 啟動檢查 | 少了必要設定、設定值不合法、監聽位址被占用時，以 exit code 1 結束並記一行 ERROR；設定錯誤寫出設定鍵與環境變數名稱，不含設定值 |

chart 約定（[chart-contract.txt](data/2026-10-10-51-service-kit/chart-contract.txt)）：`tests/chart_contract.rs` 讀 `deploy/chart/values.yaml` 的 `serviceDefaults`，確認容器埠 8080（名稱 `http`）、startup 與 liveness 探 `/healthz`、readiness 探 `/readyz`，以及 kit 的預設 drain delay 5 秒、drain timeout 20 秒加上收尾後的 3 秒共 28 秒，不超過 chart 的 `drainSeconds` 30 秒。

### advisory lock

每個「副本」是自己的連線池，就像不同的 pod；Postgres 是用完即刪的容器。`job_lock` 連跑三次（[job-lock.txt](data/2026-10-10-51-service-kit/job-lock.txt)）：

| 測試 | 結果 |
| --- | --- |
| `only_one_replica_runs_a_job_scheduled_on_both_at_once` | 兩個副本以 barrier 同時排程同一個工作，拿到鎖的一方持有到另一方的嘗試結束，確保兩次嘗試重疊。每次 10 輪，每輪恰好一個副本執行；三次的分配為 [2, 8]、[3, 7]、[2, 8] |
| `periodic_runs_on_two_replicas_never_overlap` | 兩個副本每 40 ms 排程一次、每次執行 25 ms，持續 2 秒：至少 10 次執行，執行區間互不重疊 |
| `a_lost_session_cancels_the_job_and_frees_the_lock` | 以 `pg_terminate_backend` 切斷持鎖的 session（模擬網路中斷或資料庫 failover）：3 秒內工作被取消並回 `JobLockError::Lost`，另一個副本隨後拿到鎖 |
| `dropped_guards_and_panicking_jobs_release_the_lock` | guard 被丟棄、工作 panic、執行被取消，三種情況鎖都會釋放。日誌中的 `job failed hard` panic 是這個測試故意觸發的 |
| `released_locks_return_their_connection_to_the_pool` | 連續 5 次執行用的是同一個 session，釋放後連線回到池裡，閒置時不持有 advisory lock |

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 範例服務在容器內以 PID 1 執行，收到 SIGTERM 後進行中的請求完成、行程在寬限期內結束（整合測試） | 通過：`tests/container.rs` 中服務是 PID 1，進行中的 3 秒請求回 200，`podman stop --time 15` 在 2606 ms 後返回，exit code 0；對照組不處理 SIGTERM 的 PID 1 撐滿寬限期後被 SIGKILL（137） |
| SIGTERM 後 readiness 立即回失敗（測試） | 通過：本機行程 SIGTERM 後 4 ms `/readyz` 回 503（`tests/lifecycle.rs`）；容器內也在 drain delay 內回 503（`tests/container.rs`） |
| 日誌為 JSON、帶 trace id；有測試證明 request body 不會出現在日誌 | 通過：`tests/logging.rs` 在 `trace` 等級下每行都是 JSON、請求日誌帶 trace id 並延續 `traceparent`，body、email、憑證、cookie、query 與路徑的探針值都不在 stdout 與 stderr；`tests/otlp.rs` 證明 OTLP 匯出預設關閉，開啟後匯出的內容也不含 body |
| advisory lock 工具在兩個副本同時排程時只有一個執行（測試） | 通過：`tests/job_lock.rs` 兩個副本同時排程 10 輪，每輪恰好一個執行，連跑三次都通過；週期排程不重疊，session 中斷時取消工作並釋放鎖 |
| 關閉該 feature 時 service-kit 不依賴 contract（`cargo tree` 的 CI 檢查） | 通過：`tests/dependency_isolation.rs` 以 `cargo tree` 檢查，它是 `cargo test --workspace` 的一部分，CI 跑測試時就會執行。2026-10-10 main 還沒有 CI workflow（Laysi/trustiot-v2#67 進行中），本次在本機執行 |

本 issue 不需要 Kubernetes，沒有 lab 端到端測試。pod 實際的刪除流程（preStop 加 `drainSeconds`）留待第一個以 chart 部署的服務驗證；本次以 `tests/chart_contract.rs` 對照 chart 的數值，並以 `podman stop` 模擬 kubelet 的 SIGTERM 與 SIGKILL。
