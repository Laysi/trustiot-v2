# MQTT 轉接服務（mqtt-bridge）的驗收測試

Laysi/trustiot-v2#85。

## 環境

- 開發者工作站（x86_64 Linux），2026-10-23。
- Rust 1.99.0（`rust-toolchain.toml`）、Bun 1.4.2、Helm 4.3.0（`.prototools`）；tokio-tungstenite 0.30.0。
- 分支 `feat/85-mqtt-bridge`，以 origin/main 的 c96d059d 為基礎。
- 不需要容器、叢集或網路：整合測試直接啟動服務的執行檔（`CARGO_BIN_EXE_mqtt-bridge`，監聽 127.0.0.1 的隨機埠），前面放測試自己的假 broker（回聲、MQTT CONNECT／PINGREQ 的最小回應、要求用戶端憑證的 TLS 1.3）、會切斷閒置連線的代理與假的 OTLP collector。測試用的 CA 與憑證由 rcgen 在執行時產生。

## 指令

```sh
CI=1 cargo test -p mqtt-bridge -- --nocapture
cargo clippy -p mqtt-bridge --all-targets -- -D warnings
CI=1 bun test deploy/chart
```

## 結果

`cargo test -p mqtt-bridge`：34 個測試全部通過（單元 18、整合 16），輸出見 [cargo-test-mqtt-bridge.txt](data/2026-10-23-85-mqtt-bridge/cargo-test-mqtt-bridge.txt)。

| 測試 | 驗證什麼 | 數據 |
| --- | --- | --- |
| `keepalive::pings_keep_a_keepalive_0_connection_open_past_the_idle_cutoff` | 代理 3 秒無資料就切斷；服務每 200 ms ping；keepalive 0 的 MQTT 連線閒置 9 秒（三個切斷時間）後 PINGREQ 仍有 PINGRESP，broker 只看到一條連線，代理切斷 0 次 | 9 秒內 44 次 ping |
| `keepalive::without_pings_the_idle_cutoff_ends_the_connection` | ping 間隔 100 秒（上限）時同一個代理把連線切掉：前一項的結果來自 ping | 切斷 1 次 |
| `shutdown::sigterm_closes_every_websocket_before_exit_and_gateways_reconnect_to_the_new_pod` | 6 條連線（1 條從不回 close）時送 SIGTERM：會讀的 5 條都收到 close 1001（close frame 只可能由還在執行的服務送出）；drain 期間的升級回 503；每條連線的結束原因是 `shutdown`；行程以 0 結束；舊服務的 broker 連線全部關閉，重連到第二個服務實例的連線保持開啟 | SIGTERM 到 5 台重連完成（含 MQTT CONNECT／CONNACK）：38.7、39.9、41.0、42.1、43.1 ms |
| `source_ip::spoofed_forwarding_headers_do_not_change_the_recorded_ip` | 請求同時帶 `X-Forwarded-For`（兩個）、`True-Client-IP`、`X-Real-IP`、`Forwarded` 與 `CF-Connecting-IP: 203.0.113.7`：兩行連線日誌的 `client.address` 都是 203.0.113.7，偽造的位址沒有出現在任何日誌；`broker.local_address` 等於 broker 看到的來源位址；兩行的 `connection.id` 相同 | |
| `source_ip::without_the_trusted_header_the_upgrade_is_refused_and_the_broker_untouched` | 只有偽造的標頭、`CF-Connecting-IP` 重複、值不是單一 IP：都回 400（`client_ip_missing`、`client_ip_repeated`、`client_ip_invalid`），broker 沒有任何連線 | |
| `startup::an_unknown_source_ip_mode_refuses_to_start` | `TRUSTIOT_CLIENT_IP_SOURCE` 為 `x-forwarded-for`、`true-client-ip`、`forwarded`、`CF-Connecting-IP`、`none`、空字串時：結束碼 1、沒有開始監聽、錯誤訊息指名變數而且不回顯值 | |
| `startup::the_on_prem_mode_refuses_to_start_until_it_is_implemented` | `x-forwarded-for-rightmost` 拒絕啟動，訊息指向 Laysi/trustiot-v2#446 | |
| `startup::a_missing_mode_or_broker_address_refuses_to_start` | 沒有來源 IP 模式或 broker 位址時拒絕啟動，訊息指名變數 | |
| `relay::*`（4 個） | 位元組雙向不變而且照順序、服務送出的訊息最多 8 KiB、閘道器的 mTLS（TLS 1.3、用戶端憑證）經服務完成而且明文不進日誌、文字訊息以 1003 結束、broker 結束連線時送 1000 | |
| `limits::*`（5 個） | 連線上限回 503 並在連線結束後釋放、broker 連不上回 502、沒有 `mqtt` 子協定回 400、指標（連線數、結束與拒絕原因、位元組數）經 OTLP 匯出而且關機後 `active` 為 0、超過 32 KiB 的 frame（只送標頭）與分段組成的訊息結束連線而且不轉送任何內容 | |

`cargo clippy -p mqtt-bridge --all-targets -- -D warnings`：沒有警告。chart 測試（`CI=1 bun test deploy/chart`）包含：broker 開啟時 `mqtt-bridge` 拿到 `TRUSTIOT__BROKER__ADDRESS=<release>-mqtt-broker.<namespace>.svc:8883`、broker 沒開時沒有這個變數、`services.mqtt-bridge.env` 與 `serviceDefaults.env` 都不能設定它、`mesh.calls` 不能把 `mqtt-bridge` 列為被呼叫端。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| MQTT keepalive 0 的連線閒置 125 秒不斷（ping 有效） | 通過：以縮小的時間驗證（3 秒切斷、200 ms ping、閒置 9 秒），對照組證明是 ping 讓連線存活；預設 50 秒、上限 100 秒都在 Cloudflare 的 125 秒之內（`src/config.rs` 的範圍檢查與單元測試） |
| 滾動更新時閘道器 1 秒內重連到新 pod | 服務這一側通過：SIGTERM 時每條連線在行程結束前收到 close 1001，重連到另一個實例在 43 ms 內完成。經 Cloudflare 與入口、在叢集上的滾動更新實測待測：需要閘道器這一側（Laysi/trustiot-v2#86）與部署 |
| 用戶端送的 X-Forwarded-For（最左段）或 True-Client-IP 不改變記錄的來源 IP（SaaS 設定） | 通過 |
| 不認得的來源 IP 模式拒絕啟動 | 通過 |
| 1,000 條連線的記憶體增量記在 README，以 2026-10-10 的數字為基準 | 待測：效能量測屬於進階驗證，延後到另開的 issue；緩衝區設定、每條連線的最壞情況與 2026-10-10 的基準數字已記在 services/mqtt-bridge/README.md 的「記憶體」 |
