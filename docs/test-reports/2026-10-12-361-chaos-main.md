# outbox 混沌 harness 在含 handler panic 與明確 rollback 修正的 main 上重跑（Laysi/trustiot-v2#361）

Laysi/trustiot-v2#271 的混沌驗證（[2026-10-12-271-chaos](2026-10-12-271-chaos.md)，PR Laysi/trustiot-v2#357）在 main `b4aae40` 上跑了兩次 20 分鐘，結果全部通過。之後合併的兩個修改動到 `crates/outbox/src/consumer.rs` 的投遞與失敗路徑：

- Laysi/trustiot-v2#333（PR Laysi/trustiot-v2#349）：handler panic 後 consumer 繼續執行；panic 時攔下、明確回滾、以退避重試，同一事件在同一副本連續第 3 次 panic 時記進死信（`handler panicked repeatedly`）。
- Laysi/trustiot-v2#350（PR Laysi/trustiot-v2#356，main `b1a4ad3`）：所有不 commit 的路徑都先明確回滾再記死信；`begin` 回 `Ok` 後立刻檢查交易與租戶，每個事件多一個只讀的查詢（不取得交易 ID）。

本報告在含這兩個修改的 main 上重跑同一個 harness（`docs/test-reports/data/2026-10-12-271-chaos/`），檢查項目與先前相同，另加一個選用的 handler panic 情境，並與 `b4aae40` 的兩次結果比較。只驗證、不修改產品程式碼。

## 2. harness 的變動：選用的 handler panic 情境

預設行為不變：沒有設環境變數時，亂數序列與先前的 harness 完全相同（新增的亂數只在情境開啟時才抽）。新增兩個環境變數：

| 變數 | 作用 |
| --- | --- |
| `CHAOS_PANICS=1`（產生端） | 約 0.3% 的事件標為「一定 panic」：handler 寫完 `handled_log`、`tenant_rows` 之後 `panic!`，每次嘗試都 panic。consumer 應該回滾、重試，同一副本連續第 3 次 panic 時把事件記進死信，原因是 `handler panicked repeatedly`，之後的事件照常處理 |
| `CHAOS_PANIC_RATE=0.01`（消費端） | handler 在寫入之後、commit 之前以 1% 的機率隨機 `panic!`；consumer 應該回滾並重試，事件之後被處理一次 |

為什麼加：#349 之前 handler panic 會帶走整個 `run`，所以混沌 harness 不可能含 panic；現在 consumer 要在 panic 之後繼續，並且每次 panic 的交易都要乾淨回滾（handler 在 panic 前已寫入 `handled_log`、`tenant_rows`）。這是 #349 與 #356 的新失敗路徑，與 SIGKILL、重播、Postgres 崩潰同時發生。

`verify` 為此調整（沒有放寬任何既有檢查）：

- 「毒事件集合」的定義擴大為「最後進死信的事件」＝毒事件加上一定 panic 的事件；原本的檢查（死信集合等於這個集合、它們的 handler 寫入一律回滾、inbox 等於其餘事件）不變。
- 新增：每筆死信的原因必須符合種類：一定 panic 的事件是 `handler panicked repeatedly`，毒事件是 `chaos: poison event`；摘要多了 `always_panicking_events` 與 `dead_letter_reasons`。
- 隨機 panic 的事件若碰巧在同一副本連續 3 次 panic 會被記進死信而使 `verify` 失敗；機率約 1e-6（每個事件），一次執行約 0.05，沒有發生。

只在 run D 開啟情境；run C 不開，與 run A、B 同一組件，作為乾淨的對照。

### 4.3 handler panic 情境（run D）

- 132 個一定 panic 的事件全部進死信，原因都是 `handler panicked repeatedly`（`dead_letter_reasons`：1 379 筆 `chaos: poison event`、132 筆 `handler panicked repeatedly`，沒有其他原因）。它們在每一次嘗試都已寫入 `handled_log` 與 `tenant_rows` 後 panic，`verify` 在最終資料庫沒有找到它們的任何 handler 寫入。
- 隨機 panic（1%）造成的事件之後都被處理一次：最後一個 generation 涵蓋全部 43 530 個非死信事件，沒有重複處理、沒有順序違反。
- panic 與 SIGKILL、Postgres 崩潰、連線被終止、兩種重播同時發生，consumer 沒有停止：三個副本一直處理到排空，lag 回到 0。
- 代價：每次 panic 回滾後以退避重試（輪詢間隔加倍，最多 2 秒），同一個事件擋住整個訂閱。run D 最後一次的三個消費端行程在約 660 秒的排空期間共 panic 643 次（209、231、203），排空速度因此是 29.8 事件／秒，約 run A–C 的一半；排空期間幾乎沒有完全停頓（12 秒），是持續較慢，不是卡住（[`drain-comparison.txt`](data/2026-10-12-361-chaos-main/drain-comparison.txt)）。這是這個情境刻意造成的 panic 率（每個事件 1% 加 0.3% 的一定 panic）的預期後果，不是缺陷；README 也寫明一直 panic 的事件最多佔住訂閱「副本數乘以 3」次嘗試。
- 日誌：panic 的 stderr（panic hook 的一行）由 harness 留在各行程的 `.err`，沒有納入 data（單一行程最大約 26 KB）；harness 沒有初始化遙測，consumer 的 ERROR 日誌沒有擷取。

### 4.4 #356 每個事件多一個讀取查詢的成本

不開 panic 情境的 run C，排空速度為 65.4 事件／秒，`b4aae40` 的 run A、B 為 69.5 與 66.7：差距（約 2%–6%）與 run A、B 兩次之間的差距（約 4%）同一量級，在這個共用主機的雜訊裡看不出額外讀取查詢的成本。排空時三個副本爭同一個訂閱，同一時間只有一個在處理，所以這個數字約等於「一個事件一筆交易」的上限；每個事件本來就有設定租戶、取得鎖、位置檢查、查 inbox、handler 的查詢、寫 inbox、推進位置、commit 等多個往返，多一個只讀查詢預期只佔其中一小部分。這不是專門的效能量測（主機共用、兩次對照的負載不同），只能說沒有看到明顯的退化。

## 7. 未涵蓋

- panic 只發生在 handler 的 `handle`（寫入之後）；`Handler::begin` 的 panic、handler 自己 `COMMIT` 或改租戶後 panic、輪詢本身的 panic 屬於 `tests/handler_panic.rs` 與 `tests/failure_paths.rs`，不在混沌 harness 內。
- 每個副本的 panic 計數記在記憶體，被 SIGKILL 的行程會歸零；因此一定 panic 的事件在多個副本與重啟之間可能嘗試超過 3 次才進死信，上限仍是副本數乘以 3 次（每次重啟重新計算），`verify` 只確認最後都進死信。
- 通知模式、xid wraparound、多個訂閱與多個產生端 schema 同先前，沒有測。
- 吞吐量只在共用主機上取得，不具效能基準的意義；seed 不保證重現同一串事件。
- 沒有讀 CI 結果。
