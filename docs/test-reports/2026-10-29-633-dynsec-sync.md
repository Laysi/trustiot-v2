# certs：依 Postgres 同步 broker 的閘道器 client 與角色（2026-10-29）

Laysi/trustiot-v2#633：certs 以 `service:certs` 連 MQTT broker 的服務埠，依 Postgres 冪等地同步 dynamic security 裡閘道器的 client 與角色（`services/certs/src/dynsec.rs`，規則見 [services/certs/README.md](../../services/certs/README.md) 的「broker 權限（dynamic security）」）。這份報告是驗收條件的證據：全部由下列自動化測試以 `CI=1` 實際執行（需要容器的測試不略過）。

## 環境

- **程式碼**：分支 `feat/633-certs-dynsec-sync`。測試在功能 commit `01fe4627`（以 main `5dad0429` 為基礎）上執行；之後 rebase 到 main `9d879e95`（Laysi/trustiot-v2#94，只改 `edge/` 與 `crates/protocol/README.md`），功能 commit 成為 `6c8a5063`，內容不變。本報告的 commit 只加文件與測試輸出。
- **機器**：經檢查佇列執行。`tests/dynsec.rs` 的證據與 certs 的單元測試在建置主機（macOS，arm64），workspace 的 fmt、clippy、openapi 與 `cargo test --workspace` 在建置主機（x86_64 Linux），`changes.test.ts` 在建置主機（macOS）。容器測試以 podman 起 `testkit::product` 的拋棄式 TLS Postgres（migration Job 套用整個產品的 schema）與 Mosquitto。
- **工具**：`.prototools` 與 `rust-toolchain.toml` 釘選的 Rust 1.99.0、Bun。
- **broker**：`testkit::mqtt::mosquitto::MOSQUITTO_IMAGE`（eclipse-mosquitto 2.1.2-alpine，以 digest 釘選），chart 的 `deploy/chart/files/mosquitto/mosquitto.conf` 與 `gateway-listener.conf`（8883：TLS 1.3、要求用戶端憑證、`use_identity_as_username`、CRL），dynsec 檔由 `migrate::mqtt_accounts::reconcile` 產生（三個服務帳號，密碼在執行時隨機產生、只存雜湊）。
- **服務**：真的 `certs` 執行檔，`TRUSTIOT__MQTT__*` 指向容器的 1883，`TRUSTIOT__DYNSEC__INTERVAL=2s`，`TRUSTIOT__TELEMETRY__LOG_FILTER=trace`。閘道器的憑證來自真的出廠登錄 API（工作站憑證也由服務簽發）。

`tests/dynsec.rs` 的證據行全文：[dynsec-evidence.txt](data/2026-10-29-633-dynsec-sync/dynsec-evidence.txt)。摘要：

| 步驟 | 觀察 |
| --- | --- |
| 服務啟動 | 以 `service:certs` 連上、完整比對：沒有登錄的閘道器，沒有變更 |
| 登錄 `gw-633-a`，未綁定 | TLS 與 CONNACK 0x00；發布自己的 `up/status` 得到 PUBACK 0x87 |
| 綁定 `gw-633-a` | 同一條連線第 10 次重試（每 100 毫秒）得到 PUBACK 0x10；服務記 INFO `changed a gateway's broker permissions` `hardware_id=gw-633-a` `action=added` |
| 兩台都綁定 | `gw-633-a`：自己的 `up/telemetry` 0x10、訂閱自己的 `down/config` 0x01、`gw-633-b` 的 `up/telemetry` 0x87、訂閱 `gw-633-b` 的 `down/config` 0x87；`gw-633-b`：自己的 `up/status` 0x10、`gw-633-a` 的 0x87 |
| 沒有變更 | 3 次完整比對（DEBUG `the broker's gateway permissions match postgres`），沒有變更的日誌，dynsec 檔的 SHA-256 前後相同 |
| broker 以「chart 項目＋`gw-633-ghost`」重啟 | 重啟後檔案有 4 個 client（3 個服務帳號＋ghost）；一輪比對後閘道器 client 是 `gw-633-a`、`gw-633-b`（各只有 `trustiot-gateway`），ghost 被刪除（`action=removed`）；服務帳號（username、角色、停用、密碼雜湊）與 5 個角色的規則、群組，與寫入的檔案相同；`gw-633-a` 新連線發布 0x10 |
| 日誌 | `trace` 下 27 萬餘位元組的 stdout 與 stderr，不含 broker 密碼 25 個 8 字元片段中的任何一個 |

PUBACK 0x10 是「沒有符合的訂閱者」，表示 broker 接受了發布（授權通過）；0x87 是「未授權」。

## 結論

| 驗收條件 | 結果 |
| --- | --- |
| 1. 已登錄且綁定的閘道器發布自己的 `up/`、訂閱自己的 `down/`；對另一台的發布 PUBACK 0x87、訂閱 SUBACK 0x87（MQTT 5） | 通過 |
| 2. 已登錄未綁定的閘道器連得上但每次發布 0x87；綁定後不必重連就能發布 | 通過 |
| 3. broker 以只有 chart 項目的 dynsec 檔重啟、另有手動加入的假閘道器 client：一輪同步後與 Postgres 一致，缺的補上、多的刪除，`service:*` 不變 | 通過 |
| 4. 沒有變更時重跑同步不送修改指令 | 通過（dynsec 檔逐位元組不變：Mosquitto 每個修改指令都會重寫這個檔案；也沒有變更的日誌） |
| 5. `trace` 的日誌不含 broker 密碼 | 通過 |
| 6. clippy、`cargo test --workspace`；測試讀 certs 目錄外的檔案時更新 `scripts/ci/changes.ts` 並通過 `bun test scripts/ci/changes.test.ts` | 通過（新測試讀 chart 的 `mosquitto.conf` 與 `gateway-listener.conf`，規則本來就列了這兩個路徑，只更新註解與測試描述） |
